# brigada — дизайн

Схема, по которой любое число агентов из разных харнессов (Claude Code, Codex, OpenCode, …) подключаются к проекту и дальше **сами** организуют работу над задачей человека: обсуждают, распределяют роли и подзадачи, проверяют друг друга.

Документ описывает, как устроено сейчас и почему. **(решение человека)** — решение, которое меняет только человек; остальное принято по ревью и подтверждено тестами. Здесь — только реализованное: новое сначала план в `/plans` (вне git), сюда — вместе с кодом.

---

## 1. Цели и ограничения

1. **(решение человека)** Наладка со стороны человека — разовый `brg init` в проекте и фраза агенту «подключись к бригаде». Чтобы короткая фраза работала в любом харнессе, `init` дописывает короткий блок brigada в файлы постоянных инструкций проекта — `AGENTS.md` и, если нужно, `CLAUDE.md` (§3); `init --no-agents-md` их не трогает, и тогда фраза полная: «подключись к .brigada, прочитай инструкцию в .brigada/README.md». Никакой настройки харнессов (хуков, конфигов, плагинов) и доп. установок (tmux и т.п.). **(0.9.0)** Агент, запущенный самим brg (`brg spawn`, §5.5), — тоже не настройка: brg передаёт харнессу только флаги вызова (`opencode run --format json --model … [--auto]`), конфиги харнесса не трогает.
2. **(решение человека)** Базовое взаимодействие (сообщения, ожидание, роли, подзадачи) выполняет детерминированный скрипт, а не модель, разбирающая файлы.
3. **(решение человека)** Один механизм ожидания для всех харнессов: агент не завершает ход и ждёт в блокирующем `brg wait` (§5). Возможности отдельных харнессов (фоновые команды с пробуждением, шедулеры, `codex queue`) в протокол не входят; возможно, позже — как необязательная оптимизация.
   **(решение человека, 0.9.0)** Для агентов, которых запустил сам brg (`brg spawn`, §5.5), ожидание держит не модель, а надзорный процесс brg: свободный агент **завершает ход** (харнесс выходит, простой ничего не стоит), надзор сидит в `wait` за него и, когда есть будящее, продолжает сессию харнесса, передавая пачку прямо в промпт (один запрос к модели). Работает подагент — запущенный агент ход не завершает и ждёт в `wait --busy`, как все. Подключённые вручную работают как раньше; друг для друга оба вида неотличимы (имена, задачи, lead, подзадачи, `run`, вопросы, стоп, пауза).
4. **(решение человека)** Реализация на bash (3.2+). Windows — через Git Bash (§10). **(решение человека, 0.8.0)** Единственное исключение — Python (≥ 3.8, только stdlib) для **необязательного** сервера человека `bin/brg-serve.py` (§9.1): `bin/brg` вызывает Python лишь в `board` (поднять сервер) и `doctor` (проверить, что он есть); инструмент агентов — по-прежнему один bash-файл. Без Python всё работает: доска открывается как `file://` и только показывает, отвечать — `brg say`.
5. **(решение человека)** Всё состояние — внутри `.brigada/`, по задачам; между задачами общее только `common/`. Смена задачи — без перезапуска сессий; новые агенты подключаются в любой момент.
6. **(решение человека)** Самоорганизация — суть эксперимента: агенты сами решают, кто ведёт и как решать задачу. brg ведёт состояние и правила переходов, решения принимают модели.
7. **(решение человека)** PROTOCOL задаёт только цель и минимальные рамки: безопасность; вопросы по бизнес-сути — человеку, технические решения — сами; человек видит вопросы и итог (по умолчанию — текстом в чате lead'а и тем же текстом `send --to human`, который видно на доске); не коммитить в `main`/`master` без разрешения человека и не уничтожать чужую работу; связь — через brg; стадии подзадач соответствуют действительности — человек следит по доске (§7.1.1); **участник — координатор, работу делают его подагенты** (§5.4); закрытие — `task close` с `summary.md`. Весь процесс (перекличка, лид, план, подзадачи, резервирования, ревью, ветка, `brg run`) — **рекомендации**: агенты вправе договориться о другом и строить свои инструменты. brg процесс не навязывает (например, не требует ревью для закрытия) — даёт инструменты и следит за целостностью состояния. Почему: регламент подменял бы самоорганизацию (п. 6).
8. **(решение человека)** Как работает бригада — PROTOCOL, раздел 3 «Ожидания» (не жёсткие правила):
   - решения принимаются коллегиально: что делаем, в каком порядке, кто какой объём берёт;
   - lead — фасилитатор, а не начальник: фиксирует договорённости и решает сам, только если бригада не договорилась;
   - **(решение человека, 0.7.0)** lead — единственный, кто сам обращается к человеку (вопросы, отчёты, итог); остальные отвечают, если человек написал им сам. Роли host больше нет: lead — и фасилитатор, и связь с человеком, и lead есть всегда (§6.1);
   - подзадачи раздаются участникам;
   - проверка подзадачи другим участником (силами его подагента) — рекомендация: проверять ли и как, решает бригада; стадию подзадачи агенты держат такой, как на деле (§7.1.1).

   Почему: в полевом прогоне lead, следуя совету «объёмное — подагентам», сам исследовал задачу и писал её ядро вместе со своими подагентами, а участники простаивали.

   То, что участник — координатор, а работу делают его подагенты, с версии 0.5.0 — не ожидание, а обязательная рамка (п. 7, §5.4).

Не цели MVP: параллельные задачи, worktree на агента, кросс-машинная работа (все агенты на одной машине, одна ФС), защита от злонамеренного агента.

## 2. Слои

| Слой | Чем реализован |
|---|---|
| Транспорт и состояние: каналы, курсоры, ростер, задачи, роли, дедлайны, подзадачи, резервирования, прогоны, блокировки | `bin/brg` (один bash-файл) |
| Ожидание | `brg wait` + правило «никогда не завершай ход»; у запущенных brg — надзор `brg __spawn` (§5.5) |
| Инструкции агентам | `README.md` — механика (обязательна), `PROTOCOL.md` — цель, рамки, рекомендации (из `template/`); блок brigada в `AGENTS.md`/`CLAUDE.md` проекта — указатель на `README.md` (§3) |
| Инструменты человека (§9) | глобальная `brg` (`bin/brg-global`, `install.sh`); `bin/brg.cmd` на Windows |

Каждая команда печатает короткий результат и, где уместно, `NEXT:` — следующую команду дословно, с именем агента: так цикл переживает сжатие контекста.

## 3. Подключение

1. Человек в корне проекта: `brg init` (или `bash /путь/к/brigada/bin/brg init [проект]`) — создаёт `.brigada/` (§4). Повторный `init` обновляет `bin/`, `README.md`, `PROTOCOL.md`, `board.html` (доска человека, §9.1), `config.default`, `VERSION`, не трогая состояние и `config` (называет ключи шаблона, которых в `config` нет). **(решение человека)** `init` дописывает в `.git/info/exclude` (у worktree — общего git-каталога) `.brigada/` — весь каталог не коммитится: иначе `git add -A` любого агента закоммитит переписку, рантайм, копию `brg` и настройки бригады. Строки brg ≤ 0.2.0 (`.brigada/{tasks,lobby,run,agents}/` и их комментарий) повторный `init` заменяет на `.brigada/` и подсказывает убрать из индекса уже закоммиченное (`git rm -r --cached .brigada`; сам brg git не вызывает, §7.4). `doctor` — ✗, если `.brigada/` в exclude нет.
   **(решение человека)** `init` кладёт в корень проекта блок brigada — между строками-маркерами `<!-- brigada:begin …` и `<!-- brigada:end …` (по ним блок находится и обновляется): «если человек просит подключиться к бригаде — прочитай `.brigada/README.md` и следуй ему (там `join` и цикл `wait`); без такой просьбы не подключайся». Файлы — по тому, что читают харнессы: `AGENTS.md` — Codex, OpenCode, Cursor, Copilot и др. (OpenCode без `AGENTS.md` читает `CLAUDE.md`); Claude Code читает `CLAUDE.md`, а `AGENTS.md` (с версии 2.1.277) — только если `CLAUDE.md` нет; при обоих — только `CLAUDE.md`, если в нём нет импорта `@AGENTS.md`.
   - `AGENTS.md` нет — создаётся из одного блока и исключается из git (`/AGENTS.md` в `.git/info/exclude` тем же механизмом, что `.brigada/`; без git — просто создаётся): файл появился по воле brg, коммитить ли его — решает человек (убрать строку из exclude). `AGENTS.md` есть — блок дописывается в конец после пустой строки или, если отличается, заменяется между маркерами (включая их); файл, вероятно, в git — коммитить ли блок, решает человек, `init` об этом говорит.
   - `CLAUDE.md` нет — не создаётся (Claude Code прочтёт `AGENTS.md`); есть и содержит строку-импорт `@AGENTS.md` или `@./AGENTS.md` — не трогается; есть без такой строки — тот же блок по тем же правилам (упоминание `@AGENTS.md` внутри строки импортом не считается: Claude Code увидит блок дважды — безвредно).
   - Окончания строк файла сохраняются (CRLF-файл — блок с CRLF), права файла тоже; ссылка (`CLAUDE.md` → `AGENTS.md` и наоборот) пишется насквозь, один файл — один блок. Повторные блоки удаляются, `begin` без `end` — файл не трогается (вывод `init` говорит; фраза — полная). Повторный `init` идемпотентен: файл не меняется побайтно.
   - `init --no-agents-md` — `AGENTS.md` и `CLAUDE.md` не трогаются (существующие блоки тоже). `doctor` — ⚠, если блока в `AGENTS.md` нет или `CLAUDE.md` без блока и без импорта (§10).

   Почему: фраза человека должна быть короткой и одинаковой во всех харнессах, а постоянные инструкции проекта читают все — без настройки самих харнессов (§1 п. 1). Блок не велит подключаться без просьбы — иначе любая сессия в проекте шла бы в бригаду. Цена — правка файла, который может быть в git.
2. Человек агенту — в новой сессии, открытой в каталоге проекта: «подключись к бригаде». Постоянные инструкции харнесс читает при старте сессии; сессия из другого каталога найдёт чужую `.brigada` или никакую.
   - Блок говорит: подключиться — значит работать в цикле до STOP (после `join` не отчитываться человеку, сразу `wait`); участник только координирует, любую работу делают его подагенты (§5.4); подагент участника к бригаде не подключается никогда — блок читают и подагенты.
   - Те же напоминания — в последней строке перед `NEXT:` у `join` и в строке таймаута `wait`: `── нет новых (N с) · ход не завершай · NEXT: …`.
   - Почему: в полевом прогоне модель после первого пустого `wait` сочла просьбу «подключись» выполненной и завершила ход отчётом. Запасной вариант — без блока (`--no-agents-md`, сессия открыта до `init`, харнесс не читает ни `AGENTS.md`, ни `CLAUDE.md`): «подключись к .brigada, прочитай инструкцию в .brigada/README.md».
3. Агент по README определяет харнесс (`claude`, `codex`, `opencode`, иначе короткое имя; синонимы нормализуются) и модель; `join --harness <h> --model <m>` выдаёт полное имя `<harness>-<n>.<ключ>` (`claude-1.k7f3q9`, ключ сессии — ниже) и сводку: кто онлайн, активная задача, таймаут `wait`, «Таймаут инструмента» (как вызывать `wait` в этом харнессе), `NEXT:`. Агент разрешает вызовы brg «навсегда», читает PROTOCOL и входит в цикл (§5).

- **Идентичность** — явный `--as <имя>` в каждом вызове (`BRG_AS` — альтернатива). Опознание по `$PPID` отклонено: в Codex команды идут через обёртку песочницы, на Windows/MSYS свои PID. Отклонено и опознание по дереву процессов (сравнить предка вызывающего с родителем живого `wait`): причины те же, и вдобавок нужен `ps`, которого нет в списке утилит (§11).
- **Ключ сессии в имени** — **(решение человека)** защита от ошибки модели, а не от злоумышленника (профили читаемы, §1). Случай из демо: сессия, получившая задачу в промпте, пропустила `join`, увидела в `who` агента своего харнесса (`opencode-1`) и решила, что это она; `status` ответил «Мой wait: работает» — это сошло за подтверждение личности. Итог — два процесса под одним именем: оба вели задачу как lead, дублировали подзадачи и правили одни и те же файлы (резервирования своих путей не ловят), а двойник без `wait` не получал STOP.
  - `join` выдаёт полное имя `<базовое>.<ключ>`. Ключ — 6 символов `[a-z2-9]` из `$RANDOM` (без `l` и `o`), хранится как `Key:` в `agents/<имя>`. Имена харнессов — только `[a-z0-9]`, поэтому имя и ключ однозначно делятся по первой точке.
  - **Состояние — только на базовом имени**: файлы агентов, курсоры, `From:`, `Assignee`, Lead, резервирования, флаги стопа и паузы, `metrics.log`. Ключ пишется только в профиль. Другим имя показывается без ключа (`who`, `tail`, сообщения), поэтому из `who` ключ не взять; доска показывает человеку только первые 3 символа ключа — найти окно агента (§9.2). Полное имя brg печатает только самому агенту — в подсказках `--as` и в `NEXT:`; сжатие контекста ключ переживает так же, как имя: через последний `NEXT:`.
  - **Изменяющие команды требуют ключ:** `send`, `wait`, `busy`, `leave`, `task new|close|cancel`, `lead give|take`, `item add|claim|done|release|reassign|review|cancel`, `run` (запуск и `cancel`). Голое имя → отказ: «имя занято другой сессией; твоё имя — только из вывода твоего join в этом чате; не видишь его — сделай join». `join --as` здесь не подсказывается.
  - **Команды чтения** (`status`, `read`, `who`, `task show|list`, `item show|list`, `run show|list`) принимают и голое имя — их вызывают подагенты (§5.4). Без ключа они не освежают Last-Seen (иначе двойник «оживлял» бы настоящего агента), подсказки с `--as` в их выводе — с заглушкой `<твоё имя из join>`, а `status` не подтверждает личность: «wait агента X работает (pid N). Если ты не делал join в этом чате — ты не X: сделай join», `NEXT:` — `join`.
  - Ключ не `[a-z2-9]{6}` или не совпадает с профилем → отказ в любой команде: «ключ устарел или с ошибкой: под этим именем переподключилась другая сессия».
  - При отказе по ключу `NEXT:` — `join`, а не «исправь и повтори … --as X»: повтор с тем же именем зациклил бы агента. У `wait` — по-прежнему код 0 и последняя строка `NEXT:` (§5).
  - Имена-цели (`send --to`, `item reassign --to`, `lead give`) принимаются и с ключом — ключ отбрасывается: агенты копируют своё полное имя.
  - Совместимость: профиль без `Key:` (агент подключился до 0.2.0) принимает голое имя везде; ключ он получит при `join --as`.
- **Возврат** после потери контекста — `join --as <имя> --harness <тот же>` (имя голое или полное): только тот же харнесс; снимает `Left`; курсоры сохраняются; выдаёт **новый ключ**, прежний перестаёт работать (старая сессия, если жива, получит «ключ устарел»). В `lobby` — «X переподключён новой сессией; прежний ключ недействителен» (будит lead'а). Отказ:
  - у имени живой `wait`: «если это твой wait и ключ потерян — дождись его конца и повтори join --as»;
  - **(решение человека)** агент не «выпал»: возврат разрешён только после тишины — ни `wait`, ни вызовов brg — дольше max(`wait_timeout` + 60 с, `dropout_after`), как у пометки «возможно выпал» (§5.2), либо в состоянии `asleep`/`gone` (в т.ч. после `leave` — сразу). Иначе двойник, знающий базовое имя из `who`, забрал бы имя вместе с ролями у работающего агента: «мёртвый wait» — обычное состояние агента между вызовами (в демо он подолгу работал без `wait`). Отказ: «X активен (последний вызов N с назад). Если это ты и ключ потерян — он в последней строке NEXT; иначе подожди M с или подключись под новым именем». Флаг стопа на условие не влияет. Цена: агент, потерявший ключ, ждёт до ~5 минут или подключается под новым именем.
- **Одна платформа на `.brigada`**: `join` отказывает, если платформа (Darwin, Linux, MSYS, WSL, …) не совпадает с подключёнными не-`gone` агентами — pid, блокировки и пути у WSL и Git Bash разные.
- **Глобальная команда человека:** `bash install.sh` ставит `bin/brg-global` как `~/.local/bin/brg`. Из любого подкаталога проекта она запускает ближайший `.brigada/bin/brg`, `brg init` — версией репозитория, вне проекта — `brg` репозитория; если копия в проекте устарела — подсказывает `brg init`. Агенты по-прежнему вызывают `bash .brigada/bin/brg …` — от их окружения ничего не требуется (§1 п. 1).

## 4. Хранилище

```
.brigada/
  README.md, PROTOCOL.md # для агентов (копии template/; init перезаписывает)
  board.html             # доска человека (копия template/; init перезаписывает; §9.1)
  VERSION
  config.default         # значения по умолчанию (копия template/config; init перезаписывает)
  config                 # настройки проекта: init создаёт один раз и не трогает
  bin/brg, bin/brg.cmd
  bin/brg-serve.py       # необязательный сервер доски (Python ≥ 3.8; копия из репозитория; init перезаписывает; §9.1)
  agents/<name>          # профиль: Name, Key (ключ сессии, §3), Harness, Model, Platform, Joined… [, Left, Rejoined]
  lobby/                 # канал проекта: seq, messages/000001.msg, cursors/<name>
  common/project.md      # устойчивые факты о проекте (стек, тесты, конвенции) — пишут агенты
  common/history.md      # реестр закрытых и отменённых задач — пишет brg
  tasks/active           # имя каталога активной задачи (нет файла — нет активной)
```

### 4.1 Формат записей

Все записи — «заголовки `Key: value` + пустая строка + тело» (как email). Без JSON: разбирается `sed`/`awk`, читается людьми и моделями. Сообщение `messages/000014.msg`:
```
Id: 14
Channel: T001
From: codex-1            # агент | human (say) | brg (результат run)
To: all                  # all | имя[,имя] | human (можно с именами)
Kind: msg                # msg | system
Re: 12
Reply-By: 1759838400     # необязательно, epoch
Expect: claude-1,opencode-1   # при Reply-By: чьего ответа ждём
Wake: no                 # только у системных: no — не будит; <имя>[,<имя>] — будит только их
Ask: yes                 # необязательно: вопрос человеку (send --ask, §9.2)
Time: 2026-10-07T12:03:11Z
Epoch: 1759838191

тело
```

Время: ISO для людей, epoch для вычислений (разбор дат в BSD/GNU `date` различается — только форматируем).

### 4.2 Запись и блокировки

- Блокировка — `mkdir run/locks/<имя>.lock` + `owner` («pid epoch»). Протухшая (владелец мёртв, лок старше `lock_stale` или без `owner` дольше `lock_stale`; `lock_stale` ≫ любой критической секции) снимается **атомарно**: `mv` лока в уникальное имя (побеждает ровно один; лок, сменивший владельца, не трогается), затем `rm`. Снимает лок только владелец. Вложенность: task → runs → chan; exec → runs → chan. **(0.9.0)** Полный порядок: `spawn.S00N → roster → task → runs → chan` (и `spawnseq` — номер запуска — до `roster`). Лок надзора `spawn.S00N` держится всё время жизни надзора и **никогда** не снимается по возрасту (как exec-лок — только по смерти владельца, подтверждённой его `hb`, §5.5); надзор, держа его, берёт `roster` (`leave` при `rm`); ни один держатель `roster`/`task` не ждёт лок надзора — разовые вызовы (`spawn rm|detach|rights`, `join --as`) пробуют его один раз **до** `roster`.
- **«Мёртв»** — у pid, прочитанного из файла, всегда по одной функции `pid_alive` (§11): `kill -0` успешен или отвечает EPERM («Operation not permitted» — процесс есть, но недоступен: песочница Codex, чужой пользователь) — жив; ESRCH и любой другой ответ — мёртв. Лок недоступного владельца снимается только по возрасту (`lock_stale`), exec-лок — по heartbeat (§7.3).
- Сообщение — под блокировкой канала: `seq+1` → тело во временный файл в том же каталоге → `mv` в `messages/NNNNNN.msg` → обновить `seq`. Нумерация без дыр, курсор не «перепрыгнет» сообщение. Упали между `mv` и `seq` — `seq` пересчитывается по максимальному номеру файла.
- Остальные файлы — тоже tmp + `mv`; `mv` — с повторами (Windows: файл может держать антивирус или читатель).
- **Тексты** (сообщение, постановка, описание подзадачи, комментарий ревью) — из stdin (heredoc `<<'BRG_EOF'`) или `--file`; `say` — ещё и аргументами; `item add --desc`/`item review --comment` — однострочная альтернатива (в т.ч. для PowerShell, где нет heredoc, а пайп в Windows PowerShell 5.1 портит кодировку). CRLF → LF, BOM снимается, UTF-16 отвергается. Лимиты: сообщение — `msg_max_bytes` (8 КБ; больше — отказ с подсказкой положить текст в `shared/`), постановка — 64 КБ. stdin-пайп, не закрывшийся за 10 с, — отказ, ничего не отправлено.
- **Короткие поля из опций по длине не отвергаются** (отказы стоят агентам шагов): `--title` (200 байт), `--note` (500), `--desc`/`--comment` (`msg_max_bytes`) обрезаются по границе UTF-8 с пометкой «…(обрезано)» и предупреждением.

## 5. Ожидание и рабочий цикл

**(решение человека)** Единственный механизм — блокирующий `brg wait --as <имя> [--timeout S]`. Последнее действие каждого шага агента — `wait`; ход не завершается (кроме STOP).

1. **Один wait на агента, takeover без сигналов.** Новый wait пишет свой pid в `run/wait/<имя>.pid`; старый каждый тик (1 с) проверяет владение и, увидев чужой pid, выходит. Сигналы не посылаются: pid из файла мог быть переиспользован. Дубликаты (wait, уведённый харнессом в фон) не съедают почту.
2. **Вытесненный wait не провоцирует новый:** печатает `── SUPERSEDED: … НЕ вызывай wait повторно.` — это рвёт цепочку «уведомление о завершении старого wait → модель зовёт ещё один». TERM/INT/HUP — только от харнесса или человека (лимит команды, Esc), поэтому `── прерван сигналом … · NEXT: …` — цикл продолжается (pid-файл уже чужой — SUPERSEDED).
3. **Доставка хотя бы один раз.** Wait сначала подтверждает пачку предыдущего (`Acked := Pending`), затем ищет новое. `Pending` пишется только после вывода: убитый до вывода wait не теряет сообщения.
4. **Каналы:** `lobby` и активная задача (плюс дренаж только что завершённой, §6). Доставляется адресованное агенту или `all`, кроме собственного. Чужие личные не доставляются (видны в `tail` и `read --all`): шум и контекст дороже прозрачности.
5. **Heartbeat:** каждый тик — `run/wait/<имя>.hb`, раз в `heartbeat` с — Last-Seen (его обновляет и любой вызов brg). Живой wait = pid жив (`pid_alive`, §4.2: EPERM — жив) **и** hb свежий (защита от переиспользования pid).
6. **Сироты:** умер родитель — wait выходит молча, не держа призрака в `waiting` (родитель `1` — обёртка, MSYS — не проверяется). Недоступный родитель (EPERM, песочница) считается живым: сирота там не распознаётся и выходит по таймауту — это лучше ложного `orphan` у живого агента.
7. **Сам завершается раньше лимита харнесса:** таймаут из `config` по харнессу и платформе (§5.1); `--timeout` переопределяет и повторяется в `NEXT:`; так же — `--busy` (п. 13, §5.4).
8. **Будят:** новая почта, сводка дедлайна (§8), стоп (§9), `leave` (`── LEFT`). **Тихие системные события** (`Wake: no`: подключился, отключился, взял подзадачу, взялся проверять) не будят и приходят со следующей будящей пачкой — иначе каждый join стоил бы вызова модели каждому ждущему. Адресные (`Wake: <имена>`) будят только названных. Новая/закрытая/отменённая задача, смена lead, уход lead'а, уход агента с ролью — будят всех; «подключился/вернулся» при активной задаче — lead'а (иначе он не знает, что участники пришли); `item add`, `done`, `release`, возврат сданной в работу (`claim` из `done`) — lead'а; `reassign` — нового исполнителя; `review` — исполнителя и lead'а; `cancel` — исполнителя, lead'а и проверяющих (`Reviewing:` — им проверять больше нечего); `claim` и `review --start` — никого; результат `brg run` — инициатора. Автор события не будится. **На паузе человека** (§9) будит только то, что пришло `From: human` (`say`, `task new|cancel --as human`, `lead give --as human`) и снятие паузы (п. 14); остальное — в том числе уведомление `From: brg` «X — lead» (§6.1), которое при общей паузе, таким образом, никого не будит, — приходит после паузы.
9. **Дайджест на таймауте:** при активной задаче перед `── нет новых` — строка `T001: todo 1 · в работе I002 codex-1 · на проверке I003 (claude-2) · готово I001 · прогонов идёт 1` (стадии — §7.1.1) и `· свободны: claude-2, codex-1` — агенты с живым `wait` без пометки «работает» (п. 13), кроме себя, остановленных и стоящих на паузе (иначе лид опрашивает `who`/`item list`).
10. **Кап вывода** `wait_output_max` (~20 КБ, лимит inline-вывода харнессов): `Pending` = последнее показанное, остаток — следующим wait сразу (строка `── ещё N в <канал> не вошло …` с командой `read`).
11. **Всегда код 0**, статус — в тексте. Последняя строка — `NEXT:` (кроме STOP, SUPERSEDED, LEFT и выхода сироты), в том числе при ошибке аргументов и отказе по ключу (§3) — иначе агент выпадет из цикла.
12. `read` курсор не двигает и по умолчанию показывает всё после `Acked`, включая последнюю выданную пачку — безопасный повтор, если агент не уверен, что видел вывод. Новый агент стартует с конца `lobby` и активной задачи.

13. **(решение человека, 0.6.0) «Ждёт» значит «свободен».** Участник по §5.4 работает через подагента, а подагент (в Claude Code — в фоне) идёт, пока участник сидит в `wait`: по одному `wait` не отличить «свободен, готов к поручению» от «его подагент работает». Поэтому `wait` без `--busy` — явное «я свободен» (в `who`/`status`/на доске — «ждёт»), а `wait --busy ["подпись"]` — «мой подагент работает» (пометка, §5.4). `NEXT:` повторяет `--busy`, пока пометка стоит, — копируя `NEXT:` дословно, агент держит пометку, не думая о ней.

14. **(решение человека, 0.7.0) Пауза внутри `wait`.** Пауза (§9) не завершает ход агента — он остаётся в `wait`, и вот что тот делает, пока она стоит (общая `run/paused` или своя `run/paused.<имя>`):
    - **Будит только человек.** `AWK_FMT` считает кроме `wake` второй счётчик `hwake`: будящее (по тем же правилам `Wake:`) **и** `From: human`. Проход 1 `w_deliver` на паузе будит по `hwake`, а не по `wake`; при пробуждении выдаётся всё накопленное после `Acked` без фильтра (курсор линейный: потери нет), с строкой перед `NEXT:` «пауза продолжается: отвечай человеку, новую работу не начинай». Кап вывода на паузе называет, что будет с остатком: «придут после снятия паузы или со следующим сообщением человека».
    - **Снятие паузы будит и приносит накопленное в том же `wait`.** Проход 1 на паузе сдвигает `CH_SEEN` за всё просмотренное, будящее ли оно; поэтому `wait`, видевший паузу, на переходе «пауза → нет паузы» возвращает `CH_SEEN := CH_ACK` по всем каналам и завершается строкой `── пауза снята: человек снял паузу — новую работу можно начинать.` и накопленным (нет накопленного — строка и `NEXT:`). Без сброса накопленное пришло бы только со следующим `wait`.
    - **Дедлайны на паузе не будят.** `w_deadlines` вызывается на паузе только при пробуждении сообщением человека или снятии паузы (его сводки идут с этой пачкой); маркер `.done` заранее не захватывается.
    - **Таймаут на паузе** — `── пауза · нет новых от человека (N с) · ход не завершай · NEXT: …`; сводки задачи со «свободны» там нет. Длинного ожидания на паузе (`pause_timeout`) нет — решение человека: пауза ждёт с обычным `wait_timeout`, фоновый `wait` Claude Code не используется (§1 п. 3).
    - `wait`, упавший с ошибкой после записи pid-файла (например, не записалось сообщение «X — lead»), pid-файл и heartbeat убирает сам. Самоназначение lead'а (§6.1) при общей паузе разрешено, при личной паузе агента — нет: он станет lead'ом следующим `wait` после `resume`.

Курсор `cursors/<name>`: `Acked: 14` (всё ≤ 14 обработано), `Pending: 15` (выдано последним wait, подтвердит следующий). Вывод:
```
── T001 · 2 новых ─────────────────────────────
#14 codex-1 → all · re #12 · 12:03
  Предлагаю лидом claude-1: …
#15 [система] claude-1 → all · 12:04
  …
── NEXT: обработай, затем: bash .brigada/bin/brg wait --as claude-1.k7f3q9
```
Таймаут: `── нет новых (100 с) · ход не завершай · NEXT: …`. Стоп: `── STOP: человек остановил бригаду. Заверши ход.`

### 5.1 Таймауты по харнессам

Значения **консервативные — до замеров** в каждом харнессе. Все ниже 120 с — дефолтного лимита команды: модель может не передать увеличенный таймаут инструмента (особенно после сжатия контекста). Повышать — только если замер покажет, что модель делает это стабильно.

| Харнесс | Лимит команды | `wait_timeout` сейчас | Цель после замера |
|---|---|---|---|
| Claude Code | по умолч. 2 мин, макс. 10 мин (параметр `timeout`); на лимите уводит в фон | 100 | 540, если модель стабильно передаёт `timeout: 600000` |
| OpenCode | по умолч. 2 мин, верхний предел снят | 100 | 540 при том же условии |
| Codex (macOS/Linux) | unified_exec: команда «паркуется» через 10–30 с, дальше опрос моделью (`write_stdin`) | 25 (вернуться до парковки) | по замеру |
| Codex (Windows) | unified_exec по умолчанию выключен — ближе к обычной блокирующей команде | 100 (`wait_timeout.codex.msys`) | по замеру |
| неизвестный | — | 100 (`wait_timeout.default`) | — |

Таймаут инструмента = `wait_timeout` + 60 с (≤ 600 с) — печатают `join` и `status`. `doctor`: `wait_timeout` > 540 с — ✗, > 110 с (Codex вне Windows — > 25 с) — ⚠.

«Выпадение из цикла» — латентность модели (выход `wait` → следующий вызов инструмента) > 60 с без учёта повторов запроса провайдером, или самостоятельное завершение сессии. Опросы запаркованной команды Codex в логе `wait` не видны — их стоимость оценивается по транскрипту. Токены на пробуждение = токены сессии / вызовы `wait`, на модели, что реально будет в бригаде.

**Правило жизнеспособности:** **≤ 15 вызовов модели на час простоя.** Не достигающий его харнесс (ожидаемо — Codex с парковкой) участвует с повышенной стоимостью простоя либо только «по тычку» человека — решение по итогам замера.

### 5.2 Живость агента

Состояние в `who`/`status` (и в списке «Онлайн» у `join`, `status`): **(решение человека, 0.6.0) «ждёт» ⇔ свободен** — идёт `wait` агента, а пометки «работает» (§5.4) нет; агент готов к поручению. Остальные показываются так:

| Состояние (внутреннее) | Пометка | Показ |
|---|---|---|
| `waiting` (жив wait) | нет | **ждёт** |
| `waiting` | есть | **работает: подпись, N мин** (подпись — до 2 слов; N мин — сколько стоит пометка) |
| `working` (недавний вызов brg, wait нет) | нет / есть | **работает** / **работает: подпись** — агент между двумя `wait` или его `wait` ещё не начат; дальше — «не на связи» |
| `asleep` (нет wait и вызовов дольше `asleep_after`, 15 мин) | — | `asleep` |
| `gone` (`leave` или тишина дольше `gone_after`, 1 ч) | — | `gone` |
| `waiting` / `working` при стопе человека (общем или личном, §9) | — | **остановлен** — стоп завершил ход агента, он не работает |
| `waiting` / `working` при паузе человека (общей или личной, §9) | как у состояния | то же, что у состояния, и «(пауза)»: пауза ход не завершает — агент ждёт, новую работу не начинает |

Пороги щедрые: агент, 10 минут гоняющий тесты, не пропал. Пометки: «не на связи N мин» — wait не идёт дольше `wait_timeout` + 60 с (раньше «без wait»); «возможно выпал» — ни wait, ни вызовов brg дольше max(`wait_timeout` + 60 с, `dropout_after` = 300 с), кроме остановленных: подсказка человеку написать агенту в чат «продолжай». Пометка «работает» этой подсказки не отменяет: участник с фоновым подагентом обязан сидеть в `wait`, поэтому пометка без живого `wait` — признак выпавшего агента. Единственное исключение — пометка `Via: busy` (команда `brg busy`: «подагент блокирует меня», харнесс без фоновых подагентов): «возможно выпал» у такого агента не показывается, «не на связи» — показывается. Значения внутреннего состояния (`ST`: waiting/working/asleep/gone) не меняются и не зависят от пометки; ею дополняется только показ.

**Запущенные brg (0.9.0, §5.5).** `ST` считается так же: замерший или упавший агент — живой надзорный `wait` → `waiting` («ждёт»); идёт ход — вызовы brg и `touch_seen` надзора → `working`. В `who`/`status` к строке добавляется «(запущен brg, S003)» и состояние записи (§5.5): «ход N идёт M мин · последнее событие K мин назад», «упал: …», «отказ в правах: …», «надзор не отвечает», «конфликт». У такого агента с живым надзором и идущим ходом нет «не на связи»/«возможно выпал» (`idle_note_v`) — вместо этого «ход N идёт M мин · последнее событие K мин назад (возможно, долгий инструмент)», и он «на связи» для выбора lead'а (`lead_online`, §6.2) без окна `wait_timeout` + 60 с: прошлый lead в долгом ходе не пропускается. Остановленный запущенный агент (в `stopped` надзор `wait` не держит) стареет до `asleep`/`gone`, как ручной.

### 5.3 Известные минусы (приняты сознательно)

- Сообщение человека в чате харнесса дойдёт, когда wait вернётся (до `wait_timeout`), либо после Esc.
- Простой не бесплатен: один вызов модели на таймаут на агента.
- Гарантии нет: агент может завершить ход. Это видно («не на связи», «возможно выпал», `asleep`); lead переназначает его подзадачи, человек говорит «продолжай».

### 5.4 Подагенты

**(решение человека, 0.5.0)** Участник бригады — только координатор своей части; любую работу делают подагенты, которых он запускает у себя. Это обязательная рамка (PROTOCOL, раздел 2), а не ожидание: в версии 0.4.1 это была рекомендация, и в прогонах человека она доходила не до всех — участники сами читали и правили код.

- **Сам участник** только координирует: вызовы brg и переписка, обсуждение и решения, поручения подагентам и приём их результата (отчёт подагента, `git diff --stat`), короткие документы координации (`shared/plan.md`, `summary.md`), коммит lead'а.
- **Подагент** делает всё остальное: чтение и правку кода и документов проекта, исследование, ревью и проверку чужой работы, разбор упавших тестов.
- **Сколько подагентов.** По умолчанию у участника одновременно работает один подагент (последовательно — сколько нужно). Больше — только если это явно разрешил человек: в постановке задачи, в чате участника или сообщением `human`.
- **Харнесс без подагентов** — единственное исключение: участник делает работу сам, короткими шагами между `wait`, и говорит об этом бригаде на перекличке.
- **Фоновые подагенты** есть в Claude Code и в OpenCode v2 (`task … background: true`); блокирующий вызов подагента (тот же OpenCode без `background`) — `brg busy` перед ним.

Почему так: контекст участника живёт всю задачу и растёт с каждым пробуждением — чем он меньше, тем дешевле пробуждение и позже сжатие; участник, занятый работой сам, выпадает из цикла, а бригада простаивает. Где правило повторяется, чтобы его увидел каждый: блок brigada в `AGENTS.md`/`CLAUDE.md` (§3), README (§1, «Подагенты»), PROTOCOL (раздел 2), вывод `join`, `task new`, `item claim` и `item review --start`. brg подагента от участника не отличает — проверить правило он не может.

Механика (README, обязательна): подагент ни при каких обстоятельствах не подключается к бригаде — не вызывает `join`, `wait`, `leave`, `stop` — его `wait` под именем участника вытеснит wait участника (SUPERSEDED), и тот выпадет из цикла; можно команды для чтения и короткий `run --sync` под именем участника. `run` — изменяющая команда (§3), поэтому подагенту передаётся полное имя участника, с ключом; командам чтения хватает и базового. brg подагента от участника не отличает — правило только в документах.

**Пометка «работает» (0.6.0, решение человека: «ждёт» ⇔ свободен — §5 п. 13, §5.2).** Участник сообщает «мой подагент работает» сам; brg проверить этого не может — как и само правило подагентов. Одна пометка на агента (подагент одновременно один): `run/busy/<базовое имя>` — заголовки `Task: T00N`, `Since: <epoch>`, `Note: <подпись или пусто>`, `Item: <I00N или пусто>`, `Via: wait|claim|review|busy`; запись — tmp + `mv`.

- **Действительность.** Пометка с `Task`, не равной активной задаче (или без активной задачи), **не существует** — для `agent_state`, `NEXT:`, `who`, `status`, доски. Поэтому очистка `run/busy/` при `task close|cancel` (и `--cancel-current`) — просто уборка, гонки безвредны. Читает её одна функция (`busy_read`). Без активной задачи `wait --busy` и `busy` пометку не ставят: «задачи нет — пометка не ставится» (не отказ).
- **Как ставится.** `wait --as X --busy ["подпись"]` — в начале `wait` (после проверки STOP; STOP пометку не трогает), `Via: wait`; `Since` и `Item` переносятся с прежней пометки, только если она действительна и `Note` та же. `item claim I00N` → `Note: I00N`, `Item: I00N`, `Via: claim` (и вернуть сданную в работу — тоже); `item review I00N --start` → `Note: проверка I00N`, `Item: I00N`, `Via: review` — взял (проверяет) = работает. `brg busy --as X ["подпись"]` — пометка без ожидания, `Via: busy`: харнессы, где вызов подагента блокирует участника (OpenCode), и работа вне подзадач; `busy --off` — снять; при STOP команда разрешена (она не начинает работу), первая строка — баннер STOP, `NEXT:` — «заверши ход».
- **Подпись обрезается, а не отвергается** (§4.2): управляющие символы и `"` `'` `\` `$` `` ` `` `%` → пробел (`%` — cmd.exe раскрывает его и в кавычках, а `NEXT:` на Windows идёт через `brg.cmd`), пробелы схлопываются, остаются первые 2 слова, ≤ 48 байт по границе UTF-8; если что-то изменилось — предупреждение; ничего не осталось — пометка без подписи (в `NEXT:` — голый `--busy`, не `--busy ""`).
- **Как снимается.** Простой `wait` (без `--busy`) — явное «я свободен»; `busy --off`; `leave`; `join` (в т.ч. `join --as`: новая сессия — подагента нет); смена или закрытие задачи. Пометка с **пустым** `Item` командами подзадач **не снимается никогда** (иначе `item release` lead'ом чужой подзадачи или его `--verdict skip` сняли бы пометку «финальная валидация», пока подагент работает): при `item done`/`--verdict` у такого агента — строка «ты отмечен «работает: T» — если подагент закончил, следующий wait без --busy». Пометка с `Item = I00N` снимается у **своего владельца**, когда подзадача от него уходит: у исполнителя — `item done`, `release` (кем бы ни выполнен), `cancel`, `reassign` (у старого исполнителя); у проверяющего — его `--verdict` по этой подзадаче, а также `item cancel`, `release`, возврат в работу (`claim` исполнителем сданной) и `reassign` — они очищают `Reviewing:`, и пометки «проверка I00N» у всех названных там снимаются. Действие над чужой подзадачей пометку другого агента не трогает. Строка «ты отмечен…» печатается только действующему исполнителю или проверяющему этой подзадачи (не lead'у, отпустившему чужую). Новому исполнителю `reassign` пометки не ставит — в системном сообщении ему подсказка «поручи подагенту и `wait --busy "I00N"`».
- **`NEXT:` = текущее состояние пометки.** Одна функция (`next_wait`) строит `wait --as … [--busy "<подпись>"] [--timeout S]` для **всех** `── NEXT:` и ошибочных `NEXT:` (`send`, `read`, `status`, `task …`, `item …`, `run …`, `lead …`, ошибки разбора; до `need_agent` имя берётся из `--as`/`BRG_AS`), включая `NEXT:` самого `wait` — он вычисляется при завершении (пометку могли снять за время ожидания). Поэтому после `claim`/`review --start` `NEXT:` сам содержит `--busy "I00N"`, а после `done` — нет; ошибка в `--busy` не превращает `NEXT:` в простой `wait`, снимающий пометку. Дополнительно: вывод `wait` с действительной пометкой (пачка и таймаут) — строка перед `NEXT:` «Ты отмечен «работает: T». Подагент закончил и ты свободен — следующий wait без --busy»; простой `wait` у агента с подзадачей `claimed` или с `Reviewing:` на нём — строка «У тебя I003 в работе: если подагент работает — wait с --busy "I003"» (не отказ). Гонка `item cancel` lead'ом со стартом `wait --busy "I003"` у исполнителя допустима: пометку снимет простой `wait`. Устаревший `NEXT:` (выдан до смены задачи) не должен пометить новую задачу: подпись `I00N` / `проверка I00N` ставится, только если эта подзадача активной задачи claimed этим агентом или он в её `Reviewing:`; иначе — предупреждение и пометки нет (так же у `busy`).
- **Показ.** `who`, `status`, «Онлайн» — §5.2; сводка на таймауте — «свободны» (§5 п. 9); снимок доски — поле `mark` агента `{note, since, via, item}` (§9.1).

### 5.5 Агенты, запущенные brg (0.9.0)

**(решение человека, 0.9.0)** Человек запускает агентов сам — из терминала (`brg spawn`) и с доски («Добавить агента», §9.1): видит их состояние и что они делают, а они работают в бригаде так же, как подключённые вручную. Решения человека:
1. **Два вида участников в одной бригаде.** Подключённые вручную — ровно как раньше (цикл `wait`, ход не завершают). Запущенные brg — по механизму ниже. Друг для друга неотличимы: имена с ключом, задачи, lead, подзадачи, ревью, `run`, вопросы, стоп, пауза.
2. **Запущенный агент замирает, когда свободен:** завершает ход (процесс харнесса выходит). Есть будящее (по правилам `wait`, §5 п. 8) — brg продолжает его сессию и передаёт пачку прямо в промпт (один запрос к модели). Работает подагент — ход не завершает, сидит в `wait --busy`.
3. **Права** — явный выбор при запуске, по умолчанию полные, с предупреждением. Отказ в правах **виден** на доске, кнопка «дать полные права» действует со следующего хода той же сессии.
4. **Лимитов нет; токены и стоимость видны** по каждому агенту и итогом.
5. **Отдельного «оживления» нет.** Аварийный конец хода виден на доске, lead'у — сообщение; пачка доставляется заново **следующим пробуждением** — его вызывает новое сообщение агенту или кнопка «Разбудить». Без автоповторов.
6. **Запускает только человек** (терминал и доска).

Этап A — только **OpenCode** (Claude Code и Codex — этап B), только macOS/Linux (MSYS, Cygwin, WSL — отказ «пока не поддерживается»).

**Как устроен OpenCode 2.0.23** (по коду бинаря и проверкам без LLM): команды shell-инструмента модели идут в своих группах процессов; на **SIGINT** `opencode run` штатно прерывает сессию и гасит их (код 130), обработчика SIGTERM нет. Без `--auto` запрос разрешения не висит: `run` отказывает сам, в stderr — `! permission requested: <действие> (<ресурсы>); auto-rejecting` (с ANSI), в потоке — `tool_use` со `status: "error"` и «…request was rejected». По умолчанию в каталоге проекта можно всё (shell, правки, сеть, git push); спрашивается только выход за каталог проекта и чтение `*.env`; `--auto` одобряет и это. JSON-поток stdout (`--format json`) — только основная сессия; `tool_use` пишется по **завершении** инструмента (идущий не виден). События: `step_start`, `text`, `tool_use`, `step_finish` (`part.tokens`, `part.cost`), `error` (`error.message`); у каждого `sessionID` (`ses_…`); ошибка шага или прерывание — событие `error` и код ≠ 0. Подагенты — дочерние сессии: их id — в выводе завершённого `tool_use` инструмента `task` (`task_id: ses_…`; фоновый — `sessionID: ses_…`). `opencode session export <id>` печатает JSON, в начале которого `info.cost` и `info.tokens {input, output, reasoning, cache{read, write}}`; без `--standalone` команды OpenCode поднимают у человека долгоживущий фоновый сервис. Сообщение-аргумент OpenCode перекодирует (кавычки, `\"`), **сообщение из stdin** (не TTY) проходит как есть. В окружении команд модели — `OPENCODE_SESSION_ID` (у подагента — id дочерней сессии), `OPENCODE=1`, `AGENT=1`.

#### Запись запуска

`run/spawn/S00N/` (сквозной номер по проекту, `run/spawn.seq` под локом `spawnseq`). Файл `spawn` — заголовки (tmp + `mv`); пишет его только держатель лока надзора (надзор; при создании — `brg spawn`, при `rm`/`detach`/`join --as` без живого надзора — эти команды под локом):
- `Id`, `Agent` (базовое имя), `Harness`, `Model`, `Rights: full|project`, `Session`, `State`, `Note`, `Created`, `Created-Epoch`, `Supervisor` (pid — только для показа);
- `Turn`, `Turn-Start`, `Turn-End` (эпоха выхода харнесса из `turn.N.exit`), `Turn-Result: ok|crash|interrupted`, `Turn-Stopped: 1` (ход кончился при стоящем стопе), `Last-Error`, `Perm-Denied` (последний отказ в правах: держится до смены прав, успешный ход его не снимает), `Last-Event` (эпоха последнего роста `events.log` в текущем ходе; сбрасывается в начале хода), `Hold: 1` (серия аварий);
- `Tokens-In`, `Tokens-Out`, `Tokens-Reasoning`, `Tokens-Cache-Read`, `Tokens-Cache-Write`, `Cost` (строка; складывает awk `printf "%.6f"`), `Tokens-Source: export|stream`, `Sub-Sessions`;
- `Locale-Set`, `Locale` (исходная локаль человека, §9.1);
- тело — последний текст модели за ход (≤ 2 КБ, ключ замаскирован).

Рядом: `join.out` (вывод join — часть первого промпта), `prompt.N` (промпт хода; хранятся последние 5; наружу — только путь) и `prompt.head` (первые строки последнего промпта, ключ замаскирован — для доски), `events.log` (+ `events.log.1` — ротация перед ходом, если > 50 МБ), `stderr.log`, `supervisor.log`, `activity.log` (растёт) и `activity.tail` (последние 50 строк, tmp + `mv`, его читает доска): строки `epoch<TAB>kind<TAB>текст` (`turn`, `tool`, `text`, `error`, `permission`, `end`), ≤ 300 байт, управляющие символы → пробел, ключ замаскирован; `children` (id дочерних сессий) и `children.tok` (кэш их итогов), `stream.tok` (номер последнего учтённого хода и сумма `step_finish` основной сессии по всем ходам), `sub.tok` (сумма итогов дочерних сессий по последнему экспорту), `turn.N.parse` и `turn.N.text` (разбор хода N по ходу, ниже). От обёртки хода: `turn.pid`, `turn.hb` («pid обёртки epoch», раз в секунду), `turn.event`, `turn.session`, `turn.N.exit` (код и эпоха), `turn.N.off` (смещение `events.log` и `stderr.log` до хода). **Флаги** кладут `brg spawn …` (в т.ч. по запросу сервера доски): `rm`, `detach`, `wake`, `rights` (содержимое — новое значение); надзорный `wait` их только читает, удаляет надзор после обработки; `turn.stop` — просьба обёртке остановить ход.

| State | Значит | Показ |
|---|---|---|
| `starting` | надзор запущен, первый ход не начат (в т.ч. ждёт снятия стопа) | работает · запуск |
| `running` | идёт ход (обёртка жива) | работает · ход N, M мин · последнее событие K мин назад |
| `frozen` | ход кончился, надзор ждёт будящее | **ждёт** |
| `crashed` | последний ход аварийный (`Hold: 1`), надзор ждёт **нового** будящего | ждёт · «упал: <ошибка>» |
| `stopped` | стоп человека | остановлен — снимется кнопкой «Продолжить» (`brg resume`) |
| `conflict` | надзорный `wait` раз за разом вытесняется чужим `wait` под тем же именем | ждёт · «конфликт: под именем работает другой wait» |
| `detached` | забран в окно (`spawn detach` или `join --as`) — дальше обычный агент | как обычный |
| `removed` | убран (`spawn rm`) или ушёл сам (`leave`) | gone |
| (не `detached`/`removed`, а надзор мёртв по правилу лока) | надзор умер | «надзор не отвечает» · «Разбудить» перезапускает |

#### Агент

`brg spawn` подключает агента сам: та же функция, что `join --harness H --model M` (не копия), плюс `Spawn: S00N` в профиле; вывод join (вариант для запущенного — короткие правила, без «ход не завершай») входит в первый промпт; модель `join` не делает. «Запущен ли агент» — одна функция `spawned_v` (в профиле `Spawn:` и запись не `detached`/`removed`).
- **`join --as X`** запущенного — снимает `Spawn:`, запись → `detached`. Одна попытка лока надзора **до** `roster`: живой надзор → отказ «надзор жив: `brg spawn detach S` — забрать в окно»; жива обёртка хода (даже при мёртвом надзоре) — отказ «идёт ход агента — дождись его конца или `brg spawn rm`». Правило «только после выпадения» (§3) действует как раньше.
- **`join` при `BRG_SPAWN`** в окружении, указывающем на живую запись этого же `.brigada`, — отказ: `OPENCODE_SESSION_ID` задан и ≠ сессии записи — «ты подагент участника X — к бригаде не подключайся, выполни поручение»; иначе — «join не нужен: тебя подключил brg, имя — в первом сообщении».
- **`wait`/`leave`/`busy` с `--as` запущенного**, когда `OPENCODE_SESSION_ID` задан и ≠ сессии записи (или `turn.session`, пока сессия не перенесена в запись), — отказ «ты подагент…» (`wait` — код 0 и `NEXT:` «выполни поручение и верни результат»).
- Раннер `brg run` делает `unset BRG_SPAWN`: тесты проекта его не наследуют.

**Фразы ожидания — одна функция `next_wait`** (§5.4): у ручного — как раньше (`wait --as …`); у запущенного без действительной пометки — «заверши ход — brg разбудит тебя, когда будет новое»; с пометкой — `wait --as … --busy "…"`. Через неё — все `── NEXT:`; свои строки для запущенного — у вывода `join`, `busy`, баннера и отказов стопа/паузы (`stop_banner`, `work_refuse`), `w_notes_v` («у тебя I003 в работе — продолжи (поручи подагенту) или сдай/отпусти»; «ты отмечен «работает» — подагент закончил? тогда заверши ход»), строк таймаута `wait --busy`, `status`. Ни одна строка brg запущенному не велит «не завершать ход» или ждать в простом `wait`.

**Простой `wait` запущенного** (вызвал сам агент, без надзора) не блокирует: снимает пометку, подтверждает предыдущее, выдаёт будящее, если оно уже есть; иначе сразу `── нет новых · ты свободен — заверши ход: brg разбудит тебя, когда будет новое` и `── NEXT: заверши ход`. Второй и следующие пустые возвраты в одном ходе (счётчик `turn.N.idle`, только при `BRG_SPAWN`) — строка жёстче и метрика `wait.idle_repeat`. `wait --busy` — как раньше (блокирует).

#### Надзор, лок, обёртка хода

**Надзор** `brg __spawn S00N` — отдельный процесс на агента, запускается как раннер `brg run` (`nohup` + `set -m`, все fd перенаправлены, fd 3–9 закрыты, `trap '' HUP`); не в сервере доски — закрытая доска агентов не останавливает.

**Лок надзора** `run/locks/spawn.S00N.lock` — на всё время жизни надзора, один надзор на запись. Своя функция `spawn_lock_try S [НАБЛЮДАТЬ_СЕК]` (не `lock_acquire` и никогда не по возрасту): владелец `$$` — «мой» (после `exec`); мёртвый владелец (`pid_alive`) с `hb` старше `runner_dead_grace` — лок снимается сразу (`lock_break`); живой pid с молчащим `hb` — мёртв только после **непрерывного** наблюдения дольше `spawn_stale` (30 с; `hb_obs_init`/`hb_obs_tick` с порогом — для раннеров поведение прежнее). Новый надзор наблюдает до `spawn_stale + 5` с (владелец подаёт признаки жизни — тихий выход). Разовые вызовы — одна попытка; лок у живого надзора → флаг (`rm`/`detach`/`rights`) или отказ (`join --as`); **надзор «молчит»** (pid жив, `hb` старше `spawn_stale`: остановлен, завис, pid чужой после перезагрузки) — флаги обслуживать некому, поэтому `wake`, `rm`, `detach`, `rights` ещё и запускают новый надзор, который наблюдает и забирает лок, а `join --as` подсказывает `brg spawn wake`; надзор только что умер (pid мёртв, `hb` свежий) — подождать до `runner_dead_grace`, взять лок и сделать действие самому: флаг не остаётся без обработчика. `spawn wake` — флаг живому надзору или новый надзор и сразу возврат. После `exec` новый образ добавляет лок в `HELD`. `doctor` судит `spawn.*` как exec-лок (по `hb` и `runner_gone`), без ✗ «держится N с» у живого надзора.

**Сердцебиение надзора — всегда:** `hb` в каталоге лока раз в 5 с во **всех** ожиданиях (ход, надзорный `wait`, `stopped`, паузы, ожидание обёртки, `rm`/`detach`); надзор спит шагами по 1 с, ни одна операция не держит его дольше `spawn_stale / 2`.

**Обёртка хода** — отдельный процесс `brg __turn S00N N` (как раннер: `set -m` — своя группа и свой `$$`; подшелл не годится: в bash 3.2 у него `$$` надзора). Восстанавливает локаль из записи, `cd` в проект, снимает служебные переменные (`BRG_AS`, `BRG_VIA_CMD`, `BRG_SPAWN_*`, `BRG_CMD_LC*`), `export BRG_SPAWN=S00N`; запускает харнесс своим ребёнком под `set -m` (без него bash выставил бы фоновой команде SIGINT = SIG_IGN): `<bin> run <spawn.opencode.args> --format json --model M [--auto] [--session SID] --title "brigada S003 opencode-3" <prompt.N >>events.log 2>>stderr.log`. Раз в секунду — `turn.hb` и проверка `turn.stop`; раз в 5 с — рост `events.log` → `turn.event`; первая строка с `sessionID` при пустой сессии записи → `turn.session` (надзор сразу переносит в запись: «ты подагент» работает с первого хода). По `turn.stop`: `kill -INT` своему ребёнку, через 5 с TERM, ещё через 5 с KILL. После выхода харнесса — `turn.N.exit` (код, эпоха). Обёртка переживает `kill -9` надзора. **Живость обёртки:** жива, если pid из `turn.hb` жив и `turn.hb` свежий; мёртва — pid мёртв и `turn.hb` старше grace; живой pid с молчащим `turn.hb` — мёртв после непрерывного наблюдения дольше `spawn_stale`. Пока обёртка жива, второй ход не начинается.

**Сигналы** — только своим детям: обёртка → харнесс. Надзор своему `wait` и обёртке сигналов не шлёт (флаги и `turn.stop`); чужим процессам — только флаги.

#### Цикл надзора

1. **Восстановление** (надзор не первый для записи — `Turn` > 0 — и не `--continue`; прежний надзор умер между `running` и запуском обёртки — хода не было, не авария): дождаться, пока обёртка текущего хода станет мёртвой или появится `turn.N.exit`; итог хода — по коду; первый надзорный `wait` — с откатом (`ROLLBACK`).
2. **Ход.** Промпт → `prompt.N`; `Turn`, `Turn-Start`, `State: running`; обёртка. Пока она жива: `hb`, `touch_seen` агента раз в `heartbeat`, перенос `turn.event`/`turn.session` в запись; флаги: `rm` → `turn.stop`; `rights` — применить сразу (действует со следующего хода); `detach` — после хода; `wake` — удалить (ход и так идёт). Нет `turn.N.exit` — `crash` «обёртка хода пропала».
3. **Итог хода.** `ok` — код 0 и нет события `error`; `interrupted` — ход остановлен по `turn.stop`; иначе `crash` (`Last-Error` — сообщение `error` или «код выхода N»); ход кончился при стопе — `Turn-Stopped: 1`. **Откатывать — только по коду**: `crash`/`interrupted` → следующий надзорный `wait` с `ROLLBACK`; `ok` → нет (пачка, которую модель получила своим `wait` в ходе, — `Pending`, её подтвердит следующий `wait`). **Хвостовой `wait`** (команды модели живут в своих группах и могут пережить ход): жив `wait` агента или `run/wait/<агент>.last` изменился за ход и ≥ `Turn-End` → `ROLLBACK`. Значение `.last` до хода надзор запоминает: `wait` самого надзора кончается за миг до хода, и при ходе короче секунды его `.last` совпал бы с `Turn-End` — без этой проверки пачка приходила бы снова и снова. Первая авария серии (переход в `Hold: 1`) — системное сообщение lead'у (канал задачи, `Wake: <lead>`; lead — сам агент или задачи нет — `To: human` в канал задачи или `lobby`: сообщение «всем» пришло бы в промпт самому упавшему): «opencode-3 (запущен brg, S003): ход N упал — <ошибка>. Разбудит следующее сообщение ему или «Разбудить» на доске»; следующие аварии серии — только доска; серия кончается первым успешным ходом (иначе lead и упавший будили бы друг друга по кругу). После хода — извлечение активности и токенов из потока, экспорт токенов — в фоне, после старта надзорного `wait`. **Обновление brg:** между ходами `VERSION` проекта ≠ версии надзора → `exec … __spawn S00N --continue` (лок «мой» по `$$`; без восстановления; отложенные откат и FORCE передаются аргументами; пока идёт фоновый экспорт токенов — после него).
4. **Ожидание.** `State: frozen|crashed`. Сначала флаги `rm`/`detach`. Затем надзор запускает своим ребёнком `brg wait --as <полное имя> --timeout <spawn.wait_timeout>` с `BRG_SPAWN_WAIT=<файл результата>`, `BRG_SPAWN_ID`, и при необходимости `BRG_SPAWN_HOLD=1` (`Hold: 1`), `BRG_SPAWN_FORCE=1` (`wake`, снятие стопа), `BRG_SPAWN_ROLLBACK=1`; stdout — промпт. Результат: `msg|deadline|pause_end|force` → ход (лежит флаг `detach`/`rm` — надзор сам делает `cursor_rollback` и обрабатывает флаг; `wake` — удалить и строка причины); `flag:rm|detach` → п. 6, 7; `timeout`, `epipe` → снова ждать; `stop` → `State: stopped`, опрос раз в секунду; стоп снят и `Turn-Stopped: 1` → `wait` с FORCE и строкой «── стоп снят человеком: проверь status; есть начатая работа — продолжай, нет — заверши ход», иначе обычный `wait`; `left` → `removed`, выход; `superseded` (под именем жив чужой `wait`, обычно хвост хода) → снова `wait` с `ROLLBACK`, ≥ 3 раз за 60 с — `State: conflict` и повторы раз в 30 с; `orphan|int|hup|term` и прочее → снова, с паузой. **Нет файла результата** (`wait` упал через `die` или убит) → следующий `wait` с `ROLLBACK`; профиль с `Left:` → `removed`; ключ профиля ≠ ключу, с которым `wait` запускался, или нет `Spawn:` → `detached`; иначе `Last-Error` из stderr `wait` и пауза. **Защита от горячего цикла:** `wait` кончился без результата или с ошибкой быстрее 2 с — пауза 1, 2, 4, … ≤ 60 с.
5. **Промпт пробуждения** = `── brg разбудил тебя (S003, ход N) — ты opencode-3.<ключ>` + вывод `wait` как есть (пустой FORCE — `── нового нет` и `NEXT:`). Ключ в промпте полный (он нужен агенту), на доске и в `spawn show` — замаскирован. Харнессу промпт подаётся **через stdin**; сессия — `--session <Session>`; `Session` пуст (первый ход упал до первого события) — первый промпт заново плюс вывод `wait`.
6. **`rm`.** Ход идёт → `turn.stop`, дождаться обёртки; затем `leave` от имени агента (общая функция с `brg leave`: роли, выбор lead'а, сообщения), `State: removed`, выход. Надзор мёртв → `brg spawn rm` делает это сам под локом надзора (осиротевшая обёртка видит `turn.stop` сама).
7. **`detach`.** Ход идёт → дождаться его конца (не останавливать); `State: detached`, `Spawn:` из профиля убрать, выход. `brg spawn detach` печатает `cd <проект> && opencode --session <Session>` и «напиши в окне: «продолжай: status, затем wait»»; `status` агента — «тебя забрали в окно: ход не завершай, цикл wait», `NEXT:` — обычный `wait`. Надзор мёртв → `brg spawn detach` сам, под локом.
8. **`wake`** («Разбудить», `spawn wake`). Надзор ждёт → его `wait` видит флаг и сразу завершается в режиме FORCE: всё после `Acked` (откатанное, тихое); пусто — «── человек попросил продолжить: проверь status; есть работа — продолжай, нет — заверши ход». Надзор удаляет `wake` до следующего `wait` (иначе FORCE по кругу), `Hold` снимается. Ход идёт — флаг удаляется без действия. Стоит стоп — флаг не ставится: «бригада остановлена — сначала «Продолжить» (`brg resume`)». Надзор мёртв → новый надзор (возьмёт лок или выйдет, если жив старый): восстановление, затем ход в режиме FORCE.
9. **`rights`** (0.9.1) — **не будит.** Флаг надзор применяет сразу, и в ожидании, и во время хода: `Rights` в записи, `Perm-Denied` снимается, пишется `Rights-Note` — строка о смене прав («── человек расширил права до full (вне каталога проекта и чтение .env — теперь можно): если тебе или твоему подагенту отказывали — можно повторить» / «── человек изменил права на project: вне каталога проекта и чтение .env — отказ»). Новые права действуют со следующего хода (идёт ход — с конца текущего). `Rights-Note` входит в **каждый** промпт пробуждения (первой строкой после `── brg разбудил тебя …`); при составлении промпта надзор пишет `Rights-Note-Turn: N`, после хода `ok` номер N строка снимается, если с тех пор права не менялись (смена прав сбрасывает `Rights-Note-Turn`). Так строка переживает аварийный ход, перезапуск надзора и `exec`. Без живого надзора `spawn rights` пишет то же сам, под локом. Вывод и доска: «права S001: full — со следующего хода; разбудить сейчас — «Разбудить»». (В 0.9.0 смена прав будила агента FORCE-ходом «повтори действие» — в живом прогоне отказ получил подагент, и ход был потрачен впустую.)

#### Надзорный `wait` (`BRG_SPAWN_WAIT`)

Только для запущенного агента с совпадающим `BRG_SPAWN_ID`. `w_finish` пишет результат в файл (tmp + `mv`); вывод — как обычно (он и есть промпт). Каждый тик **до** выдачи — флаги записи (только чтение): `wake` → FORCE на этом же тике (`rights` не будит, 0.9.1); `rm`/`detach` → результат `flag:<имя>` без выдачи.
- **HOLD** (после аварии будит только новое): отметки `H[канал]` берёт надзор **в момент аварии, до отката** (`hold.marks`): это `Pending` курсора агента в каждом слушаемом канале — то, что упавший ход видел. Будит всё, чего упавший ход не видел, — в том числе сообщение, пришедшее во время хода или между аварией и стартом wait; без новых сообщений ходов нет («провайдер лежит» не крутится: каждый следующий ход — на новую порцию). Wait отметки читает (файла нет — берёт `seq` на старте); в `w_channels_init` (на старте и при смене задачи) для этих каналов `CH_SEEN := max(Acked, H)`, для новых (новая задача) — `CH_SEEN := Acked`. Будит только **новое** будящее — в том числе «новая задача» и «ты lead» (`task new` пишет `tasks/active` раньше сообщений), а выдаётся всё после `Acked`. Дедлайны в HOLD сами не будят (как на паузе); снятие паузы будит (`W_LIFT`) — один повтор по действию человека.
- **FORCE**: на первом тике выдать всё после `Acked`, даже тихое и пустое (результат `force`; пусто — `── нового нет`); на паузе — как пробуждение человеком.
- **ROLLBACK** — до всего, что может завершить wait (в том числе до проверки STOP), строго по порядку: (1) прочитать pid-файл (предшественник); (2) `w_claim`; (3) дождаться смерти предшественника (`pid_alive`; вытесненный `wait` выходит на ближайшем тике и дописывает начатую выдачу; ≤ 5 с); (4) `cursor_rollback`; (5) `w_channels_init`. Пачка, выданная хвостовым, вытесненным или осиротевшим `wait` в никуда, придёт снова, а бесконечного дубля нет. Сделанный откат wait отмечает в файле результата второй строкой `rolled`; **надзор снимает желание отката только по ней** (STOP, отсутствие результата его сохраняют), а FORCE — только когда wait выдал пачку. **Любой переход в `detached` откатывает:** надзор — если откат ещё должен; `spawn detach` и `join --as` при мёртвом надзоре — всегда (итог последнего хода неизвестен), после того как живого `wait` у агента нет. Агент в окне получит дубль, но не потерю. `cursor_rollback NAME` — во всех каналах агента `Pending := Acked`.
- Метрика — `wait … spawn=1` (главная метрика пробуждений, §11, не смешивается с ожиданием надзора). STOP, пауза, дедлайны, смена задачи — как у обычного `wait`. Тестовый крючок `BRG_TEST_DELIVER_DELAY` — задержка между выводом и `cursor_write`.

**Принятые остатки.** Пачка, которую фоновый `wait` выдал в файл **посреди** хода и модель не прочитала, теряется — как у ручного агента (README: `brg wait` никогда не запускать в фоне). Сводки дедлайнов, выданные в упавшем ходе, откат не вернёт (индекс удаляется после вывода, §8). На редком пути (откат после успешного хода, ход и хвостовой `wait` в одну секунду) возможен дубль одной пачки — потери нет.

#### Лента по ходу, чей отказ, контекст, токены (0.9.1)

**Разбор событий по ходу.** В 0.9.0 события разбирались только в конце хода — 19 минут хода доска показывала пустую ленту. Теперь, пока обёртка жива, надзор не чаще раза в 3 с и только если `events.log` вырос разбирает новые байты той же awk-программой (с маскировкой ключа) и копит итог в файле состояния хода `turn.N.parse` (одной записью, tmp + `mv`): **абсолютные** смещения `events.log` и `stderr.log`, до которых всё разобрано; суммы `step_finish` хода; последняя ошибка (`error`); `Context`; отказы основной сессии из потока (их `input`) и строки отказов из stderr; `Activity-Size` — размер `activity.log` после дописки строк этого разбора. Последний непустой текст — в `turn.N.text`. Итог хода (`ok`/`crash`, текст аварии — сообщение провайдера, а не «код выхода N», последний текст, отказы) `sv_turn_end` подводит по `turn.N.parse` и разбору остатка.
- **Только полные строки:** замерить размер `S` (`wc -c`); кусок — `tail -c +$((off + 1)) | head -c $((S - off))` (дописанное после замера не попадёт); последний байт `x=$(tail -c +$S … | head -c 1)` — пустой `x` ⇔ кусок кончается `\n`; если нет — awk пропускает последнюю запись; awk возвращает число потреблённых байт — сумму `length($0) + 1` разобранных записей (под `LC_ALL=C` это байты). В **конце хода** остаток разбирается целиком, вместе с последней строкой без `\n` (харнесс могли убить посреди строки; битая JSON-строка просто не распознаётся).
- **Порядок записи** (kill -9 надзора — без дублей и потерь): (1) дописать строки в `activity.log`; (2) атомарно записать `turn.N.parse` с новыми смещениями и `Activity-Size`. Перед каждым разбором (и при восстановлении): `activity.log` длиннее сохранённого `Activity-Size` — обрезать до него (`head -c N >tmp && mv`) и разбирать с сохранённых смещений. Затем `activity.tail`.
- Запись запуска при промежуточном разборе переписывается, только если её поля изменились (`Session`, `Context`, живые токены, последний текст, `Last-Event`). Цена — один `awk` раз в ≥ 3 с на идущий ход и только при росте лога; у тика доски новых процессов нет.
- **Токены без двойного счёта:** `stream.tok` хранит номер последнего учтённого хода, `sv_turn_end` прибавляет ход, только если его номер больше (повтор после kill -9 не задваивает); так же строка `end` ленты и сообщение lead'у об аварии — по одному на ход (маркеры `turn.N.ended`, `turn.N.notified`, захват — `noclobber`). **Живые токены** во время хода — `stream.tok` + суммы `turn.N.parse` (основная сессия) + подагенты с последнего экспорта; после хода, когда пришёл экспорт, — его итог плюс поток после **запуска** экспорта (`stream.tok` снимается при запуске: ход, прошедший, пока экспорт шёл, не теряется). Строки, которые надзор пишет в ленту сам во время хода (смена прав, конец хода), тоже обновляют `Activity-Size` — иначе следующий разбор или восстановление срезали бы их как остаток kill -9.
- `Last-Event` сбрасывается в начале хода.

**Чей отказ в правах — эвристика.** Отказ основной сессии виден в потоке: `tool_use` основной сессии со `status: "error"` и «request was rejected». Строка stderr `permission requested: <действие> (<ресурсы>); auto-rejecting` печатается для любой сессии, в том числе подагента, и **раньше** события `tool_use`. Поэтому классификация — **в конце хода**, по всем отказам хода: строка stderr, ресурс которой (без хвостового `/*`) — подстрока `input` отказанного `tool_use` основной сессии (или наоборот), — отказ **агента**, каждый такой `tool_use` закрывает одну строку; несопоставленные строки — по счёту: столько, сколько осталось несопоставленных отказов основной сессии, — агента, остальные — «(подагент)». В записи `Perm-Denied: <действие> (<ресурсы>)` или `… (подагент)`; на доске и в `spawn show|list` — «отказ в правах: …» / «отказ в правах (подагент): …». Во время хода строка ленты `permission` пишется сразу, без пометки «чей». Это эвристика: сопоставление — по вхождению пути, поэтому широкий ресурс (например, `/Users/x/*`) может приписать агенту отказ подагента под тем же путём; при нескольких отказах с похожими путями пометка может ошибиться.

**Контекст и токены.** `Context` — как его считает OpenCode: `input + output + reasoning + cache.read + cache.write` последнего `step_finish` основной сессии с ненулевыми токенами (шаг-ошибка с нулями его не обнуляет); подагенты не входят. `Tokens-Main-In|Out` и `Tokens-Sub-In|Out`: источник `export` — основная сессия и сумма дочерних раздельно; `stream` — только основная (подагенты неизвестны, не показываются). `Tokens-In|Out` — сумма (совместимость). **Стоимость** показывается, только если `Cost > 0` (у провайдера без цен — `0`, «$0.0000» не пишется). `Last-Text-Turn` — номер хода последнего текста: на доске «последний ответ (ход N[, идёт])».

#### Первый промпт, права, активность и токены

**Первый промпт** — короткий текст в `bin/brg` (имя с ключом, S, права и их смысл, подпись человека `--note`) + вывод join: «Окна у тебя нет: человек видит только `send --to human` и доску… `join` уже сделан… Когда свободен — заверши ход… Работает подагент — ход не завершай, жди в `wait --busy`… `brg wait` никогда не запускай в фоне».

**Права** — по тому, что реально делает OpenCode: `full` (по умолчанию) → `--auto`: «агент может всё, что можешь ты, в том числе вне каталога проекта и чтение `.env`»; `project` → без `--auto`: «правила OpenCode по умолчанию: в проекте можно всё — любые команды, правки, сеть, git push; вне проекта и `.env` — отказ». Настоящего ограничения внутри проекта этап A не даёт (§12). Вывод `spawn` и доска называют смысл дословно. **Отказ виден:** после хода надзор ищет в stderr хода `permission requested: … auto-rejecting` (ANSI снимается), запасной признак — `tool_use` со `"status":"error"` и «request was rejected»; найдено → строка `permission` в activity, `Last-Error`, на доске — «отказ в правах: <что>» и кнопка «дать полные права».

**Активность** — одна awk-программа по событиям хода (`events.log` с запомненного смещения): строки activity (`tool` — имя и `input.command|filePath|pattern|description`, до 200 байт; `text` — первые 200 байт; `error`), `sessionID`, сумма токенов и стоимости `step_finish`, последний текст, id дочерних сессий из вывода `task` (оба вида). JSON — регулярками по строке, без jq; неизвестные события пропускаются (сменится формат — теряется показ, не работа). **Маскировка ключа** — там же: `<харнесс>-<n>.` + шесть символов `[a-z2-9]`, за которыми не `[a-z0-9]`, → `<имя>.<3 символа>…` (шесть классов подряд, без интервалов `{6}` — их не понимает mawk); касается activity, последнего текста, `prompt.head`, вывода `spawn show|list`. Доска показывает «последний завершённый шаг» и «нет событий K мин», без обещания «сейчас делает»: идущий инструмент в потоке не виден.

**Токены.** После хода, в фоне: `"$bin" session export <spawn.opencode.args> <id>` своим ребёнком (`$!` — сам OpenCode, не конвейер), тайм-аут 20 с — SIGINT, затем TERM; из файла — только `head -c 2048 | tr -d '\n '` и регулярка `cost`/`tokens` (полный вывод большого экспорта через пайп может обрываться). **Только с `--standalone`** — иначе экспорт поднимет у человека фоновый сервис OpenCode. Основная сессия и все дочерние (`children`) считаются раздельно и складываются → `Tokens-*`, `Cost`, `Tokens-Source: export`, `Sub-Sessions`; дочернюю не экспортировать заново, если её итог не менялся 2 хода подряд и её id не встретился снова в выводе `task` этого хода. Экспорт не удался или выключен (`spawn.opencode.export: 0`) — сумма `step_finish` основной сессии, `Tokens-Source: stream`: доска честно подписывает «без подагентов».

**Настройки** (`config`): `spawn.opencode.bin` (`opencode`), `spawn.opencode.args` (`--standalone`), `spawn.opencode.export` (1), `spawn.wait_timeout` (3600), `spawn_stale` (30). Значения `spawn.*` — сырые (путь, несколько аргументов через пробел), остальные ключи — как раньше. Тестовые крючки: `BRG_SPAWN_STEP` (шаг сна надзора и обёртки, по умолчанию 1 с), `BRG_SPAWN_TEST_MAXLIFE` (надзор и обёртка выходят сами через N с или когда исчез каталог проекта), `BRG_SPAWN_EXPORT_TIMEOUT` (тайм-аут экспорта, по умолчанию 20 с), `BRG_SPAWN_TEST_DELAY_PARSE` / `BRG_SPAWN_TEST_DELAY_TOK` (пауза между дописками в `activity.log` и `turn.N.parse` / между `stream.tok` и итогом хода — тесты kill -9 в этих точках), `BRG_SPAWN_TEST_DELAY_END` (пауза между строкой «конец хода» и итогом в записи). Экспорт, как и харнесс хода, запускается под `set -m`: фоновая команда без управления заданиями получила бы SIGINT = SIG_IGN, и тайм-аут не мог бы прервать её штатно.

## 6. Задачи

**(решение человека)** В проекте одна активная задача; все подключённые агенты — её участники (неявное членство). Хранилище — по задачам, чтобы параллельные задачи с явным членством потом не требовали миграции.

- `task new --as X --title "…"` + постановка (дословно от человека → `brief.md`) → `T00N[-<slug>]`, Lead = X (автор), «новая задача» в `lobby`. Есть активная — отказ, либо `--cancel-current` (текущая отменяется); технически он доступен любому агенту, PROTOCOL рекомендует его, только если человек сам сказал бросить текущую. `task new` агентом снимает общий стоп и стоп автора, а также общую паузу и паузу автора: человек только что дал работу.
- **`task new --as human`** — человек даёт задачу сам, без чата агента (из терминала; из браузера — тем же вызовом): §6.2.
- Переключение: wait всех агентов замечает смену `tasks/active` на ближайшем тике и слушает новую задачу. Из прошлых задач — только `common/` (рекомендация PROTOCOL).
- `task close --as <lead> [--force]`: всегда нужен непустой `summary.md` (первая строка — итог в `common/history.md`); отказ, пока есть подзадачи `claimed` или идущие прогоны (`--force` отменяет и останавливает их). Ревью не требуется (§1 п. 7; иначе тупик при одном агенте).
- **Непрочитанное перед закрытием — «отказ = доставка» (решение человека).** Сразу после проверки «ты lead» и **до** проверки `summary.md` (lead должен увидеть сообщения до того, как напишет итог) close ищет то, что разбудило бы wait lead'а: в его каналах (`lobby`, задача, недренированные завершённые — как у wait) после `Pending` есть будящее (`FMT_WAKE` > 0: сообщения ему или всем, в т.ч. личные системные — результат `run`, ревью, сданные подзадачи). Тихие системные (join/leave/claim) и собственные не мешают; сводки дедлайнов (§8) не учитываются — придут wait'у. Нашлось — close печатает на stdout всё для lead'а после `Pending` (тихое тоже), как wait, с капом `wait_output_max`; после вывода сдвигает `Pending` на последнее показанное (`Acked` не трогает) и отказывает: «учти их (при необходимости поправь summary.md) и повтори task close». Подсказка — повтор `close`, не `read`: `read` курсор не двигает, отказ «прочитай» зациклил бы. Повтор проходит, если нового нет; при капе — несколько отказов подряд, каждый двигает `Pending`. `--force` проверку не обходит (показанное уже доставлено — повтор проходит). Следующий wait подтверждает показанное (`Acked := Pending`) и не выдаёт его повторно; гонка с фоновым wait lead'а (он держит курсоры в памяти) даёт не потерю, а максимум дубль — at-least-once.
- `task cancel --as <lead|human>`: `claimed` → `cancelled`, резервирования и прогоны снимаются, всем — «прекрати правки»; незавершённые правки остаются в рабочем дереве — их судьбу решает lead новой задачи или человек. Человек отменяет только явным `--as human`: агент, забывший `--as`, не отменит задачу «от имени человека».
- `common/history.md` — строка при закрытии и при отмене. Статусы: `active`, `done`, `cancelled`; фазы работы — только в рекомендациях. События «новая / закрыта / отменена» — в `lobby`, смена lead — в канал задачи (уход lead'а — в `lobby`); в канал завершённой задачи писать нельзя.
- **Дренаж:** перестав слушать закрытую или отменённую задачу, wait сначала выдаёт её недоставленные адресованные сообщения (`── T001 (закрыта)`) — финальное слово лида не теряется.
- Курсоры канала задачи: бывшие на момент создания читают с начала, подключившиеся посреди — с конца (история — `read --channel T00N --since 0`); `join --as` после `leave` — с конца, без переписки задач, завершённых за время отсутствия. Нумерация сообщений своя в каждом канале, `--re` — к выбранному.

### 6.1 Роли

**(решение человека, 0.7.0)** Роль одна — **lead**: фасилитатор (§1 п. 8) **и** связь с человеком (вопросы, отчёты, итог). Роль host (кому человек дал задачу и кто пишет ему) убрана: она нужна была на случай «задачу дали A, вести лучше B», но тогда вопросы человеку шли из одного окна, а решения принимались в другом; с доской и браузером привязка к чату почти не нужна. Показать человеку что-то в чате (картинку, файл) — окно lead'а.

- **Lead** собирает предложения, фиксирует договорённости, решает спор, если бригада не договорилась. Он же — единственный, кто сам обращается к человеку: пишет в своём чате **и** тем же текстом `send --to human` (видно на доске — когда задачу дали с доски, это основной канал); вопрос — ещё и `--ask` (§9.2); остальные отвечают, если человек написал им сам. Запись задачи: `Host:` больше не пишется, у старых задач читается и игнорируется.
- **Lead есть всегда.** Выбор — §6.2. Уход (`leave`) lead'а: сразу, под блокировкой `task`, тот же детерминированный выбор среди оставшихся на связи (§6.2, шаги 2–3, ушедший исключён), сообщение в `lobby` («X отключился (был lead задачи T00N — lead теперь Y …)») будит всех, а строка «lead задачи T00N: X → Y (X отключился)» в канале задачи (`Wake: no`, без двойного пробуждения) нужна, чтобы смена была видна в переписке задачи на доске; на связи никого — `Lead:` пуст («lead — нет (назначится первому, кто выйдет на связь)» в `who`, `task show|list`, `status`, `history.md` и на доске), и дальше его берёт первый, кто выйдет на связь (самоназначение, §6.2).
- `lead give <имя>` — только текущий lead, не `gone`-агенту; `lead take` — только если текущий lead `asleep`/`gone` или его нет. **Человек** назначает lead'а в любой момент: `lead give <имя> --as human` — отдельная ветка без `need_agent`, `touch_seen`, `NEXT:`; правила «только текущий lead» на него не распространяются; цель — не `gone`; задача без lead'а — тоже можно; уже lead — «уже lead», сообщения нет; системное сообщение `From: human` в канал задачи будит всех (и на паузе). Агенты могут договориться о другом лиде — самоорганизация без тупика «лида нет».
- `host give|take` — отказ «роли host больше нет: связь с человеком — у lead'а» с подсказкой `lead give|take` и `NEXT:`.
- `send --to human` — не только копия для протокола: доска показывает такое сообщение, и когда задачу дали с доски, это основной канал lead'а к человеку (чат харнесса — по-прежнему, PROTOCOL, раздел 2 п. 3).

### 6.2 Задача от человека; выбор lead'а

**(решение человека, 0.7.0)** Человек даёт задачу сам: `brg task new --as human --title "…" [--cancel-current] [--file F] < постановка` — из терминала (бессерверная версия) и из браузера (кнопка «Новая задача» на доске с сервером, §9.1: тот же вызов). Отдельная ветка, как `task cancel --as human`: без `need_agent`, `touch_seen` и `NEXT:`; `Created-By: human`. Она снимает общий стоп и общую паузу (личные не трогает; стоп снят — «остановленные агенты завершили ход — напиши им «продолжай»»). Агенту — `task new` как раньше (lead = автор).

- **Выбор lead'а** (детерминированный, под блокировкой `task`):
  1. lead последней задачи (наибольший номер, любой статус), если он **на связи**;
  2. иначе — агент на связи: сначала свободные (без действительной пометки «работает», §5.4), затем занятые; при равенстве — раньше подключившийся (`Joined-Epoch`, затем имя);
  3. на связи никого — задача без lead'а (`Lead:` пуст), самоназначение ниже.
  
  **«На связи»** = `waiting`, **или** `working` без «не на связи» (между двумя `wait`: последнее присутствие в цикле `wait` не дальше таймаута `wait` + 60 с — без этого прошлый lead, отвечавший в эту минуту, был бы пропущен случайно). `asleep`/`gone` — не на связи. Агенты с личной паузой или личным стопом пропускаются (и прошлый lead тоже: задачу, которую он не может начать, ему не отдают). С `--cancel-current` занятость оценивается **до** отмены текущей задачи (после неё все пометки недействительны). **При общем стопе на связи никого нет** (стоп завершил ход всех, хотя их `wait` кончились секунды назад и по `agent_state` они `working`): lead остаётся пустым — и у `task new --as human` (стоп снимается после выбора), и при `leave` lead'а; первый оживший агент становится lead'ом сам.
- **Самоназначение при пустом `Lead:`** — в `wait` (на старте, после проверки STOP, до записи pid-файла; и при смене активной задачи в цикле — иначе агент, чей `wait` начался за миг до `task new --as human`, не стал бы lead'ом до конца `wait`), в `join` (после записи курсоров: сообщение окажется за ними и придёт его первому `wait`) и `lead take`. Двойная проверка: чтение без блокировки, блокировка `task` — только при пустом `Lead`, повторная проверка под ней: из двух одновременных `wait` побеждает один. Не для агента с личной паузой или личным стопом (после `resume` его следующий `wait` назначит), при общем стопе — тоже нет. Уведомление — обычное сообщение `From: brg`, `To: all`, в канал задачи: «X — lead задачи T00N (назначен brg: первый на связи). X: постановка — brief.md; начни с PROTOCOL.md, раздел 4…»; сам X получает его своей доставкой (`From: X` не годился бы: свои не доставляются). При общей паузе оно, как всякое сообщение не от человека, никого не будит — новый lead узнаёт о роли после снятия паузы.
- **Сообщения `task new --as human`:** в `lobby` — `From: human`, «новая задача T00N от человека: «…» · lead: X» (или «lead: нет — назначится первому, кто выйдет на связь») — будит всех; lead'у лично, в канал задачи (там все читают с начала) — «ты lead задачи T00N (назначил brg): прочитай постановку…; человек дал задачу не в твоём чате — он смотрит доску: вопросы ему — `send --to human --ask`, отчёты — `send --to human`».

## 7. Подзадачи и код

### 7.1 Подзадачи

- `item add` → `I00N` (`todo`); `--paths` — предлагаемые пути (`Paths-Hint`).
- `item claim I00N [--paths …|none]` — атомарно. Пути надо назвать (`--paths` или подсказка из `add`) либо сказать `none` (исследование, ревью) — резервирование не забудется случайно. Пересечение с чужим резервированием → отказ со списком конфликтов. Повторный `claim` своей меняет пути.
- Пересечение со **своим** резервированием (другая своя подзадача в работе) — не отказ, а предупреждение после взятия: «эти пути уже твои по I001 …; если I001 брал не ты — под твоим именем работает другая сессия: сообщи lead'у и человеку». Так всплывает двойник под одним именем (§3). Без предупреждения: `--paths none` и пересечение подзадачи с самой собой при повторном `claim`; `.` пересекается со всеми своими — так и задумано.
- `item done` — только исполнитель (`--note`, `--result <путь>`); снимает резервирование.
- `item release` (в `todo`) — исполнитель, или lead, если исполнитель `asleep`/`gone`. `item reassign --to <имя>` — lead, только если исполнитель `asleep`/`gone` и новый не `gone`; резервирование переходит новому. Так же передаются правки сданной подзадачи (стадия «правки», §7.1.1).
- `item review --verdict ok|changes|skip` — для `claimed` или `done`; `ok`/`changes` — ревью: своё исполнитель писать не может; ревьюер той же модели, что исполнитель, при онлайн-агенте другой модели — предупреждение, не отказ. `skip` — решение «проверка не нужна» (§7.1.1). Записи ревью неизменяемы.
- Все изменения подзадач — под локом задачи (claim не проскочит в закрывающуюся задачу).

### 7.1.1 Проверка и стадии подзадачи

**(решение человека, 0.5.0)** Как работать с подзадачей — проверять ли, кем, в каком порядке, передумать по ходу — решает бригада: проверка другим участником — рекомендация (PROTOCOL, раздел 3), не правило. Обязательно одно (PROTOCOL, раздел 2): **стадия подзадачи в brg соответствует тому, что происходит**, — человек следит за работой по доске (§9.1). Поэтому brg даёт гибкие инструменты на каждый случай, а переводят подзадачи сами агенты. brg порядок не навязывает: `task close` не отказывает из-за непроверенных, только перечисляет их.

| Ситуация | Команда | Стадия (доска) |
|---|---|---|
| взял | `item claim` | в работе |
| бросил | `item release` | todo |
| сдал, проверка нужна (по умолчанию) | `item done` | на проверке |
| взялся проверять | `item review --start` | на проверке · проверяет X |
| проверил | `item review --verdict ok` / `changes` | готово / правки |
| правки | `item claim` (исполнитель) → `item done` | в работе → на проверке |
| проверка не нужна — решили заранее | `item add --no-review` | после сдачи — готово · без проверки |
| … при сдаче | `item done --no-review` | готово · без проверки |
| … передумали после сдачи (на проверке, правки) | `item review --verdict skip [--comment "почему"]` | готово · без проверки |
| передумали: проверка нужна | `item review --start` (тот, кто проверит) | на проверке |
| переделать сданное (в т.ч. принятое) | `item claim` (исполнитель) | в работе |
| подзадача не нужна | `item cancel [--comment "почему"]` | отменено |
| свой порядок (отдельная подзадача-ревью, парная работа, …) | итог отметить командами выше | — |

- `item add --no-review` → заголовок `Review: no`. Исключение `--paths none` (раньше исследование не считалось ждущим ревью) снято.
- `item done` пишет `Done-Reviews: N` — сколько записей ревью было на момент сдачи (так ревью «после сдачи» отличается от ревью «до неё», без сравнения времени). `item done --no-review` — сдача и сразу запись ревью `skip` от исполнителя (комментарий — «при сдаче»), одно системное сообщение.
- **Вердикты** `item review --verdict`: `ok`, `changes` — ревью; свою подзадачу так не проверить; при той же модели, что у исполнителя, — предупреждение (§7.1). `skip` — решение «проверка не нужна»: может записать любой участник, и исполнитель тоже (решение бригады, а не ревью); комментарий необязателен, stdin без `--comment`/`--file` не ждёт. Все вердикты — неизменяемые записи ревью (история на доске). Любой вердикт по `done` очищает `Reviewing:` целиком — круг проверки закончен (кто ещё проверяет — снова `--start`); по `claimed` — убирает только автора.
- `item review I00N --start` — «взялся проверять»: имя — в `Reviewing:` (через запятую, без повторов), тихое системное сообщение всем (как `claim`). Подзадача `claimed` или `done`, не исполнитель; при стопе — отказ (начинает работу, §9); вместе с `--verdict` и текстом нельзя; stdin не читается; повторный `--start` того же — без дубля и без сообщения; предупреждение о той же модели — уже здесь.
- **Вернуть в работу** — `item claim I00N` исполнителем из `done` в любой стадии: правки после `changes`, переделка принятого или сданного без проверки, отзыв подзадачи с проверки. Пути по умолчанию — прежние (`Paths`), пересечения проверяются как у обычного `claim`; `Claimed`/`Claimed-Epoch` — заново; `Done`, `Done-Reviews`, `Note`, `Result`, `Reviewing` очищаются (прежняя сдача остаётся в переписке); системное сообщение будит lead'а. Чужую сданную подзадачу так не взять (отказ называет стадию и последний вердикт); исполнитель `asleep`/`gone` — lead передаёт правки `item reassign` (подзадача становится `claimed` у нового исполнителя с прежними путями). `item done` на подзадаче в стадии «правки» отказывает с подсказкой `item claim`.
- `item reassign` убирает нового исполнителя из `Reviewing:`; `item release` очищает `Reviewing:`.
- `item cancel I00N [--comment "почему"]` → `cancelled` (+ `Cancelled`, `Cancelled-By`): `todo` — любой участник; `claimed`/`done` — исполнитель или lead. Снимает резервирование и `Reviewing:`; системное сообщение будит lead'а и исполнителя (кроме автора). При стопе разрешена (не начинает работу). Из `cancelled` не возвращается — нужна снова: новая подзадача.
- **Стадия** — одно правило для `wait`, `item list|show`, `status`, `task close` и доски (bash `item_stage_v` и JS страницы — одинаково, включая нештатные значения). `todo`, `claimed` (в работе), `cancelled` — как есть. Для `done`: n — число записей ревью (файлы с числовым именем), последнее — с наибольшим номером, d — `Done-Reviews` (нет — 0); вердикт последнего: `skip` — всегда «готово · без проверки» (решение, а не ревью); `changes` и любой другой (`ok`, нештатный) — как ниже:
  - n > d (вердикт после сдачи): `changes` → **правки** (на доске — в колонке «в работе», красной пометкой), иначе → **готово**;
  - 0 < n ≤ d (сдана после последнего вердикта): → **на проверке** — `changes`: пересдана после правок; `ok`: сдана после ревью — работа могла измениться (ревью в работе, переделка принятой), нужна новая проверка;
  - n = 0: `Review: no` (точно) → **готово · без проверки**, иначе → **на проверке**;
  - «готово» (в т.ч. без проверки) при непустом `Reviewing:` → **на проверке** (кто-то проверяет — значит, проверка идёт: так работает «передумали, проверка нужна»).
  - `claimed`, у которой последний вердикт — `changes`, — «в работе · правки по ревью».
- **Где видно.** Сводка `wait` (§5): `… · в работе I001 codex-1 · на проверке I003 (claude-2), I005 · правки I004 codex-1 · готово I002 · …` («(имена)» — из `Reviewing:`; было «ревью ждут»). `item list` — стадия в строке и в итоговом счётчике; `item show` — стадия, проверяющие, «без проверки» и кто решил. Каждое сообщение и вывод команды подзадачи называет стадию, в которую она перешла (например, ok после чужого `changes` без пересдачи: «правки не нужны — I00N готова»). `task close` перечисляет непринятые — «не приняты: I003 (на проверке), I005 (правки)» — предупреждением, не отказом.

### 7.2 Резервирования путей

- Пути от корня проекта, через запятую; нормализуются (`\` → `/`, без `./`, `//`, хвостового `/`; `.` — весь проект). Запрещены `..`, абсолютные пути, `~`, маски, управляющие символы. Без глобов — детерминированно и просто в bash.
- Пересечение — префикс по границе компонента (`src` и `src/a` — да, `src/a` и `src/ab` — нет), **без учёта регистра** (ФС macOS и Windows; на Linux возможны ложные конфликты — сознательно консервативно).
- Резервирование действует, пока подзадача `claimed` этим агентом (остаток после падения игнорируется); снимается `done`, `release`, закрытием и отменой задачи.
- Защищает только тех, кто им пользуется: brg правки файлов не отслеживает.
- Резервирования охраняют только запись. Чтение в общем дереве brg не ограничивает и не проверяет (§1: одна ФС, без защиты от агента): условие постановки вида «не читать чужое до раскрытия» — лишь договорённость. PROTOCOL рекомендует lead'у сразу назвать такое условие человеку непроверяемым и предложить проверяемую рамку (работа вне общего дерева до раскрытия, раскрытие по договорённости).

### 7.3 `brg run`

Тесты, сборка, линтеры — под глобальной блокировкой: не гонять тесты на полуотредактированных файлах соседа. **По умолчанию в фоне**: агент сразу получает `R00N` и место в очереди, результат (статус, код, хвост лога, путь к логу) приходит инициатору системным сообщением — долгие операции не упираются в лимит команды харнесса и встраиваются в механику «всё — сообщения».

- Только при активной задаче; создаётся под её локом (нет гонки с `close`). `--item I00N`, `--timeout` (по умолчанию `run_timeout`, 30 мин). Одна строка-аргумент — через `bash -c`, несколько — как есть; cwd — корень проекта.
- Очередь `run/execq/` в порядке запросов; голова запускается, захватив `run/locks/exec.lock`. Он держится всю команду и **не ломается по возрасту** — только по смерти владельца (подтверждённой heartbeat, см. ниже) или устаревшему heartbeat.
- Раннер — `nohup` под `set -m`, все fd перенаправлены (харнесс его не ждёт); команда — в своей группе процессов, после неё остатки группы добиваются; таймаут или отмена — TERM группе, через 5 с KILL. Статусы: `queued`, `running`, `done`, `failed`, `timeout`, `killed`, `cancelled`. Результат — сообщение `From: brg` инициатору в канал задачи (задача уже завершена — в `lobby`), ровно один раз.
- `--sync` — для коротких команд: ждёт на месте не дольше `wait_timeout` агента (`--timeout` больше — отказ), код выхода — код команды; не уложилась (в т.ч. из-за очереди) — результат придёт сообщением. Раннер, закончив, даёт ещё ждущему синхронному вызывающему до 3 с напечатать результат самому; недоступный pid вызывающего (EPERM) считается живым — тогда отдельное сообщение уходит с задержкой до 3 с (допустимо).
- `run cancel R00N` — инициатор или lead, через файл-флаг (без сигналов чужим pid).
- **Heartbeat раннера** — раз в секунду. Живой pid (в т.ч. недоступный, EPERM) с молчащим heartbeat объявляет мёртвым только ждущий раннер, непрерывно наблюдавший молчание дольше `runner_stale` (60 с, > `lock_stale`); провал времени у наблюдателя (сон ноутбука, SIGSTOP) сбрасывает отсчёт. «Оживший» раннер, у которого забрали лок или закрыли прогон, убивает свою команду и не перезаписывает вердикт (край: до ~1 с его команда может идти параллельно с командой победителя).
- **Мёртвый pid раннера — ещё не смерть:** в pid-namespace песочницы живой процесс может отвечать ESRCH. Раннер мёртв, только если (1) pid мёртв (`pid_alive`, §4.2), (2) его heartbeat (exec-лок или запись очереди) старше `runner_dead_grace` (5 с; 0 — верить одному pid) и (3) судящий ждущий раннер наблюдал без провала не меньше `runner_dead_grace` (провал дольше grace/2, но не меньше 2 с, сбрасывает отсчёт: после сна heartbeat у всех старый). Этот отсчёт отдельный от отсчёта `runner_stale` (тот сбрасывает провал дольше runner_stale/2, от 2 до 10 с): короткие провалы на загруженной машине не откладывают вердикт `runner_stale`. Пока условия не выполнены, раннер с мёртвым pid судится как живой — по `runner_stale`, поэтому и частые провалы не повесят очередь. Раннер, убитый `kill -9`, снимается примерно через `runner_dead_grace`.
- Просмотр (`run show/list`, `status`, `task close/cancel`, `run cancel`, `doctor` — разовые проверки, вердикт у всех один): pid раннера мёртв и heartbeat старше `runner_dead_grace` → `killed` (умерший только что — со следующего просмотра после grace; `run cancel` перепроверяет, пока ждёт); живой, но молчащий → «раннер не отвечает N с» (разовый вызов не отличит сон от зависания), `run cancel` закрывает и такой. Раннер убит `kill -9` → лок снимается; команда-сирота не убивается (сообщение предупреждает, pgid записан). **Остаток:** разовая проверка не наблюдает непрерывно (условия (3) нет) — в среде с ESRCH сразу после сна ноутбука, когда heartbeat у всех старый, она может отметить живой прогон `killed` (сам раннер, проснувшись, увидит вердикт и остановит команду).
- `task cancel`, `--cancel-current`, `close --force` останавливают прогоны задачи; их перечисляет сообщение о задаче, отдельных сообщений нет.

## 8. Дедлайны

`send … --reply-by 5m` (от 1 с до 24 ч). По сроку wait отправителя возвращается со сводкой `── дедлайн по #N (T001) истёк: ответили: …; не ответили: …` — детерминированная основа правила «молчание = согласие».

- `Expect` — адресаты на момент отправки (для `all` — все не-`gone`, кроме отправителя); их нет — дедлайн не ставится.
- Ответ — не системное сообщение адресата в том же канале после исходного: с `Re: <id>` **или** любое сообщение отправителю (лично или `all`) — модели забывают ставить `Re:`.
- Ответили все до срока — сводка приходит сразу, с пачкой последнего ответа (экономит пробуждение).
- Сводка выдаётся один раз: перед печатью атомарно создаётся маркер `<канал>-<id>.done`, индекс удаляется после вывода. Индекс остался через минуту после срока (репортёр умер) — сводка выдаётся повторно: дубль лучше потери.

## 9. Команды

Агентам: `join`, `leave`, `send`, `wait` (`--busy`: пометка «работает», §5.4), `busy` (пометка без ожидания), `read`, `status` (одноэкранная реориентация после сжатия: кто я, роль, задача, мои подзадачи и прогоны, непрочитанное, дедлайны, жив ли мой wait, NEXT), `who`, `task …`, `lead give|take`, `item …`, `run …`. Человеку: `init`, `board` (доска в браузере; с Python — с управлением, §9.1), `say` (от `human`; `--re N` — ответ на вопрос агента, §9.2), `tail [-f]`, `who`, `stop`, `pause`, `resume`, `task new --as human` и `task cancel --as human` (§6.2), `lead give <имя> --as human` (§6.1), `item list`, `run list`, `doctor`, `spawn` (§5.5, ниже). Агент передаёт в `--as` полное имя из своего `join` (с ключом, §3); команды чтения принимают и базовое, `stop`/`pause`/`resume` и имена-цели — базовое. `who` и `status` называют состояние словами «ждёт» (свободен) и «работает[: подпись]» (§5.2). Синтаксис — `brg help` и `brg <команда> --help`.

**Стоп.** `stop` ставит флаг `run/stopped` (`stop <имя>` — `run/stopped.<имя>`, в т.ч. для зачистки призраков). Пока флаг стоит, любой wait возвращает STOP **сразу** (агент, бывший в работе, не заблокируется снова); живые wait видят флаг на ближайшем тике — без сигналов, как и takeover. Флаг снимают `resume`, `say` (общий и названных адресатов) и `task new` (общий и автора; человеческий `task new --as human` — общий). Остановленные агенты завершили ход — после снятия стопа человек пишет им в чат «продолжай».

**(решение человека)** Стоп видит и агент, давно не звавший wait: любая команда с `--as` (общий стоп или стоп этого агента, по базовому имени) первой строкой stdout печатает `── STOP: …`. Кроме `wait` и `status` — они печатают STOP сами (без дубля), и `task new` — он стоп снимает и говорит об этом. Команды, **начинающие работу**, — `item add|claim|reassign`, `item review --start` и запуск `run` — при стопе отказывают, `NEXT:` — «заверши ход» (не wait: иначе агент вернётся в цикл, а wait тут же вернёт STOP). Сдать сделанное и сообщить — можно: `send`, `item done|release|cancel`, `item review --verdict`, `task close|cancel`, `run cancel`, `lead give|take`, `busy` (пометка не начинает работу, §5.4), `leave`, команды чтения.

**Пауза (решение человека, 0.7.0).** Стоп завершает ход агента — «продолжай» ему приходится писать в его окне, а из браузера этого не сделать. Пауза мягче: `pause` ставит флаг `run/paused` (`pause <имя>` — `run/paused.<имя>`), агент **ход не завершает**, остаётся в `wait` и просыпается только от сообщений человека и снятия паузы (§5 п. 14); `resume` снимает и стопы, и паузы (без имени — все; с именем — только этого агента; общая пауза стоит, пока не вызван `resume` без имени, и `resume <имя>` при ней говорит об этом); из браузера — кнопкой «Продолжить» (доска с сервером, §9.1). `say` паузу **не** снимает (стоп снимает): человек может поговорить с бригадой на паузе. `task new` (агентом и человеком) снимает общую паузу, агентский — ещё и паузу автора.
- **Начинать работу нельзя.** Одна функция `work_refuse` на тех же местах, что стоп: `item add|claim|reassign`, `item review --start` при паузе отказывают; `NEXT:` — `wait` (агент остаётся в цикле), текст называет, кто снимает паузу («`brg resume` или с доски; `say` её не снимает»). **`run` на паузе разрешён**: подагент проверяет начатую работу (`run --sync`), а подагент, работающий у участника, доводит своё — пауза его не останавливает, пометка «работает» (§5.4) остаётся как есть. Сдать сделанное можно (`send`, `item done|release|cancel`, `item review --verdict`, `task close`).
- **Баннер.** Первой строкой любой команды с `--as`: `── ПАУЗА: человек поставил на паузу <бригаду|тебя (имя)>. Новую работу не начинай; сдай сделанное и жди (wait).` — раз на процесс, STOP приоритетнее; `wait` и `status` сообщают о паузе сами (`status` — строкой в своём выводе, `wait` — строками пачки, §5 п. 14), `join` — предупреждением.
- **Показ.** `who` (строка «── ПАУЗА» при общей, «(пауза)» у состояния агента), `status`, `doctor` (флаги паузы рядом со стопами), доска (общая — плашка, личная — чип «пауза»), сводка `wait` («свободны» — без стоящих на паузе). Остановленный агент на доске — «остановлен — напиши «продолжай» в его окне (имя · префикс ключа…)» (§9.1); запущенный brg — «остановлен — снимется кнопкой «Продолжить»» (его будит надзор, §5.5).

**Запуск агентов (0.9.0, §5.5) — только человеку.** Отказ «запускает агентов только человек; попроси его: `send --to human --ask`» — при `--as <агент>`, а также при `BRG_SPAWN` или `OPENCODE_SESSION_ID` в окружении (по `CLAUDECODE`/`OPENCODE=1` — нет: человек может работать в терминале харнесса). В инструкциях агентам `spawn` не описывается, кроме «попроси человека».
- `brg spawn <harness> --model M [--rights full|project] [--count N] [--note "…"]` — проверки: `.brigada` есть; macOS/Linux; харнесс поддерживается (этап A — `opencode`); бинарь найден (`spawn.<h>.bin`); платформа как у подключённых (§3); `--model` — `[A-Za-z0-9][A-Za-z0-9._:/@#+-]{0,119}` (не с `-`); `--count` 1–9; `--note` — одна строка ≤ 200 байт. Стоит стоп — предупреждение «первый ход — после снятия стопа». Строка на агента: `S003 → opencode-3 (provider/model) запущен · права: full — <смысл>`. Возвращается сразу (надзор отвязан, все fd перенаправлены).
- `brg spawn list` — S, агент, харнесс/модель, права, состояние, ход, токены, стоимость, источник токенов, последняя ошибка (читают и агенты). `brg spawn show <S|имя>` — запись, 20 строк активности, пути логов; ключ замаскирован.
- `brg spawn wake|rm|detach <S|имя>`, `brg spawn rights <S|имя> full|project`; внутренние — `__spawn S00N [--continue]`, `__turn S00N N`.
- `who`/`status` — «(запущен brg, S003)» и состояние записи; `doctor` — раздел запусков: живые и мёртвые надзоры (по локу и `hb`), висящие обёртки, бинарь харнесса.

### 9.1 Доска

**(решение человека)** `brg board [--interval S] [--port P] [--bind ADDR] [--static] [--once]` — страница для человека: текущая задача и статус, бригада (состояние, lead, взятые подзадачи), канбан подзадач с ревью, прогоны, переписка (задача и `lobby`), постановка, план, итог, прошлые задачи. Без Python открывается как `file://` — без сервера и зависимостей, только просмотр. **(решение человека, 0.8.0)** С Python (≥ 3.8) `brg board` сам поднимает сервер человека (ниже), и на той же странице появляется управление: писать бригаде, отвечать на вопросы, давать задачу, назначать lead'а, ставить паузу и стоп.

- **Устройство.** `init` ставит `template/board.html` как `.brigada/board.html`. `board` раз в `S` с (по умолчанию 2, минимум 1) пишет снимок в `run/board/` и работает на переднем плане до Ctrl+C; TERM/INT/HUP — удалить свой `.tmp` и выйти с кодом 0 (как `tail -f`). `--once` — один снимок (без сервера). Первая строка вывода — адрес: `http://127.0.0.1:ПОРТ/?t=ТОКЕН` при сервере (с `--bind IP` — `http://IP:ПОРТ/?t=ТОКЕН`, ниже), иначе `file://…` (пробел, `#`, `?`, `%` кодируются); через `brg.cmd` путь берётся из `BRG_VIA_CMD` (`C:\…` → `file:///C:/…`), Git Bash без него — `/c/…` → `file:///C:/…`; другие пути MSYS и WSL — подсказка «открой `.brigada/board.html` в браузере».
- **Снимок.** `run/board/data.js` = `window.BRG_BOARD = {…};` — `meta` (время, интервал, версия, проект, стоп, общая пауза), агенты (с флагами `stopped`, `paused`), все задачи (запись `task` + первая строка итога), lobby и **текущая задача** целиком (постановка, план, итог, подзадачи с ревью, прогоны, переписка). Текущая — активная, а если её нет — последняя (по номеру) закрытая или отменённая: сразу после `close` человек видит итог. Остальные завершённые задачи — кэш `run/board/T00N.js` (`(window.BRG_TASKS = window.BRG_TASKS || {})["T00N"] = {…};`), пишется один раз, когда задача «улеглась» (все прогоны в финальном статусе или закрыта больше 60 с назад; до того — переписывается каждый тик). `run/board/VERSION` не совпал с версией brg — кэш удаляется. Запись — tmp + `mv`; ошибка `mv` (Windows: файл держит браузер) не фатальна и печатается не чаще раза в минуту.
- **Снимок только читает.** Снимок и страница только читают; действия с доски при сервере — вызовы brg от имени человека, сервер сам состояние не пишет (ниже). `board` пишет только в `run/board/`: без блокировок, курсоров, Last-Seen, `metrics.log`, никого не будит; своя проверка «есть `.brigada`» без `mkdir` (не `need_root`), ошибки без `metric`. Прогоны не «досуживаются»: мёртвый или молчащий раннер показывается по разовой проверке (`run_health`) как «раннер мёртв» / «не отвечает N с», в `killed` его переводит brg при следующем просмотре (§7.3). Страница данные только показывает.
- **Экранирование.** `data.js` браузер выполняет: ошибка экранирования = исполнение текста сообщения как кода. Все данные (заголовки и тела записей, тексты, вычисленные строки) превращает в JSON одна awk-программа; на вход — список директив на stdin (данные — только через файлы и stdin, не `awk -v`: он разворачивает `\n` и `\\`). `\` и `"` — `gsub(/[\\"]/, "\\\\&")` (переносимо между BWK awk, gawk и mawk: `"\\\\"` в gawk дал бы одиночную черту); `\t`, `\r`, прочие `\001`–`\037`, `\177`, U+2028/2029 → `\t`, `\r`, `\u00XX`, `\u2028`/`\u2029` — циклом по совпадениям, только если они есть в строке (быстрый путь). NUL: BWK awk теряет его вместе с остатком строки, gawk может пропустить сырым (JS это переживает) — brg таких тел не пишет. Перевод строки в элементе списка директив (имя файла из glob, путь `.brigada`) заменяется на `?` — иначе он начал бы поддельную директиву; такой путь читается как отсутствующий. Страница вставляет данные только через `textContent`/`createElement`, тексты — `white-space: pre-wrap` (без markdown), ссылки — только внутренние.
- **Цена тика — O(1) процессов:** `date`, один awk на все файлы (переписка — последние 500 сообщений канала, отобранные glob'ом в bash), `tail` лога — только у идущего прогона (у завершённых — один раз за процесс). Объём `data.js` — до ~2 МБ: сверх — отбрасываются старые сообщения, `meta` говорит «показаны последние N из M»; постановка, план, итог и тела записей — до 64 КБ.
- **Страница** (`board.html`, один файл, без CDN): данные — классическим `<script charset="utf-8">` с `?<время>` раз в 2 с (старый тег удаляется); нет файла — «снимка ещё нет — запусти `brg board`»; снимок старше max(10 с, 3 × интервал) — «доска не обновляется». Раздел перерисовывается, только если изменился `JSON.stringify` его данных (прокрутка и раскрытое сохраняются); выбранная задача — в `location.hash`, прошлая подгружается из `T00N.js`. Дедлайны («ждём / ответили»), канбан, роли и длительности считает страница.
- **Вид (0.5.0, решение человека).** Задача — заголовок, статус, lead (пустой — «нет — назначится первому, кто выйдет на связь») и прогресс (готово / всего). Канбан — `todo` · «в работе» · «на проверке» · «готово» (+ «отменено», только если такие есть); стадия — по правилу §7.1.1; у закрытой или отменённой задачи колонка «на проверке» называется «не проверено». Карточка — номер и заголовок, кто делает (на проверке — кто проверяет из `Reviewing:` или «ждёт проверяющего»), время в стадии, пометки «правки по ревью от X», «без проверки» (и кто решил — `Review: no` или вердикт `skip`), «исполнитель выпал»; пути, описание, итог, ревью и прогоны подзадачи — свёрнуты. У каждого агента свой цвет, стабильный (по имени) и один на всей странице — бригада, карточки, переписка: кто что делает, видно с первого взгляда. Переписка — отдельные блоки с полосой цвета автора: шапка (автор → кому, «лично», ответ на #N с первой строкой цитируемого, время, дедлайн), длинное тело свёрнуто до ~12 строк; системные — компактной строкой; сообщения человека выделены. Бригада — компактная полоса: чип агента показывает **«ждёт»** (серый: свободен), **«остановлен — напиши «продолжай» в его окне (имя · префикс ключа…)»** (стоп человека завершил ход агента — флаг снимается и кнопкой, но «продолжай» агенту можно написать только в его окне), чип **«пауза»** (личная пауза, §9) либо **«работает · подпись · N мин»** (цвет агента; подпись и время — из пометки `mark` снимка, §5.4; без пометки — «работает», когда `working`); подпись, повторяющая подзадачу из списка его работы («делает I015», «проверяет I014»), опускается — остаётся «работает · 15 с · делает I015», подпись нужна только для работы вне списка («финальная проверка»), а у `working` без wait — ещё «не на связи N мин»; ушедшие (`gone`) без роли, подзадачи в работе и открытого вопроса не показываются — вместо них чип «ушли N» (имена — во всплывающей подсказке); пустые разделы не занимают места.
- **Пауза и стоп на странице (0.7.0).** Общая пауза — плашка «ПАУЗА» (`brg resume`), личная — чип «пауза» и строка «На паузе агенты: …»; общий стоп — плашка STOP с напоминанием, что остановленные агенты завершили ход; плашка «бригада простаивает» на паузе не показывается (простой — решение человека). Кнопки «Пауза» / «Продолжить» — в режиме с сервером (ниже).
- **Сервер человека (0.8.0, решение человека).** Необязательный `bin/brg-serve.py` (Python ≥ 3.8, stdlib; `init` ставит его в `.brigada/bin/`). Правило Python — §1 п. 4. Нет Python, нет файла, `--static`, `--once` или сервер не поднялся — доска как раньше (`file://`, только просмотр), с одной строкой причины («Python 3.8+ не найден — доска только для просмотра; отвечать — `brg say`»).
  - **Python ищет одна функция** (`py_find_v`; её же зовёт `doctor`): `BRG_PYTHON` (если задан — только он; голое имя — через PATH) → `type -P python3` (встроенная команда; Homebrew, python.org, pyenv, conda подходят) → на Windows (MSYS/Cygwin) `py -3`, `python3`, `python`. macOS: `/usr/bin/python3` — заглушка установщика Command Line Tools, поэтому берётся, только если есть хотя бы одно из `$DEVELOPER_DIR/usr/bin/python3`, `/var/db/xcode_select_link/usr/bin/python3`, `/Library/Developer/CommandLineTools/usr/bin/python3`, `/Applications/Xcode.app/Contents/Developer/usr/bin/python3`; иначе «Python нет» — ни `xcode-select`, ни заглушка не вызываются (диалог установки не всплывёт). Windows: кандидаты из `…\Microsoft\WindowsApps\` (заглушки Store) пропускаются. Проверка: `"$py" -I -c` — версия ≥ 3.8 и `sys.executable`; хранится **исполняемый файл** (не команда `py -3`) — им и запускается сервер, поэтому `$!` — сам Python.
  - **Запуск и родство.** bash — родитель: цикл снимка остаётся в `brg board`, сервер — его ребёнок (`"$py" -I -X utf8 …/bin/brg-serve.py --root <корень> --port P [--bind ADDR] --interval S`, в фоне, stdout/stderr — тот же терминал; на Windows `--root` в форме `C:/…`). Сигналы — только своему ребёнку (`$!`, не pid из файла): TERM/INT/HUP у `brg board` → TERM серверу, ожидание до 4 с, затем KILL. **Сердцебиение:** bash-цикл каждый тик пишет `run/board/alive.<свой pid>` (tmp + `mv`; свой файл у каждого `brg board` проекта — сервер смотрит только на файл своего родителя); сервер выходит, если файл старше max(15 с, 5 × interval) (на Windows `os.getppid()` не меняется со смертью родителя, а `kill` мог убить лаунчер `py.exe` — поэтому основной признак не родство, а файл); на Unix дополнительно — родитель сменился. Убитый `kill -9` `brg board` не оставляет сервер. **Тестовые крючки** (окружение сервера; в обычной работе не нужны): `BRG_SERVE_ALIVE_MAX` (предел возраста `alive`, с), `BRG_SERVE_NO_PPID` (не смотреть на смену родителя), `BRG_SERVE_TEST_LISTEN=127.0.0.1` (0.9.2: сервер реально слушает loopback, а правила Host/Origin и строки brg следуют `--bind` — чтобы тесты не слушали сетевой адрес; действует **только** значение `127.0.0.1`, любое другое игнорируется: крючок может лишь сузить, но не расширить то, что слушается). **Рукопожатие:** bash удаляет `run/board/ready` и запускает сервер; тот после `bind` создаёт токен (если нет) и атомарно пишет `port`, затем `ready` (порт, pid[, занятый прежний порт]); bash опрашивает ≤ 5 с, проверяя `kill -0 $!` (свой ребёнок). Адрес печатается только после `ready`. Сервер умер сразу или не ответил за 5 с — причина и `file://` (код выхода сервера: 3 — порт занят или недоступен, 5 — адрес `--bind` не на этой машине, 2 — неверные параметры, 4 — не записан `ready`); умер позже — раз в тик bash видит это (`kill -0 $!`): «сервер доски остановился — доска только для просмотра» и адрес `file://`, цикл снимка идёт дальше.
  - **Адрес и порт.** `http://127.0.0.1:ПОРТ/?t=ТОКЕН` — первой строкой (с `--bind`, ниже, — адрес, по которому доска точно открывается). Порт: `--port P` (0 — любой свободный), иначе сохранённый (`run/board/port`), иначе любой свободный. Сохранённый занят — новый порт и строка «порт P занят — новый адрес»; явный `--port` занят или недоступен (`EACCES`: порты < 1024, зарезервированные диапазоны Windows) — «сервер доски не запустился: порт занят или недоступен» и `file://`. Токен — `run/board/token` (`secrets.token_hex(16)`, создаётся один раз, права 600; постоянный — чтобы закладка `/` и адрес работали между запусками; утёк или хочется сменить — удалить файл и перезапустить `brg board`, старые cookie перестанут подходить); второй `brg board` в том же проекте получит другой порт (оба цикла пишут один `data.js` — как и раньше без сервера; файлы `token`, `port`, `ready` общие, `alive.*` — свои).

  - **`--bind ADDR` (0.9.2, решение человека: доска на виртуалке, браузер на хосте).** По умолчанию — только `127.0.0.1`, как раньше. `--bind ADDR` — слушать этот IPv4-адрес машины (десятичная запись `a.b.c.d`, октеты 0–255 без ведущих нулей: `010` неоднозначен) или `0.0.0.0` (все адреса); имена (`myvm.local`, `localhost`) и IPv6 — отказ (код 1, «Использование»; проверка в bash до запуска сервера: сначала форма — ровно три точки, только цифры и точки, без пустых октетов, потому что `1.2.3.4.` и `1..2.3` читаются как четыре поля, затем октеты; в Python — повторно, своим регулярным выражением, не `ipaddress`: в 3.8.0–3.8.11 и 3.9.0–3.9.4 он принимает ведущие нули; код 2). **Только на этот запуск** (в `config` и в `run/board/` адрес не пишется; следующий `brg board` без флага снова слушает один `127.0.0.1` — безопасно по умолчанию; порт сохраняется как раньше). Со `--static` и `--once` неверное значение — по-прежнему ошибка, верное молча не действует (как `--port`). Явный `--bind 127.0.0.1` — то же, что без флага (серверу `--bind` не передаётся, строк ниже нет); loopback — весь `127.0.0.0/8`. **Вывод**, порядок строк: адрес → [строка «доска слушает все адреса машины…»] → «ВНИМАНИЕ» (две строки) → [«порт P занят — новый адрес»] → «доска обновляется…». Первая строка: `--bind IP` — `http://IP:ПОРТ/?t=ТОКЕН`; `--bind 0.0.0.0` — `http://127.0.0.1:ПОРТ/?t=ТОКЕН` (по нему точно откроется на этой машине), следующая строка говорит заменить `127.0.0.1` на IP этой машины (с подсказкой команды: `ip -4 addr` / `ipconfig getifaddr en0`; сам IP brg не угадывает — у виртуалок с NAT и host-only их несколько, `getfqdn` может зависнуть, а токен второй раз не печатается). Для любого адреса вне `127.0.0.0/8` — «ВНИМАНИЕ»: HTTP без шифрования, токен и переписка идут открытым текстом, с доски можно управлять бригадой и **запускать агентов с полными правами** (это выполнение команд на машине), доверенная сеть или SSH-туннель (`ssh -N -L ПОРТ:127.0.0.1:ПОРТ <машина>` — тот же номер порта с обеих сторон: от него зависит имя cookie и проверка `Host`), после работы по сети сменить токен (`rm .brigada/run/board/token` и перезапуск), брандмауэр macOS/Windows может спросить разрешение для Python. **Адрес не на этой машине** (`EADDRNOTAVAIL`; на Windows `WSAEADDRNOTAVAIL` 10049) — сервер выходит с кодом **5** и причиной в stderr, brg: «сервер доски не запустился: адрес ADDR не на этой машине — доска только для просмотра (адреса машины: ifconfig / ip addr; все адреса: --bind 0.0.0.0)» и `file://`; проверка errno идёт **до** повтора на другом порту (`--retry-any` не поможет). Причину «порт» не путать с адресом: `EACCES` при `bind` — это порт, он остаётся кодом 3. Слушающий сокет `0.0.0.0` — без `SO_REUSEADDR` на всех платформах: на macOS с ним `bind(0.0.0.0:P)` проходит поверх чужого `127.0.0.1:P`, «порт занят» не обнаружился бы, а адрес на первой строке открыл бы чужое приложение (цена: перезапуск на сохранённом порту в пределах `TIME_WAIT` даст «порт P занят — новый адрес»). Сервер не вызывает `getfqdn` для адреса (`server_bind` переопределён): обратный DNS-запрос съел бы 5 с рукопожатия.
  - **Защита** (на странице вся переписка, кнопки управляют агентами): по умолчанию только `127.0.0.1` (на Windows `allow_reuse_address = False`: иначе второй процесс занимает тот же порт и «порт занят» не обнаружить; `--bind` — выше); `Host` на **всех** запросах (DNS rebinding): порт — свой всегда (иначе 403 «порт в адресе должен быть P — SSH-туннель с тем же номером порта с обеих сторон»), имя — `127.0.0.1` или `localhost` (всегда: и через туннель на сервер, слушающий сеть; у страницы атакующего в `Host` имя её домена), `--bind IP` — ещё `IP`, `--bind 0.0.0.0` — ещё **любой IPv4-литерал** (но не `0.0.0.0`: это не адрес назначения). Имена — нет, ни при каком `--bind` (403 «открой доску по IP-адресу, не по имени»): защита от DNS rebinding держится на том, что в `Host` перепривязанной страницы стоит имя; `[::1]` — нет; `GET /?t=ТОКЕН` ставит cookie `brg_<порт>` (`HttpOnly; SameSite=Strict; Path=/`; имя с портом — доски двух проектов не затирают cookie друг друга) и отвечает `303` на `/` — токен не остаётся в адресной строке и истории; все GET — только с верной cookie (иначе 403 «открой адрес из вывода brg board»); токен кладётся в страницу (`<meta name="brg-token">` вместо комментария `<!--BRG_META-->`) только при верной cookie; POST — cookie **и** заголовок `X-Brg-Token`, `Content-Type: application/json`, `Origin` (если есть) = `http://` + **`Host` этого же запроса** (уже прошедший проверку; same-origin; **с 0.9.2 строже и по умолчанию**: при `Host: localhost:P` теперь отказ для `Origin: http://127.0.0.1:P`, которого браузер и так не пришлёт), `Content-Length` обязателен (chunked — 411), ≤ 1 МБ (413), невалидный JSON — 400; токен сравнивается `hmac.compare_digest`; только GET и POST (`OPTIONS` и прочие — 405 без CORS); на всех ответах `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` (кликджекинг кнопок «Стоп всех» со страницы соседнего localhost-порта), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`; свой `log_message` без URL (стандартный печатал бы `?t=` в терминал). Защита от злонамеренного локального агента — не цель (§1, «Не цели»): токен лежит в `run/board/`, а `brg say` и так доступен без ключа. С `--bind` защита дополняется, не ослабляется: cookie не получает `Secure` (HTTP), `SameSite=Strict` и cookie с именем порта работают как прежде (браузер к другому `Host` cookie не отправит — открывать надо тот адрес с токеном, которым пользуешься); от прослушивания сети (HTTP) защиты нет — только доверенная сеть или туннель; от злонамеренного соседа по сети — токен (128 бит) и проверки выше.
  - **Пути.** `GET /` — `board.html`, `GET /run/board/data.js` и `/run/board/T00N.js` — белый список (с любым `?…`); остальное — 404. Снимок отдаётся, только если нет `Sec-Fetch-Site` или он `same-origin`: страница с соседнего порта того же хоста — тот же «сайт» для `SameSite` и подключила бы `data.js` тегом `<script>` вместе с cookie, а читать снимок должна только сама доска. **Токен в адресе скрипта (0.9.2):** браузеры шлют `Sec-Fetch-*` только на potentially trustworthy URL (loopback, https), поэтому по сетевому адресу (`http://192.168.64.5:P`) заголовка нет и проверка по нему молча проходила бы — например dev-сервер разрабатываемого приложения на `0.0.0.0:3000` читал бы всю переписку. Поэтому страница, получившая `<meta name="brg-token">`, добавляет `&k=ТОКЕН` к адресам `data.js` и `T00N.js` (без meta — `file://` — как было), а сервер: `k` есть — должен совпасть (`hmac.compare_digest`), иначе 403; `Host` не loopback (`127.0.0.0/8`, `localhost`) — `k` обязателен. На loopback `k` не нужен (прежнее поведение, `Sec-Fetch-Site` там работает). `Referrer-Policy: no-referrer` и свой `log_message` не дают токену утечь из адреса. Заодно `k` закрывает Safari < 16.4 (§12, п. 10). Журнал действий с доски по не-loopback адресу дописывает адрес клиента: `── с доски: say → all (#42) (с 192.168.64.1)`.
  - **Действия** — `POST /api/<действие>`, JSON → `{ok, code, out}` (ошибка проверки аргументов — 400 с тем же видом; ошибка brg — 200, `ok: false`, слова brg в `out`): `say` {to: "all" | [имена], channel?, re?, text}, `task-new` {title, brief, cancel_current?}, `task-cancel`, `lead` {name}, `pause` / `resume` / `stop` {name?}. Сервер **ничего не пишет в состояние сам** (кроме `run/board/token|port|ready` и временных файлов текста): каждое действие — вызов brg от имени человека (`say`, `task new --as human`, `task cancel --as human`, `lead give <имя> --as human`, `pause|resume|stop`), поэтому все правила brg — выбор lead'а, снятие паузы, закрытие вопроса `--re`, отказы — действуют как из терминала. Вызов: `bash <корень>/bin/brg …` (`BRG_SERVE_BASH` от `brg board`), на Windows — `bin\brg.cmd` (решает `sys.platform == 'win32'` в Python, не `PLATFORM` brg: MSYS-Python понимает POSIX-пути); аргументы — списком, без оболочки; `stdin=DEVNULL`, `cwd` — корень проекта (иначе `brg.cmd` добавит строку `WIN_CD_HINT`), окружение без `BRG_AS` и с `BRG_NO_CHCP=1` (параллельные вызовы не должны переключать кодовую страницу общей консоли) и `MSYS=noglob` (Git Bash, запущенный из `python.exe`, иначе раскрыл бы маску вроде `README*` в незакавыченном аргументе — заголовке задачи), `timeout` 60 с, вывод — UTF-8 с заменой. Имена, каналы, номера — по регулярным выражениям; **тексты** (сообщение, постановка) — только через `--file` во временный файл `run/board/.srv.tmp.*.txt` (UTF-8, удаляется в `finally`; оставшиеся старше 60 с, как и `alive.*` убитых `brg board`, удаляются на старте сервера); заголовок задачи (`--title`) — одна строка без управляющих символов, ≤ 200 байт, на Windows ещё без `" % ^ & | < > !` (cmd.exe раскрывает их и в кавычках) — иначе понятный отказ. Каждое действие — строка в терминале `brg board` (stdout сервера; `-X utf8`): `── с доски: say → all (#42)`.
  - **Страница.** Одна на `file://` и `http://`: управление включается, если сервер вложил `<meta name="brg-token">` (в `file://` его нет — страница как раньше). Шапка: «Новая задача» (заголовок и постановка; если есть активная — окно честно говорит, что она будет отменена: `cancel_current`), «Пауза» / «Продолжить» (снять общие и личные паузы и стопы), «Стоп всех» и «Отменить задачу» — **с подтверждением**. Переписка: поле сообщения (кому — «всем» или чипы агентов, несколько; канал — задача или `lobby`; Ctrl/⌘+Enter), у вопроса в плашке «Ждут вашего ответа» и у каждого сообщения агента — «Ответить» (поле получает адресата, канал и `Re: N`: ответ закрывает вопрос на доске, §9.2). Меню «⋯» у чипа агента: «сделать lead'ом», «пауза» / «снять паузу» (при общей паузе пункта нет), «остановить» (с подтверждением) / «снять стоп». После действия — внеочередная загрузка снимка через 0,3 и 1 с. Ответ brg — всплывающая строка внизу; ошибка — красным, словами brg.
- **Запущенные brg (0.9.0, §5.5).** Снимок: у агента поле `spawn` — `null` или `{id, harness, model, rights, state, turn, turn_start, turn_end, turn_result, last_event, last_error, perm_denied, rights_note, last_text, last_text_turn, context, tokens{in, out, reasoning, cache_read, cache_write, main_in, main_out, sub_in, sub_out}, cost, tokens_source, sub_sessions, supervisor_alive, note, prompt_head, activity}` (`activity` — `activity.tail` строкой, строки с TAB разбирает страница); полный ключ в снимок не попадает (всё записанное надзором уже замаскировано). `meta.spawn = {supported: ["opencode"], available: […]}` — бинари ищутся (`type -P`) один раз при запуске `brg board`, не на тик; цена тика — по-прежнему O(1) процессов. Страница: у чипа запущенного — «⚙ S003», модель, права, токены (основная · подагенты), стоимость — только если > 0, контекст («без подагентов» при `stream`; 0.9.1); раскрывающаяся панель — активность, «ход N идёт M мин · последнее событие K мин назад» / «ждёт N мин» / «упал: …» / «отказ в правах: …» / «надзор не отвечает» / «конфликт», последний ответ («(ход N)» или «(ход N, идёт)»); в шапке задачи — сумма токенов запущенных. **Лента (0.9.1):** строка «ход N начат» выделена (новый ход виден сразу); панель перерисовывается, только если изменились её данные; по ключу панели (id запуска) страница помнит, был ли человек внизу ленты (или ещё не прокручивал) — тогда после перерисовки лента прокручена к последней строке; прокрутил вверх — его `scrollTop` сохраняется. С сервером: «Добавить агента» (харнесс из `meta.spawn.available`, модель — текст и последняя использованная, число 1–5, права — радио `full`/`project` со смыслом дословно, подпись) и в меню «⋯» запущенного — «Разбудить», «Дать полные права» (при `project`), «Забрать в окно» (показывает команду), «Убрать» (с подтверждением). Сервер: действия `spawn` {harness, model, rights, count, note?} и `spawn-ctl` {id, op: wake|rm|detach|rights, rights?} — валидация как в CLI (`model` не с `-`; `id` — `S\d{3,}` или имя агента), вызов `brg spawn …`, ответ < 2 с (надзор не держит пайп). **Локаль:** brg экспортирует `LC_ALL=C`, поэтому `brg board` передаёт серверу исходные `BRG_CMD_LC_SET`/`BRG_CMD_LC` (как раннеру `brg run`), сервер — в окружение вызова `brg`; `brg spawn` сохраняет их в запись, предпочитая `BRG_CMD_LC*` из окружения своей (там уже `C`); обёртка хода восстанавливает локаль. `LANG`/`LC_*` brg не трогает.
- **«Работает» честно (0.6.0, решение человека).** Участник «ждёт» ⇔ свободен (§5 п. 13). Снимок: у агента поле `mark` — `{note, since, via, item}` или `null` (читается тем же `busy_read`, только чтение). Страница добавляет два места, где видно «непонятно, что происходит»: (1) **строка состояния задачи** под заголовком — если у активной (текущей) задачи есть подзадачи и все они в финальных стадиях (готово / отменено): «подзадачи готовы · lead X работает: T» или «подзадачи готовы · lead X ждёт — итог ещё не подведён» (полевой случай: все подзадачи «готово», lead делал финальную проверку, а все «ждали»); (2) **плашка «бригада простаивает»** — задача активна, есть живой `wait` без пометки, **нет ни одного «работает»** (с пометкой или `working`), нет открытых вопросов человеку и идущих прогонов, бригада не остановлена. Длительность = max(сколько страница непрерывно наблюдает такое состояние, сейчас − время последнего сообщения задачи); плашка показывается при > 2 мин.

### 9.2 Вопросы человеку

**(решение человека, 0.5.1)** Вопрос агента человеку не должен теряться. Полевой случай: lead спросил человека в своём чате (можно ли закрыть работающее приложение для smoke-теста), дальше его чат заполнили выводы `wait`, вопрос уехал вверх, человек его не увидел; доска час показывала подзадачу «в работе», бригада ждала. Чат харнесса — по-прежнему основной канал (PROTOCOL, раздел 2 п. 3); brg добавляет к нему видимость: открытый вопрос виден на доске, в `who` и в терминале `brg board`, пока на него не ответили.

- **Задать** — `send --as <имя> --to human --ask` (вместе с тем же текстом в своём чате). `--ask` — только когда среди адресатов есть `human`; заголовок `Ask: yes`. Вопрос — одно сообщение: несколько вопросов — списком в одном теле.
- **Открыт**, пока в том же канале нет сообщения с `Re: <номер вопроса>` **от человека или от автора вопроса**: автор получил ответ в своём чате и пересылает его суть бригаде `send --re N` (это и закрывает вопрос — так бригада узнаёт решение человека), или человек отвечает из терминала `say --re N …` (у `say` появляется `--re`). Ответ `--re N` другого агента (вопрос был и ему: `--to human,codex-1`) вопрос не закрывает — человек ещё не ответил. Уточнить вопрос — новым `--ask`, не `--re`. Закрытие или отмена задачи снимает её открытые вопросы (сообщения остаются). Подсказки ответа (`who`, `status`, вывод `send --ask`, доска, терминал `board`) называют `--channel`, если канал вопроса — не канал по умолчанию.
- **Индекс** — маркер на открытый вопрос в `run/asks/` (пишется вместе с сообщением `--ask`, снимается записью сообщения с `Re` на него и закрытием/отменой задачи): так `who`, `status` и тик доски видят открытые вопросы за O(1), без чтения переписки.
- **Где видно:**
  - доска — плашка «Ждут вашего ответа» над задачей: кто спросил (чип агента), когда (живое «N мин назад»), начало вопроса (раскрывается целиком), куда отвечать — «в чате <имя> (в окне агента ищи «<имя>.<3 символа ключа>») или `brg say --to <имя> --re N …`»; при сервере (§9.1) вместо команды — кнопка «Ответить» (поле сообщения получает адресата, канал и `Re: N`); число открытых вопросов — в начале заголовка вкладки; у спросившего агента в полосе бригады — «ждёт вашего ответа»; в переписке вопрос помечен «вопрос человеку · открыт / отвечен #M / снят без ответа» (последнее — задачу закрыли или отменили, а ответа с `Re` не было);
  - `brg board` в терминале — строка на каждый новый открытый вопрос (один раз): `── вопрос человеку от opencode-2 (#20, T004): <первая строка> — ответь в его чате`;
  - `who` — строка «ждут ответа человека: opencode-2 #20 (55 мин)»; `status --as <имя>` — свои открытые вопросы.
- **Ключ на доске.** Чтобы человек нашёл окно агента, доска показывает рядом с именем **первые 3 символа ключа** (`opencode-2 · xqp…`): в окне агента каждая команда содержит полное имя `opencode-2.xqprxp`. Полный ключ доска не показывает (§3: из общедоступного вывода ключ не взять) — снимок пишет только префикс.
- Агентам (README, раздел 3, механика): вопрос человеку — текстом в чате **и** `send --to human --ask`; получил ответ — перешли суть бригаде с `--re N`. Отчёт человеку (не вопрос) — без `--ask`.

## 10. Windows

- `bin/brg.cmd` (ASCII, CRLF) сам находит Git Bash: `BRG_BASH` → `%ProgramFiles%\Git\…` → `%ProgramFiles(x86)%\…` → `%LOCALAPPDATA%\Programs\Git\…` → scoop → через `where git`. `bash` из PATH не вызывает, bash из System32/WindowsApps (WSL) отвергает. Ставит `BRG_VIA_CMD` — brg печатает `NEXT:` в форме `.\.brigada\bin\brg.cmd …` (работает и в PowerShell, и в cmd; вызов не из корня — с подсказкой `cd <корень>`). На время вызова `chcp 65001` (`BRG_NO_CHCP=1` отключает); код выхода brg сохраняется.
- `.gitattributes`: `bin/brg`, `bin/brg-global`, `bin/brg-serve.py`, `*.sh`, `template/*` — `eol=lf`, `*.cmd` — `eol=crlf`.
- **Сервер доски (0.8.0, §9.1).** Python ищется без шимов (`py -3`, `python3`, `python`; заглушки `…\Microsoft\WindowsApps\` пропускаются) и хранится как `sys.executable`; `--root` сервера — `C:/…` (из `BRG_VIA_CMD` или `/c/…`); решение «`brg.cmd` или bash» принимает сам сервер (`sys.platform == 'win32'`); `BRG_NO_CHCP=1`, чтобы параллельные вызовы не трогали кодовую страницу консоли `brg board`; `MSYS=noglob` — Git Bash не раскрывает маски (`*`, `?`, `[`) в аргументах, которые ему передал не-MSYS процесс; `allow_reuse_address = False`. Закрытие окна и Ctrl+C останавливают сервер через TERM от bash, а если не дошло — сердцебиением `run/board/alive.*` (≤ 15 с). brg с CRLF в самом себе выдаёт понятную ошибку (код 2).
- Агентам в PowerShell/cmd: `.\.brigada\bin\brg.cmd …`, тело — `--file` (или `--desc`/`--comment`); харнесс, выполняющий команды в Git Bash (Claude Code на Windows), вызывает как обычно.
- Таймауты по платформе: `wait_timeout.<харнесс>.<платформа>` (`darwin`, `linux`, `msys`, `wsl`). Пользовательский `config` побеждает любые значения по умолчанию: `config` (`<h>.<plat>`, `<h>`) → `config.default` (то же) → встроенные (то же) → `wait_timeout.default` в том же порядке файлов.
- `brg doctor [проект]` — проверки среды и состояния (bash и платформа, CRLF, атомарность `mkdir`, `mv` поверх открытого файла, видимость процессов, `.git/info/exclude`, блок brigada в `AGENTS.md`/`CLAUDE.md` (§3), блокировки, раннеры, зависшие wait, таймауты): ✓/⚠/✗ с подсказками, ничего не меняет, код 1 только при ✗. Видимость процессов: `kill -0` родителя даёт EPERM — ⚠ «песочница: чужие процессы недоступны, brg считает их живыми, сироту wait не распознает»; EPERM даёт уже завершённый собственный ребёнок — ⚠ «смерть процессов не видна, раннер снимается только по heartbeat (до `runner_stale`)». Песочницу, где pid-namespace прячет живые процессы (ESRCH), doctor не распознаёт (§12 п. 3). Блокировки и раннеры doctor оценивает тем же вердиктом, что и brg (§7.3, с `runner_dead_grace`). Сломанную установку (CRLF) проверяют копией из репозитория: `bash /путь/к/brigada/bin/brg doctor <проект>`.
- На Windows ничего ещё не запускалось — проверка по `WINDOWS.md` на машине человека.

## 11. Реализация

- bash 3.2 (запреты — в `AGENTS.md`). Утилиты: `mkdir mv rm cat sed awk date sleep kill ls head tail wc sort tr printf cp uname nohup`; без jq/node, Python — только `bin/brg-serve.py` и только в `board`/`doctor` (§1 п. 4); `date` — только форматирование. CLI харнесса (`opencode run`, `opencode session export`) вызывают только надзор и обёртка хода запущенных агентов (§5.5); `spawn` и `doctor` лишь ищут бинарь (`type -P`). Внутри `LC_ALL=C` (байтовая семантика), UTF-8 проходит насквозь.
- Один файл `bin/brg` (+ необязательный `bin/brg-serve.py`, §9.1). Тесты — на чистом bash (`tests/`; клиент `test_brg_serve.sh` — Python, без него тесты сервера пропускаются), включая конкурентный стресс, takeover, протухшие блокировки и скриптовый пинг-понг ≥ 200 обменов с убийствами wait; `test_brg_docs.sh` сверяет команды и флаги в `template/*.md` и `WINDOWS.md` с `--help`.
- **Живость процесса по pid из файла** — только `pid_alive` (§4.2); единственное место, где разбирается текст ошибки `kill` (под `LC_ALL=C` он английский). `kill -0` напрямую — только для своих детей и `$$`. Тестовый крючок `BRG_TEST_EPERM_PIDS` («pid pid …»; `*` — любой): перечисленные pid отвечают как EPERM — так тесты воспроизводят песочницу на любой ОС (pid 1 как «живой, но недоступный» есть не везде).
- `run/metrics.log`: строка на команду — `epoch агент команда ключ=значение…`. Главная метрика эксперимента — пробуждения на агента в час и (вручную) токены. Исключение — `board`: он только читает (§9.1) и в `metrics.log` не пишет.

## 12. Открытые вопросы

1. **Стоимость ожидания:** можно ли в Claude Code и OpenCode поднять `wait_timeout` до 540 с и во что обходится ожидание в Codex — нужен замер, правило §5.1. При `wait_timeout.codex: 25` простой Codex — до ~144 пробуждений в час, далеко за правилом.
2. Windows и bash ≥ 4 (Git Bash) не проверялись — `WINDOWS.md`.
3. **Живость процессов в песочнице Codex — исправлено (этап 6.1), подтвердить на машине с Codex.** EPERM («Operation not permitted»; воспроизводится и на macOS без песочницы: `kill -0 1`) brg теперь считает «жив» (`pid_alive`, §4.2), а смерть раннера требует ещё и молчания heartbeat (`runner_dead_grace`, §7.3). Проверить из песочницы: `doctor` даёт ⚠ про EPERM; `wait` не уходит в `orphan`; два одновременных `run` идут строго по очереди; `run list` не помечает живой прогон `killed`.
   **Остаток.** Если pid-namespace песочницы прячет живой процесс (ESRCH, а не EPERM): обычные блокировки снимаются у живого владельца сразу, сирота `wait` ложно уходит в `orphan`, разовые проверки прогонов сразу после сна ноутбука могут отметить живой прогон `killed` (§7.3); exec-лок и очередь защищены heartbeat. `doctor` этот случай не распознаёт. Сирота `wait` при EPERM не распознаётся (выходит по таймауту). `run` из песочницы не достучится до локальных сервисов (БД) — это brg не исправит: README для Codex велит запускать меняющие состояние команды brg, прежде всего `wait` и `run`, вне песочницы.
4. ~~Повторная сдача после `item review --verdict changes`~~ — решено в 0.5.0: исполнитель возвращает подзадачу в работу `item claim` и пересдаёт `item done` (§7.1.1).
5. **`model=unknown` у Codex** — проверка «ревьюер той же модели» (§7.1) не работает. Подсказка в README (`--model` из `~/.codex/config.toml`) или считать разные харнессы разными моделями.
6. **Объём задачи меняется внутри задачи** («изучить» → реализация), и заголовок в `history.md` вводит в заблуждение: команда переименования задачи или рекомендация «реализация — новой задачей».

На macOS проверен тестами.

Открыто: Claude Code и Codex (этап B); Windows (MSYS/WSL — пока отказ); свой id сессии (`--session` «create if not exist» — проверить живьём); выходит ли `opencode run`, пока идёт фоновый подагент; раздельность токенов основной и дочерних сессий в `session export`; настоящее ограничение прав внутри проекта (`project` сейчас — правила OpenCode по умолчанию; возможный путь — `OPENCODE_CONFIG_CONTENT` с `permission` на время вызова).
13. **Доска по сети (`brg board --bind`, 0.9.2).** Не поддерживаются IPv6 и имена хостов в `--bind` и в `Host` (открывать — по IPv4-адресу), HTTPS и обратный прокси (`Host` — имя, `Origin` — `https://…`: оба отказ): снаружи доску открывает только SSH-туннель на тот же номер порта. Известный остаток: на macOS обычный `brg board` (`127.0.0.1:P`, с `SO_REUSEADDR`) может занять порт поверх чужого процесса, слушающего `0.0.0.0:P`; обратная ситуация закрыта (`0.0.0.0` без `SO_REUSEADDR`), тестом не проверить — крючок слушает loopback. Токен постоянный и по сети идёт открытым текстом: после работы по сети его надо менять вручную. На Windows `--bind` не проверялся (брандмауэр, `WSAEADDRNOTAVAIL`).
14. **Установка одной командой (0.9.2)**: `curl -fsSL …/install.sh | bash` клонирует репозиторий (нужен git) и ставит `brg`; проверено только на macOS (bash 3.2); на Windows (Git Bash) и bash ≥ 4 не проверялось (признак режима — `BASH_SOURCE` на верхнем уровне и `-f`; в функции из пайпа там бывает `main`); без git установки одной командой нет (только вручную).
