# brigada — design

A scheme by which any number of agents from different harnesses (Claude Code, Codex, OpenCode, …) join a project and then organise the work on the human's task **by themselves**: they discuss, share out roles and items, and check each other.

The document describes how things work now and why. **(the human's decision)** marks a decision that only the human changes; the rest was accepted through review and is confirmed by tests. Only what is implemented belongs here: new things are first a plan in `/plans` (outside git) and come here together with the code.

---

## 1. Goals and constraints

1. **(the human's decision)** Setup on the human's side is a one-off `brg init` in the project and the phrase «подключись к бригаде» to an agent. So that the short phrase works in any harness, `init` appends a short brigada block to the project's standing-instruction files — `AGENTS.md` and, if needed, `CLAUDE.md` (§3); `init --no-agents-md` leaves them alone, and then the phrase is the full one: «подключись к .brigada, прочитай инструкцию в .brigada/README.md». No configuration of harnesses (hooks, configs, plugins) and no extra installs (tmux and the like). An agent launched by brg itself (`brg spawn`, §5.5) is not configuration either: brg passes the harness only call flags (`opencode run --format json --model … [--auto]`) and does not touch the harness's configs.
2. **(the human's decision)** The basic interaction (messages, waiting, roles, items) is done by a deterministic script, not by a model parsing files.
3. **(the human's decision)** One waiting mechanism for all harnesses: the agent does not end its turn and waits in a blocking `brg wait` (§5). Features of particular harnesses (background commands with a wake-up, schedulers, `codex queue`) are not part of the protocol.
   **(the human's decision)** For agents launched by brg itself (`brg spawn`, §5.5) the waiting is held not by the model but by a brg supervisor process: a free agent **ends its turn** (the harness exits, idling costs nothing), the supervisor sits in `wait` for it and, when there is something that wakes, continues the harness session and passes the batch straight into the prompt (one request to the model). While a subagent works, the launched agent does not end its turn and waits in `wait --busy`, like everyone. Agents connected by hand work as described in §5; to each other both kinds are indistinguishable (names, tasks, lead, items, `run`, questions, stop, pause).
4. **(the human's decision)** The implementation is bash (3.2+). Windows — through Git Bash (§10). **(the human's decision)** The only exception is Python (≥ 3.8, stdlib only) for the **optional** human's server `bin/brg-serve.py` (§9.1): `bin/brg` calls Python only in `board` (to start the server) and `doctor` (to check that it is there); the agents' tool is one bash file. Without Python everything works: the board opens as `file://` and only shows; to answer — `brg say`.
5. **(the human's decision)** All state is inside `.brigada/`, per task; only `common/` is shared between tasks. Switching tasks needs no session restarts; new agents join at any moment.
6. **(the human's decision)** Self-organisation is the point of the experiment: the agents decide themselves who leads and how to solve the task. brg keeps the state and the transition rules; the models make the decisions.
7. **(the human's decision)** PROTOCOL sets only the goal and minimal frames: safety; questions about the business substance go to the human, technical decisions are made by the agents; the human sees the questions and the result (by default — as text in the lead's chat and the same text via `send --to human`, which is visible on the board); no commits to `main`/`master` without the human's permission and no destroying others' work; communication through brg; item stages match reality — the human follows them on the board (§7.1.1); **a participant is a coordinator, the work is done by its subagents** (§5.4); closing — `task close` with `summary.md`. The whole process (roll call, lead, plan, items, reservations, review, branch, `brg run`) is **recommendations**: the agents may agree on something else and build their own tools. brg does not impose a process (for example, it does not require review for closing) — it gives tools and guards the integrity of the state. Why: a set procedure would replace self-organisation (item 6).
8. **(the human's decision)** How the brigade works — PROTOCOL, section 3 «Ожидания» (not hard rules):
   - decisions are made collectively: what we do, in what order, who takes what share;
   - the lead is a facilitator, not a boss: it records agreements and decides by itself only if the brigade did not agree;
   - **(the human's decision)** the lead is the only one who addresses the human on its own (questions, reports, the result); the others answer if the human wrote to them directly. There is no host role: the lead is both the facilitator and the link to the human, and there is always a lead (§6.1);
   - items are handed out to participants;
   - review of an item by another participant (through its subagent) is a recommendation: whether and how to review is up to the brigade; the agents keep an item's stage as it is in fact (§7.1.1).

   Why: when the lead itself researches the task and writes its core together with its subagents (following the advice "bulky work — to subagents"), the participants stand idle.

   That a participant is a coordinator and the work is done by its subagents is not an expectation but a mandatory frame (item 7, §5.4).

Not goals of the MVP: parallel tasks, a worktree per agent, cross-machine work (all agents on one machine, one file system), protection from a malicious agent.

## 2. Layers

| Layer | Implemented by |
|---|---|
| Transport and state: channels, cursors, roster, tasks, roles, deadlines, items, reservations, runs, locks | `bin/brg` (one bash file) |
| Waiting | `brg wait` + the rule "never end the turn" (an agent connected by hand); for agents launched by brg — the supervisor `brg __spawn` (§5.5) |
| Instructions for agents | `README.md` — the mechanics (mandatory), `PROTOCOL.md` — goal, frames, recommendations (from `template/`); the brigada block in the project's `AGENTS.md`/`CLAUDE.md` — a pointer to `README.md` (§3) |
| The human's tools (§9) | the global `brg` (`bin/brg-global`, `install.sh`); `bin/brg.cmd` on Windows |

Every command prints a short result and, where it fits, `NEXT:` — the next command verbatim, with the agent's name: this way the cycle survives context compaction.

## 3. Joining

1. The human, in the project root: `brg init` (or `bash /path/to/brigada/bin/brg init [project]`) — creates `.brigada/` (§4). A repeated `init` updates `bin/`, `README.md`, `PROTOCOL.md`, `board.html` (the human's board, §9.1), `config.default`, `VERSION`, without touching the state and `config` (it names the template keys that `config` has neither as a `key: value` line nor as a commented `# key: value` one). **(the human's decision)** For a new project `init` writes `config` as a copy of the template where every setting is commented out (`# key: value`): the default values act from `config.default`, and their new values reach the project with the next `init`; to set your own value, uncomment the line. `init` never changes an existing `config`, not a byte; an uncommented value in it beats `config.default` — for such a key a change of the default has no effect. **(the human's decision)** `init` appends `.brigada/` to `.git/info/exclude` (for a worktree — of the common git directory): the whole directory is never committed, otherwise any agent's `git add -A` would commit the conversation, the runtime, the copy of `brg` and the brigade's settings. The lines of brg ≤ 0.2.0 (`.brigada/{tasks,lobby,run,agents}/` and their comment) a repeated `init` replaces with `.brigada/` and hints to remove what is already committed from the index (`git rm -r --cached .brigada`; brg itself does not call git, §7.4). `doctor` — ✗ if `.brigada/` is not in exclude.
   **(the human's decision)** `init` puts the brigada block into the project root — between the marker lines `<!-- brigada:begin …` and `<!-- brigada:end …` (the block is found and updated by them): "if the human asks to join the brigade — read `.brigada/README.md` and follow it (there are `join` and the `wait` cycle); without such a request do not join". The block text is in English (agents read it); the human's phrases are verbatim, in quotes: «подключиться к бригаде», brigada, .brigada next to "join the brigade", and the name of the agent README section «Тебя запустил brg». A block of an earlier version (different text between the same markers) is replaced by the next `init`. The files follow what harnesses read: `AGENTS.md` — Codex, OpenCode, Cursor, Copilot and others (OpenCode without `AGENTS.md` reads `CLAUDE.md`); Claude Code reads `CLAUDE.md`, and `AGENTS.md` (since version 2.1.277) only if there is no `CLAUDE.md`; with both — only `CLAUDE.md`, unless it imports `@AGENTS.md`.
   - No `AGENTS.md` — it is created from the block alone and excluded from git (`/AGENTS.md` in `.git/info/exclude` by the same mechanism as `.brigada/`; without git — simply created; the comments for the `.brigada/` and `/AGENTS.md` lines are in English; `exclude` is recognised by the lines themselves, not by the comments, so an existing file with the Russian comments of an earlier version is not rewritten and the lines are not duplicated): the file appeared by brg's will, whether to commit it is the human's call (remove the line from exclude). `AGENTS.md` exists — the block is appended at the end after an empty line or, if it differs, replaced between the markers (inclusive); the file is probably in git — whether to commit the block is the human's call, and `init` says so.
   - No `CLAUDE.md` — it is not created (Claude Code will read `AGENTS.md`); it exists and contains the import line `@AGENTS.md` or `@./AGENTS.md` — it is not touched; it exists without such a line — the same block by the same rules (a mention of `@AGENTS.md` inside a line does not count as an import: Claude Code will see the block twice — harmless).
   - The file's line endings are kept (a CRLF file gets the block with CRLF), and so are its permissions; a symlink (`CLAUDE.md` → `AGENTS.md` and the other way) is written through, one file — one block. Repeated blocks are removed; `begin` without `end` — the file is not touched (the `init` output says so; the phrase is the full one). A repeated `init` is idempotent: the file does not change by a byte.
   - `init --no-agents-md` — `AGENTS.md` and `CLAUDE.md` are not touched (existing blocks too). `doctor` — ⚠ if there is no block in `AGENTS.md`, or `CLAUDE.md` has neither the block nor the import (§10).

   Why: the human's phrase must be short and the same in all harnesses, and every harness reads the project's standing instructions — without configuring the harnesses themselves (§1 item 1). The block does not tell an agent to join without a request — otherwise any session in the project would go into the brigade. The price is an edit of a file that may be in git.
2. The human to an agent — in a new session opened in the project directory: «подключись к бригаде». A harness reads the standing instructions when a session starts; a session from another directory will find someone else's `.brigada` or none.
   - The block says: to join means to work in the cycle until STOP (after `join` do not report to the human, go straight to `wait`); a participant only coordinates, any work is done by its subagents (§5.4); a participant's subagent never joins the brigade — subagents read the block too.
   - The same reminders are in the last line before `NEXT:` of `join` and in the `wait` timeout line: `── нет новых (N с) · ход не завершай · NEXT: …`.
   - Why: a model may take the request «подключись» as done after the first empty `wait` and end its turn with a report. The fallback without the block (`--no-agents-md`, a session opened before `init`, a harness that reads neither `AGENTS.md` nor `CLAUDE.md`): «подключись к .brigada, прочитай инструкцию в .brigada/README.md».
3. From the README the agent determines its harness (`claude`, `codex`, `opencode`, otherwise a short name; synonyms are normalised) and model; `join --harness <h> --model <m>` (the model is up to 120 bytes, as for `spawn --model`; a longer one is cut at a UTF-8 character boundary with the mark «…(обрезано)» and a warning) returns the full name `<harness>-<n>.<key>` (`claude-1.k7f3q9`, the session key — below) and a summary: who is online, the active task, the `wait` timeout, «Таймаут инструмента» (how to call `wait` in this harness), `NEXT:`. The agent allows brg calls "forever", reads PROTOCOL and enters the cycle (§5).

- **Identity** — an explicit `--as <name>` in every call (`BRG_AS` is the alternative). Identification by `$PPID` was rejected: in Codex commands go through the sandbox wrapper, Windows/MSYS has its own PIDs. Identification by the process tree (comparing the caller's ancestor with the parent of a live `wait`) was rejected too: the same reasons, and it also needs `ps`, which is not in the list of utilities (§11).
- **The session key in the name** — **(the human's decision)** protection from a model's mistake, not from an attacker (profiles are readable, §1). Why: a session that got the task in its prompt and skipped `join` may see an agent of its own harness in `who` (`opencode-1`) and decide that this is itself, and the `status` answer «Мой wait: работает» would pass for a confirmation of identity. The result is two processes under one name: both run the task as lead, duplicate items and edit the same files (reservations do not catch one's own paths), and the twin without `wait` does not get STOP.
  - `join` returns the full name `<base>.<key>`. The key is 6 characters `[a-z2-9]` from `$RANDOM` (without `l` and `o`), stored as `Key:` in `agents/<name>`. Harness names are only `[a-z0-9]`, so the name and the key split unambiguously at the first dot.
  - **State is only on the base name**: agent files, cursors, `From:`, `Assignee`, Lead, reservations, stop and pause flags, `metrics.log`. The key is written only into the profile. To others the name is shown without the key (`who`, `tail`, messages), so the key cannot be taken from `who`; the board shows the human only the first 3 characters of the key — to find the agent's window (§9.2). brg prints the full name only to the agent itself — in the `--as` hints and in `NEXT:`; the key survives context compaction the same way as the name: through the last `NEXT:`.
  - **Changing commands require the key:** `send`, `wait`, `busy`, `leave`, `task new|close|cancel`, `lead give|take`, `item add|claim|done|release|reassign|review|cancel`, `run` (start and `cancel`). A bare name → refusal: «имя занято другой сессией; твоё имя — только из вывода твоего join в этом чате; не видишь его — сделай join». `join --as` is not suggested here.
  - **Reading commands** (`status`, `read`, `who`, `task show|list`, `item show|list`, `run show|list`) accept a bare name too — subagents call them (§5.4). Without the key they do not refresh Last-Seen (otherwise a twin would "revive" the real agent), the hints with `--as` in their output carry the placeholder `<твоё имя из join>`, and `status` does not confirm identity: «wait агента X работает (pid N). Если ты не делал join в этом чате — ты не X: сделай join», `NEXT:` — `join`.
  - A key that is not `[a-z2-9]{6}` or does not match the profile → refusal in any command: «ключ устарел или с ошибкой: под этим именем переподключилась другая сессия».
  - On a key refusal `NEXT:` is `join`, not "fix and repeat … --as X": a repeat with the same name would loop the agent. `wait` keeps exit code 0 and `NEXT:` as the last line here too (§5).
  - Target names (`send --to`, `item reassign --to`, `lead give`) are accepted with a key too — the key is dropped: agents copy their full name.
  - Compatibility: a profile without `Key:` (an agent that joined before 0.2.0) accepts the bare name everywhere; it gets a key on `join --as`.
- **Return** after a context loss — `join --as <name> --harness <the same>` (the name bare or full): only the same harness; clears `Left`; cursors are kept; it issues a **new key**, the old one stops working (the old session, if alive, gets «ключ устарел»). In `lobby` — «X переподключён новой сессией; прежний ключ недействителен» (wakes the lead). Refusal:
  - the name has a live `wait`: «если это твой wait и ключ потерян — дождись его конца и повтори join --as»;
  - **(the human's decision)** the agent has not "dropped out": a return is allowed only after silence — neither `wait` nor brg calls — longer than max(`wait_timeout` + 60 s, `dropout_after`), as for the «возможно выпал» mark (§5.2), or in the `asleep`/`gone` state (including right after `leave`). Otherwise a twin that knows the base name from `who` would take the name, together with the roles, from a working agent: a "dead wait" is an agent's normal state between calls. Refusal: «X активен (последний вызов N с назад). Если это ты и ключ потерян — он в последней строке NEXT; иначе подожди M с или подключись под новым именем». The stop flag does not affect the condition. The price: an agent that lost its key waits up to ~5 minutes or joins under a new name.
- **One platform per `.brigada`**: `join` refuses if the platform (Darwin, Linux, MSYS, WSL, …) differs from that of the joined non-`gone` agents — pids, locks and paths differ between WSL and Git Bash.
- **The human's global command:** `bash install.sh` installs `bin/brg-global` as `~/.local/bin/brg`. From any subdirectory of a project it runs the nearest `.brigada/bin/brg`, `brg init` — with the repository's version, outside a project — the repository's `brg`; if the copy in the project is outdated, it suggests `brg init`. Agents call `bash .brigada/bin/brg …` — nothing is required of their environment (§1 item 1).

```
  common/project.md      # lasting facts about the project (stack, tests, conventions) — written by agents
```

### 4.1 Record format

All records are "headers `Key: value` + an empty line + a body" (like email). No JSON: parsed by `sed`/`awk`, readable by people and models. A message `messages/000014.msg`:
```
Id: 14
Channel: T001
From: codex-1            # agent | human (say) | brg (result of run)
To: all                  # all | name[,name] | human (may come with names)
Kind: msg                # msg | system
Re: 12
Reply-By: 1759838400     # optional, epoch
Expect: claude-1,opencode-1   # with Reply-By: whose answer is expected
Wake: no                 # system messages only: no — does not wake; <name>[,<name>] — wakes only them
Ask: yes                 # optional: a question to the human (send --ask, §9.2)
Time: 2026-10-07T12:03:11Z
Epoch: 1759838191

body
```

Time: ISO for people, epoch for computation (date parsing differs between BSD and GNU `date` — we only format).

### 4.2 Writing and locks

- A lock is `mkdir run/locks/<name>.lock` + `owner` ("pid epoch"). A stale one (owner dead, the lock older than `lock_stale`, or without `owner` for longer than `lock_stale`; `lock_stale` ≫ any critical section) is broken **atomically**: `mv` of the lock to a unique name (exactly one wins; a lock that changed owner is not touched), then `rm`. Only the owner releases a lock. Nesting: task → runs → chan; exec → runs → chan. The full order: `spawn.S00N → roster → task → runs → chan` (and `spawnseq` — the launch number — before `roster`). The supervisor lock `spawn.S00N` is held for the supervisor's whole life and is **never** broken by age (like the exec lock — only on the owner's death confirmed by its `hb`, §5.5); the supervisor, holding it, takes `roster` (`leave` on `rm`); no holder of `roster`/`task` waits for a supervisor lock — one-shot calls (`spawn rm|detach|rights`, `join --as`) try it once **before** `roster`.
- **"Dead"** — for a pid read from a file, always by one function `pid_alive` (§11): `kill -0` succeeds or answers EPERM ("Operation not permitted" — the process exists but is out of reach: the Codex sandbox, another user) — alive; ESRCH and any other answer — dead. The lock of an unreachable owner is broken only by age (`lock_stale`), the exec lock — by heartbeat (§7.3).
- A message is written under the channel lock: `seq+1` → the body into a temporary file in the same directory → `mv` to `messages/NNNNNN.msg` → update `seq`. Numbering has no holes, a cursor will not "skip" a message. A crash between `mv` and `seq` — `seq` is recomputed from the highest file number.
- Other files are tmp + `mv` too; `mv` with retries (Windows: an antivirus or a reader may hold the file).
- **Texts** (a message, a brief, an item description, a review comment) come from stdin (heredoc `<<'BRG_EOF'`) or `--file`; `say` also takes arguments; `item add --desc`/`item review --comment` are a one-line alternative (including for PowerShell, which has no heredoc, while a pipe in Windows PowerShell 5.1 spoils the encoding). CRLF → LF, a BOM is stripped, UTF-16 is rejected. Limits: a message — `msg_max_bytes` (8 KB; more — refusal with a hint to put the text into `shared/`), a brief — 64 KB. A stdin pipe that did not close within 10 s — refusal, nothing is sent.
- **Short fields from options are not rejected for length** (refusals cost agents steps): `--title` (200 bytes), `--note` (500), `--desc`/`--comment` (`msg_max_bytes`) are cut at a UTF-8 boundary with the mark «…(обрезано)» and a warning.

## 5. Waiting and the work cycle

**(the human's decision)** The only mechanism is the blocking `brg wait --as <name> [--timeout S]`. The last action of every step of an agent is `wait`; the turn does not end (except on STOP) (an agent connected by hand; an agent launched by brg — §5.5).

1. **One wait per agent, takeover without signals.** A new wait writes its pid into `run/wait/<name>.pid`; the old one checks ownership every tick (1 s) and, seeing another pid, exits. No signals are sent: a pid from a file may have been reused. Duplicates (a wait moved to the background by the harness) do not eat the mail.
2. **A superseded wait does not provoke a new one:** it prints `── SUPERSEDED: … НЕ вызывай wait повторно.` — this breaks the chain "notification that the old wait finished → the model calls one more". TERM/INT/HUP come only from the harness or the human (the command limit, Esc), so `── прерван сигналом … · NEXT: …` — the cycle goes on (if the pid file is already someone else's — SUPERSEDED).
3. **At-least-once delivery.** A wait first acknowledges the previous one's batch (`Acked := Pending`), then looks for new mail. `Pending` is written only after the output: a wait killed before the output does not lose messages.
4. **Channels:** `lobby` and the active task (plus the drain of the just finished one, §6). What is delivered is addressed to the agent or to `all`, except its own. Others' personal messages are not delivered (they are visible in `tail` and `read --all`): noise and context cost more than transparency.
5. **Heartbeat:** every tick — `run/wait/<name>.hb`, every `heartbeat` s — Last-Seen (any brg call refreshes it too). A live wait = the pid is alive (`pid_alive`, §4.2: EPERM — alive) **and** the hb is fresh (protection from pid reuse).
6. **Orphans:** the parent died — the wait exits silently, without holding a ghost in `waiting` (a parent `1` — a wrapper, MSYS — is not checked). An unreachable parent (EPERM, a sandbox) counts as alive: an orphan there is not recognised and exits by timeout — better than a false `orphan` for a live agent.
7. **It finishes by itself before the harness limit:** the timeout comes from `config` per harness and platform (§5.1); `--timeout` overrides it and is repeated in `NEXT:`; so is `--busy` (item 13, §5.4). `--timeout 0` returns at once and is repeated in `NEXT:` — a hot loop; `wait --help` says not to use it.
8. **What wakes:** new mail, a deadline summary (§8), a stop (§9), `leave` (`── LEFT`). **Quiet system events** (`Wake: no`: joined, left, claimed an item, started reviewing) do not wake and arrive with the next waking batch — otherwise every join would cost a model call to everyone waiting. Addressed ones (`Wake: <names>`) wake only those named. A new/closed/cancelled task, a lead change, the lead leaving, an agent with a role leaving — wake everyone; "joined/returned" while a task is active — the lead (otherwise it does not know the participants have come); `item add`, `done`, `release`, a handed-in item taken back to work (`claim` from `done`) — the lead; `reassign` — the new assignee; `review` — the assignee and the lead, and a verdict on a handed-in item also the other reviewers from `Reviewing:` (with a separate addressed message, §7.1.1); `cancel` — the assignee, the lead and the reviewers (`Reviewing:` — they have nothing left to review); `claim` and `review --start` — nobody; the result of `brg run` — its initiator. The author of an event is not woken. **During the human's pause** (§9) only what came `From: human` wakes (`say`, `task new|cancel --as human`, `lead give --as human`) and the pause being lifted (item 14); everything else — including the notice `From: brg` «X — lead» (§6.1), which under a general pause thus wakes nobody — arrives after the pause.
9. **Digest on timeout:** with an active task, before `── нет новых` — the line `T001: todo 1 · в работе I002 codex-1 · на проверке I003 (claude-2) · готово I001 · прогонов идёт 1` (stages — §7.1.1) and `· свободны: claude-2, codex-1` — agents with a live `wait` without the busy mark (item 13), except oneself, the stopped and the paused (otherwise the lead polls `who`/`item list`).
10. **Output cap** `wait_output_max` (~20 KB, the harnesses' inline output limit): `Pending` = the last one shown, the rest comes with the next wait at once (the line `── ещё N в <канал> не вошло …` with a `read` command).
11. **Always exit code 0**, the status is in the text. The last line is `NEXT:` (except STOP, SUPERSEDED, LEFT and an orphan's exit), including on an argument error and a key refusal (§3) — otherwise the agent drops out of the cycle.
12. `read` does not move the cursor and by default shows everything after `Acked`, including the last batch handed out — a safe repeat if the agent is not sure it saw the output. A new agent starts from the end of `lobby` and of the active task.

13. **(the human's decision) "Waiting" means "free".** By §5.4 a participant works through a subagent, and the subagent (in Claude Code — in the background) runs while the participant sits in `wait`: a `wait` alone cannot tell "free, ready for an assignment" from "its subagent is working". So `wait` without `--busy` is an explicit "I am free" (in `who`/`status`/on the board — «ждёт»), and `wait --busy ["label"]` is "my subagent is working" (the mark, §5.4). `NEXT:` repeats `--busy` while the mark stands — copying `NEXT:` verbatim, the agent keeps the mark without thinking about it.

14. **(the human's decision) The pause inside `wait`.** A pause (§9) does not end the agent's turn — it stays in `wait`, and this is what the wait does while the pause stands (the general `run/paused` or its own `run/paused.<name>`):
    - **Only the human wakes.** Besides `wake`, `AWK_FMT` counts a second counter `hwake`: waking (by the same `Wake:` rules) **and** `From: human`. Pass 1 of `w_deliver` under a pause wakes by `hwake`, not by `wake`; on a wake-up everything accumulated after `Acked` is handed out without a filter (the cursor is linear: nothing is lost), with a line before `NEXT:` «пауза продолжается: отвечай человеку, новую работу не начинай». The output cap under a pause says what happens to the rest: «придут после снятия паузы или со следующим сообщением человека».
    - **Lifting the pause wakes and brings what accumulated, in the same `wait`.** Pass 1 under a pause moves `CH_SEEN` past everything viewed, waking or not; so a `wait` that saw the pause, on the transition "pause → no pause", sets `CH_SEEN := CH_ACK` on all channels and finishes with the line `── пауза снята: человек снял паузу — новую работу можно начинать.` and what accumulated (nothing accumulated — the line and `NEXT:`). Without the reset what accumulated would arrive only with the next `wait`.
    - **Deadlines do not wake under a pause.** Under a pause `w_deadlines` is called only on a wake-up by a human's message or on the pause being lifted (its summaries go with that batch); the `.done` marker is not taken in advance.
    - **Timeout under a pause** — `── пауза · нет новых от человека (N с) · ход не завершай · NEXT: …`; the task digest with «свободны» is not there. There is no long wait under a pause (`pause_timeout`) — the human's decision: the pause waits with the usual `wait_timeout`, the background `wait` of Claude Code is not used (§1 item 3).
    - A `wait` that failed with an error after writing its pid file (for example, the message «X — lead» could not be written) removes the pid file and the heartbeat by itself. Self-assignment of the lead (§6.1) is allowed under a general pause, not under the agent's personal pause: it becomes lead with the next `wait` after `resume`.

The cursor `cursors/<name>`: `Acked: 14` (everything ≤ 14 is processed), `Pending: 15` (handed out by the last wait, the next one acknowledges it). Output:
```
── T001 · 2 новых ─────────────────────────────
#14 codex-1 → all · re #12 · 12:03
  Предлагаю лидом claude-1: …
#15 [система] claude-1 → all · 12:04
  …
── NEXT: обработай, затем: bash .brigada/bin/brg wait --as claude-1.k7f3q9
```
Timeout: `── нет новых (100 с) · ход не завершай · NEXT: …`. Stop: `── STOP: человек остановил бригаду. Заверши ход.`

### 5.1 Timeouts per harness

The values are **conservative**: they have not been measured in the harnesses. All are below 120 s — the default command limit: a model may fail to pass an increased tool timeout (especially after context compaction).

| Harness | Command limit | `wait_timeout` |
|---|---|---|
| Claude Code | default 2 min, max 10 min (the `timeout` parameter); at the limit moves the command to the background | 100 |
| OpenCode | default 2 min, the upper bound removed | 100 |
| Codex (macOS/Linux) | unified_exec: a command is "parked" after 10–30 s, then the model polls it (`write_stdin`) | 25 (return before parking) |
| Codex (Windows) | unified_exec is off by default — closer to an ordinary blocking command | 100 (`wait_timeout.codex.msys`) |
| unknown | — | 100 (`wait_timeout.default`) |

Tool timeout = `wait_timeout` + 60 s (≤ 600 s) — printed by `join` and `status`. `doctor`: `wait_timeout` > 540 s — ✗, > 110 s (Codex outside Windows — > 25 s) — ⚠. Numbers in options, `config` and the environment are decimal (`08` is 8, leading zeros are allowed, up to 9 digits). A value of a numeric `config`/`config.default` key that is not a number is skipped by brg (it takes the next layer or the built-in value), and `doctor` gives a ⚠ with the key and the value taken.

### 5.2 Agent liveness

The state in `who`/`status` (and in the «Онлайн» list of `join`, `status`): **(the human's decision) «ждёт» ⇔ free** — the agent's `wait` is running and there is no busy mark (§5.4); the agent is ready for an assignment. The rest are shown like this:

| State (internal) | Mark | Shown |
|---|---|---|
| `waiting` (wait alive) | no | **«ждёт»** |
| `waiting` | yes | **«работает: подпись, N мин»** (the label — up to 2 words; N min — how long the mark has stood) |
| `working` (a recent brg call, no wait) | no / yes | **«работает»** / **«работает: подпись»** — the agent is between two `wait`s or its `wait` has not started yet; after that — «не на связи» |
| `asleep` (no wait and no calls for longer than `asleep_after`, 15 min) | — | `asleep` |
| `gone` (`leave` or silence for longer than `gone_after`, 1 h) | — | `gone` |
| `waiting` / `working` under the human's stop (general or personal, §9) | — | **«остановлен»** — the stop ended the agent's turn, it is not working |
| `waiting` / `working` under the human's pause (general or personal, §9) | as for the state | the same as for the state, plus «(пауза)»: a pause does not end the turn — the agent waits and starts no new work |

The thresholds are generous: an agent running tests for 10 minutes has not vanished. Marks: «не на связи N мин» — no wait for longer than `wait_timeout` + 60 s; «возможно выпал» — neither wait nor brg calls for longer than max(`wait_timeout` + 60 s, `dropout_after` = 300 s), except the stopped: a hint to the human to write «продолжай» to the agent in its chat. The busy mark does not cancel this hint: a participant with a background subagent must sit in `wait`, so a mark without a live `wait` is a sign of an agent that dropped out. The only exception is a mark with `Via: busy` (the `brg busy` command: "a subagent blocks me", a harness without background subagents): «возможно выпал» is not shown for such an agent, «не на связи» is. The values of the internal state (`ST`: waiting/working/asleep/gone) do not change and do not depend on the mark; only the display is extended with it.

**Agents launched by brg (§5.5).** `ST` is computed the same way: a frozen or crashed agent — a live supervisor `wait` → `waiting` («ждёт»); a turn in progress — brg calls and the supervisor's `touch_seen` → `working`. In `who`/`status` the line gets «(запущен brg, S003)» and the record's state (§5.5): «ход N идёт M мин · последнее событие K мин назад», «упал: …», «отказ в правах: …», «надзор не отвечает», «конфликт». Such an agent with a live supervisor and a turn in progress has no «не на связи»/«возможно выпал» (`idle_note_v`) — instead «ход N идёт M мин · последнее событие K мин назад (возможно, долгий инструмент)», and it is "online" for choosing the lead (`lead_online`, §6.2) without the `wait_timeout` + 60 s window: a former lead in a long turn is not skipped. A stopped launched agent (in `stopped` the supervisor holds no `wait`) ages to `asleep`/`gone` like one connected by hand.

### 5.3 Known drawbacks (accepted deliberately)

- A human's message in the harness chat arrives when the wait returns (within `wait_timeout`), or after Esc.
- Idling is not free: one model call per timeout per agent.
- There is no guarantee: an agent may end its turn. This is visible («не на связи», «возможно выпал», `asleep`); the lead reassigns its items, the human says «продолжай».

### 5.4 Subagents

**(the human's decision)** A brigade participant only coordinates its part; any work is done by subagents that it starts on its side. This is a mandatory frame (PROTOCOL, section 2), not an expectation: as a recommendation it did not reach every participant — they read and edited the code themselves.

- **The participant itself** only coordinates: brg calls and the conversation, discussion and decisions, assignments to subagents and taking their result (the subagent's report, `git diff --stat`), short coordination documents (`shared/plan.md`, `summary.md`), the lead's commit.
- **A subagent** does everything else: reading and editing the project's code and documents, research, review and checking of others' work, analysis of failed tests.
- **How many subagents.** By default one subagent works at a time per participant (sequentially — as many as needed). More only if the human explicitly allowed it: in the task brief, in the participant's chat or with a `human` message.
- **A harness without subagents** is the only exception: the participant does the work itself, in short steps between `wait`s, and tells the brigade so at the roll call.
- **Background subagents** exist in Claude Code and in OpenCode v2 (`task … background: true`); a blocking subagent call (the same OpenCode without `background`) — `brg busy` before it.

Why: a participant's context lives for the whole task and grows with every wake-up — the smaller it is, the cheaper the wake-up and the later the compaction; a participant busy with the work itself drops out of the cycle, and the brigade stands idle. Where the rule is repeated so that everyone sees it: the brigada block in `AGENTS.md`/`CLAUDE.md` (§3), README (section 2, «Подагенты»), PROTOCOL (section 2), the output of `join`, `task new`, `item claim` and `item review --start`. brg cannot tell a subagent from a participant — it cannot check the rule.

The mechanics (README, mandatory): a subagent under no circumstances joins the brigade — it does not call `join`, `wait`, `leave`, `stop` — its `wait` under the participant's name would supersede the participant's wait (SUPERSEDED), and the participant would drop out of the cycle; reading commands and a short `run --sync` under the participant's name are allowed. `run` is a changing command (§3), so the subagent is given the participant's full name, with the key; the base name is enough for reading commands. brg cannot tell a subagent from a participant — the rule lives only in the documents.

**The busy mark** (the human's decision: «ждёт» ⇔ free — §5 item 13, §5.2). The participant reports "my subagent is working" itself; brg cannot check this — just as it cannot check the subagent rule itself. One mark per agent (one subagent at a time): `run/busy/<base name>` — headers `Task: T00N`, `Since: <epoch>`, `Note: <label or empty>`, `Item: <I00N or empty>`, `Via: wait|claim|review|busy`; written as tmp + `mv`.

- **Validity.** A mark whose `Task` is not the active task (or with no active task) **does not exist** — for `agent_state`, `NEXT:`, `who`, `status`, the board. So clearing `run/busy/` on `task close|cancel` (and `--cancel-current`) is just tidying, races are harmless. One function reads it (`busy_read`). Without an active task `wait --busy` and `busy` set no mark: «задачи нет — пометка не ставится» (not a refusal).
- **How it is set.** `wait --as X --busy ["label"]` — at the start of `wait` (after the STOP check; STOP does not touch the mark), `Via: wait`; `Since` and `Item` are carried over from the previous mark only if it is valid and has the same `Note`. `item claim I00N` → `Note: I00N`, `Item: I00N`, `Via: claim` (taking a handed-in item back to work too); `item review I00N --start` → `Note: проверка I00N`, `Item: I00N`, `Via: review` — took it (is reviewing) = busy. `brg busy --as X ["label"]` — a mark without waiting, `Via: busy`: for harnesses where a subagent call blocks the participant (OpenCode), and for work outside items; `busy --off` — clear it; under STOP the command is allowed (it starts no work), the first line is the STOP banner, `NEXT:` — «заверши ход».
- **The label is trimmed, not rejected** (§4.2): control characters, `"`, `'`, `\`, `$`, the backtick and `%` → a space (`%` — cmd.exe expands it even in quotes, and `NEXT:` on Windows goes through `brg.cmd`), spaces collapse, the first 2 words remain, ≤ 48 bytes at a UTF-8 boundary; if anything changed — a warning; nothing left — a mark without a label (in `NEXT:` — a bare `--busy`, not `--busy ""`).
- **How it is cleared.** A plain `wait` (without `--busy`) — an explicit "I am free"; `busy --off`; `leave`; `join` (including `join --as`: a new session has no subagent); a task change or close. A mark with an **empty** `Item` is **never** cleared by item commands (otherwise the lead's `item release` of someone else's item or its `--verdict skip` would clear the mark «финальная валидация» while the subagent works): on `item done`/`--verdict` such an agent gets the line `ты отмечен «работает: T» — если подагент закончил, следующий wait без --busy`. A mark with `Item = I00N` is cleared for **its owner** when the item leaves it: for the assignee — `item done`, `release` (whoever does it), `cancel`, `reassign` (for the old assignee); for a reviewer — its own `--verdict` on this item (another's verdict on a handed-in item does not clear its mark: its own valid mark on an item whose `Reviewing:` no longer names it stays, also on `wait --busy`, §7.1.1), and also `item cancel`, `release` and taking it back to work (`claim` of a handed-in item by the assignee) — they clear `Reviewing:`, and the «проверка I00N» marks of everyone named there are cleared. `reassign` of an item in work removes from `Reviewing:` only the new assignee (and clears its «проверка I00N» mark: it does not review its own work); `reassign` of a handed-in item waiting for changes (the stage «правки», §7.1.1) clears `Reviewing:` and the marks of everyone named there, like `claim`. An action on someone else's item does not touch another agent's mark. The line «ты отмечен…» is printed only to the current assignee or a reviewer of this item (not to a lead that released someone else's). `reassign` sets no mark for the new assignee — the system message gives it the hint «поручи подагенту и `wait --busy "I00N"`».
- **`NEXT:` = the current state of the mark.** One function (`next_wait`) builds `wait --as … [--busy "<label>"] [--timeout S]` for **all** `── NEXT:` and error `NEXT:` (`send`, `read`, `status`, `task …`, `item …`, `run …`, `lead …`, parse errors; before `need_agent` the name is taken from `--as`/`BRG_AS`), including the `NEXT:` of `wait` itself — it is computed when it finishes (the mark may have been cleared while it waited). So after `claim`/`review --start` the `NEXT:` itself contains `--busy "I00N"`, and after `done` it does not; an error in `--busy` does not turn `NEXT:` into a plain `wait` that clears the mark. In addition: the output of `wait` with a valid mark (a batch and a timeout) has a line before `NEXT:` `Ты отмечен «работает: T». Подагент закончил и ты свободен — следующий wait без --busy`; a plain `wait` of an agent with a `claimed` item or with `Reviewing:` on it gets the line «У тебя I003 в работе: если подагент работает — wait с --busy "I003"» (not a refusal). A race between the lead's `item cancel` and the assignee starting `wait --busy "I003"` is acceptable: a plain `wait` clears the mark. A stale `NEXT:` (handed out before a task change) must not mark the new task: the label `I00N` / `проверка I00N` is set only if this item of the active task is claimed by this agent or the agent is in its `Reviewing:`; otherwise — a warning and no mark (the same for `busy`).
- **Display.** `who`, `status`, «Онлайн» — §5.2; the digest on timeout — «свободны» (§5 item 9); the board snapshot — the agent's `mark` field `{note, since, via, item}` (§9.1).

### 5.5 Agents launched by brg

**(the human's decision)** The human launches agents themselves — from the terminal (`brg spawn`) and from the board («Добавить агента», §9.1): sees their state and what they do, and they work in the brigade the same way as those connected by hand. The human's decisions:
1. **Two kinds of participants in one brigade.** Those connected by hand work exactly as in §5 (the `wait` cycle, they do not end the turn). Those launched by brg — by the mechanism below. To each other they are indistinguishable: names with a key, tasks, lead, items, review, `run`, questions, stop, pause.
2. **A launched agent freezes when free:** it ends its turn (the harness process exits). When there is something that wakes (by the `wait` rules, §5 item 8), brg continues its session and passes the batch straight into the prompt (one request to the model). While a subagent works, it does not end its turn and sits in `wait --busy`.
3. **Rights** are an explicit choice at launch, full by default, with a warning. A rights refusal is **visible** on the board; the button «дать полные права» acts from the next turn of the same session.
4. **There are no limits; tokens and cost are visible** per agent and in total.
5. **There is no separate "revival".** An abnormal end of a turn is visible on the board, the lead gets a message; the batch is delivered again by **the next wake-up** — caused by a new message to the agent or by the «Разбудить» button. No automatic retries.
6. **Only the human launches** (the terminal and the board).

Only **OpenCode** is supported, only macOS/Linux (MSYS, Cygwin, WSL — refusal «пока не поддерживается»).

**How OpenCode 2.0.23 works** (from the binary's code and checks without an LLM): the commands of the model's shell tool run in their own process groups; on **SIGINT** `opencode run` interrupts the session in an orderly way and kills them (exit code 130); there is no SIGTERM handler. Without `--auto` a permission request does not hang: `run` refuses by itself, in stderr — `! permission requested: <action> (<resources>); auto-rejecting` (with ANSI), in the stream — a `tool_use` with `status: "error"` and «…request was rejected». By default everything is allowed in the project directory (shell, edits, network, git push); only going outside the project directory and reading `*.env` is asked; `--auto` approves that too. The JSON stream on stdout (`--format json`) is the main session only; a `tool_use` is written on the tool's **completion** (a running one is not visible). Events: `step_start`, `text`, `tool_use`, `step_finish` (`part.tokens`, `part.cost`), `error` (`error.message`); each has a `sessionID` (`ses_…`); a step error or an interruption — an `error` event and an exit code ≠ 0. Subagents are child sessions: their ids are in the output of a completed `tool_use` of the `task` tool (`task_id: ses_…`; a background one — `sessionID: ses_…`). `opencode session export <id>` prints JSON that starts with `info.cost` and `info.tokens {input, output, reasoning, cache{read, write}}`; without `--standalone` OpenCode commands start a long-lived background service on the human's machine. OpenCode re-encodes a message passed as an argument (quotes, `\"`); **a message from stdin** (not a TTY) passes as is. The environment of the model's commands has `OPENCODE_SESSION_ID` (for a subagent — the child session's id), `OPENCODE=1`, `AGENT=1`.

#### The spawn record

`run/spawn/S00N/` (a project-wide number, `run/spawn.seq` under the `spawnseq` lock). The `spawn` file is headers (tmp + `mv`); only the holder of the supervisor lock writes it (the supervisor; at creation — `brg spawn`; on `rm`/`detach`/`join --as` without a live supervisor — these commands, under the lock):
- `Id`, `Agent` (base name), `Harness`, `Model`, `Rights: full|project`, `Session`, `State`, `Note`, `Created`, `Created-Epoch`, `Supervisor` (pid — for display only);
- `Turn`, `Turn-Start`, `Turn-End` (the epoch of the harness exit from `turn.N.exit`), `Turn-Result: ok|crash|interrupted`, `Turn-Stopped: 1` (the turn ended while a stop stood), `Last-Error`, `Perm-Denied` (the last rights refusal: kept until the rights change, a successful turn does not clear it), `Last-Event` (the epoch of the last growth of `events.log` in the current turn; reset at the start of a turn), `Hold: 1` (a series of crashes);
- `Tokens-In`, `Tokens-Out`, `Tokens-Reasoning`, `Tokens-Cache-Read`, `Tokens-Cache-Write`, `Cost` (a string; summed by awk `printf "%.6f"`), `Tokens-Source: export|stream`, `Sub-Sessions`;
- `Locale-Set`, `Locale` (the human's original locale, §9.1);
- the body — the model's last text of the turn (≤ 2 KB, the key masked).

Next to it: `join.out` (the join output — part of the first prompt), `prompt.N` (the turn's prompt; the last 5 are kept; only the path goes out) and `prompt.head` (the first lines of the last prompt, the key masked — for the board), `events.log` (+ `events.log.1` — rotation before a turn if > 50 MB), `stderr.log`, `supervisor.log`, `activity.log` (grows) and `activity.tail` (the last 50 lines, tmp + `mv`, the board reads it): lines `epoch<TAB>kind<TAB>текст` (`turn`, `tool`, `text`, `error`, `permission`, `end`), ≤ 300 bytes, control characters → a space, the key masked; `children` (ids of child sessions) and `children.tok` (a cache of their totals), `stream.tok` (the number of the last counted turn and the sum of the main session's `step_finish` over all turns), `sub.tok` (the sum of the child sessions' totals from the last export), `turn.N.parse` and `turn.N.text` (the parse of turn N during the turn, below). From the turn wrapper: `turn.pid`, `turn.hb` ("wrapper pid epoch", once a second), `turn.event`, `turn.session`, `turn.N.exit` (exit code and epoch), `turn.N.off` (the offsets of `events.log` and `stderr.log` before the turn). **Flags** are put by `brg spawn …` (including at the board server's request): `rm`, `detach`, `wake`, `rights` (the content is the new value); the supervisor `wait` only reads them, the supervisor removes them after handling; `turn.stop` — a request to the turn wrapper to stop the turn.

| State | Means | Shown |
|---|---|---|
| `starting` | the supervisor started, the first turn has not begun (including waiting for a stop to be lifted) | «работает · запуск» |
| `running` | a turn is in progress (the wrapper is alive) | «работает · ход N, M мин · последнее событие K мин назад» |
| `frozen` | the turn ended, the supervisor waits for something that wakes | **«ждёт»** |
| `crashed` | the last turn was abnormal (`Hold: 1`), the supervisor waits for a **new** waking event | «ждёт» · «упал: <ошибка>» |
| `stopped` | the human's stop | «остановлен» — lifted by the «Продолжить» button (`brg resume`) |
| `conflict` | the supervisor `wait` is superseded again and again by another `wait` under the same name | «ждёт» · «конфликт: под именем работает другой wait» |
| `detached` | taken into a window (`spawn detach` or `join --as`) — from then on an ordinary agent | as an ordinary one |
| `removed` | removed (`spawn rm`) or left by itself (`leave`) | gone |
| (not `detached`/`removed`, and the supervisor is dead by the lock rule) | the supervisor died | «надзор не отвечает» · «Разбудить» restarts it |

#### The agent

`brg spawn` joins the agent itself: the same function as `join --harness H --model M` (not a copy), plus `Spawn: S00N` in the profile; the join output (the variant for a launched agent — short rules, without «ход не завершай») goes into the first prompt; the model does not do `join`. "Is the agent launched" — one function `spawned_v` (`Spawn:` in the profile and the record not `detached`/`removed`).
- **`join --as X`** of a launched agent — removes `Spawn:`, the record → `detached`. One attempt at the supervisor lock **before** `roster`: a live supervisor → refusal «надзор жив: `brg spawn detach S` — забрать в окно»; the turn wrapper is alive (even with a dead supervisor) — refusal «идёт ход агента — дождись его конца или `brg spawn rm`». The rule "only after dropping out" (§3) applies too.
- **`join` with `BRG_SPAWN`** in the environment pointing to a live record of the same `.brigada` — refusal: `OPENCODE_SESSION_ID` is set and ≠ the record's session — «ты подагент участника X — к бригаде не подключайся, выполни поручение»; otherwise — «join не нужен: тебя подключил brg, имя — в первом сообщении».
- **`wait`/`leave`/`busy` with the `--as` of a launched agent**, when `OPENCODE_SESSION_ID` is set and ≠ the record's session (or `turn.session`, until the session is moved into the record) — refusal «ты подагент…» (`wait` — exit code 0 and `NEXT:` «выполни поручение и верни результат»).
- The `brg run` runner does `unset BRG_SPAWN`: the project's tests do not inherit it.

**Waiting phrases — one function `next_wait`** (§5.4): for an agent connected by hand — the usual `wait --as …`; for a launched one without a valid mark — «заверши ход — brg разбудит тебя, когда будет новое»; with a mark — `wait --as … --busy "…"`. All `── NEXT:` go through it; a launched agent gets its own lines in the output of `join`, `busy`, the banner and the stop/pause refusals (`stop_banner`, `work_refuse`), `w_notes_v` («у тебя I003 в работе — продолжи (поручи подагенту) или сдай/отпусти»; `ты отмечен «работает» — подагент закончил? тогда заверши ход`), the timeout lines of `wait --busy`, `status`. No brg line tells a launched agent "do not end the turn" or to wait in a plain `wait`.

**A plain `wait` of a launched agent** (called by the agent itself, without the supervisor) does not block: it clears the mark, acknowledges the previous batch, hands out what wakes if it is already there; otherwise at once `── нет новых · ты свободен — заверши ход: brg разбудит тебя, когда будет новое` and `── NEXT: заверши ход`. The second and later empty returns in one turn (the counter `turn.N.idle`, only with `BRG_SPAWN`) — a harsher line and the metric `wait.idle_repeat`. `wait --busy` blocks as usual.

#### Supervisor, lock, turn wrapper

**The supervisor** `brg __spawn S00N` is a separate process per agent, started like the `brg run` runner (`nohup` + `set -m`, all fds redirected, fds 3–9 closed, `trap '' HUP`); not inside the board server — a closed board does not stop the agents.

**The supervisor lock** `run/locks/spawn.S00N.lock` — for the supervisor's whole life, one supervisor per record. Its own function `spawn_lock_try S [НАБЛЮДАТЬ_СЕК]` (not `lock_acquire` and never by age): owner `$$` — "mine" (after `exec`); a dead owner (`pid_alive`) with an `hb` older than `runner_dead_grace` — the lock is broken at once (`lock_break`); a live pid with a silent `hb` — dead only after **continuous** observation longer than `spawn_stale` (30 s; `hb_obs_init`/`hb_obs_tick` take the threshold as a parameter; runners use the default, `runner_stale`). A new supervisor observes for up to `spawn_stale + 5` s (the owner shows signs of life — a quiet exit). One-shot calls make one attempt; the lock is held by a live supervisor → a flag (`rm`/`detach`/`rights`) or a refusal (`join --as`); **the supervisor is "silent"** (the pid is alive, `hb` older than `spawn_stale`: stopped, hung, a foreign pid after a reboot) — nobody would serve the flags, so `wake`, `rm`, `detach`, `rights` also start a new supervisor that observes and takes the lock, and `join --as` suggests `brg spawn wake`; the supervisor has just died (the pid is dead, `hb` fresh) — wait up to `runner_dead_grace`, take the lock and do the action itself: no flag is left without a handler. `spawn wake` — a flag to a live supervisor or a new supervisor, and an immediate return. After `exec` the new image adds the lock to `HELD`. `doctor` judges `spawn.*` like the exec lock (by `hb` and `runner_gone`), without the ✗ «держится N с» for a live supervisor.

**The supervisor's heartbeat — always:** `hb` in the lock directory every 5 s in **all** waits (the turn, the supervisor `wait`, `stopped`, pauses, waiting for the wrapper, `rm`/`detach`); the supervisor sleeps in steps of 1 s, no operation holds it longer than `spawn_stale / 2`.

**The turn wrapper** is a separate process `brg __turn S00N N` (like the runner: `set -m` — its own group and its own `$$`; a subshell will not do: in bash 3.2 it has the supervisor's `$$`). It restores the locale from the record, does `cd` into the project, removes the service variables (`BRG_AS`, `BRG_VIA_CMD`, `BRG_SPAWN_*`, `BRG_CMD_LC*`), `export BRG_SPAWN=S00N`; starts the harness as its own child under `set -m` (without it bash would set SIGINT = SIG_IGN for a background command): `<bin> run <spawn.opencode.args> --format json --model M [--auto] [--session SID] --title "brigada S003 opencode-3" <prompt.N >>events.log 2>>stderr.log`. Once a second — `turn.hb` and a check of `turn.stop`; every 5 s — growth of `events.log` → `turn.event`; the first line with a `sessionID` while the record's session is empty → `turn.session` (the supervisor moves it into the record at once: «ты подагент» works from the first turn). On `turn.stop`: `kill -INT` to its child, after 5 s TERM, after 5 more s KILL. After the harness exits — `turn.N.exit` (exit code, epoch). The wrapper survives a `kill -9` of the supervisor. **Wrapper liveness:** alive if the pid from `turn.hb` is alive and `turn.hb` is fresh; dead — the pid is dead and `turn.hb` is older than the grace; a live pid with a silent `turn.hb` — dead after continuous observation longer than `spawn_stale`. While the wrapper is alive, a second turn does not start.

**Signals** only to one's own children: wrapper → harness. The supervisor sends no signals to its `wait` or to the wrapper (flags and `turn.stop`); to other processes — only flags.

#### The supervisor loop

1. **Recovery** (the supervisor is not the first for the record — `Turn` > 0 — and not `--continue`; if the previous supervisor died between `running` and starting the wrapper, there was no turn, not a crash): wait until the wrapper of the current turn is dead or `turn.N.exit` appears; the turn's result — by the exit code; the first supervisor `wait` — with a rollback (`ROLLBACK`).
2. **A turn.** The prompt → `prompt.N`; `Turn`, `Turn-Start`, `State: running`; the wrapper. While it is alive: `hb`, the agent's `touch_seen` every `heartbeat`, moving `turn.event`/`turn.session` into the record; flags: `rm` → `turn.stop`; `rights` — apply at once (acts from the next turn); `detach` — after the turn; `wake` — remove (a turn is running anyway). No `turn.N.exit` — `crash` «обёртка хода пропала».
3. **The turn's result.** `ok` — exit code 0 and no `error` event; `interrupted` — the turn was stopped by `turn.stop`; otherwise `crash` (`Last-Error` — the `error` message or «код выхода N»); the turn ended under a stop — `Turn-Stopped: 1`. **Roll back only by the exit code**: `crash`/`interrupted` → the next supervisor `wait` with `ROLLBACK`; `ok` → no (the batch the model got with its own `wait` during the turn is `Pending`, the next `wait` acknowledges it). **A tail `wait`** (the model's commands live in their own groups and may outlive the turn): the agent's `wait` is alive, or `run/wait/<agent>.last` changed during the turn and is ≥ `Turn-End` → `ROLLBACK`. The supervisor remembers the value of `.last` before the turn: the supervisor's own `wait` finishes a moment before the turn, and with a turn shorter than a second its `.last` would equal `Turn-End` — without this check the batch would come again and again. The first crash of a series (the transition to `Hold: 1`) — a system message to the lead (the task channel, `Wake: <lead>`; if the lead is the agent itself or there is no task — `To: human` into the task channel or `lobby`: a message "to all" would come into the crashed agent's own prompt): `opencode-3 (запущен brg, S003): ход N упал — <ошибка>. Разбудит следующее сообщение ему или «Разбудить» на доске`; the next crashes of the series — the board only; the series ends with the first successful turn (otherwise the lead and the crashed agent would wake each other in a circle). After the turn — extraction of the activity and tokens from the stream; the token export runs in the background, after the supervisor `wait` starts. **brg update:** between turns, the project's `VERSION` ≠ the supervisor's version → `exec … __spawn S00N --continue` (the lock is "mine" by `$$`; no recovery; a pending rollback and FORCE are passed as arguments; while a background token export runs — after it).
4. **Waiting.** `State: frozen|crashed`. First the `rm`/`detach` flags. Then the supervisor starts, as its own child, `brg wait --as <full name> --timeout <spawn.wait_timeout>` with `BRG_SPAWN_WAIT=<result file>`, `BRG_SPAWN_ID`, and when needed `BRG_SPAWN_HOLD=1` (`Hold: 1`), `BRG_SPAWN_FORCE=1` (`wake`, a stop lifted), `BRG_SPAWN_ROLLBACK=1`; stdout is the prompt. The result: `msg|deadline|pause_end|force` → a turn (if a `detach`/`rm` flag lies there, the supervisor itself does `cursor_rollback` and handles the flag; `wake` — remove it and a reason line); `flag:rm|detach` → items 6, 7; `timeout`, `epipe` → wait again; `stop` → `State: stopped`, polling once a second; the stop lifted and `Turn-Stopped: 1` → `wait` with FORCE and the line «── стоп снят человеком: проверь status; есть начатая работа — продолжай, нет — заверши ход», otherwise an ordinary `wait`; `left` → `removed`, exit; `superseded` (another `wait` is alive under the name, usually a turn's tail) → `wait` again with `ROLLBACK`, ≥ 3 times within 60 s — `State: conflict` and retries every 30 s; `orphan|int|hup|term` and anything else → again, after a pause. **No result file** (`wait` failed through `die` or was killed) → the next `wait` with `ROLLBACK`; a profile with `Left:` → `removed`; the profile's key ≠ the key the `wait` was started with, or no `Spawn:` → `detached`; otherwise `Last-Error` from the `wait`'s stderr and a pause. **Hot-loop protection:** a `wait` that ended without a result or with an error faster than 2 s — a pause of 1, 2, 4, … ≤ 60 s.
5. **The wake-up prompt** = `── brg разбудил тебя (S003, ход N) — ты opencode-3.<ключ>` + the `wait` output as is (an empty FORCE — `── нового нет` and `NEXT:`). The key in the prompt is full (the agent needs it); on the board and in `spawn show` it is masked. The prompt is fed to the harness **through stdin**; the session — `--session <Session>`; `Session` is empty (the first turn failed before the first event) — the first prompt again plus the `wait` output.
6. **`rm`.** A turn is running → `turn.stop`, wait for the wrapper; then `leave` on the agent's behalf (a function shared with `brg leave`: roles, choosing the lead, messages), `State: removed`, exit. The supervisor is dead → `brg spawn rm` does this itself under the supervisor lock (an orphaned wrapper sees `turn.stop` by itself).
7. **`detach`.** A turn is running → wait for its end (do not stop it); `State: detached`, remove `Spawn:` from the profile, exit. `brg spawn detach` prints `cd <project> && opencode --session <Session>` and «напиши в окне: «продолжай: status, затем wait»»; the agent's `status` — «тебя забрали в окно: ход не завершай, цикл wait», `NEXT:` — an ordinary `wait`. The supervisor is dead → `brg spawn detach` itself, under the lock.
8. **`wake`** («Разбудить», `spawn wake`). The supervisor is waiting → its `wait` sees the flag and finishes at once in FORCE mode: everything after `Acked` (rolled back, quiet); empty — «── человек попросил продолжить: проверь status; есть работа — продолжай, нет — заверши ход». The supervisor removes `wake` before the next `wait` (otherwise FORCE in a circle), `Hold` is cleared. A turn is running — the flag is removed without action. A stop stands — the flag is not set: «бригада остановлена — сначала «Продолжить» (`brg resume`)». The supervisor is dead → a new supervisor (it takes the lock, or exits if the old one is alive): recovery, then a turn in FORCE mode.
9. **`rights`** — **does not wake.** The supervisor applies the flag at once, both while waiting and during a turn: `Rights` in the record, `Perm-Denied` is cleared, `Rights-Note` is written — a line about the rights change («── человек расширил права до full (вне каталога проекта и чтение .env — теперь можно): если тебе или твоему подагенту отказывали — можно повторить» / «── человек изменил права на project: вне каталога проекта и чтение .env — отказ»). The new rights act from the next turn (if a turn is running — from the end of the current one). `Rights-Note` goes into **every** wake-up prompt (as the first line after `── brg разбудил тебя …`); when composing the prompt the supervisor writes `Rights-Note-Turn: N`, and after an `ok` turn number N the line is cleared if the rights have not changed since (a rights change resets `Rights-Note-Turn`). So the line survives an abnormal turn, a supervisor restart and `exec`. Without a live supervisor `spawn rights` writes the same itself, under the lock. The output and the board: «права S001: full — со следующего хода; разбудить сейчас — «Разбудить»». Why it does not wake: a wake-up "repeat the action" would spend a turn for nothing when the refusal was a subagent's.

#### The supervisor `wait` (`BRG_SPAWN_WAIT`)

Only for a launched agent with a matching `BRG_SPAWN_ID`. `w_finish` writes the result into the file (tmp + `mv`); the output is as usual (it is the prompt). Every tick **before** the hand-out — the record's flags (read only): `wake` → FORCE on the same tick (`rights` does not wake); `rm`/`detach` → the result `flag:<name>` without a hand-out.
- **HOLD** (after a crash only something new wakes): the marks `H[channel]` are taken by the supervisor **at the moment of the crash, before the rollback** (`hold.marks`): this is the `Pending` of the agent's cursor in each listened channel — what the crashed turn saw. Everything the crashed turn did not see wakes — including a message that came during the turn or between the crash and the start of the wait; without new messages there are no turns ("the provider is down" does not spin: each next turn is on a new portion). The wait reads the marks (no file — it takes `seq` at the start); in `w_channels_init` (at the start and on a task change) for these channels `CH_SEEN := max(Acked, H)`, for new ones (a new task) — `CH_SEEN := Acked`. Only **new** waking mail wakes — including «новая задача» and «ты lead» (`task new` writes `tasks/active` before the messages), and everything after `Acked` is handed out. Deadlines do not wake by themselves in HOLD (as under a pause); lifting the pause wakes (`W_LIFT`) — one repeat on a human's action.
- **FORCE**: on the first tick hand out everything after `Acked`, even quiet and empty (the result `force`; empty — `── нового нет`); under a pause — like a wake-up by the human.
- **ROLLBACK** — before anything that may finish the wait (including before the STOP check), strictly in order: (1) read the pid file (the predecessor); (2) `w_claim`; (3) wait for the predecessor's death (`pid_alive`; a superseded `wait` exits on the nearest tick and finishes a hand-out it started; ≤ 5 s); (4) `cursor_rollback`; (5) `w_channels_init`. A batch handed out into nowhere by a tail, superseded or orphaned `wait` comes again, and there is no endless duplicate. A wait marks a rollback it did in the result file with a second line `rolled`; **the supervisor drops the wish to roll back only by it** (STOP and a missing result keep it), and FORCE only when the wait handed out a batch. **Any transition to `detached` rolls back:** the supervisor — if a rollback is still owed; `spawn detach` and `join --as` with a dead supervisor — always (the result of the last turn is unknown), after the agent has no live `wait`. The agent in the window gets a duplicate, but not a loss. `cursor_rollback NAME` — in all channels of the agent `Pending := Acked`.
- The metric is `wait … spawn=1` (the main wake-up metric, §11, not mixed with the supervisor's waiting). STOP, pause, deadlines, a task change — as for an ordinary `wait`. The test hook `BRG_TEST_DELIVER_DELAY` — a delay between the output and `cursor_write`.

**Accepted remainders.** A batch that a background `wait` handed out into a file **in the middle** of a turn and the model did not read is lost — as for an agent connected by hand (README: never run `brg wait` in the background). Deadline summaries handed out in a crashed turn are not returned by the rollback (the index is removed after the output, §8). On a rare path (a rollback after a successful turn, the turn and a tail `wait` in the same second) a duplicate of one batch is possible — no loss.

#### Per-turn feed, whose refusal, context, tokens

**Parsing events during the turn.** So that the board shows the feed during a long turn, while the wrapper is alive the supervisor, at most once every 3 s and only if `events.log` grew, parses the new bytes with the same awk program (with key masking) and accumulates the result in the turn's state file `turn.N.parse` (one record, tmp + `mv`): the **absolute** offsets of `events.log` and `stderr.log` up to which everything is parsed; the turn's `step_finish` sums; the last error (`error`); `Context`; the main session's refusals from the stream (their `input`) and the refusal lines from stderr; `Activity-Size` — the size of `activity.log` after appending this parse's lines. The last non-empty text — in `turn.N.text`. The turn's result (`ok`/`crash`, the crash text — the provider's message, not «код выхода N», the last text, refusals) is summed up by `sv_turn_end` from `turn.N.parse` and the parse of the remainder.
- **Only complete lines:** measure the size `S` (`wc -c`); the chunk — `tail -c +$((off + 1)) | head -c $((S - off))` (what is appended after the measurement does not get in); the last byte `x=$(tail -c +$S … | head -c 1)` — an empty `x` ⇔ the chunk ends with `\n`; if not, awk skips the last record; awk returns the number of bytes consumed — the sum of `length($0) + 1` of the parsed records (under `LC_ALL=C` these are bytes). At **the end of the turn** the remainder is parsed whole, together with the last line without `\n` (the harness may have been killed mid-line; a broken JSON line is simply not recognised).
- **Write order** (a kill -9 of the supervisor — no duplicates and no losses): (1) append the lines to `activity.log`; (2) atomically write `turn.N.parse` with the new offsets and `Activity-Size`. Before every parse (and on recovery): `activity.log` longer than the saved `Activity-Size` — truncate it to that (`head -c N >tmp && mv`) and parse from the saved offsets. Then `activity.tail`.
- On an intermediate parse the spawn record is rewritten only if its fields changed (`Session`, `Context`, live tokens, the last text, `Last-Event`). The price — one `awk` every ≥ 3 s per running turn and only when the log grows; the board tick starts no new processes.
- **Tokens without double counting:** `stream.tok` keeps the number of the last counted turn, `sv_turn_end` adds a turn only if its number is greater (a repeat after kill -9 does not double it); likewise the feed's `end` line and the crash message to the lead — one per turn (markers `turn.N.ended`, `turn.N.notified`, taken with `noclobber`). **Live tokens** during a turn — `stream.tok` + the sums of `turn.N.parse` (the main session) + subagents from the last export; after the turn, when the export has come, — its total plus the stream after the export **started** (`stream.tok` is snapshotted at the start: a turn that passed while the export ran is not lost). The lines the supervisor writes into the feed itself during a turn (a rights change, the end of the turn) update `Activity-Size` too — otherwise the next parse or a recovery would cut them as a kill -9 remainder.
- `Last-Event` is reset at the start of a turn.

**Whose rights refusal — a heuristic.** A refusal of the main session is visible in the stream: a `tool_use` of the main session with `status: "error"` and «request was rejected». The stderr line `permission requested: <action> (<resources>); auto-rejecting` is printed for any session, including a subagent's, and **before** the `tool_use` event. So the classification is done **at the end of the turn**, over all refusals of the turn: a stderr line whose resource (without a trailing `/*`) is a substring of the `input` of a refused `tool_use` of the main session (or the other way round) is the **agent's** refusal, and each such `tool_use` closes one line; unmatched lines go by count: as many as there are unmatched refusals of the main session left are the agent's, the rest — «(подагент)». In the record `Perm-Denied: <action> (<resources>)` or `… (подагент)`; on the board and in `spawn show|list` — «отказ в правах: …» / «отказ в правах (подагент): …». During a turn the feed's `permission` line is written at once, without the "whose" mark. This is a heuristic: matching is by path inclusion, so a wide resource (for example, `/Users/x/*`) may attribute a subagent's refusal under the same path to the agent; with several refusals with similar paths the mark may be wrong.

**Context and tokens.** `Context` — as OpenCode counts it: `input + output + reasoning + cache.read + cache.write` of the main session's last `step_finish` with non-zero tokens (an error step with zeros does not reset it); subagents are not included. `Tokens-Main-In|Out` and `Tokens-Sub-In|Out`: source `export` — the main session and the sum of the child ones separately; `stream` — only the main one (subagents are unknown, not shown). `Tokens-In|Out` — the sum (compatibility). **Cost** is shown only if `Cost > 0` (a provider without prices gives `0`; «$0.0000» is not written). `Last-Text-Turn` — the number of the turn of the last text: on the board «последний ответ (ход N[, идёт])».

#### First prompt, rights, activity and tokens

**The first prompt** — a short text in `bin/brg` (the name with the key, S, the rights and their meaning, the human's `--note`) + the join output: «Окна у тебя нет: человек видит только `send --to human` и доску… `join` уже сделан… Когда свободен — заверши ход… Работает подагент — ход не завершай, жди в `wait --busy`… `brg wait` никогда не запускай в фоне».

**Rights** — by what OpenCode really does: `full` (default) → `--auto`: «агент может всё, что можешь ты, в том числе вне каталога проекта и чтение `.env`»; `project` → without `--auto`: «правила OpenCode по умолчанию: в проекте можно всё — любые команды, правки, сеть, git push; вне проекта и `.env` — отказ». There is no real restriction inside the project (§12). The `spawn` output and the board state the meaning verbatim. **The refusal is visible:** after the turn the supervisor looks in the turn's stderr for `permission requested: … auto-rejecting` (ANSI is stripped), the fallback sign — a `tool_use` with `"status":"error"` and «request was rejected»; found → a `permission` line in activity, `Last-Error`, on the board — «отказ в правах: <что>» and the button «дать полные права».

**Activity** — one awk program over the turn's events (`events.log` from the remembered offset): activity lines (`tool` — the name and `input.command|filePath|pattern|description`, up to 200 bytes; `text` — the first 200 bytes; `error`), `sessionID`, the sum of tokens and cost of `step_finish`, the last text, ids of child sessions from the `task` output (both kinds). JSON — by regular expressions per line, without jq; unknown events are skipped (if the format changes, the display is lost, not the work). **Key masking** — in the same place: `<harness>-<n>.` + six characters `[a-z2-9]` not followed by `[a-z0-9]` → `<name>.<3 chars>…` (six classes in a row, without `{6}` intervals — mawk does not understand them); it covers activity, the last text, `prompt.head`, the output of `spawn show|list`. The board shows «последний завершённый шаг» and «нет событий K мин», without promising «сейчас делает»: a running tool is not visible in the stream.

**Tokens.** After the turn, in the background: `"$bin" session export <spawn.opencode.args> <id>` as its own child (`$!` is OpenCode itself, not a pipeline), a timeout of 20 s — SIGINT, then TERM; from the file — only `head -c 2048 | tr -d '\n '` and a regular expression for `cost`/`tokens` (the full output of a big export through a pipe may break off). **Only with `--standalone`** — otherwise the export starts a background OpenCode service on the human's machine. The main session and all child ones (`children`) are counted separately and summed → `Tokens-*`, `Cost`, `Tokens-Source: export`, `Sub-Sessions`; a child one is not exported again if its total has not changed for 2 turns in a row and its id did not appear again in this turn's `task` output. The export failed or is off (`spawn.opencode.export: 0`) — the sum of the main session's `step_finish`, `Tokens-Source: stream`: the board honestly labels it «без подагентов».

**Settings** (`config`): `spawn.opencode.bin` (`opencode`), `spawn.opencode.args` (`--standalone`), `spawn.opencode.export` (1), `spawn.wait_timeout` (3600), `spawn_stale` (30). The `spawn.*` values are raw (a path, several arguments separated by spaces); the other keys are numbers (§5.1). Test hooks: `BRG_SPAWN_STEP` (the sleep step of the supervisor and the wrapper, 1 s by default), `BRG_SPAWN_TEST_MAXLIFE` (the supervisor and the wrapper exit by themselves after N s or when the project directory disappears), `BRG_SPAWN_EXPORT_TIMEOUT` (the export timeout, 20 s by default), `BRG_SPAWN_TEST_DELAY_PARSE` / `BRG_SPAWN_TEST_DELAY_TOK` (a pause between the appends to `activity.log` and `turn.N.parse` / between `stream.tok` and the turn's result — the kill -9 tests at these points), `BRG_SPAWN_TEST_DELAY_END` (a pause between the line «конец хода» and the result in the record). The export, like the turn's harness, is started under `set -m`: a background command without job control would get SIGINT = SIG_IGN, and the timeout could not interrupt it in an orderly way.

## 6. Tasks

**(the human's decision)** A project has one active task; all joined agents are its participants (implicit membership). Storage is per task, so that parallel tasks with explicit membership would not need a migration.

- `task new --as X --title "…"` + the brief (verbatim from the human → `brief.md`) → `T00N[-<slug>]`, Lead = X (the author), «новая задача» in `lobby`. There is an active one — refusal, or `--cancel-current` (the current one is cancelled); technically it is available to any agent, PROTOCOL recommends it only if the human said to drop the current task. **(the human's decision)** An agent's `task new` under the general stop or the general pause, and also under the author's own stop or pause, refuses (the banner as the first line, as for commands that start work, §9; the check comes before everything, `--cancel-current` does not cancel the current task): only the human lifts these flags. The hint for the lead: general ones — «попроси человека: `brg resume`, `task new --as human` или доска»; own ones — «`brg resume <имя>`» (for a stop — also `say --to <name>`). Other agents' personal stops and pauses do not get in the way and are not lifted.
- **`task new --as human`** — the human gives the task directly, without an agent's chat (from the terminal; from the browser — with the same call): §6.2.
- Switching: every agent's wait notices the change of `tasks/active` on the nearest tick and listens to the new task. From past tasks only `common/` carries over (a PROTOCOL recommendation).
- `task close --as <lead> [--force]`: a non-empty `summary.md` is always required (its first line is the result in `common/history.md`); refusal while there are `claimed` items or runs in progress (`--force` cancels and stops them). Review is not required (§1 item 7; otherwise a dead end with a single agent).
- **Unread mail before closing — "a refusal is a delivery" (the human's decision).** Right after the "you are the lead" check and **before** the `summary.md` check (the lead must see the messages before writing the result) close looks for what would wake the lead's wait: in its channels (`lobby`, the task, the undrained finished ones — as for wait) after `Pending` there is something that wakes (`FMT_WAKE` > 0: messages to it or to all, including personal system ones — a `run` result, reviews, handed-in items). Quiet system messages (join/leave/claim) and its own do not get in the way; deadline summaries (§8) are not counted — they come to the wait. Found — close prints on stdout everything for the lead after `Pending` (quiet ones too), like wait, with the `wait_output_max` cap; after the output it moves `Pending` to the last one shown (does not touch `Acked`) and refuses: «учти их (при необходимости поправь summary.md) и повтори task close». The hint is to repeat `close`, not `read`: `read` does not move the cursor, a refusal "read it" would loop. A repeat passes if there is nothing new; with the cap — several refusals in a row, each moves `Pending`. `--force` does not bypass the check (what was shown is already delivered — the repeat passes). The next wait acknowledges what was shown (`Acked := Pending`) and does not hand it out again; a race with the lead's background wait (it keeps the cursors in memory) gives not a loss but at most a duplicate — at-least-once.
- `task cancel --as <lead|human>`: `claimed` → `cancelled`, reservations and runs are removed, everyone gets «прекрати правки»; unfinished edits stay in the working tree — their fate is decided by the lead of the new task or the human. The human cancels only with an explicit `--as human`: an agent that forgot `--as` will not cancel the task "on the human's behalf".
- `common/history.md` — a line on closing and on cancelling. Statuses: `active`, `done`, `cancelled`; work phases exist only in the recommendations. The events "new / closed / cancelled" go to `lobby`, a lead change — to the task channel (the lead leaving — to `lobby`); one cannot write to the channel of a finished task.
- **Drain:** having stopped listening to a closed or cancelled task, a wait first hands out its undelivered addressed messages (`── T001 (закрыта)`) — the lead's final word is not lost.
- Cursors of a task channel: those who existed when it was created read from the beginning, those who joined midway — from the end (history — `read --channel T00N --since 0`); `join --as` after `leave` — from the end, without the conversation of tasks finished during the absence. Message numbering is separate in each channel, `--re` refers to the selected one.

### 6.1 Roles

**(the human's decision)** There is one role — **lead**: the facilitator (§1 item 8) **and** the link to the human (questions, reports, the result). There is no host role (the one the human gave the task to and who writes to the human): with it, questions to the human came from one window while decisions were made in another; with the board and the browser the tie to a chat is rarely needed. To show the human something in the chat (a picture, a file) — the lead's window.

- **The lead** collects proposals, records agreements, settles a dispute if the brigade did not agree. It is also the only one who addresses the human on its own: it writes in its chat **and** the same text via `send --to human` (visible on the board — when the task was given from the board, this is the main channel); a question — also with `--ask` (§9.2); the others answer if the human wrote to them directly. The task record: `Host:` is not written; for old tasks it is read and ignored.
- **There is always a lead.** Choice — §6.2. The lead leaving (`leave`): at once, under the `task` lock, the same deterministic choice among those still online (§6.2, steps 2–3, the one who left excluded); the message in `lobby` («X отключился (был lead задачи T00N — lead теперь Y …)») wakes everyone, and the line «lead задачи T00N: X → Y (X отключился)» in the task channel (`Wake: no`, no double wake-up) is there so that the change is visible in the task conversation on the board; nobody online — `Lead:` is empty («lead — нет (назначится первому, кто выйдет на связь)» in `who`, `task show|list`, `status`, `history.md` and on the board), and then the first one who shows up takes it (self-assignment, §6.2).
- `lead give <name>` — only the current lead, not to a `gone` agent; `lead take` — only if the current lead is `asleep`/`gone` or there is none. **The human** appoints the lead at any moment: `lead give <name> --as human` — a separate branch without `need_agent`, `touch_seen`, `NEXT:`; the rule "only the current lead" does not apply to it; the target — not `gone`; a task without a lead — allowed too; already lead — «уже lead», no message; a system message `From: human` into the task channel wakes everyone (also under a pause). Agents may agree on another lead — self-organisation without the dead end "there is no lead".
- `host give|take` — refusal «роли host больше нет: связь с человеком — у lead'а» with the hint `lead give|take` and `NEXT:`.
- `send --to human` is not just a copy for the record: the board shows such a message, and when the task was given from the board, it is the lead's main channel to the human (the harness chat is a channel too, PROTOCOL, section 2 item 3).

### 6.2 A task from the human; choosing the lead

**(the human's decision)** The human gives a task directly: `brg task new --as human --title "…" [--cancel-current] [--file F] < постановка` — from the terminal (the serverless way) and from the browser (the «Новая задача» button on the board with a server, §9.1: the same call). A separate branch, like `task cancel --as human`: without `need_agent`, `touch_seen` and `NEXT:`; `Created-By: human`. It lifts the general stop and the general pause (does not touch personal ones; the stop lifted — «остановленные агенты завершили ход — напиши им «продолжай»»). For an agent, `task new` makes the author the lead.

- **Choosing the lead** (deterministic, under the `task` lock):
  1. the lead of the last task (the highest number, any status), if it is **online**;
  2. otherwise — an agent online: first the free ones (without a valid busy mark, §5.4), then the busy ones; on a tie — the one who joined earlier (`Joined-Epoch`, then the name);
  3. nobody online — the task has no lead (`Lead:` empty), self-assignment below.
  
  **"Online"** = `waiting`, **or** `working` without «не на связи» (between two `wait`s: the last presence in the `wait` cycle no further back than the `wait` timeout + 60 s — without it a former lead that answered in this very minute would be skipped by chance). `asleep`/`gone` — not online. Agents with a personal pause or a personal stop are skipped (the former lead too: it is not given a task it cannot start). With `--cancel-current` busyness is judged **before** the current task is cancelled (after that all marks are invalid). **Under the general stop nobody is online** (the stop ended everyone's turn, although their `wait`s finished seconds ago and by `agent_state` they are `working`): the lead stays empty — both for `task new --as human` (the stop is lifted after the choice) and on the lead's `leave`; the first agent to come back becomes the lead by itself.
- **Self-assignment with an empty `Lead:`** — in `wait` (at the start, after the STOP check, before writing the pid file; and on a change of the active task in the loop — otherwise an agent whose `wait` started a moment before `task new --as human` would not become lead until the end of that `wait`), in `join` (after writing the cursors: the message lands after them and comes to its first `wait`) and `lead take`. A double check: a read without the lock, the `task` lock only with an empty `Lead`, a repeated check under it: of two simultaneous `wait`s one wins. Not for an agent with a personal pause or a personal stop (after `resume` its next `wait` assigns it), and not under the general stop either. The notice is an ordinary message `From: brg`, `To: all`, into the task channel: «X — lead задачи T00N (назначен brg: первый на связи). X: постановка — brief.md; начни с PROTOCOL.md, раздел 4…»; X itself gets it through its own delivery (`From: X` would not do: one's own messages are not delivered). Under a general pause it, like any message not from the human, wakes nobody — the new lead learns about the role after the pause is lifted.
- **Messages of `task new --as human`:** in `lobby` — `From: human`, «новая задача T00N от человека: «…» · lead: X» (or «lead: нет — назначится первому, кто выйдет на связь») — wakes everyone; to the lead personally, into the task channel (everyone reads it from the beginning) — «ты lead задачи T00N (назначил brg): прочитай постановку…; человек дал задачу не в твоём чате — он смотрит доску: вопросы ему — `send --to human --ask`, отчёты — `send --to human`».

## 7. Подзадачи и код

### 7.1 Подзадачи

- `item add` → `I00N` (`todo`); `--paths` — предлагаемые пути (`Paths-Hint`).
- `item claim I00N [--paths …|none]` — атомарно. Пути надо назвать (`--paths` или подсказка из `add`) либо сказать `none` (исследование, ревью) — резервирование не забудется случайно. Пересечение с чужим резервированием → отказ со списком конфликтов. Повторный `claim` своей меняет пути.
- Пересечение со **своим** резервированием (другая своя подзадача в работе) — не отказ, а предупреждение после взятия: «эти пути уже твои по I001 …; если I001 брал не ты — под твоим именем работает другая сессия: сообщи lead'у и человеку». Так всплывает двойник под одним именем (§3). Без предупреждения: `--paths none` и пересечение подзадачи с самой собой при повторном `claim`; `.` пересекается со всеми своими — так и задумано.
- `item done` — только исполнитель (`--note`, `--result <путь>`); снимает резервирование.
- `item release` (в `todo`) — исполнитель, или lead, если исполнитель `asleep`/`gone`. `item reassign --to <имя>` — lead, только если исполнитель `asleep`/`gone` и новый не `gone`; резервирование переходит новому. Так же передаются правки сданной подзадачи (стадия «правки», §7.1.1).
- `item review --verdict ok|changes|skip` — для `claimed` или `done`; `ok`/`changes` — ревью: своё исполнитель писать не может; ревьюер той же модели, что исполнитель, при онлайн-агенте другой модели — предупреждение, не отказ. `skip` — решение «проверка не нужна» (§7.1.1). Записи ревью неизменяемы.
- Все изменения подзадач — под локом задачи (claim не проскочит в закрывающуюся задачу).

### 7.1.1 Проверка и стадии подзадачи

**(решение человека, 0.5.0)** Как работать с подзадачей — проверять ли, кем, в каком порядке, передумать по ходу — решает бригада: проверка другим участником — рекомендация (PROTOCOL, раздел 3), не правило. Обязательно одно (PROTOCOL, раздел 2): **стадия подзадачи в brg соответствует тому, что происходит**, — человек следит за работой по доске (§9.1). Поэтому brg даёт гибкие инструменты на каждый случай, а переводят подзадачи сами агенты. brg порядок не навязывает: `task close` не отказывает из-за непроверенных, только перечисляет их.

| Ситуация | Команда | Стадия (доска) |
|---|---|---|
| взял | `item claim` | в работе |
| бросил | `item release` | todo |
| сдал, проверка нужна (по умолчанию) | `item done` | на проверке |
| взялся проверять | `item review --start` | на проверке · проверяет X |
| проверил | `item review --verdict ok` / `changes` | готово / правки |
| правки | `item claim` (исполнитель) → `item done` | в работе → на проверке |
| проверка не нужна — решили заранее | `item add --no-review` | после сдачи — готово · без проверки |
| … при сдаче | `item done --no-review` | готово · без проверки |
| … передумали после сдачи (на проверке, правки) | `item review --verdict skip [--comment "почему"]` | готово · без проверки |
| передумали: проверка нужна | `item review --start` (тот, кто проверит) | на проверке |
| переделать сданное (в т.ч. принятое) | `item claim` (исполнитель) | в работе |
| подзадача не нужна | `item cancel [--comment "почему"]` | отменено |
| свой порядок (отдельная подзадача-ревью, парная работа, …) | итог отметить командами выше | — |

- `item add --no-review` → заголовок `Review: no`. Исключение `--paths none` (раньше исследование не считалось ждущим ревью) снято.
- `item done` пишет `Done-Reviews: N` — сколько записей ревью было на момент сдачи (так ревью «после сдачи» отличается от ревью «до неё», без сравнения времени). `item done --no-review` — сдача и сразу запись ревью `skip` от исполнителя (комментарий — «при сдаче»), одно системное сообщение.
- **Вердикты** `item review --verdict`: `ok`, `changes` — ревью; свою подзадачу так не проверить; при той же модели, что у исполнителя, — предупреждение (§7.1). `skip` — решение «проверка не нужна»: может записать любой участник, и исполнитель тоже (решение бригады, а не ревью); комментарий необязателен, stdin без `--comment`/`--file` не ждёт. Все вердикты — неизменяемые записи ревью (история на доске). Любой вердикт по `done` очищает `Reviewing:` целиком — круг проверки закончен (кто ещё проверяет — снова `--start`); остальным проверяющим (кроме автора вердикта) — системное сообщение, будящее только их (`Wake: <имена>`): «круг проверки I00N закрыт вердиктом X от Y — вас больше нет среди проверяющих; продолжаете проверку — повторите `item review I00N --start`; не нужна — дайте подагенту закончить, затем wait без --busy». Их пометки «проверка I00N» не снимаются (подагент может ещё работать), и их `wait --busy "проверка I00N"` пометку сохраняет (§5.4). По `claimed` — убирает только автора, остальным ничего не шлёт.
- `item review I00N --start` — «взялся проверять»: имя — в `Reviewing:` (через запятую, без повторов), тихое системное сообщение всем (как `claim`). Подзадача `claimed` или `done`, не исполнитель; при стопе — отказ (начинает работу, §9); вместе с `--verdict` и текстом нельзя; stdin не читается; повторный `--start` того же — без дубля и без сообщения; предупреждение о той же модели — уже здесь.
- **Вернуть в работу** — `item claim I00N` исполнителем из `done` в любой стадии: правки после `changes`, переделка принятого или сданного без проверки, отзыв подзадачи с проверки. Пути по умолчанию — прежние (`Paths`), пересечения проверяются как у обычного `claim`; `Claimed`/`Claimed-Epoch` — заново; `Done`, `Done-Reviews`, `Note`, `Result`, `Reviewing` очищаются (прежняя сдача остаётся в переписке); системное сообщение будит lead'а. Чужую сданную подзадачу так не взять (отказ называет стадию и последний вердикт); исполнитель `asleep`/`gone` — lead передаёт правки `item reassign` (подзадача становится `claimed` у нового исполнителя с прежними путями). `item done` на подзадаче в стадии «правки» отказывает с подсказкой `item claim`.
- `item reassign` убирает нового исполнителя из `Reviewing:`; `item release` очищает `Reviewing:`.
- `item cancel I00N [--comment "почему"]` → `cancelled` (+ `Cancelled`, `Cancelled-By`): `todo` — любой участник; `claimed`/`done` — исполнитель или lead. Снимает резервирование и `Reviewing:`; системное сообщение будит lead'а и исполнителя (кроме автора). При стопе разрешена (не начинает работу). Из `cancelled` не возвращается — нужна снова: новая подзадача.
- **Стадия** — одно правило для `wait`, `item list|show`, `status`, `task close` и доски (bash `item_stage_v` и JS страницы — одинаково, включая нештатные значения). `todo`, `claimed` (в работе), `cancelled` — как есть. Для `done`: n — число записей ревью (файлы с числовым именем), последнее — с наибольшим номером, d — `Done-Reviews` (нет — 0); вердикт последнего: `skip` — всегда «готово · без проверки» (решение, а не ревью); `changes` и любой другой (`ok`, нештатный) — как ниже:
  - n > d (вердикт после сдачи): `changes` → **правки** (на доске — в колонке «в работе», красной пометкой), иначе → **готово**;
  - 0 < n ≤ d (сдана после последнего вердикта): → **на проверке** — `changes`: пересдана после правок; `ok`: сдана после ревью — работа могла измениться (ревью в работе, переделка принятой), нужна новая проверка;
  - n = 0: `Review: no` (точно) → **готово · без проверки**, иначе → **на проверке**;
  - «готово» (в т.ч. без проверки) при непустом `Reviewing:` → **на проверке** (кто-то проверяет — значит, проверка идёт: так работает «передумали, проверка нужна»).
  - `claimed`, у которой последний вердикт — `changes`, — «в работе · правки по ревью».
- **Где видно.** Сводка `wait` (§5): `… · в работе I001 codex-1 · на проверке I003 (claude-2), I005 · правки I004 codex-1 · готово I002 · …` («(имена)» — из `Reviewing:`; было «ревью ждут»). `item list` — стадия в строке и в итоговом счётчике; `item show` — стадия, проверяющие, «без проверки» и кто решил. Каждое сообщение и вывод команды подзадачи называет стадию, в которую она перешла (например, ok после чужого `changes` без пересдачи: «правки не нужны — I00N готова»). `task close` перечисляет непринятые — «не приняты: I003 (на проверке), I005 (правки)» — предупреждением, не отказом.

### 7.2 Резервирования путей

- Пути от корня проекта, через запятую; нормализуются (`\` → `/`, без `./`, `//`, хвостового `/`; `.` — весь проект). Запрещены `..`, абсолютные пути, `~`, маски, управляющие символы. Без глобов — детерминированно и просто в bash.
- Пересечение — префикс по границе компонента (`src` и `src/a` — да, `src/a` и `src/ab` — нет), **без учёта регистра** (ФС macOS и Windows; на Linux возможны ложные конфликты — сознательно консервативно). **(решение человека)** Регистр сводится для ASCII `A–Z` и русской кириллицы (`А–Я`, `Ё` ↔ `а–я`, `ё`: 33 пары двухбайтовых литералов в awk под `LC_ALL=C`): `Данные` и `данные` конфликтуют, `Данные` и `Дорога` — нет. Другие буквы (`É`, другие алфавиты) и формы NFC/NFD (`й` двумя кодовыми точками) не сводятся (§12).
- Резервирование действует, пока подзадача `claimed` этим агентом (остаток после падения игнорируется); снимается `done`, `release`, закрытием и отменой задачи.
- Защищает только тех, кто им пользуется: brg правки файлов не отслеживает.
- Резервирования охраняют только запись. Чтение в общем дереве brg не ограничивает и не проверяет (§1: одна ФС, без защиты от агента): условие постановки вида «не читать чужое до раскрытия» — лишь договорённость. PROTOCOL рекомендует lead'у сразу назвать такое условие человеку непроверяемым и предложить проверяемую рамку (работа вне общего дерева до раскрытия, раскрытие по договорённости).

### 7.3 `brg run`

Тесты, сборка, линтеры — под глобальной блокировкой: не гонять тесты на полуотредактированных файлах соседа. **По умолчанию в фоне**: агент сразу получает `R00N` и место в очереди, результат (статус, код, хвост лога, путь к логу) приходит инициатору системным сообщением — долгие операции не упираются в лимит команды харнесса и встраиваются в механику «всё — сообщения».

- Только при активной задаче; создаётся под её локом (нет гонки с `close`). `--item I00N`, `--timeout` (по умолчанию `run_timeout`, 30 мин). Одна строка-аргумент — через `bash -c`, несколько — как есть; cwd — корень проекта.
- Очередь `run/execq/` в порядке запросов; голова запускается, захватив `run/locks/exec.lock`. Он держится всю команду и **не ломается по возрасту** — только по смерти владельца (подтверждённой heartbeat, см. ниже) или устаревшему heartbeat.
- Раннер — `nohup` под `set -m`, все fd перенаправлены (харнесс его не ждёт); команда — в своей группе процессов, после неё остатки группы добиваются; таймаут или отмена — TERM группе, через 5 с KILL. Статусы: `queued`, `running`, `done`, `failed`, `timeout`, `killed`, `cancelled`. Результат — сообщение `From: brg` инициатору в канал задачи (задача уже завершена — в `lobby`), ровно один раз.
- `--sync` — для коротких команд: ждёт на месте не дольше `wait_timeout` агента (`--timeout` больше — отказ), код выхода — код команды; не уложилась (в т.ч. из-за очереди) — результат придёт сообщением. Раннер, закончив, даёт ещё ждущему синхронному вызывающему до 3 с напечатать результат самому; недоступный pid вызывающего (EPERM) считается живым — тогда отдельное сообщение уходит с задержкой до 3 с (допустимо).
- `run cancel R00N` — инициатор или lead, через файл-флаг (без сигналов чужим pid).
- **Heartbeat раннера** — раз в секунду. Живой pid (в т.ч. недоступный, EPERM) с молчащим heartbeat объявляет мёртвым только ждущий раннер, непрерывно наблюдавший молчание дольше `runner_stale` (60 с, > `lock_stale`); провал времени у наблюдателя (сон ноутбука, SIGSTOP) сбрасывает отсчёт. «Оживший» раннер, у которого забрали лок или закрыли прогон, убивает свою команду и не перезаписывает вердикт (край: до ~1 с его команда может идти параллельно с командой победителя).
- **Мёртвый pid раннера — ещё не смерть:** в pid-namespace песочницы живой процесс может отвечать ESRCH. Раннер мёртв, только если (1) pid мёртв (`pid_alive`, §4.2), (2) его heartbeat (exec-лок или запись очереди) старше `runner_dead_grace` (5 с; 0 — верить одному pid) и (3) судящий ждущий раннер наблюдал без провала не меньше `runner_dead_grace` (провал дольше grace/2, но не меньше 2 с, сбрасывает отсчёт: после сна heartbeat у всех старый). Этот отсчёт отдельный от отсчёта `runner_stale` (тот сбрасывает провал дольше runner_stale/2, от 2 до 10 с): короткие провалы на загруженной машине не откладывают вердикт `runner_stale`. Пока условия не выполнены, раннер с мёртвым pid судится как живой — по `runner_stale`, поэтому и частые провалы не повесят очередь. Раннер, убитый `kill -9`, снимается примерно через `runner_dead_grace`.
- Просмотр (`run show/list`, `status`, `task close/cancel`, `run cancel`, `doctor` — разовые проверки, вердикт у всех один): pid раннера мёртв и heartbeat старше `runner_dead_grace` → `killed` (умерший только что — со следующего просмотра после grace; `run cancel` перепроверяет, пока ждёт); живой, но молчащий → «раннер не отвечает N с» (разовый вызов не отличит сон от зависания), `run cancel` закрывает и такой. Раннер убит `kill -9` → лок снимается; команда-сирота не убивается (сообщение предупреждает, pgid записан). **Остаток:** разовая проверка не наблюдает непрерывно (условия (3) нет) — в среде с ESRCH сразу после сна ноутбука, когда heartbeat у всех старый, она может отметить живой прогон `killed` (сам раннер, проснувшись, увидит вердикт и остановит команду).
- `task cancel`, `--cancel-current`, `close --force` останавливают прогоны задачи; их перечисляет сообщение о задаче, отдельных сообщений нет.

### 7.4 git

- Обязательно (PROTOCOL, §1 п. 7): не коммитить в `main`/`master` без разрешения человека. Рабочее дерево одно на всех: не переключать ветки и не трогать чужие незакоммиченные правки без договорённости (никаких `stash`, `reset`, `checkout`, `restore`, `clean` поверх них).
- Рекомендовано: одна ветка на задачу, её создаёт lead в начале, коммитит lead. У Codex `.git` может быть только для чтения — тогда сказать lead'у.
- **(решение человека)** Авторство (рекомендация PROTOCOL lead'у): автор коммита — из git config (человек: он отвечает за слияние), участники — трейлерами в конце сообщения коммита, по одному на каждого, кто внёс вклад, плюс номер задачи:

  Имя — базовое (без ключа), харнесс и модель — как в `who`. Email обязателен: без него GitHub трейлер не распознаёт; домен `.invalid` зарезервирован и никуда не ведёт. Запрет называть провайдеров и модели относится только к репозиторию brigada, не к проектам пользователей.
- brg сам git не вызывает (только находит git-каталог для `info/exclude`). Worktree на агента — отложено.

## 8. Дедлайны

`send … --reply-by 5m` (от 1 с до 24 ч). По сроку wait отправителя возвращается со сводкой `── дедлайн по #N (T001) истёк: ответили: …; не ответили: …` — детерминированная основа правила «молчание = согласие».

- `Expect` — адресаты на момент отправки (для `all` — все не-`gone`, кроме отправителя); их нет — дедлайн не ставится.
- Ответ — не системное сообщение адресата в том же канале после исходного: с `Re: <id>` **или** любое сообщение отправителю (лично или `all`) — модели забывают ставить `Re:`.
- Ответили все до срока — сводка приходит сразу, с пачкой последнего ответа (экономит пробуждение).
- Сводка выдаётся один раз: перед печатью атомарно создаётся маркер `<канал>-<id>.done`, индекс удаляется после вывода. Индекс остался через минуту после срока (репортёр умер) — сводка выдаётся повторно: дубль лучше потери.

## 9. Команды

Агентам: `join`, `leave`, `send`, `wait` (`--busy`: пометка «работает», §5.4), `busy` (пометка без ожидания), `read`, `status` (одноэкранная реориентация после сжатия: кто я, роль, задача, мои подзадачи и прогоны, непрочитанное, дедлайны, жив ли мой wait, NEXT), `who`, `task …`, `lead give|take`, `item …`, `run …`. Человеку: `init`, `board` (доска в браузере; с Python — с управлением, §9.1), `say` (от `human`; `--re N` — ответ на вопрос агента, §9.2), `tail [-f]`, `who`, `stop`, `pause`, `resume`, `task new --as human` и `task cancel --as human` (§6.2), `lead give <имя> --as human` (§6.1), `item list`, `run list`, `doctor`, `spawn` (§5.5, ниже). Агент передаёт в `--as` полное имя из своего `join` (с ключом, §3); команды чтения принимают и базовое, `stop`/`pause`/`resume` и имена-цели — базовое. `who` и `status` называют состояние словами «ждёт» (свободен) и «работает[: подпись]» (§5.2). Синтаксис — `brg help` и `brg <команда> --help`.

**Стоп.** `stop` ставит флаг `run/stopped` (`stop <имя>` — `run/stopped.<имя>`, в т.ч. для зачистки призраков). Пока флаг стоит, любой wait возвращает STOP **сразу** (агент, бывший в работе, не заблокируется снова); живые wait видят флаг на ближайшем тике — без сигналов, как и takeover. Флаг снимают `resume`, `say` (общий и названных адресатов) и `task new --as human` (общий); агентский `task new` при стопе отказывает (§6). Остановленные агенты завершили ход — после снятия стопа человек пишет им в чат «продолжай».

**(решение человека)** Стоп видит и агент, давно не звавший wait: любая команда с `--as` (общий стоп или стоп этого агента, по базовому имени) первой строкой stdout печатает `── STOP: …`. Кроме `wait` и `status` — они печатают STOP сами (без дубля). Команды, **начинающие работу**, — `item add|claim|reassign`, `item review --start`, запуск `run` и агентский `task new` (§6) — при стопе отказывают, `NEXT:` — «заверши ход» (не wait: иначе агент вернётся в цикл, а wait тут же вернёт STOP). Сдать сделанное и сообщить — можно: `send`, `item done|release|cancel`, `item review --verdict`, `task close|cancel`, `run cancel`, `lead give|take`, `busy` (пометка не начинает работу, §5.4), `leave`, команды чтения.

**Пауза (решение человека, 0.7.0).** Стоп завершает ход агента — «продолжай» ему приходится писать в его окне, а из браузера этого не сделать. Пауза мягче: `pause` ставит флаг `run/paused` (`pause <имя>` — `run/paused.<имя>`), агент **ход не завершает**, остаётся в `wait` и просыпается только от сообщений человека и снятия паузы (§5 п. 14); `resume` снимает и стопы, и паузы (без имени — все; с именем — только этого агента; общая пауза стоит, пока не вызван `resume` без имени, и `resume <имя>` при ней говорит об этом); из браузера — кнопкой «Продолжить» (доска с сервером, §9.1). `say` паузу **не** снимает (стоп снимает): человек может поговорить с бригадой на паузе. `task new --as human` снимает общую паузу; агентский `task new` на паузе (общей или своей) отказывает (§6).
- **Начинать работу нельзя.** Одна функция `work_refuse` на тех же местах, что стоп: `item add|claim|reassign`, `item review --start` при паузе отказывают (агентский `task new` — тоже, своей функцией, §6); `NEXT:` — `wait` (агент остаётся в цикле), текст называет, кто снимает паузу («`brg resume` или с доски; `say` её не снимает»). **`run` на паузе разрешён**: подагент проверяет начатую работу (`run --sync`), а подагент, работающий у участника, доводит своё — пауза его не останавливает, пометка «работает» (§5.4) остаётся как есть. Сдать сделанное можно (`send`, `item done|release|cancel`, `item review --verdict`, `task close`).
- **Баннер.** Первой строкой любой команды с `--as`: `── ПАУЗА: человек поставил на паузу <бригаду|тебя (имя)>. Новую работу не начинай; сдай сделанное и жди (wait).` У запущенного brg агента (§5.5) — по пометке «работает», как `next_wait`: свободен — «сдай сделанное и заверши ход — brg разбудит тебя…», действительная пометка (работает подагент) — «доведи начатое и жди в wait --busy (как в NEXT), ход не завершай»; так же — подсказка отказа `work_refuse`. Раз на процесс, STOP приоритетнее; `wait` и `status` сообщают о паузе сами (`status` — строкой в своём выводе, `wait` — строками пачки, §5 п. 14), `join` — предупреждением.
- **Показ.** `who` (строка «── ПАУЗА» при общей, «(пауза)» у состояния агента), `status`, `doctor` (флаги паузы рядом со стопами), доска (общая — плашка, личная — чип «пауза»), сводка `wait` («свободны» — без стоящих на паузе). Остановленный агент на доске — «остановлен — напиши «продолжай» в его окне (имя · префикс ключа…)» (§9.1); запущенный brg — «остановлен — снимется кнопкой «Продолжить»» (его будит надзор, §5.5).

**Запуск агентов (0.9.0, §5.5) — только человеку.** Отказ «запускает агентов только человек; попроси его: `send --to human --ask`» — при `--as <агент>`, а также при `BRG_SPAWN` или `OPENCODE_SESSION_ID` в окружении (по `CLAUDECODE`/`OPENCODE=1` — нет: человек может работать в терминале харнесса). В инструкциях агентам `spawn` не описывается, кроме «попроси человека».
- `brg spawn <harness> --model M [--rights full|project] [--count N] [--note "…"]` — проверки: `.brigada` есть; macOS/Linux; харнесс поддерживается (этап A — `opencode`); бинарь найден (`spawn.<h>.bin`); платформа как у подключённых (§3); `--model` — `[A-Za-z0-9][A-Za-z0-9._:/@#+-]{0,119}` (не с `-`); `--count` 1–9; `--note` — одна строка ≤ 200 байт. Стоит стоп — предупреждение «первый ход — после снятия стопа». Строка на агента: `S003 → opencode-3 (provider/model) запущен · права: full — <смысл>`. Возвращается сразу (надзор отвязан, все fd перенаправлены).
- `brg spawn list` — S, агент, харнесс/модель, права, состояние, ход, токены, стоимость, источник токенов, последняя ошибка (читают и агенты). `brg spawn show <S|имя>` — запись, 20 строк активности, пути логов; ключ замаскирован.
- `brg spawn wake|rm|detach <S|имя>`, `brg spawn rights <S|имя> full|project`; внутренние — `__spawn S00N [--continue]`, `__turn S00N N`.
- `who`/`status` — «(запущен brg, S003)» и состояние записи; `doctor` — раздел запусков: живые и мёртвые надзоры (по локу и `hb`), висящие обёртки, бинарь харнесса.

### 9.1 Доска

**(решение человека)** `brg board [--interval S] [--port P] [--bind ADDR] [--static] [--once]` — страница для человека: текущая задача и статус, бригада (состояние, lead, взятые подзадачи), канбан подзадач с ревью, прогоны, переписка (задача и `lobby`), постановка, план, итог, прошлые задачи. Без Python открывается как `file://` — без сервера и зависимостей, только просмотр. **(решение человека, 0.8.0)** С Python (≥ 3.8) `brg board` сам поднимает сервер человека (ниже), и на той же странице появляется управление: писать бригаде, отвечать на вопросы, давать задачу, назначать lead'а, ставить паузу и стоп.

- **Устройство.** `init` ставит `template/board.html` как `.brigada/board.html`. `board` раз в `S` с (по умолчанию 2, от 1 до 999999) пишет снимок в `run/board/` и работает на переднем плане до Ctrl+C; TERM/INT/HUP — удалить свой `.tmp` и выйти с кодом 0 (как `tail -f`). `--once` — один снимок (без сервера). Первая строка вывода — адрес: `http://127.0.0.1:ПОРТ/?t=ТОКЕН` при сервере (с `--bind IP` — `http://IP:ПОРТ/?t=ТОКЕН`, ниже), иначе `file://…` (пробел, `#`, `?`, `%` кодируются); через `brg.cmd` путь берётся из `BRG_VIA_CMD` (`C:\…` → `file:///C:/…`), Git Bash без него — `/c/…` → `file:///C:/…`; другие пути MSYS и WSL — подсказка «открой `.brigada/board.html` в браузере».
- **Снимок.** `run/board/data.js` = `window.BRG_BOARD = {…};` — `meta` (время, интервал, версия, проект, стоп, общая пауза), агенты (с флагами `stopped`, `paused`), все задачи (запись `task` + первая строка итога), lobby и **текущая задача** целиком (постановка, план, итог, подзадачи с ревью, прогоны, переписка). Текущая — активная, а если её нет — последняя (по номеру) закрытая или отменённая: сразу после `close` человек видит итог. Остальные завершённые задачи — кэш `run/board/T00N.js` (`(window.BRG_TASKS = window.BRG_TASKS || {})["T00N"] = {…};`), пишется один раз, когда задача «улеглась» (все прогоны в финальном статусе или закрыта больше 60 с назад; до того — переписывается каждый тик). `run/board/VERSION` не совпал с версией brg — кэш удаляется. Запись — tmp + `mv`; ошибка `mv` (Windows: файл держит браузер) не фатальна и печатается не чаще раза в минуту.
- **Снимок только читает.** Снимок и страница только читают; действия с доски при сервере — вызовы brg от имени человека, сервер сам состояние не пишет (ниже). `board` пишет только в `run/board/`: без блокировок, курсоров, Last-Seen, `metrics.log`, никого не будит; своя проверка «есть `.brigada`» без `mkdir` (не `need_root`), ошибки без `metric`. Прогоны не «досуживаются»: мёртвый или молчащий раннер показывается по разовой проверке (`run_health`) как «раннер мёртв» / «не отвечает N с», в `killed` его переводит brg при следующем просмотре (§7.3). Страница данные только показывает.
- **Экранирование.** `data.js` браузер выполняет: ошибка экранирования = исполнение текста сообщения как кода. Все данные (заголовки и тела записей, тексты, вычисленные строки) превращает в JSON одна awk-программа; на вход — список директив на stdin (данные — только через файлы и stdin, не `awk -v`: он разворачивает `\n` и `\\`). `\` и `"` — `gsub(/[\\"]/, "\\\\&")` (переносимо между BWK awk, gawk и mawk: `"\\\\"` в gawk дал бы одиночную черту); `\t`, `\r`, прочие `\001`–`\037`, `\177`, U+2028/2029 → `\t`, `\r`, `\u00XX`, `\u2028`/`\u2029` — циклом по совпадениям, только если они есть в строке (быстрый путь). NUL: BWK awk теряет его вместе с остатком строки, gawk может пропустить сырым (JS это переживает) — brg таких тел не пишет. Перевод строки в элементе списка директив (имя файла из glob, путь `.brigada`) заменяется на `?` — иначе он начал бы поддельную директиву; такой путь читается как отсутствующий. Страница вставляет данные только через `textContent`/`createElement`, тексты — `white-space: pre-wrap` (без markdown), ссылки — только внутренние.
- **Цена тика — O(1) процессов:** `date`, один awk на все файлы (переписка — последние 500 сообщений канала, отобранные glob'ом в bash), `tail` лога — только у идущего прогона (у завершённых — один раз за процесс). Объём `data.js` — до ~2 МБ: сверх — отбрасываются старые сообщения, `meta` говорит «показаны последние N из M»; постановка, план, итог и тела записей — до 64 КБ.
- **Страница** (`board.html`, один файл, без CDN): данные — классическим `<script charset="utf-8">` с `?<время>` раз в 2 с (старый тег удаляется); нет файла — «снимка ещё нет — запусти `brg board`»; снимок старше max(10 с, 3 × интервал) — «доска не обновляется». Раздел перерисовывается, только если изменился `JSON.stringify` его данных (прокрутка и раскрытое сохраняются); выбранная задача — в `location.hash`, прошлая подгружается из `T00N.js`. Дедлайны («ждём / ответили»), канбан, роли и длительности считает страница.
- **Вид (0.5.0, решение человека).** Задача — заголовок, статус, lead (пустой — «нет — назначится первому, кто выйдет на связь») и прогресс (готово / всего). Канбан — `todo` · «в работе» · «на проверке» · «готово» (+ «отменено», только если такие есть); стадия — по правилу §7.1.1; у закрытой или отменённой задачи колонка «на проверке» называется «не проверено». Карточка — номер и заголовок, кто делает (на проверке — кто проверяет из `Reviewing:` или «ждёт проверяющего»), время в стадии, пометки «правки по ревью от X», «без проверки» (и кто решил — `Review: no` или вердикт `skip`), «исполнитель выпал»; пути, описание, итог, ревью и прогоны подзадачи — свёрнуты. У каждого агента свой цвет, стабильный (по имени) и один на всей странице — бригада, карточки, переписка: кто что делает, видно с первого взгляда. Переписка — отдельные блоки с полосой цвета автора: шапка (автор → кому, «лично», ответ на #N с первой строкой цитируемого, время, дедлайн), длинное тело свёрнуто до ~12 строк; системные — компактной строкой; сообщения человека выделены. Бригада — компактная полоса: чип агента показывает **«ждёт»** (серый: свободен), **«остановлен — напиши «продолжай» в его окне (имя · префикс ключа…)»** (стоп человека завершил ход агента — флаг снимается и кнопкой, но «продолжай» агенту можно написать только в его окне), чип **«пауза»** (личная пауза, §9) либо **«работает · подпись · N мин»** (цвет агента; подпись и время — из пометки `mark` снимка, §5.4; без пометки — «работает», когда `working`); подпись, повторяющая подзадачу из списка его работы («делает I015», «проверяет I014»), опускается — остаётся «работает · 15 с · делает I015», подпись нужна только для работы вне списка («финальная проверка»), а у `working` без wait — ещё «не на связи N мин»; ушедшие (`gone`) без роли, подзадачи в работе и открытого вопроса не показываются — вместо них чип «ушли N» (имена — во всплывающей подсказке); пустые разделы не занимают места.
- **Пауза и стоп на странице (0.7.0).** Общая пауза — плашка «ПАУЗА» (`brg resume`), личная — чип «пауза» и строка «На паузе агенты: …»; общий стоп — плашка STOP с напоминанием, что остановленные агенты завершили ход; плашка «бригада простаивает» на паузе не показывается (простой — решение человека). Кнопки «Пауза» / «Продолжить» — в режиме с сервером (ниже).
- **Сервер человека (0.8.0, решение человека).** Необязательный `bin/brg-serve.py` (Python ≥ 3.8, stdlib; `init` ставит его в `.brigada/bin/`). Правило Python — §1 п. 4. Нет Python, нет файла, `--static`, `--once` или сервер не поднялся — доска как раньше (`file://`, только просмотр), с одной строкой причины («Python 3.8+ не найден — доска только для просмотра; отвечать — `brg say`»).
  - **Python ищет одна функция** (`py_find_v`; её же зовёт `doctor`): `BRG_PYTHON` (если задан — только он; голое имя — через PATH) → `type -P python3` (встроенная команда; Homebrew, python.org, pyenv, conda подходят) → на Windows (MSYS/Cygwin) `py -3`, `python3`, `python`. macOS: `/usr/bin/python3` — заглушка установщика Command Line Tools, поэтому берётся, только если есть хотя бы одно из `$DEVELOPER_DIR/usr/bin/python3`, `/var/db/xcode_select_link/usr/bin/python3`, `/Library/Developer/CommandLineTools/usr/bin/python3`, `/Applications/Xcode.app/Contents/Developer/usr/bin/python3`; иначе «Python нет» — ни `xcode-select`, ни заглушка не вызываются (диалог установки не всплывёт). Windows: кандидаты из `…\Microsoft\WindowsApps\` (заглушки Store) пропускаются. Проверка: `"$py" -I -c` — версия ≥ 3.8 и `sys.executable`; хранится **исполняемый файл** (не команда `py -3`) — им и запускается сервер, поэтому `$!` — сам Python. Python не найден — `brg board` пишет «Python 3.8+ не найден — доска только для просмотра …» с подсказкой `BRG_PYTHON=/путь/к/python3 brg board`; `BRG_PYTHON` задан, но не Python ≥ 3.8 — «BRG_PYTHON=… — не Python 3.8+».
  - **Запуск и родство.** bash — родитель: цикл снимка остаётся в `brg board`, сервер — его ребёнок (`"$py" -I -X utf8 …/bin/brg-serve.py --root <корень> --port P [--bind ADDR] --interval S --alive alive.<свой pid> --ready ready.<свой pid>`, в фоне, stdout/stderr — тот же терминал; на Windows `--root` в форме `C:/…`). Сигналы — только своему ребёнку (`$!`, не pid из файла): TERM/INT/HUP у `brg board` → TERM серверу, ожидание до 4 с, затем KILL. **Сердцебиение:** bash-цикл каждый тик пишет `run/board/alive.<свой pid>` (tmp + `mv`; свой файл у каждого `brg board` проекта — сервер смотрит только на файл своего родителя); сервер выходит, если файл старше max(15 с, 5 × interval) (на Windows `os.getppid()` не меняется со смертью родителя, а `kill` мог убить лаунчер `py.exe` — поэтому основной признак не родство, а файл); на Unix дополнительно — родитель сменился. Убитый `kill -9` `brg board` не оставляет сервер. **Тестовые крючки** (окружение сервера; в обычной работе не нужны): `BRG_SERVE_ALIVE_MAX` (предел возраста `alive`, с), `BRG_SERVE_NO_PPID` (не смотреть на смену родителя), `BRG_SERVE_TEST_TOKEN` — значения через запятую: `nolink` (создание токена без жёстких ссылок), `stall` (пауза победителя между созданием файла и записью), `race` (пауза 0,5 с после «токена нет» — оба первых запуска точно идут создавать), `BRG_SERVE_TEST_LISTEN=127.0.0.1` (0.9.2: сервер реально слушает loopback, а правила Host/Origin и строки brg следуют `--bind` — чтобы тесты не слушали сетевой адрес; действует **только** значение `127.0.0.1`, любое другое игнорируется: крючок может лишь сузить, но не расширить то, что слушается). **Рукопожатие:** у каждого `brg board` свой файл `run/board/ready.<свой pid>` (имя передаётся серверу `--ready`, как `--alive`: pid Python в MSYS не равен `$!`); bash удаляет его и запускает сервер; тот после `bind` создаёт токен (если нет) и атомарно пишет `port`, затем свой `ready.<pid>` (порт, pid[, занятый прежний порт]); bash опрашивает ≤ 5 с только свой файл, проверяя `kill -0 $!` (свой ребёнок). Адрес печатается только после `ready`. Сервер на выходе удаляет свой `ready.<pid>`, `brg board` — тоже; `ready.<pid>` без `alive.<pid>` (доска убита) сервер удаляет на старте, общий `run/board/ready` прежних версий — если старше 60 с. Сервер умер сразу или не ответил за 5 с — причина и `file://` (код выхода сервера: 3 — порт занят или недоступен, 5 — адрес `--bind` не на этой машине, 2 — неверные параметры, 4 — не записан `ready`); умер позже — раз в тик bash видит это (`kill -0 $!`): «сервер доски остановился — доска только для просмотра» и адрес `file://`, цикл снимка идёт дальше.
  - **Адрес и порт.** `http://127.0.0.1:ПОРТ/?t=ТОКЕН` — первой строкой (с `--bind`, ниже, — адрес, по которому доска точно открывается). Порт: `--port P` (0 — любой свободный), иначе сохранённый (`run/board/port`), иначе любой свободный. Сохранённый занят — новый порт и строка «порт P занят — новый адрес»; явный `--port` занят или недоступен (`EACCES`: порты < 1024, зарезервированные диапазоны Windows) — «сервер доски не запустился: порт занят или недоступен» и `file://`. Токен — `run/board/token` (`secrets.token_hex(16)`, создаётся один раз, права 600; два первых запуска одновременно получают один токен: полное значение пишется во временный файл и публикуется `os.link` — атомарно и без перезаписи, проигравший читает готовый файл; без жёстких ссылок (SMB, exFAT) — `O_EXCL`, проигравший ждёт до 2 с, пока победитель допишет; верный токен не меняется никогда, файл не с токеном заменяется новым; постоянный — чтобы закладка `/` и адрес работали между запусками; утёк или хочется сменить — удалить файл и перезапустить `brg board`, старые cookie перестанут подходить); второй `brg board` в том же проекте получит другой порт (оба цикла пишут один `data.js` — как и раньше без сервера; файлы `token`, `port` общие, `alive.*` и `ready.*` — свои).

  - **`--bind ADDR` (0.9.2, решение человека: доска на виртуалке, браузер на хосте).** По умолчанию — только `127.0.0.1`, как раньше. `--bind ADDR` — слушать этот IPv4-адрес машины (десятичная запись `a.b.c.d`, октеты 0–255 без ведущих нулей: `010` неоднозначен) или `0.0.0.0` (все адреса); имена (`myvm.local`, `localhost`) и IPv6 — отказ (код 1, «Использование»; проверка в bash до запуска сервера: сначала форма — ровно три точки, только цифры и точки, без пустых октетов, потому что `1.2.3.4.` и `1..2.3` читаются как четыре поля, затем октеты; в Python — повторно, своим регулярным выражением, не `ipaddress`: в 3.8.0–3.8.11 и 3.9.0–3.9.4 он принимает ведущие нули; код 2). **Только на этот запуск** (в `config` и в `run/board/` адрес не пишется; следующий `brg board` без флага снова слушает один `127.0.0.1` — безопасно по умолчанию; порт сохраняется как раньше). Со `--static` и `--once` неверное значение — по-прежнему ошибка, верное молча не действует (как `--port`). Явный `--bind 127.0.0.1` — то же, что без флага (серверу `--bind` не передаётся, строк ниже нет); loopback — весь `127.0.0.0/8`. **Вывод**, порядок строк: адрес → [строка «доска слушает все адреса машины…»] → «ВНИМАНИЕ» (две строки) → [«порт P занят — новый адрес»] → «доска обновляется…». Первая строка: `--bind IP` — `http://IP:ПОРТ/?t=ТОКЕН`; `--bind 0.0.0.0` — `http://127.0.0.1:ПОРТ/?t=ТОКЕН` (по нему точно откроется на этой машине), следующая строка говорит заменить `127.0.0.1` на IP этой машины (с подсказкой команды: `ip -4 addr` / `ipconfig getifaddr en0`; сам IP brg не угадывает — у виртуалок с NAT и host-only их несколько, `getfqdn` может зависнуть, а токен второй раз не печатается). Для любого адреса вне `127.0.0.0/8` — «ВНИМАНИЕ»: HTTP без шифрования, токен и переписка идут открытым текстом, с доски можно управлять бригадой и **запускать агентов с полными правами** (это выполнение команд на машине), доверенная сеть или SSH-туннель (`ssh -N -L ПОРТ:127.0.0.1:ПОРТ <машина>` — тот же номер порта с обеих сторон: от него зависит имя cookie и проверка `Host`), после работы по сети сменить токен (`rm .brigada/run/board/token` и перезапуск), брандмауэр macOS/Windows может спросить разрешение для Python. **Адрес не на этой машине** (`EADDRNOTAVAIL`; на Windows `WSAEADDRNOTAVAIL` 10049) — сервер выходит с кодом **5** и причиной в stderr, brg: «сервер доски не запустился: адрес ADDR не на этой машине — доска только для просмотра (адреса машины: ifconfig / ip addr; все адреса: --bind 0.0.0.0)» и `file://`; проверка errno идёт **до** повтора на другом порту (`--retry-any` не поможет). Причину «порт» не путать с адресом: `EACCES` при `bind` — это порт, он остаётся кодом 3. Слушающий сокет `0.0.0.0` — без `SO_REUSEADDR` на всех платформах: на macOS с ним `bind(0.0.0.0:P)` проходит поверх чужого `127.0.0.1:P`, «порт занят» не обнаружился бы, а адрес на первой строке открыл бы чужое приложение (цена: перезапуск на сохранённом порту в пределах `TIME_WAIT` даст «порт P занят — новый адрес»). Сервер не вызывает `getfqdn` для адреса (`server_bind` переопределён): обратный DNS-запрос съел бы 5 с рукопожатия.
  - **Защита** (на странице вся переписка, кнопки управляют агентами): по умолчанию только `127.0.0.1` (на Windows `allow_reuse_address = False`: иначе второй процесс занимает тот же порт и «порт занят» не обнаружить; `--bind` — выше); `Host` на **всех** запросах (DNS rebinding): порт — свой всегда (иначе 403 «порт в адресе должен быть P — SSH-туннель с тем же номером порта с обеих сторон»), имя — `127.0.0.1` или `localhost` (всегда: и через туннель на сервер, слушающий сеть; у страницы атакующего в `Host` имя её домена), `--bind IP` — ещё `IP`, `--bind 0.0.0.0` — ещё **любой IPv4-литерал** (но не `0.0.0.0`: это не адрес назначения). Имена — нет, ни при каком `--bind` (403 «открой доску по IP-адресу, не по имени»): защита от DNS rebinding держится на том, что в `Host` перепривязанной страницы стоит имя; `[::1]` — нет; `GET /?t=ТОКЕН` ставит cookie `brg_<порт>` (`HttpOnly; SameSite=Strict; Path=/`; имя с портом — доски двух проектов не затирают cookie друг друга) и отвечает `303` на `/` — токен не остаётся в адресной строке и истории; все GET — только с верной cookie (иначе 403 «открой адрес из вывода brg board»); токен кладётся в страницу (`<meta name="brg-token">` вместо комментария `<!--BRG_META-->`) только при верной cookie; POST — cookie **и** заголовок `X-Brg-Token`, `Content-Type: application/json`, `Origin` (если есть) = `http://` + **`Host` этого же запроса** (уже прошедший проверку; same-origin; **с 0.9.2 строже и по умолчанию**: при `Host: localhost:P` теперь отказ для `Origin: http://127.0.0.1:P`, которого браузер и так не пришлёт), `Content-Length` обязателен (chunked — 411), ≤ 1 МБ (413), невалидный JSON — 400; токен сравнивается `hmac.compare_digest`; только GET и POST (любой другой метод — `OPTIONS`, `TRACE`, `CONNECT`, … — 405 с `Allow: GET, POST`, без CORS); на всех ответах `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` (кликджекинг кнопок «Стоп всех» со страницы соседнего localhost-порта), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`; свой `log_message` без URL (стандартный печатал бы `?t=` в терминал). Защита от злонамеренного локального агента — не цель (§1, «Не цели»): токен лежит в `run/board/`, а `brg say` и так доступен без ключа. С `--bind` защита дополняется, не ослабляется: cookie не получает `Secure` (HTTP), `SameSite=Strict` и cookie с именем порта работают как прежде (браузер к другому `Host` cookie не отправит — открывать надо тот адрес с токеном, которым пользуешься); от прослушивания сети (HTTP) защиты нет — только доверенная сеть или туннель; от злонамеренного соседа по сети — токен (128 бит) и проверки выше.
  - **Пути.** `GET /` — `board.html`, `GET /run/board/data.js` и `/run/board/T00N.js` — белый список (с любым `?…`); остальное — 404. Снимок отдаётся, только если нет `Sec-Fetch-Site` или он `same-origin`: страница с соседнего порта того же хоста — тот же «сайт» для `SameSite` и подключила бы `data.js` тегом `<script>` вместе с cookie, а читать снимок должна только сама доска. **Токен в адресе скрипта (0.9.2):** браузеры шлют `Sec-Fetch-*` только на potentially trustworthy URL (loopback, https), поэтому по сетевому адресу (`http://192.168.64.5:P`) заголовка нет и проверка по нему молча проходила бы — например dev-сервер разрабатываемого приложения на `0.0.0.0:3000` читал бы всю переписку. Поэтому страница, получившая `<meta name="brg-token">`, добавляет `&k=ТОКЕН` к адресам `data.js` и `T00N.js` (без meta — `file://` — как было), а сервер: `k` есть — должен совпасть (`hmac.compare_digest`), иначе 403; `Host` не loopback (`127.0.0.0/8`, `localhost`) — `k` обязателен. На loopback `k` не нужен (прежнее поведение, `Sec-Fetch-Site` там работает). `Referrer-Policy: no-referrer` и свой `log_message` не дают токену утечь из адреса. Журнал действий с доски по не-loopback адресу дописывает адрес клиента: `── с доски: say → all (#42) (с 192.168.64.1)`.
  - **Действия** — `POST /api/<действие>`, JSON → `{ok, code, out}` (ошибка проверки аргументов — 400 с тем же видом; ошибка brg — 200, `ok: false`, слова brg в `out`): `say` {to: "all" | [имена], channel?, re?, text}, `task-new` {title, brief, cancel_current?}, `task-cancel`, `lead` {name}, `pause` / `resume` / `stop` {name?}. Сервер **ничего не пишет в состояние сам** (кроме `run/board/token|port|ready.*` и временных файлов текста): каждое действие — вызов brg от имени человека (`say`, `task new --as human`, `task cancel --as human`, `lead give <имя> --as human`, `pause|resume|stop`), поэтому все правила brg — выбор lead'а, снятие паузы, закрытие вопроса `--re`, отказы — действуют как из терминала. Вызов: `bash <корень>/bin/brg …` (`BRG_SERVE_BASH` от `brg board`), на Windows — `bin\brg.cmd` (решает `sys.platform == 'win32'` в Python, не `PLATFORM` brg: MSYS-Python понимает POSIX-пути); аргументы — списком, без оболочки; `stdin=DEVNULL`, `cwd` — корень проекта (иначе `brg.cmd` добавит строку `WIN_CD_HINT`), окружение без `BRG_AS` и с `BRG_NO_CHCP=1` (параллельные вызовы не должны переключать кодовую страницу общей консоли) и `MSYS=noglob` (Git Bash, запущенный из `python.exe`, иначе раскрыл бы маску вроде `README*` в незакавыченном аргументе — заголовке задачи), `timeout` 60 с, вывод — UTF-8 с заменой. Имена, каналы, номера — по регулярным выражениям; **тексты** (сообщение, постановка) — только через `--file` во временный файл `run/board/.srv.tmp.*.txt` (UTF-8, удаляется в `finally`; оставшиеся старше 60 с, как и `alive.*` убитых `brg board`, удаляются на старте сервера); заголовок задачи (`--title`) — одна строка без управляющих символов, ≤ 200 байт, на Windows ещё без `" % ^ & | < > !` (cmd.exe раскрывает их и в кавычках) — иначе понятный отказ. Каждое действие — строка в терминале `brg board` (stdout сервера; `-X utf8`): `── с доски: say → all (#42)`.
  - **Страница.** Одна на `file://` и `http://`: управление включается, если сервер вложил `<meta name="brg-token">` (в `file://` его нет — страница как раньше). Шапка: «Новая задача» (заголовок и постановка; если есть активная — окно честно говорит, что она будет отменена: `cancel_current`), «Пауза» / «Продолжить» (снять общие и личные паузы и стопы), «Стоп всех» и «Отменить задачу» — **с подтверждением**. Переписка: поле сообщения (кому — «всем» или чипы агентов, несколько; канал — задача или `lobby`; Ctrl/⌘+Enter), у вопроса в плашке «Ждут вашего ответа» и у каждого сообщения агента — «Ответить» (поле получает адресата, канал и `Re: N`: ответ закрывает вопрос на доске, §9.2). Меню «⋯» у чипа агента: «сделать lead'ом», «пауза» / «снять паузу» (при общей паузе пункта нет), «остановить» (с подтверждением) / «снять стоп». После действия — внеочередная загрузка снимка через 0,3 и 1 с. Ответ brg — всплывающая строка внизу; ошибка — красным, словами brg.
- **Запущенные brg (0.9.0, §5.5).** Снимок: у агента поле `spawn` — `null` или `{id, harness, model, rights, state, turn, turn_start, turn_end, turn_result, last_event, last_error, perm_denied, rights_note, last_text, last_text_turn, context, tokens{in, out, reasoning, cache_read, cache_write, main_in, main_out, sub_in, sub_out}, cost, tokens_source, sub_sessions, supervisor_alive, note, prompt_head, activity}` (`activity` — `activity.tail` строкой, строки с TAB разбирает страница); полный ключ в снимок не попадает (всё записанное надзором уже замаскировано). `meta.spawn = {supported: ["opencode"], available: […]}` — бинари ищутся (`type -P`) один раз при запуске `brg board`, не на тик; цена тика — по-прежнему O(1) процессов. Страница: у чипа запущенного — «⚙ S003», модель, права, токены (основная · подагенты), стоимость — только если > 0, контекст («без подагентов» при `stream`; 0.9.1); раскрывающаяся панель — активность, «ход N идёт M мин · последнее событие K мин назад» / «ждёт N мин» / «упал: …» / «отказ в правах: …» / «надзор не отвечает» / «конфликт», последний ответ («(ход N)» или «(ход N, идёт)»); в шапке задачи — сумма токенов запущенных. **Лента (0.9.1):** строка «ход N начат» выделена (новый ход виден сразу); панель перерисовывается, только если изменились её данные; по ключу панели (id запуска) страница помнит, был ли человек внизу ленты (или ещё не прокручивал) — тогда после перерисовки лента прокручена к последней строке; прокрутил вверх — его `scrollTop` сохраняется. С сервером: «Добавить агента» (харнесс из `meta.spawn.available`, модель — текст и последняя использованная, число 1–5, права — радио `full`/`project` со смыслом дословно, подпись) и в меню «⋯» запущенного — «Разбудить», «Дать полные права» (при `project`), «Забрать в окно» (показывает команду), «Убрать» (с подтверждением). Сервер: действия `spawn` {harness, model, rights, count, note?} и `spawn-ctl` {id, op: wake|rm|detach|rights, rights?} — валидация как в CLI (`model` не с `-`; `id` — `S\d{3,}` или имя агента), вызов `brg spawn …`, ответ < 2 с (надзор не держит пайп). **Локаль:** brg экспортирует `LC_ALL=C`, поэтому `brg board` передаёт серверу исходные `BRG_CMD_LC_SET`/`BRG_CMD_LC` (как раннеру `brg run`), сервер — в окружение вызова `brg`; `brg spawn` сохраняет их в запись, предпочитая `BRG_CMD_LC*` из окружения своей (там уже `C`); обёртка хода восстанавливает локаль. `LANG`/`LC_*` brg не трогает.
- **«Работает» честно (0.6.0, решение человека).** Участник «ждёт» ⇔ свободен (§5 п. 13). Снимок: у агента поле `mark` — `{note, since, via, item}` или `null` (читается тем же `busy_read`, только чтение). Страница добавляет два места, где видно «непонятно, что происходит»: (1) **строка состояния задачи** под заголовком — если у активной (текущей) задачи есть подзадачи и все они в финальных стадиях (готово / отменено): «подзадачи готовы · lead X работает: T» или «подзадачи готовы · lead X ждёт — итог ещё не подведён» (полевой случай: все подзадачи «готово», lead делал финальную проверку, а все «ждали»); (2) **плашка «бригада простаивает»** — задача активна, есть живой `wait` без пометки, **нет ни одного «работает»** (с пометкой или `working`), нет открытых вопросов человеку и идущих прогонов, бригада не остановлена. Длительность = max(сколько страница непрерывно наблюдает такое состояние, сейчас − время последнего сообщения задачи); плашка показывается при > 2 мин.

### 9.2 Вопросы человеку

**(решение человека, 0.5.1)** Вопрос агента человеку не должен теряться. Полевой случай: lead спросил человека в своём чате (можно ли закрыть работающее приложение для smoke-теста), дальше его чат заполнили выводы `wait`, вопрос уехал вверх, человек его не увидел; доска час показывала подзадачу «в работе», бригада ждала. Чат харнесса — по-прежнему основной канал (PROTOCOL, раздел 2 п. 3); brg добавляет к нему видимость: открытый вопрос виден на доске, в `who` и в терминале `brg board`, пока на него не ответили.

- **Задать** — `send --as <имя> --to human --ask` (вместе с тем же текстом в своём чате). `--ask` — только когда среди адресатов есть `human`; заголовок `Ask: yes`. Вопрос — одно сообщение: несколько вопросов — списком в одном теле.
- **Открыт**, пока в том же канале нет сообщения с `Re: <номер вопроса>` **от человека или от автора вопроса**: автор получил ответ в своём чате и пересылает его суть бригаде `send --re N` (это и закрывает вопрос — так бригада узнаёт решение человека), или человек отвечает из терминала `say --re N …` (у `say` появляется `--re`). Ответ `--re N` другого агента (вопрос был и ему: `--to human,codex-1`) вопрос не закрывает — человек ещё не ответил. Уточнить вопрос — новым `--ask`, не `--re`. Закрытие или отмена задачи снимает её открытые вопросы (сообщения остаются). Подсказки ответа (`who`, `status`, вывод `send --ask`, доска, терминал `board`) называют `--channel`, если канал вопроса — не канал по умолчанию.
- **Индекс** — маркер на открытый вопрос в `run/asks/` (пишется вместе с сообщением `--ask`, снимается записью сообщения с `Re` на него и закрытием/отменой задачи): так `who`, `status` и тик доски видят открытые вопросы за O(1), без чтения переписки.
- **Где видно:**
  - доска — плашка «Ждут вашего ответа» над задачей: кто спросил (чип агента), когда (живое «N мин назад»), начало вопроса (раскрывается целиком), куда отвечать — «в чате <имя> (в окне агента ищи «<имя>.<3 символа ключа>») или `brg say --to <имя> --re N …`»; при сервере (§9.1) вместо команды — кнопка «Ответить» (поле сообщения получает адресата, канал и `Re: N`); число открытых вопросов — в начале заголовка вкладки; у спросившего агента в полосе бригады — «ждёт вашего ответа»; в переписке вопрос помечен «вопрос человеку · открыт / отвечен #M / снят без ответа» (последнее — задачу закрыли или отменили, а ответа с `Re` не было);
  - `brg board` в терминале — строка на каждый новый открытый вопрос (один раз): `── вопрос человеку от opencode-2 (#20, T004): <первая строка> — ответь в его чате`;
  - `who` — строка «ждут ответа человека: opencode-2 #20 (55 мин)»; `status --as <имя>` — свои открытые вопросы.
- **Ключ на доске.** Чтобы человек нашёл окно агента, доска показывает рядом с именем **первые 3 символа ключа** (`opencode-2 · xqp…`): в окне агента каждая команда содержит полное имя `opencode-2.xqprxp`. Полный ключ доска не показывает (§3: из общедоступного вывода ключ не взять) — снимок пишет только префикс.
- Агентам (README, раздел 3, механика): вопрос человеку — текстом в чате **и** `send --to human --ask`; получил ответ — перешли суть бригаде с `--re N`. Отчёт человеку (не вопрос) — без `--ask`.

## 10. Windows

- `bin/brg.cmd` (ASCII, CRLF) сам находит Git Bash: `BRG_BASH` → `%ProgramFiles%\Git\…` → `%ProgramFiles(x86)%\…` → `%LOCALAPPDATA%\Programs\Git\…` → scoop → через `where git`. `bash` из PATH не вызывает, bash из System32/WindowsApps (WSL) отвергает. Ставит `BRG_VIA_CMD` — brg печатает `NEXT:` в форме `.\.brigada\bin\brg.cmd …` (работает и в PowerShell, и в cmd; вызов не из корня — с подсказкой `cd <корень>`). На время вызова `chcp 65001` (`BRG_NO_CHCP=1` отключает); код выхода brg сохраняется.
- `.gitattributes`: `bin/brg`, `bin/brg-global`, `bin/brg-serve.py`, `*.sh`, `template/*` — `eol=lf`, `*.cmd` — `eol=crlf`.
- **Сервер доски (0.8.0, §9.1).** Python ищется без шимов (`py -3`, `python3`, `python`; заглушки `…\Microsoft\WindowsApps\` пропускаются) и хранится как `sys.executable`; `--root` сервера — `C:/…` (из `BRG_VIA_CMD` или `/c/…`); решение «`brg.cmd` или bash» принимает сам сервер (`sys.platform == 'win32'`); `BRG_NO_CHCP=1`, чтобы параллельные вызовы не трогали кодовую страницу консоли `brg board`; `MSYS=noglob` — Git Bash не раскрывает маски (`*`, `?`, `[`) в аргументах, которые ему передал не-MSYS процесс; `allow_reuse_address = False`. Закрытие окна и Ctrl+C останавливают сервер через TERM от bash, а если не дошло — сердцебиением `run/board/alive.*` (≤ 15 с). brg с CRLF в самом себе выдаёт понятную ошибку (код 2).
- Агентам в PowerShell/cmd: `.\.brigada\bin\brg.cmd …`, тело — `--file` (или `--desc`/`--comment`); харнесс, выполняющий команды в Git Bash (Claude Code на Windows), вызывает как обычно.
- Таймауты по платформе: `wait_timeout.<харнесс>.<платформа>` (`darwin`, `linux`, `msys`, `wsl`). Пользовательский `config` побеждает любые значения по умолчанию: `config` (`<h>.<plat>`, `<h>`) → `config.default` (то же) → встроенные (то же) → `wait_timeout.default` в том же порядке файлов.
- `brg doctor [проект]` — проверки среды и состояния (bash и платформа, CRLF, атомарность `mkdir`, `mv` поверх открытого файла, видимость процессов, `.git/info/exclude`, блок brigada в `AGENTS.md`/`CLAUDE.md` (§3), блокировки, раннеры, зависшие wait, таймауты): ✓/⚠/✗ с подсказками, ничего не меняет, код 1 только при ✗. Видимость процессов: `kill -0` родителя даёт EPERM — ⚠ «песочница: чужие процессы недоступны, brg считает их живыми, сироту wait не распознает»; EPERM даёт уже завершённый собственный ребёнок — ⚠ «смерть процессов не видна, раннер снимается только по heartbeat (до `runner_stale`)». Песочницу, где pid-namespace прячет живые процессы (ESRCH), doctor не распознаёт (§12 п. 3). Блокировки и раннеры doctor оценивает тем же вердиктом, что и brg (§7.3, с `runner_dead_grace`). Сломанную установку (CRLF) проверяют копией из репозитория: `bash /путь/к/brigada/bin/brg doctor <проект>`.
- На Windows ничего ещё не запускалось — проверка по `WINDOWS.md` на машине человека.

Сирота `wait` при EPERM не распознаётся (выходит по таймауту). `run` из песочницы не достучится до локальных сервисов (БД) — это brg не исправит: README для Codex велит запускать меняющие состояние команды brg, прежде всего `wait` и `run`, вне песочницы.

10. Доска не проверялась в Safari (`?<время>` у скрипта под `file://`; cookie `SameSite=Strict` сервера) и на Windows (`WINDOWS.md`, п. 2.7). В Safari до 16.4 нет `Sec-Fetch-Site`: защита снимка от страницы с соседнего localhost-порта (§9.1) на loopback там не работает (по сети её держит токен `k`, с 0.9.2); остальное (cookie, `Host`, токен в заголовке POST) работает.
11. **Сервер человека (0.8.0) на Windows не запускался:** `brg.cmd` из Python (кавычки и кириллица в аргументах, заголовок вида `README*` при `MSYS=noglob`), остановка `python.exe` из Git Bash по TERM (запасной путь — сердцебиение `alive`), поиск `py -3` (`WINDOWS.md`, п. 2.8). На macOS проверен тестами.
12. **Агенты, запущенные brg (0.9.0, §5.5)**, проверены только с поддельным OpenCode. Открыто: Claude Code и Codex (этап B); Windows (MSYS/WSL — пока отказ); свой id сессии (`--session` «create if not exist» — проверить живьём); выходит ли `opencode run`, пока идёт фоновый подагент; раздельность токенов основной и дочерних сессий в `session export`; настоящее ограничение прав внутри проекта (`project` сейчас — правила OpenCode по умолчанию; возможный путь — `OPENCODE_CONFIG_CONTENT` с `permission` на время вызова).
13. **Доска по сети (`brg board --bind`, 0.9.2).** Не поддерживаются IPv6 и имена хостов в `--bind` и в `Host` (открывать — по IPv4-адресу), HTTPS и обратный прокси (`Host` — имя, `Origin` — `https://…`: оба отказ): снаружи доску открывает только SSH-туннель на тот же номер порта. Известный остаток: на macOS обычный `brg board` (`127.0.0.1:P`, с `SO_REUSEADDR`) может занять порт поверх чужого процесса, слушающего `0.0.0.0:P`; обратная ситуация закрыта (`0.0.0.0` без `SO_REUSEADDR`), тестом не проверить — крючок слушает loopback. Токен постоянный и по сети идёт открытым текстом: после работы по сети его надо менять вручную. На Windows `--bind` не проверялся (брандмауэр, `WSAEADDRNOTAVAIL`).
14. **Установка одной командой (0.9.2)**: `curl -fsSL …/install.sh | bash` клонирует репозиторий (нужен git) и ставит `brg`; проверено только на macOS (bash 3.2); на Windows (Git Bash) и bash ≥ 4 не проверялось (признак режима — `BASH_SOURCE` на верхнем уровне и `-f`; в функции из пайпа там бывает `main`); без git установки одной командой нет (только вручную).
15. **Регистр в путях резервирований (§7.2)** сводится только для ASCII и русской кириллицы. `É`/`é`, другие алфавиты и разные нормальные формы Unicode (NFC/NFD) одного имени считаются разными путями: на macOS и Windows такие пути могут быть одним каталогом, а конфликт не обнаружится.
