# brigada — дизайн

Схема, по которой любое число агентов из разных харнессов (Claude Code, Codex, OpenCode, …) подключаются к проекту и дальше **сами** организуют работу над задачей человека: обсуждают, распределяют роли и подзадачи, проверяют друг друга.

Документ описывает, как устроено сейчас и почему. **(решение человека)** — решение, которое меняет только человек; остальное принято по ревью и подтверждено тестами. Здесь — только реализованное: новое сначала план в `/plans` (вне git), сюда — вместе с кодом.

---

## 1. Цели и ограничения

1. **(решение человека)** Наладка со стороны человека — разовый `brg init` в проекте и фраза агенту «подключись к бригаде». Чтобы короткая фраза работала в любом харнессе, `init` дописывает короткий блок brigada в файлы постоянных инструкций проекта — `AGENTS.md` и, если нужно, `CLAUDE.md` (§3); `init --no-agents-md` их не трогает, и тогда фраза полная: «подключись к .brigada, прочитай инструкцию в .brigada/README.md». Никакой настройки харнессов (хуков, конфигов, плагинов) и доп. установок (tmux и т.п.). **(0.9.0)** Агент, запущенный самим brg (`brg spawn`, §5.5), — тоже не настройка: brg передаёт харнессу только флаги вызова (`opencode run --format json --model … [--auto]`), конфиги харнесса не трогает.
2. **(решение человека)** Базовое взаимодействие (сообщения, ожидание, роли, подзадачи) выполняет детерминированный скрипт, а не модель, разбирающая файлы.
3. **(решение человека)** Один механизм ожидания для всех харнессов: агент не завершает ход и ждёт в блокирующем `brg wait` (§5). Возможности отдельных харнессов (фоновые команды с пробуждением, шедулеры, `codex queue`) в протокол не входят; возможно, позже — как необязательная оптимизация.
   **(решение человека, 0.9.0)** Для агентов, которых запустил сам brg (`brg spawn`, §5.5), ожидание держит не модель, а надзорный процесс brg: свободный агент **завершает ход** (харнесс выходит, простой ничего не стоит), надзор сидит в `wait` за него и, когда есть будящее, продолжает сессию харнесса, передавая пачку прямо в промпт (один запрос к модели). Работает подагент — запущенный агент ход не завершает и ждёт в `wait --busy`, как все. Подключённые вручную работают как раньше; друг для друга оба вида неотличимы (имена, задачи, lead, подзадачи, `run`, вопросы, стоп, пауза).
4. **(решение человека)** Реализация на bash (3.2+). Windows — через Git Bash (§10). **(решение человека, 0.8.0)** Единственное исключение — Python (≥ 3.8, только stdlib) для **необязательного** сервера человека `bin/brg-serve.py` (§9.1): `bin/brg` вызывает Python лишь в `board` (поднять сервер) и `doctor` (проверить, что он есть); инструмент агентов — по-прежнему один bash-файл. Без Python всё работает: доска открывается как `file://` и только показывает, отвечать — `brg say`.
5. **(решение человека)** Всё состояние — внутри `.brigada/`, по задачам; между задачами общее только `common/`. Смена задачи — без перезапуска сессий; новые агенты подключаются в любой момент.
6. **(решение человека)** Самоорганизация — суть эксперимента: агенты сами решают, кто ведёт и как решать задачу. brg ведёт состояние и правила переходов, решения принимают модели.
7. **(решение человека)** PROTOCOL задаёт только цель и минимальные рамки: безопасность; вопросы по бизнес-сути — человеку, технические решения — сами; человек видит вопросы и итог (по умолчанию — текстом в чате lead'а и тем же текстом `send --to human`, который видно на доске); не коммитить в `main`/`master` без разрешения человека и не уничтожать чужую работу; связь — через brg; стадии подзадач соответствуют действительности — человек следит по доске (§7.1.1); **участник — координатор, работу делают его подагенты** (§5.4); закрытие — `task close` с `summary.md`. Весь процесс (перекличка, лид, план, подзадачи, резервирования, ревью, ветка, `brg run`) — **рекомендации**: агенты вправе договориться о другом и строить свои инструменты. brg процесс не навязывает (например, не требует ревью для закрытия) — даёт инструменты и следит за целостностью состояния. Почему: регламент подменял бы самоорганизацию (п. 6).
8. **(решение человека)** Как работает бригада — PROTOCOL, раздел 3 «Ожидания» (не жёсткие правила):
   - решения принимаются коллегиально: что делаем, в каком порядке, кто какой объём берёт;
   - lead — фасилитатор, а не начальник: фиксирует договорённости и решает сам, только если бригада не договорилась;
   - **(решение человека, 0.7.0)** lead — единственный, кто сам обращается к человеку (вопросы, отчёты, итог); остальные отвечают, если человек написал им сам. Роли host больше нет: lead — и фасилитатор, и связь с человеком, и lead есть всегда (§6.1);
   - подзадачи раздаются участникам;
   - проверка подзадачи другим участником (силами его подагента) — рекомендация: проверять ли и как, решает бригада; стадию подзадачи агенты держат такой, как на деле (§7.1.1).

   Почему: в полевом прогоне lead, следуя совету «объёмное — подагентам», сам исследовал задачу и писал её ядро вместе со своими подагентами, а участники простаивали.

   То, что участник — координатор, а работу делают его подагенты, с версии 0.5.0 — не ожидание, а обязательная рамка (п. 7, §5.4).

Не цели MVP: параллельные задачи, worktree на агента, кросс-машинная работа (все агенты на одной машине, одна ФС), защита от злонамеренного агента.

## 2. Слои

| Слой | Чем реализован |
|---|---|
| Транспорт и состояние: каналы, курсоры, ростер, задачи, роли, дедлайны, подзадачи, резервирования, прогоны, блокировки | `bin/brg` (один bash-файл) |
| Ожидание | `brg wait` + правило «никогда не завершай ход»; у запущенных brg — надзор `brg __spawn` (§5.5) |
| Инструкции агентам | `README.md` — механика (обязательна), `PROTOCOL.md` — цель, рамки, рекомендации (из `template/`); блок brigada в `AGENTS.md`/`CLAUDE.md` проекта — указатель на `README.md` (§3) |
| Инструменты человека (§9) | глобальная `brg` (`bin/brg-global`, `install.sh`); `bin/brg.cmd` на Windows |

Каждая команда печатает короткий результат и, где уместно, `NEXT:` — следующую команду дословно, с именем агента: так цикл переживает сжатие контекста.

## 3. Подключение

1. Человек в корне проекта: `brg init` (или `bash /путь/к/brigada/bin/brg init [проект]`) — создаёт `.brigada/` (§4). Повторный `init` обновляет `bin/`, `README.md`, `PROTOCOL.md`, `board.html` (доска человека, §9.1), `config.default`, `VERSION`, не трогая состояние и `config` (называет ключи шаблона, которых в `config` нет ни строкой `key: value`, ни закомментированной `# key: value`). **(решение человека)** Новому проекту `init` пишет `config` копией шаблона, где каждая настройка закомментирована (`# key: value`): значения по умолчанию действуют из `config.default`, и их новые значения доходят до проекта со следующим `init`; своё значение — раскомментировать строку. Существующий `config` `init` не меняет ни на байт; раскомментированное значение в нём побеждает `config.default` — для такого ключа смена умолчания не действует. **(решение человека)** `init` дописывает в `.git/info/exclude` (у worktree — общего git-каталога) `.brigada/` — весь каталог не коммитится: иначе `git add -A` любого агента закоммитит переписку, рантайм, копию `brg` и настройки бригады. Строки brg ≤ 0.2.0 (`.brigada/{tasks,lobby,run,agents}/` и их комментарий) повторный `init` заменяет на `.brigada/` и подсказывает убрать из индекса уже закоммиченное (`git rm -r --cached .brigada`; сам brg git не вызывает, §7.4). `doctor` — ✗, если `.brigada/` в exclude нет.
   **(решение человека)** `init` кладёт в корень проекта блок brigada — между строками-маркерами `<!-- brigada:begin …` и `<!-- brigada:end …` (по ним блок находится и обновляется): «если человек просит подключиться к бригаде — прочитай `.brigada/README.md` и следуй ему (там `join` и цикл `wait`); без такой просьбы не подключайся». Текст блока — по-английски (его читают агенты); фразы человека — дословно, в кавычках: «подключиться к бригаде», brigada, .brigada рядом с "join the brigade", и название раздела README агента «Тебя запустил brg». Блок прежней версии (другой текст между теми же маркерами) следующий `init` заменяет. Файлы — по тому, что читают харнессы: `AGENTS.md` — Codex, OpenCode, Cursor, Copilot и др. (OpenCode без `AGENTS.md` читает `CLAUDE.md`); Claude Code читает `CLAUDE.md`, а `AGENTS.md` (с версии 2.1.277) — только если `CLAUDE.md` нет; при обоих — только `CLAUDE.md`, если в нём нет импорта `@AGENTS.md`.
   - `AGENTS.md` нет — создаётся из одного блока и исключается из git (`/AGENTS.md` в `.git/info/exclude` тем же механизмом, что `.brigada/`; без git — просто создаётся; комментарии к строкам `.brigada/` и `/AGENTS.md` — по-английски; `exclude` узнаётся по самим строкам, не по комментариям, поэтому из-за русских комментариев прежней версии существующий файл не переписывается и строки не дублируются): файл появился по воле brg, коммитить ли его — решает человек (убрать строку из exclude). `AGENTS.md` есть — блок дописывается в конец после пустой строки или, если отличается, заменяется между маркерами (включая их); файл, вероятно, в git — коммитить ли блок, решает человек, `init` об этом говорит.
   - `CLAUDE.md` нет — не создаётся (Claude Code прочтёт `AGENTS.md`); есть и содержит строку-импорт `@AGENTS.md` или `@./AGENTS.md` — не трогается; есть без такой строки — тот же блок по тем же правилам (упоминание `@AGENTS.md` внутри строки импортом не считается: Claude Code увидит блок дважды — безвредно).
   - Окончания строк файла сохраняются (CRLF-файл — блок с CRLF), права файла тоже; ссылка (`CLAUDE.md` → `AGENTS.md` и наоборот) пишется насквозь, один файл — один блок. Повторные блоки удаляются, `begin` без `end` — файл не трогается (вывод `init` говорит; фраза — полная). Повторный `init` идемпотентен: файл не меняется побайтно.
   - `init --no-agents-md` — `AGENTS.md` и `CLAUDE.md` не трогаются (существующие блоки тоже). `doctor` — ⚠, если блока в `AGENTS.md` нет или `CLAUDE.md` без блока и без импорта (§10).

   Почему: фраза человека должна быть короткой и одинаковой во всех харнессах, а постоянные инструкции проекта читают все — без настройки самих харнессов (§1 п. 1). Блок не велит подключаться без просьбы — иначе любая сессия в проекте шла бы в бригаду. Цена — правка файла, который может быть в git.
2. Человек агенту — в новой сессии, открытой в каталоге проекта: «подключись к бригаде». Постоянные инструкции харнесс читает при старте сессии; сессия из другого каталога найдёт чужую `.brigada` или никакую.
   - Блок говорит: подключиться — значит работать в цикле до STOP (после `join` не отчитываться человеку, сразу `wait`); участник только координирует, любую работу делают его подагенты (§5.4); подагент участника к бригаде не подключается никогда — блок читают и подагенты.
   - Те же напоминания — в последней строке перед `NEXT:` у `join` и в строке таймаута `wait`: `── нет новых (N с) · ход не завершай · NEXT: …`.
   - Почему: в полевом прогоне модель после первого пустого `wait` сочла просьбу «подключись» выполненной и завершила ход отчётом. Запасной вариант — без блока (`--no-agents-md`, сессия открыта до `init`, харнесс не читает ни `AGENTS.md`, ни `CLAUDE.md`): «подключись к .brigada, прочитай инструкцию в .brigada/README.md».
3. Агент по README определяет харнесс (`claude`, `codex`, `opencode`, иначе короткое имя; синонимы нормализуются) и модель; `join --harness <h> --model <m>` (модель — до 120 байт, как у `spawn --model`; длиннее — обрезается по границе символа UTF-8 с пометкой «…(обрезано)» и предупреждением) выдаёт полное имя `<harness>-<n>.<ключ>` (`claude-1.k7f3q9`, ключ сессии — ниже) и сводку: кто онлайн, активная задача, таймаут `wait`, «Таймаут инструмента» (как вызывать `wait` в этом харнессе), `NEXT:`. Агент разрешает вызовы brg «навсегда», читает PROTOCOL и входит в цикл (§5).

- **Идентичность** — явный `--as <имя>` в каждом вызове (`BRG_AS` — альтернатива). Опознание по `$PPID` отклонено: в Codex команды идут через обёртку песочницы, на Windows/MSYS свои PID. Отклонено и опознание по дереву процессов (сравнить предка вызывающего с родителем живого `wait`): причины те же, и вдобавок нужен `ps`, которого нет в списке утилит (§11).
- **Ключ сессии в имени** — **(решение человека)** защита от ошибки модели, а не от злоумышленника (профили читаемы, §1). Случай из демо: сессия, получившая задачу в промпте, пропустила `join`, увидела в `who` агента своего харнесса (`opencode-1`) и решила, что это она; `status` ответил «Мой wait: работает» — это сошло за подтверждение личности. Итог — два процесса под одним именем: оба вели задачу как lead, дублировали подзадачи и правили одни и те же файлы (резервирования своих путей не ловят), а двойник без `wait` не получал STOP.
  - `join` выдаёт полное имя `<базовое>.<ключ>`. Ключ — 6 символов `[a-z2-9]` из `$RANDOM` (без `l` и `o`), хранится как `Key:` в `agents/<имя>`. Имена харнессов — только `[a-z0-9]`, поэтому имя и ключ однозначно делятся по первой точке.
  - **Состояние — только на базовом имени**: файлы агентов, курсоры, `From:`, `Assignee`, Lead, резервирования, флаги стопа и паузы, `metrics.log`. Ключ пишется только в профиль. Другим имя показывается без ключа (`who`, `tail`, сообщения), поэтому из `who` ключ не взять; доска показывает человеку только первые 3 символа ключа — найти окно агента (§9.2). Полное имя brg печатает только самому агенту — в подсказках `--as` и в `NEXT:`; сжатие контекста ключ переживает так же, как имя: через последний `NEXT:`.
  - **Изменяющие команды требуют ключ:** `send`, `wait`, `busy`, `leave`, `task new|close|cancel`, `lead give|take`, `item add|claim|done|release|reassign|review|cancel`, `run` (запуск и `cancel`). Голое имя → отказ: «имя занято другой сессией; твоё имя — только из вывода твоего join в этом чате; не видишь его — сделай join». `join --as` здесь не подсказывается.
  - **Команды чтения** (`status`, `read`, `who`, `task show|list`, `item show|list`, `run show|list`) принимают и голое имя — их вызывают подагенты (§5.4). Без ключа они не освежают Last-Seen (иначе двойник «оживлял» бы настоящего агента), подсказки с `--as` в их выводе — с заглушкой `<твоё имя из join>`, а `status` не подтверждает личность: «wait агента X работает (pid N). Если ты не делал join в этом чате — ты не X: сделай join», `NEXT:` — `join`.
  - Ключ не `[a-z2-9]{6}` или не совпадает с профилем → отказ в любой команде: «ключ устарел или с ошибкой: под этим именем переподключилась другая сессия».
  - При отказе по ключу `NEXT:` — `join`, а не «исправь и повтори … --as X»: повтор с тем же именем зациклил бы агента. У `wait` — по-прежнему код 0 и последняя строка `NEXT:` (§5).
  - Имена-цели (`send --to`, `item reassign --to`, `lead give`) принимаются и с ключом — ключ отбрасывается: агенты копируют своё полное имя.
  - Совместимость: профиль без `Key:` (агент подключился до 0.2.0) принимает голое имя везде; ключ он получит при `join --as`.
- **Возврат** после потери контекста — `join --as <имя> --harness <тот же>` (имя голое или полное): только тот же харнесс; снимает `Left`; курсоры сохраняются; выдаёт **новый ключ**, прежний перестаёт работать (старая сессия, если жива, получит «ключ устарел»). В `lobby` — «X переподключён новой сессией; прежний ключ недействителен» (будит lead'а). Отказ:
  - у имени живой `wait`: «если это твой wait и ключ потерян — дождись его конца и повтори join --as»;
  - **(решение человека)** агент не «выпал»: возврат разрешён только после тишины — ни `wait`, ни вызовов brg — дольше max(`wait_timeout` + 60 с, `dropout_after`), как у пометки «возможно выпал» (§5.2), либо в состоянии `asleep`/`gone` (в т.ч. после `leave` — сразу). Иначе двойник, знающий базовое имя из `who`, забрал бы имя вместе с ролями у работающего агента: «мёртвый wait» — обычное состояние агента между вызовами (в демо он подолгу работал без `wait`). Отказ: «X активен (последний вызов N с назад). Если это ты и ключ потерян — он в последней строке NEXT; иначе подожди M с или подключись под новым именем». Флаг стопа на условие не влияет. Цена: агент, потерявший ключ, ждёт до ~5 минут или подключается под новым именем.
- **Одна платформа на `.brigada`**: `join` отказывает, если платформа (Darwin, Linux, MSYS, WSL, …) не совпадает с подключёнными не-`gone` агентами — pid, блокировки и пути у WSL и Git Bash разные.
- **Глобальная команда человека:** `bash install.sh` ставит `bin/brg-global` как `~/.local/bin/brg`. Из любого подкаталога проекта она запускает ближайший `.brigada/bin/brg`, `brg init` — версией репозитория, вне проекта — `brg` репозитория; если копия в проекте устарела — подсказывает `brg init`. Агенты по-прежнему вызывают `bash .brigada/bin/brg …` — от их окружения ничего не требуется (§1 п. 1).

### 4.1 Формат записей

Все записи — «заголовки `Key: value` + пустая строка + тело» (как email). Без JSON: разбирается `sed`/`awk`, читается людьми и моделями. Сообщение `messages/000014.msg`:
```
Id: 14
Channel: T001
From: codex-1            # агент | human (say) | brg (результат run)
To: all                  # all | имя[,имя] | human (можно с именами)
Kind: msg                # msg | system
Re: 12
Reply-By: 1759838400     # необязательно, epoch
Expect: claude-1,opencode-1   # при Reply-By: чьего ответа ждём
Wake: no                 # только у системных: no — не будит; <имя>[,<имя>] — будит только их
Ask: yes                 # необязательно: вопрос человеку (send --ask, §9.2)
Time: 2026-10-07T12:03:11Z
Epoch: 1759838191

тело
```

Время: ISO для людей, epoch для вычислений (разбор дат в BSD/GNU `date` различается — только форматируем).

### 4.2 Запись и блокировки

- Блокировка — `mkdir run/locks/<имя>.lock` + `owner` («pid epoch»). Протухшая (владелец мёртв, лок старше `lock_stale` или без `owner` дольше `lock_stale`; `lock_stale` ≫ любой критической секции) снимается **атомарно**: `mv` лока в уникальное имя (побеждает ровно один; лок, сменивший владельца, не трогается), затем `rm`. Снимает лок только владелец. Вложенность: task → runs → chan; exec → runs → chan. **(0.9.0)** Полный порядок: `spawn.S00N → roster → task → runs → chan` (и `spawnseq` — номер запуска — до `roster`). Лок надзора `spawn.S00N` держится всё время жизни надзора и **никогда** не снимается по возрасту (как exec-лок — только по смерти владельца, подтверждённой его `hb`, §5.5); надзор, держа его, берёт `roster` (`leave` при `rm`); ни один держатель `roster`/`task` не ждёт лок надзора — разовые вызовы (`spawn rm|detach|rights`, `join --as`) пробуют его один раз **до** `roster`.
- **«Мёртв»** — у pid, прочитанного из файла, всегда по одной функции `pid_alive` (§11): `kill -0` успешен или отвечает EPERM («Operation not permitted» — процесс есть, но недоступен: песочница Codex, чужой пользователь) — жив; ESRCH и любой другой ответ — мёртв. Лок недоступного владельца снимается только по возрасту (`lock_stale`), exec-лок — по heartbeat (§7.3).
- Сообщение — под блокировкой канала: `seq+1` → тело во временный файл в том же каталоге → `mv` в `messages/NNNNNN.msg` → обновить `seq`. Нумерация без дыр, курсор не «перепрыгнет» сообщение. Упали между `mv` и `seq` — `seq` пересчитывается по максимальному номеру файла.
- Остальные файлы — тоже tmp + `mv`; `mv` — с повторами (Windows: файл может держать антивирус или читатель).
- **Тексты** (сообщение, постановка, описание подзадачи, комментарий ревью) — из stdin (heredoc `<<'BRG_EOF'`) или `--file`; `say` — ещё и аргументами; `item add --desc`/`item review --comment` — однострочная альтернатива (в т.ч. для PowerShell, где нет heredoc, а пайп в Windows PowerShell 5.1 портит кодировку). CRLF → LF, BOM снимается, UTF-16 отвергается. Лимиты: сообщение — `msg_max_bytes` (8 КБ; больше — отказ с подсказкой положить текст в `shared/`), постановка — 64 КБ. stdin-пайп, не закрывшийся за 10 с, — отказ, ничего не отправлено.
- **Короткие поля из опций по длине не отвергаются** (отказы стоят агентам шагов): `--title` (200 байт), `--note` (500), `--desc`/`--comment` (`msg_max_bytes`) обрезаются по границе UTF-8 с пометкой «…(обрезано)» и предупреждением.

## 5. Ожидание и рабочий цикл

**(решение человека)** Единственный механизм — блокирующий `brg wait --as <имя> [--timeout S]`. Последнее действие каждого шага агента — `wait`; ход не завершается (кроме STOP).

1. **Один wait на агента, takeover без сигналов.** Новый wait пишет свой pid в `run/wait/<имя>.pid`; старый каждый тик (1 с) проверяет владение и, увидев чужой pid, выходит. Сигналы не посылаются: pid из файла мог быть переиспользован. Дубликаты (wait, уведённый харнессом в фон) не съедают почту.
2. **Вытесненный wait не провоцирует новый:** печатает `── SUPERSEDED: … НЕ вызывай wait повторно.` — это рвёт цепочку «уведомление о завершении старого wait → модель зовёт ещё один». TERM/INT/HUP — только от харнесса или человека (лимит команды, Esc), поэтому `── прерван сигналом … · NEXT: …` — цикл продолжается (pid-файл уже чужой — SUPERSEDED).
3. **Доставка хотя бы один раз.** Wait сначала подтверждает пачку предыдущего (`Acked := Pending`), затем ищет новое. `Pending` пишется только после вывода: убитый до вывода wait не теряет сообщения.
4. **Каналы:** `lobby` и активная задача (плюс дренаж только что завершённой, §6). Доставляется адресованное агенту или `all`, кроме собственного. Чужие личные не доставляются (видны в `tail` и `read --all`): шум и контекст дороже прозрачности.
5. **Heartbeat:** каждый тик — `run/wait/<имя>.hb`, раз в `heartbeat` с — Last-Seen (его обновляет и любой вызов brg). Живой wait = pid жив (`pid_alive`, §4.2: EPERM — жив) **и** hb свежий (защита от переиспользования pid).
6. **Сироты:** умер родитель — wait выходит молча, не держа призрака в `waiting` (родитель `1` — обёртка, MSYS — не проверяется). Недоступный родитель (EPERM, песочница) считается живым: сирота там не распознаётся и выходит по таймауту — это лучше ложного `orphan` у живого агента.
7. **Сам завершается раньше лимита харнесса:** таймаут из `config` по харнессу и платформе (§5.1); `--timeout` переопределяет и повторяется в `NEXT:`; так же — `--busy` (п. 13, §5.4). `--timeout 0` возвращается сразу и повторяется в `NEXT:` — горячий цикл; `wait --help` велит его не использовать.
8. **Будят:** новая почта, сводка дедлайна (§8), стоп (§9), `leave` (`── LEFT`). **Тихие системные события** (`Wake: no`: подключился, отключился, взял подзадачу, взялся проверять) не будят и приходят со следующей будящей пачкой — иначе каждый join стоил бы вызова модели каждому ждущему. Адресные (`Wake: <имена>`) будят только названных. Новая/закрытая/отменённая задача, смена lead, уход lead'а, уход агента с ролью — будят всех; «подключился/вернулся» при активной задаче — lead'а (иначе он не знает, что участники пришли); `item add`, `done`, `release`, возврат сданной в работу (`claim` из `done`) — lead'а; `reassign` — нового исполнителя; `review` — исполнителя и lead'а, вердикт по сданной — ещё и остальных проверяющих из `Reviewing:` (отдельным адресным сообщением, §7.1.1); `cancel` — исполнителя, lead'а и проверяющих (`Reviewing:` — им проверять больше нечего); `claim` и `review --start` — никого; результат `brg run` — инициатора. Автор события не будится. **На паузе человека** (§9) будит только то, что пришло `From: human` (`say`, `task new|cancel --as human`, `lead give --as human`) и снятие паузы (п. 14); остальное — в том числе уведомление `From: brg` «X — lead» (§6.1), которое при общей паузе, таким образом, никого не будит, — приходит после паузы.
9. **Дайджест на таймауте:** при активной задаче перед `── нет новых` — строка `T001: todo 1 · в работе I002 codex-1 · на проверке I003 (claude-2) · готово I001 · прогонов идёт 1` (стадии — §7.1.1) и `· свободны: claude-2, codex-1` — агенты с живым `wait` без пометки «работает» (п. 13), кроме себя, остановленных и стоящих на паузе (иначе лид опрашивает `who`/`item list`).
10. **Кап вывода** `wait_output_max` (~20 КБ, лимит inline-вывода харнессов): `Pending` = последнее показанное, остаток — следующим wait сразу (строка `── ещё N в <канал> не вошло …` с командой `read`).
11. **Всегда код 0**, статус — в тексте. Последняя строка — `NEXT:` (кроме STOP, SUPERSEDED, LEFT и выхода сироты), в том числе при ошибке аргументов и отказе по ключу (§3) — иначе агент выпадет из цикла.
12. `read` курсор не двигает и по умолчанию показывает всё после `Acked`, включая последнюю выданную пачку — безопасный повтор, если агент не уверен, что видел вывод. Новый агент стартует с конца `lobby` и активной задачи.

13. **(решение человека, 0.6.0) «Ждёт» значит «свободен».** Участник по §5.4 работает через подагента, а подагент (в Claude Code — в фоне) идёт, пока участник сидит в `wait`: по одному `wait` не отличить «свободен, готов к поручению» от «его подагент работает». Поэтому `wait` без `--busy` — явное «я свободен» (в `who`/`status`/на доске — «ждёт»), а `wait --busy ["подпись"]` — «мой подагент работает» (пометка, §5.4). `NEXT:` повторяет `--busy`, пока пометка стоит, — копируя `NEXT:` дословно, агент держит пометку, не думая о ней.

14. **(решение человека, 0.7.0) Пауза внутри `wait`.** Пауза (§9) не завершает ход агента — он остаётся в `wait`, и вот что тот делает, пока она стоит (общая `run/paused` или своя `run/paused.<имя>`):
    - **Будит только человек.** `AWK_FMT` считает кроме `wake` второй счётчик `hwake`: будящее (по тем же правилам `Wake:`) **и** `From: human`. Проход 1 `w_deliver` на паузе будит по `hwake`, а не по `wake`; при пробуждении выдаётся всё накопленное после `Acked` без фильтра (курсор линейный: потери нет), с строкой перед `NEXT:` «пауза продолжается: отвечай человеку, новую работу не начинай». Кап вывода на паузе называет, что будет с остатком: «придут после снятия паузы или со следующим сообщением человека».
    - **Снятие паузы будит и приносит накопленное в том же `wait`.** Проход 1 на паузе сдвигает `CH_SEEN` за всё просмотренное, будящее ли оно; поэтому `wait`, видевший паузу, на переходе «пауза → нет паузы» возвращает `CH_SEEN := CH_ACK` по всем каналам и завершается строкой `── пауза снята: человек снял паузу — новую работу можно начинать.` и накопленным (нет накопленного — строка и `NEXT:`). Без сброса накопленное пришло бы только со следующим `wait`.
    - **Дедлайны на паузе не будят.** `w_deadlines` вызывается на паузе только при пробуждении сообщением человека или снятии паузы (его сводки идут с этой пачкой); маркер `.done` заранее не захватывается.
    - **Таймаут на паузе** — `── пауза · нет новых от человека (N с) · ход не завершай · NEXT: …`; сводки задачи со «свободны» там нет. Длинного ожидания на паузе (`pause_timeout`) нет — решение человека: пауза ждёт с обычным `wait_timeout`, фоновый `wait` Claude Code не используется (§1 п. 3).
    - `wait`, упавший с ошибкой после записи pid-файла (например, не записалось сообщение «X — lead»), pid-файл и heartbeat убирает сам. Самоназначение lead'а (§6.1) при общей паузе разрешено, при личной паузе агента — нет: он станет lead'ом следующим `wait` после `resume`.

Курсор `cursors/<name>`: `Acked: 14` (всё ≤ 14 обработано), `Pending: 15` (выдано последним wait, подтвердит следующий). Вывод:
```
── T001 · 2 новых ─────────────────────────────
#14 codex-1 → all · re #12 · 12:03
  Предлагаю лидом claude-1: …
#15 [система] claude-1 → all · 12:04
  …
── NEXT: обработай, затем: bash .brigada/bin/brg wait --as claude-1.k7f3q9
```
Таймаут: `── нет новых (100 с) · ход не завершай · NEXT: …`. Стоп: `── STOP: человек остановил бригаду. Заверши ход.`

### 5.1 Таймауты по харнессам

Значения **консервативные — до замеров** в каждом харнессе. Все ниже 120 с — дефолтного лимита команды: модель может не передать увеличенный таймаут инструмента (особенно после сжатия контекста). Повышать — только если замер покажет, что модель делает это стабильно.

| Харнесс | Лимит команды | `wait_timeout` сейчас | Цель после замера |
|---|---|---|---|
| Claude Code | по умолч. 2 мин, макс. 10 мин (параметр `timeout`); на лимите уводит в фон | 100 | 540, если модель стабильно передаёт `timeout: 600000` |
| OpenCode | по умолч. 2 мин, верхний предел снят | 100 | 540 при том же условии |
| Codex (macOS/Linux) | unified_exec: команда «паркуется» через 10–30 с, дальше опрос моделью (`write_stdin`) | 25 (вернуться до парковки) | по замеру |
| Codex (Windows) | unified_exec по умолчанию выключен — ближе к обычной блокирующей команде | 100 (`wait_timeout.codex.msys`) | по замеру |
| неизвестный | — | 100 (`wait_timeout.default`) | — |

Таймаут инструмента = `wait_timeout` + 60 с (≤ 600 с) — печатают `join` и `status`. `doctor`: `wait_timeout` > 540 с — ✗, > 110 с (Codex вне Windows — > 25 с) — ⚠. Числа в опциях, `config` и окружении — десятичные (`08` — это 8, ведущие нули допустимы, до 9 цифр). Значение числового ключа `config`/`config.default`, которое не число, brg пропускает (берёт следующий слой или встроенное значение), а `doctor` даёт ⚠ с ключом и взятым значением.

«Выпадение из цикла» — латентность модели (выход `wait` → следующий вызов инструмента) > 60 с без учёта повторов запроса провайдером, или самостоятельное завершение сессии. Опросы запаркованной команды Codex в логе `wait` не видны — их стоимость оценивается по транскрипту. Токены на пробуждение = токены сессии / вызовы `wait`, на модели, что реально будет в бригаде.

**Правило жизнеспособности:** **≤ 15 вызовов модели на час простоя.** Не достигающий его харнесс (ожидаемо — Codex с парковкой) участвует с повышенной стоимостью простоя либо только «по тычку» человека — решение по итогам замера.

### 5.2 Живость агента

Состояние в `who`/`status` (и в списке «Онлайн» у `join`, `status`): **(решение человека, 0.6.0) «ждёт» ⇔ свободен** — идёт `wait` агента, а пометки «работает» (§5.4) нет; агент готов к поручению. Остальные показываются так:

| Состояние (внутреннее) | Пометка | Показ |
|---|---|---|
| `waiting` (жив wait) | нет | **ждёт** |
| `waiting` | есть | **работает: подпись, N мин** (подпись — до 2 слов; N мин — сколько стоит пометка) |
| `working` (недавний вызов brg, wait нет) | нет / есть | **работает** / **работает: подпись** — агент между двумя `wait` или его `wait` ещё не начат; дальше — «не на связи» |
| `asleep` (нет wait и вызовов дольше `asleep_after`, 15 мин) | — | `asleep` |
| `gone` (`leave` или тишина дольше `gone_after`, 1 ч) | — | `gone` |
| `waiting` / `working` при стопе человека (общем или личном, §9) | — | **остановлен** — стоп завершил ход агента, он не работает |
| `waiting` / `working` при паузе человека (общей или личной, §9) | как у состояния | то же, что у состояния, и «(пауза)»: пауза ход не завершает — агент ждёт, новую работу не начинает |

Пороги щедрые: агент, 10 минут гоняющий тесты, не пропал. Пометки: «не на связи N мин» — wait не идёт дольше `wait_timeout` + 60 с (раньше «без wait»); «возможно выпал» — ни wait, ни вызовов brg дольше max(`wait_timeout` + 60 с, `dropout_after` = 300 с), кроме остановленных: подсказка человеку написать агенту в чат «продолжай». Пометка «работает» этой подсказки не отменяет: участник с фоновым подагентом обязан сидеть в `wait`, поэтому пометка без живого `wait` — признак выпавшего агента. Единственное исключение — пометка `Via: busy` (команда `brg busy`: «подагент блокирует меня», харнесс без фоновых подагентов): «возможно выпал» у такого агента не показывается, «не на связи» — показывается. Значения внутреннего состояния (`ST`: waiting/working/asleep/gone) не меняются и не зависят от пометки; ею дополняется только показ.

**Запущенные brg (0.9.0, §5.5).** `ST` считается так же: замерший или упавший агент — живой надзорный `wait` → `waiting` («ждёт»); идёт ход — вызовы brg и `touch_seen` надзора → `working`. В `who`/`status` к строке добавляется «(запущен brg, S003)» и состояние записи (§5.5): «ход N идёт M мин · последнее событие K мин назад», «упал: …», «отказ в правах: …», «надзор не отвечает», «конфликт». У такого агента с живым надзором и идущим ходом нет «не на связи»/«возможно выпал» (`idle_note_v`) — вместо этого «ход N идёт M мин · последнее событие K мин назад (возможно, долгий инструмент)», и он «на связи» для выбора lead'а (`lead_online`, §6.2) без окна `wait_timeout` + 60 с: прошлый lead в долгом ходе не пропускается. Остановленный запущенный агент (в `stopped` надзор `wait` не держит) стареет до `asleep`/`gone`, как ручной.

### 5.3 Известные минусы (приняты сознательно)

- Сообщение человека в чате харнесса дойдёт, когда wait вернётся (до `wait_timeout`), либо после Esc.
- Простой не бесплатен: один вызов модели на таймаут на агента.
- Гарантии нет: агент может завершить ход. Это видно («не на связи», «возможно выпал», `asleep`); lead переназначает его подзадачи, человек говорит «продолжай».

### 5.4 Подагенты

**(решение человека, 0.5.0)** Участник бригады — только координатор своей части; любую работу делают подагенты, которых он запускает у себя. Это обязательная рамка (PROTOCOL, раздел 2), а не ожидание: в версии 0.4.1 это была рекомендация, и в прогонах человека она доходила не до всех — участники сами читали и правили код.

- **Сам участник** только координирует: вызовы brg и переписка, обсуждение и решения, поручения подагентам и приём их результата (отчёт подагента, `git diff --stat`), короткие документы координации (`shared/plan.md`, `summary.md`), коммит lead'а.
- **Подагент** делает всё остальное: чтение и правку кода и документов проекта, исследование, ревью и проверку чужой работы, разбор упавших тестов.
- **Сколько подагентов.** По умолчанию у участника одновременно работает один подагент (последовательно — сколько нужно). Больше — только если это явно разрешил человек: в постановке задачи, в чате участника или сообщением `human`.
- **Харнесс без подагентов** — единственное исключение: участник делает работу сам, короткими шагами между `wait`, и говорит об этом бригаде на перекличке.
- **Фоновые подагенты** есть в Claude Code и в OpenCode v2 (`task … background: true`); блокирующий вызов подагента (тот же OpenCode без `background`) — `brg busy` перед ним.

Почему так: контекст участника живёт всю задачу и растёт с каждым пробуждением — чем он меньше, тем дешевле пробуждение и позже сжатие; участник, занятый работой сам, выпадает из цикла, а бригада простаивает. Где правило повторяется, чтобы его увидел каждый: блок brigada в `AGENTS.md`/`CLAUDE.md` (§3), README (§1, «Подагенты»), PROTOCOL (раздел 2), вывод `join`, `task new`, `item claim` и `item review --start`. brg подагента от участника не отличает — проверить правило он не может.

Механика (README, обязательна): подагент ни при каких обстоятельствах не подключается к бригаде — не вызывает `join`, `wait`, `leave`, `stop` — его `wait` под именем участника вытеснит wait участника (SUPERSEDED), и тот выпадет из цикла; можно команды для чтения и короткий `run --sync` под именем участника. `run` — изменяющая команда (§3), поэтому подагенту передаётся полное имя участника, с ключом; командам чтения хватает и базового. brg подагента от участника не отличает — правило только в документах.

**Пометка «работает» (0.6.0, решение человека: «ждёт» ⇔ свободен — §5 п. 13, §5.2).** Участник сообщает «мой подагент работает» сам; brg проверить этого не может — как и само правило подагентов. Одна пометка на агента (подагент одновременно один): `run/busy/<базовое имя>` — заголовки `Task: T00N`, `Since: <epoch>`, `Note: <подпись или пусто>`, `Item: <I00N или пусто>`, `Via: wait|claim|review|busy`; запись — tmp + `mv`.

- **Действительность.** Пометка с `Task`, не равной активной задаче (или без активной задачи), **не существует** — для `agent_state`, `NEXT:`, `who`, `status`, доски. Поэтому очистка `run/busy/` при `task close|cancel` (и `--cancel-current`) — просто уборка, гонки безвредны. Читает её одна функция (`busy_read`). Без активной задачи `wait --busy` и `busy` пометку не ставят: «задачи нет — пометка не ставится» (не отказ).
- **Как ставится.** `wait --as X --busy ["подпись"]` — в начале `wait` (после проверки STOP; STOP пометку не трогает), `Via: wait`; `Since` и `Item` переносятся с прежней пометки, только если она действительна и `Note` та же. `item claim I00N` → `Note: I00N`, `Item: I00N`, `Via: claim` (и вернуть сданную в работу — тоже); `item review I00N --start` → `Note: проверка I00N`, `Item: I00N`, `Via: review` — взял (проверяет) = работает. `brg busy --as X ["подпись"]` — пометка без ожидания, `Via: busy`: харнессы, где вызов подагента блокирует участника (OpenCode), и работа вне подзадач; `busy --off` — снять; при STOP команда разрешена (она не начинает работу), первая строка — баннер STOP, `NEXT:` — «заверши ход».
- **Подпись обрезается, а не отвергается** (§4.2): управляющие символы и `"` `'` `\` `$` `` ` `` `%` → пробел (`%` — cmd.exe раскрывает его и в кавычках, а `NEXT:` на Windows идёт через `brg.cmd`), пробелы схлопываются, остаются первые 2 слова, ≤ 48 байт по границе UTF-8; если что-то изменилось — предупреждение; ничего не осталось — пометка без подписи (в `NEXT:` — голый `--busy`, не `--busy ""`).
- **Как снимается.** Простой `wait` (без `--busy`) — явное «я свободен»; `busy --off`; `leave`; `join` (в т.ч. `join --as`: новая сессия — подагента нет); смена или закрытие задачи. Пометка с **пустым** `Item` командами подзадач **не снимается никогда** (иначе `item release` lead'ом чужой подзадачи или его `--verdict skip` сняли бы пометку «финальная валидация», пока подагент работает): при `item done`/`--verdict` у такого агента — строка «ты отмечен «работает: T» — если подагент закончил, следующий wait без --busy». Пометка с `Item = I00N` снимается у **своего владельца**, когда подзадача от него уходит: у исполнителя — `item done`, `release` (кем бы ни выполнен), `cancel`, `reassign` (у старого исполнителя); у проверяющего — его `--verdict` по этой подзадаче (чужой вердикт по сданной его пометку не снимает: собственная действующая пометка на подзадаче, из `Reviewing:` уже убранного, остаётся и при `wait --busy`, §7.1.1), а также `item cancel`, `release`, возврат в работу (`claim` исполнителем сданной) и `reassign` — они очищают `Reviewing:`, и пометки «проверка I00N» у всех названных там снимаются. Действие над чужой подзадачей пометку другого агента не трогает. Строка «ты отмечен…» печатается только действующему исполнителю или проверяющему этой подзадачи (не lead'у, отпустившему чужую). Новому исполнителю `reassign` пометки не ставит — в системном сообщении ему подсказка «поручи подагенту и `wait --busy "I00N"`».
- **`NEXT:` = текущее состояние пометки.** Одна функция (`next_wait`) строит `wait --as … [--busy "<подпись>"] [--timeout S]` для **всех** `── NEXT:` и ошибочных `NEXT:` (`send`, `read`, `status`, `task …`, `item …`, `run …`, `lead …`, ошибки разбора; до `need_agent` имя берётся из `--as`/`BRG_AS`), включая `NEXT:` самого `wait` — он вычисляется при завершении (пометку могли снять за время ожидания). Поэтому после `claim`/`review --start` `NEXT:` сам содержит `--busy "I00N"`, а после `done` — нет; ошибка в `--busy` не превращает `NEXT:` в простой `wait`, снимающий пометку. Дополнительно: вывод `wait` с действительной пометкой (пачка и таймаут) — строка перед `NEXT:` «Ты отмечен «работает: T». Подагент закончил и ты свободен — следующий wait без --busy»; простой `wait` у агента с подзадачей `claimed` или с `Reviewing:` на нём — строка «У тебя I003 в работе: если подагент работает — wait с --busy "I003"» (не отказ). Гонка `item cancel` lead'ом со стартом `wait --busy "I003"` у исполнителя допустима: пометку снимет простой `wait`. Устаревший `NEXT:` (выдан до смены задачи) не должен пометить новую задачу: подпись `I00N` / `проверка I00N` ставится, только если эта подзадача активной задачи claimed этим агентом или он в её `Reviewing:`; иначе — предупреждение и пометки нет (так же у `busy`).
- **Показ.** `who`, `status`, «Онлайн» — §5.2; сводка на таймауте — «свободны» (§5 п. 9); снимок доски — поле `mark` агента `{note, since, via, item}` (§9.1).

### 5.5 Агенты, запущенные brg (0.9.0)

**(решение человека, 0.9.0)** Человек запускает агентов сам — из терминала (`brg spawn`) и с доски («Добавить агента», §9.1): видит их состояние и что они делают, а они работают в бригаде так же, как подключённые вручную. Решения человека:
1. **Два вида участников в одной бригаде.** Подключённые вручную — ровно как раньше (цикл `wait`, ход не завершают). Запущенные brg — по механизму ниже. Друг для друга неотличимы: имена с ключом, задачи, lead, подзадачи, ревью, `run`, вопросы, стоп, пауза.
2. **Запущенный агент замирает, когда свободен:** завершает ход (процесс харнесса выходит). Есть будящее (по правилам `wait`, §5 п. 8) — brg продолжает его сессию и передаёт пачку прямо в промпт (один запрос к модели). Работает подагент — ход не завершает, сидит в `wait --busy`.
3. **Права** — явный выбор при запуске, по умолчанию полные, с предупреждением. Отказ в правах **виден** на доске, кнопка «дать полные права» действует со следующего хода той же сессии.
4. **Лимитов нет; токены и стоимость видны** по каждому агенту и итогом.
5. **Отдельного «оживления» нет.** Аварийный конец хода виден на доске, lead'у — сообщение; пачка доставляется заново **следующим пробуждением** — его вызывает новое сообщение агенту или кнопка «Разбудить». Без автоповторов.
6. **Запускает только человек** (терминал и доска).

Этап A — только **OpenCode** (Claude Code и Codex — этап B), только macOS/Linux (MSYS, Cygwin, WSL — отказ «пока не поддерживается»).

**Как устроен OpenCode 2.0.23** (по коду бинаря и проверкам без LLM): команды shell-инструмента модели идут в своих группах процессов; на **SIGINT** `opencode run` штатно прерывает сессию и гасит их (код 130), обработчика SIGTERM нет. Без `--auto` запрос разрешения не висит: `run` отказывает сам, в stderr — `! permission requested: <действие> (<ресурсы>); auto-rejecting` (с ANSI), в потоке — `tool_use` со `status: "error"` и «…request was rejected». По умолчанию в каталоге проекта можно всё (shell, правки, сеть, git push); спрашивается только выход за каталог проекта и чтение `*.env`; `--auto` одобряет и это. JSON-поток stdout (`--format json`) — только основная сессия; `tool_use` пишется по **завершении** инструмента (идущий не виден). События: `step_start`, `text`, `tool_use`, `step_finish` (`part.tokens`, `part.cost`), `error` (`error.message`); у каждого `sessionID` (`ses_…`); ошибка шага или прерывание — событие `error` и код ≠ 0. Подагенты — дочерние сессии: их id — в выводе завершённого `tool_use` инструмента `task` (`task_id: ses_…`; фоновый — `sessionID: ses_…`). `opencode session export <id>` печатает JSON, в начале которого `info.cost` и `info.tokens {input, output, reasoning, cache{read, write}}`; без `--standalone` команды OpenCode поднимают у человека долгоживущий фоновый сервис. Сообщение-аргумент OpenCode перекодирует (кавычки, `\"`), **сообщение из stdin** (не TTY) проходит как есть. В окружении команд модели — `OPENCODE_SESSION_ID` (у подагента — id дочерней сессии), `OPENCODE=1`, `AGENT=1`.

#### Запись запуска

`run/spawn/S00N/` (сквозной номер по проекту, `run/spawn.seq` под локом `spawnseq`). Файл `spawn` — заголовки (tmp + `mv`); пишет его только держатель лока надзора (надзор; при создании — `brg spawn`, при `rm`/`detach`/`join --as` без живого надзора — эти команды под локом):
- `Id`, `Agent` (базовое имя), `Harness`, `Model`, `Rights: full|project`, `Session`, `State`, `Note`, `Created`, `Created-Epoch`, `Supervisor` (pid — только для показа);
- `Turn`, `Turn-Start`, `Turn-End` (эпоха выхода харнесса из `turn.N.exit`), `Turn-Result: ok|crash|interrupted`, `Turn-Stopped: 1` (ход кончился при стоящем стопе), `Last-Error`, `Perm-Denied` (последний отказ в правах: держится до смены прав, успешный ход его не снимает), `Last-Event` (эпоха последнего роста `events.log` в текущем ходе; сбрасывается в начале хода), `Hold: 1` (серия аварий);
- `Tokens-In`, `Tokens-Out`, `Tokens-Reasoning`, `Tokens-Cache-Read`, `Tokens-Cache-Write`, `Cost` (строка; складывает awk `printf "%.6f"`), `Tokens-Source: export|stream`, `Sub-Sessions`;
- `Locale-Set`, `Locale` (исходная локаль человека, §9.1);
- тело — последний текст модели за ход (≤ 2 КБ, ключ замаскирован).

Рядом: `join.out` (вывод join — часть первого промпта), `prompt.N` (промпт хода; хранятся последние 5; наружу — только путь) и `prompt.head` (первые строки последнего промпта, ключ замаскирован — для доски), `events.log` (+ `events.log.1` — ротация перед ходом, если > 50 МБ), `stderr.log`, `supervisor.log`, `activity.log` (растёт) и `activity.tail` (последние 50 строк, tmp + `mv`, его читает доска): строки `epoch<TAB>kind<TAB>текст` (`turn`, `tool`, `text`, `error`, `permission`, `end`), ≤ 300 байт, управляющие символы → пробел, ключ замаскирован; `children` (id дочерних сессий) и `children.tok` (кэш их итогов), `stream.tok` (номер последнего учтённого хода и сумма `step_finish` основной сессии по всем ходам), `sub.tok` (сумма итогов дочерних сессий по последнему экспорту), `turn.N.parse` и `turn.N.text` (разбор хода N по ходу, ниже). От обёртки хода: `turn.pid`, `turn.hb` («pid обёртки epoch», раз в секунду), `turn.event`, `turn.session`, `turn.N.exit` (код и эпоха), `turn.N.off` (смещение `events.log` и `stderr.log` до хода). **Флаги** кладут `brg spawn …` (в т.ч. по запросу сервера доски): `rm`, `detach`, `wake`, `rights` (содержимое — новое значение); надзорный `wait` их только читает, удаляет надзор после обработки; `turn.stop` — просьба обёртке остановить ход.

| State | Значит | Показ |
|---|---|---|
| `starting` | надзор запущен, первый ход не начат (в т.ч. ждёт снятия стопа) | работает · запуск |
| `running` | идёт ход (обёртка жива) | работает · ход N, M мин · последнее событие K мин назад |
| `frozen` | ход кончился, надзор ждёт будящее | **ждёт** |
| `crashed` | последний ход аварийный (`Hold: 1`), надзор ждёт **нового** будящего | ждёт · «упал: <ошибка>» |
| `stopped` | стоп человека | остановлен — снимется кнопкой «Продолжить» (`brg resume`) |
| `conflict` | надзорный `wait` раз за разом вытесняется чужим `wait` под тем же именем | ждёт · «конфликт: под именем работает другой wait» |
| `detached` | забран в окно (`spawn detach` или `join --as`) — дальше обычный агент | как обычный |
| `removed` | убран (`spawn rm`) или ушёл сам (`leave`) | gone |
| (не `detached`/`removed`, а надзор мёртв по правилу лока) | надзор умер | «надзор не отвечает» · «Разбудить» перезапускает |

#### Агент

`brg spawn` подключает агента сам: та же функция, что `join --harness H --model M` (не копия), плюс `Spawn: S00N` в профиле; вывод join (вариант для запущенного — короткие правила, без «ход не завершай») входит в первый промпт; модель `join` не делает. «Запущен ли агент» — одна функция `spawned_v` (в профиле `Spawn:` и запись не `detached`/`removed`).
- **`join --as X`** запущенного — снимает `Spawn:`, запись → `detached`. Одна попытка лока надзора **до** `roster`: живой надзор → отказ «надзор жив: `brg spawn detach S` — забрать в окно»; жива обёртка хода (даже при мёртвом надзоре) — отказ «идёт ход агента — дождись его конца или `brg spawn rm`». Правило «только после выпадения» (§3) действует как раньше.
- **`join` при `BRG_SPAWN`** в окружении, указывающем на живую запись этого же `.brigada`, — отказ: `OPENCODE_SESSION_ID` задан и ≠ сессии записи — «ты подагент участника X — к бригаде не подключайся, выполни поручение»; иначе — «join не нужен: тебя подключил brg, имя — в первом сообщении».
- **`wait`/`leave`/`busy` с `--as` запущенного**, когда `OPENCODE_SESSION_ID` задан и ≠ сессии записи (или `turn.session`, пока сессия не перенесена в запись), — отказ «ты подагент…» (`wait` — код 0 и `NEXT:` «выполни поручение и верни результат»).
- Раннер `brg run` делает `unset BRG_SPAWN`: тесты проекта его не наследуют.

**Фразы ожидания — одна функция `next_wait`** (§5.4): у ручного — как раньше (`wait --as …`); у запущенного без действительной пометки — «заверши ход — brg разбудит тебя, когда будет новое»; с пометкой — `wait --as … --busy "…"`. Через неё — все `── NEXT:`; свои строки для запущенного — у вывода `join`, `busy`, баннера и отказов стопа/паузы (`stop_banner`, `work_refuse`), `w_notes_v` («у тебя I003 в работе — продолжи (поручи подагенту) или сдай/отпусти»; «ты отмечен «работает» — подагент закончил? тогда заверши ход»), строк таймаута `wait --busy`, `status`. Ни одна строка brg запущенному не велит «не завершать ход» или ждать в простом `wait`.

**Простой `wait` запущенного** (вызвал сам агент, без надзора) не блокирует: снимает пометку, подтверждает предыдущее, выдаёт будящее, если оно уже есть; иначе сразу `── нет новых · ты свободен — заверши ход: brg разбудит тебя, когда будет новое` и `── NEXT: заверши ход`. Второй и следующие пустые возвраты в одном ходе (счётчик `turn.N.idle`, только при `BRG_SPAWN`) — строка жёстче и метрика `wait.idle_repeat`. `wait --busy` — как раньше (блокирует).

#### Надзор, лок, обёртка хода

**Надзор** `brg __spawn S00N` — отдельный процесс на агента, запускается как раннер `brg run` (`nohup` + `set -m`, все fd перенаправлены, fd 3–9 закрыты, `trap '' HUP`); не в сервере доски — закрытая доска агентов не останавливает.

**Лок надзора** `run/locks/spawn.S00N.lock` — на всё время жизни надзора, один надзор на запись. Своя функция `spawn_lock_try S [НАБЛЮДАТЬ_СЕК]` (не `lock_acquire` и никогда не по возрасту): владелец `$$` — «мой» (после `exec`); мёртвый владелец (`pid_alive`) с `hb` старше `runner_dead_grace` — лок снимается сразу (`lock_break`); живой pid с молчащим `hb` — мёртв только после **непрерывного** наблюдения дольше `spawn_stale` (30 с; `hb_obs_init`/`hb_obs_tick` с порогом — для раннеров поведение прежнее). Новый надзор наблюдает до `spawn_stale + 5` с (владелец подаёт признаки жизни — тихий выход). Разовые вызовы — одна попытка; лок у живого надзора → флаг (`rm`/`detach`/`rights`) или отказ (`join --as`); **надзор «молчит»** (pid жив, `hb` старше `spawn_stale`: остановлен, завис, pid чужой после перезагрузки) — флаги обслуживать некому, поэтому `wake`, `rm`, `detach`, `rights` ещё и запускают новый надзор, который наблюдает и забирает лок, а `join --as` подсказывает `brg spawn wake`; надзор только что умер (pid мёртв, `hb` свежий) — подождать до `runner_dead_grace`, взять лок и сделать действие самому: флаг не остаётся без обработчика. `spawn wake` — флаг живому надзору или новый надзор и сразу возврат. После `exec` новый образ добавляет лок в `HELD`. `doctor` судит `spawn.*` как exec-лок (по `hb` и `runner_gone`), без ✗ «держится N с» у живого надзора.

**Сердцебиение надзора — всегда:** `hb` в каталоге лока раз в 5 с во **всех** ожиданиях (ход, надзорный `wait`, `stopped`, паузы, ожидание обёртки, `rm`/`detach`); надзор спит шагами по 1 с, ни одна операция не держит его дольше `spawn_stale / 2`.

**Обёртка хода** — отдельный процесс `brg __turn S00N N` (как раннер: `set -m` — своя группа и свой `$$`; подшелл не годится: в bash 3.2 у него `$$` надзора). Восстанавливает локаль из записи, `cd` в проект, снимает служебные переменные (`BRG_AS`, `BRG_VIA_CMD`, `BRG_SPAWN_*`, `BRG_CMD_LC*`), `export BRG_SPAWN=S00N`; запускает харнесс своим ребёнком под `set -m` (без него bash выставил бы фоновой команде SIGINT = SIG_IGN): `<bin> run <spawn.opencode.args> --format json --model M [--auto] [--session SID] --title "brigada S003 opencode-3" <prompt.N >>events.log 2>>stderr.log`. Раз в секунду — `turn.hb` и проверка `turn.stop`; раз в 5 с — рост `events.log` → `turn.event`; первая строка с `sessionID` при пустой сессии записи → `turn.session` (надзор сразу переносит в запись: «ты подагент» работает с первого хода). По `turn.stop`: `kill -INT` своему ребёнку, через 5 с TERM, ещё через 5 с KILL. После выхода харнесса — `turn.N.exit` (код, эпоха). Обёртка переживает `kill -9` надзора. **Живость обёртки:** жива, если pid из `turn.hb` жив и `turn.hb` свежий; мёртва — pid мёртв и `turn.hb` старше grace; живой pid с молчащим `turn.hb` — мёртв после непрерывного наблюдения дольше `spawn_stale`. Пока обёртка жива, второй ход не начинается.

**Сигналы** — только своим детям: обёртка → харнесс. Надзор своему `wait` и обёртке сигналов не шлёт (флаги и `turn.stop`); чужим процессам — только флаги.

#### Цикл надзора

1. **Восстановление** (надзор не первый для записи — `Turn` > 0 — и не `--continue`; прежний надзор умер между `running` и запуском обёртки — хода не было, не авария): дождаться, пока обёртка текущего хода станет мёртвой или появится `turn.N.exit`; итог хода — по коду; первый надзорный `wait` — с откатом (`ROLLBACK`).
2. **Ход.** Промпт → `prompt.N`; `Turn`, `Turn-Start`, `State: running`; обёртка. Пока она жива: `hb`, `touch_seen` агента раз в `heartbeat`, перенос `turn.event`/`turn.session` в запись; флаги: `rm` → `turn.stop`; `rights` — применить сразу (действует со следующего хода); `detach` — после хода; `wake` — удалить (ход и так идёт). Нет `turn.N.exit` — `crash` «обёртка хода пропала».
3. **Итог хода.** `ok` — код 0 и нет события `error`; `interrupted` — ход остановлен по `turn.stop`; иначе `crash` (`Last-Error` — сообщение `error` или «код выхода N»); ход кончился при стопе — `Turn-Stopped: 1`. **Откатывать — только по коду**: `crash`/`interrupted` → следующий надзорный `wait` с `ROLLBACK`; `ok` → нет (пачка, которую модель получила своим `wait` в ходе, — `Pending`, её подтвердит следующий `wait`). **Хвостовой `wait`** (команды модели живут в своих группах и могут пережить ход): жив `wait` агента или `run/wait/<агент>.last` изменился за ход и ≥ `Turn-End` → `ROLLBACK`. Значение `.last` до хода надзор запоминает: `wait` самого надзора кончается за миг до хода, и при ходе короче секунды его `.last` совпал бы с `Turn-End` — без этой проверки пачка приходила бы снова и снова. Первая авария серии (переход в `Hold: 1`) — системное сообщение lead'у (канал задачи, `Wake: <lead>`; lead — сам агент или задачи нет — `To: human` в канал задачи или `lobby`: сообщение «всем» пришло бы в промпт самому упавшему): «opencode-3 (запущен brg, S003): ход N упал — <ошибка>. Разбудит следующее сообщение ему или «Разбудить» на доске»; следующие аварии серии — только доска; серия кончается первым успешным ходом (иначе lead и упавший будили бы друг друга по кругу). После хода — извлечение активности и токенов из потока, экспорт токенов — в фоне, после старта надзорного `wait`. **Обновление brg:** между ходами `VERSION` проекта ≠ версии надзора → `exec … __spawn S00N --continue` (лок «мой» по `$$`; без восстановления; отложенные откат и FORCE передаются аргументами; пока идёт фоновый экспорт токенов — после него).
4. **Ожидание.** `State: frozen|crashed`. Сначала флаги `rm`/`detach`. Затем надзор запускает своим ребёнком `brg wait --as <полное имя> --timeout <spawn.wait_timeout>` с `BRG_SPAWN_WAIT=<файл результата>`, `BRG_SPAWN_ID`, и при необходимости `BRG_SPAWN_HOLD=1` (`Hold: 1`), `BRG_SPAWN_FORCE=1` (`wake`, снятие стопа), `BRG_SPAWN_ROLLBACK=1`; stdout — промпт. Результат: `msg|deadline|pause_end|force` → ход (лежит флаг `detach`/`rm` — надзор сам делает `cursor_rollback` и обрабатывает флаг; `wake` — удалить и строка причины); `flag:rm|detach` → п. 6, 7; `timeout`, `epipe` → снова ждать; `stop` → `State: stopped`, опрос раз в секунду; стоп снят и `Turn-Stopped: 1` → `wait` с FORCE и строкой «── стоп снят человеком: проверь status; есть начатая работа — продолжай, нет — заверши ход», иначе обычный `wait`; `left` → `removed`, выход; `superseded` (под именем жив чужой `wait`, обычно хвост хода) → снова `wait` с `ROLLBACK`, ≥ 3 раз за 60 с — `State: conflict` и повторы раз в 30 с; `orphan|int|hup|term` и прочее → снова, с паузой. **Нет файла результата** (`wait` упал через `die` или убит) → следующий `wait` с `ROLLBACK`; профиль с `Left:` → `removed`; ключ профиля ≠ ключу, с которым `wait` запускался, или нет `Spawn:` → `detached`; иначе `Last-Error` из stderr `wait` и пауза. **Защита от горячего цикла:** `wait` кончился без результата или с ошибкой быстрее 2 с — пауза 1, 2, 4, … ≤ 60 с.
5. **Промпт пробуждения** = `── brg разбудил тебя (S003, ход N) — ты opencode-3.<ключ>` + вывод `wait` как есть (пустой FORCE — `── нового нет` и `NEXT:`). Ключ в промпте полный (он нужен агенту), на доске и в `spawn show` — замаскирован. Харнессу промпт подаётся **через stdin**; сессия — `--session <Session>`; `Session` пуст (первый ход упал до первого события) — первый промпт заново плюс вывод `wait`.
6. **`rm`.** Ход идёт → `turn.stop`, дождаться обёртки; затем `leave` от имени агента (общая функция с `brg leave`: роли, выбор lead'а, сообщения), `State: removed`, выход. Надзор мёртв → `brg spawn rm` делает это сам под локом надзора (осиротевшая обёртка видит `turn.stop` сама).
7. **`detach`.** Ход идёт → дождаться его конца (не останавливать); `State: detached`, `Spawn:` из профиля убрать, выход. `brg spawn detach` печатает `cd <проект> && opencode --session <Session>` и «напиши в окне: «продолжай: status, затем wait»»; `status` агента — «тебя забрали в окно: ход не завершай, цикл wait», `NEXT:` — обычный `wait`. Надзор мёртв → `brg spawn detach` сам, под локом.
8. **`wake`** («Разбудить», `spawn wake`). Надзор ждёт → его `wait` видит флаг и сразу завершается в режиме FORCE: всё после `Acked` (откатанное, тихое); пусто — «── человек попросил продолжить: проверь status; есть работа — продолжай, нет — заверши ход». Надзор удаляет `wake` до следующего `wait` (иначе FORCE по кругу), `Hold` снимается. Ход идёт — флаг удаляется без действия. Стоит стоп — флаг не ставится: «бригада остановлена — сначала «Продолжить» (`brg resume`)». Надзор мёртв → новый надзор (возьмёт лок или выйдет, если жив старый): восстановление, затем ход в режиме FORCE.
9. **`rights`** (0.9.1) — **не будит.** Флаг надзор применяет сразу, и в ожидании, и во время хода: `Rights` в записи, `Perm-Denied` снимается, пишется `Rights-Note` — строка о смене прав («── человек расширил права до full (вне каталога проекта и чтение .env — теперь можно): если тебе или твоему подагенту отказывали — можно повторить» / «── человек изменил права на project: вне каталога проекта и чтение .env — отказ»). Новые права действуют со следующего хода (идёт ход — с конца текущего). `Rights-Note` входит в **каждый** промпт пробуждения (первой строкой после `── brg разбудил тебя …`); при составлении промпта надзор пишет `Rights-Note-Turn: N`, после хода `ok` номер N строка снимается, если с тех пор права не менялись (смена прав сбрасывает `Rights-Note-Turn`). Так строка переживает аварийный ход, перезапуск надзора и `exec`. Без живого надзора `spawn rights` пишет то же сам, под локом. Вывод и доска: «права S001: full — со следующего хода; разбудить сейчас — «Разбудить»». (В 0.9.0 смена прав будила агента FORCE-ходом «повтори действие» — в живом прогоне отказ получил подагент, и ход был потрачен впустую.)

#### Надзорный `wait` (`BRG_SPAWN_WAIT`)

Только для запущенного агента с совпадающим `BRG_SPAWN_ID`. `w_finish` пишет результат в файл (tmp + `mv`); вывод — как обычно (он и есть промпт). Каждый тик **до** выдачи — флаги записи (только чтение): `wake` → FORCE на этом же тике (`rights` не будит, 0.9.1); `rm`/`detach` → результат `flag:<имя>` без выдачи.
- **HOLD** (после аварии будит только новое): отметки `H[канал]` берёт надзор **в момент аварии, до отката** (`hold.marks`): это `Pending` курсора агента в каждом слушаемом канале — то, что упавший ход видел. Будит всё, чего упавший ход не видел, — в том числе сообщение, пришедшее во время хода или между аварией и стартом wait; без новых сообщений ходов нет («провайдер лежит» не крутится: каждый следующий ход — на новую порцию). Wait отметки читает (файла нет — берёт `seq` на старте); в `w_channels_init` (на старте и при смене задачи) для этих каналов `CH_SEEN := max(Acked, H)`, для новых (новая задача) — `CH_SEEN := Acked`. Будит только **новое** будящее — в том числе «новая задача» и «ты lead» (`task new` пишет `tasks/active` раньше сообщений), а выдаётся всё после `Acked`. Дедлайны в HOLD сами не будят (как на паузе); снятие паузы будит (`W_LIFT`) — один повтор по действию человека.
- **FORCE**: на первом тике выдать всё после `Acked`, даже тихое и пустое (результат `force`; пусто — `── нового нет`); на паузе — как пробуждение человеком.
- **ROLLBACK** — до всего, что может завершить wait (в том числе до проверки STOP), строго по порядку: (1) прочитать pid-файл (предшественник); (2) `w_claim`; (3) дождаться смерти предшественника (`pid_alive`; вытесненный `wait` выходит на ближайшем тике и дописывает начатую выдачу; ≤ 5 с); (4) `cursor_rollback`; (5) `w_channels_init`. Пачка, выданная хвостовым, вытесненным или осиротевшим `wait` в никуда, придёт снова, а бесконечного дубля нет. Сделанный откат wait отмечает в файле результата второй строкой `rolled`; **надзор снимает желание отката только по ней** (STOP, отсутствие результата его сохраняют), а FORCE — только когда wait выдал пачку. **Любой переход в `detached` откатывает:** надзор — если откат ещё должен; `spawn detach` и `join --as` при мёртвом надзоре — всегда (итог последнего хода неизвестен), после того как живого `wait` у агента нет. Агент в окне получит дубль, но не потерю. `cursor_rollback NAME` — во всех каналах агента `Pending := Acked`.
- Метрика — `wait … spawn=1` (главная метрика пробуждений, §11, не смешивается с ожиданием надзора). STOP, пауза, дедлайны, смена задачи — как у обычного `wait`. Тестовый крючок `BRG_TEST_DELIVER_DELAY` — задержка между выводом и `cursor_write`.

**Принятые остатки.** Пачка, которую фоновый `wait` выдал в файл **посреди** хода и модель не прочитала, теряется — как у ручного агента (README: `brg wait` никогда не запускать в фоне). Сводки дедлайнов, выданные в упавшем ходе, откат не вернёт (индекс удаляется после вывода, §8). На редком пути (откат после успешного хода, ход и хвостовой `wait` в одну секунду) возможен дубль одной пачки — потери нет.

#### Лента по ходу, чей отказ, контекст, токены (0.9.1)

**Разбор событий по ходу.** В 0.9.0 события разбирались только в конце хода — 19 минут хода доска показывала пустую ленту. Теперь, пока обёртка жива, надзор не чаще раза в 3 с и только если `events.log` вырос разбирает новые байты той же awk-программой (с маскировкой ключа) и копит итог в файле состояния хода `turn.N.parse` (одной записью, tmp + `mv`): **абсолютные** смещения `events.log` и `stderr.log`, до которых всё разобрано; суммы `step_finish` хода; последняя ошибка (`error`); `Context`; отказы основной сессии из потока (их `input`) и строки отказов из stderr; `Activity-Size` — размер `activity.log` после дописки строк этого разбора. Последний непустой текст — в `turn.N.text`. Итог хода (`ok`/`crash`, текст аварии — сообщение провайдера, а не «код выхода N», последний текст, отказы) `sv_turn_end` подводит по `turn.N.parse` и разбору остатка.
- **Только полные строки:** замерить размер `S` (`wc -c`); кусок — `tail -c +$((off + 1)) | head -c $((S - off))` (дописанное после замера не попадёт); последний байт `x=$(tail -c +$S … | head -c 1)` — пустой `x` ⇔ кусок кончается `\n`; если нет — awk пропускает последнюю запись; awk возвращает число потреблённых байт — сумму `length($0) + 1` разобранных записей (под `LC_ALL=C` это байты). В **конце хода** остаток разбирается целиком, вместе с последней строкой без `\n` (харнесс могли убить посреди строки; битая JSON-строка просто не распознаётся).
- **Порядок записи** (kill -9 надзора — без дублей и потерь): (1) дописать строки в `activity.log`; (2) атомарно записать `turn.N.parse` с новыми смещениями и `Activity-Size`. Перед каждым разбором (и при восстановлении): `activity.log` длиннее сохранённого `Activity-Size` — обрезать до него (`head -c N >tmp && mv`) и разбирать с сохранённых смещений. Затем `activity.tail`.
- Запись запуска при промежуточном разборе переписывается, только если её поля изменились (`Session`, `Context`, живые токены, последний текст, `Last-Event`). Цена — один `awk` раз в ≥ 3 с на идущий ход и только при росте лога; у тика доски новых процессов нет.
- **Токены без двойного счёта:** `stream.tok` хранит номер последнего учтённого хода, `sv_turn_end` прибавляет ход, только если его номер больше (повтор после kill -9 не задваивает); так же строка `end` ленты и сообщение lead'у об аварии — по одному на ход (маркеры `turn.N.ended`, `turn.N.notified`, захват — `noclobber`). **Живые токены** во время хода — `stream.tok` + суммы `turn.N.parse` (основная сессия) + подагенты с последнего экспорта; после хода, когда пришёл экспорт, — его итог плюс поток после **запуска** экспорта (`stream.tok` снимается при запуске: ход, прошедший, пока экспорт шёл, не теряется). Строки, которые надзор пишет в ленту сам во время хода (смена прав, конец хода), тоже обновляют `Activity-Size` — иначе следующий разбор или восстановление срезали бы их как остаток kill -9.
- `Last-Event` сбрасывается в начале хода.

**Чей отказ в правах — эвристика.** Отказ основной сессии виден в потоке: `tool_use` основной сессии со `status: "error"` и «request was rejected». Строка stderr `permission requested: <действие> (<ресурсы>); auto-rejecting` печатается для любой сессии, в том числе подагента, и **раньше** события `tool_use`. Поэтому классификация — **в конце хода**, по всем отказам хода: строка stderr, ресурс которой (без хвостового `/*`) — подстрока `input` отказанного `tool_use` основной сессии (или наоборот), — отказ **агента**, каждый такой `tool_use` закрывает одну строку; несопоставленные строки — по счёту: столько, сколько осталось несопоставленных отказов основной сессии, — агента, остальные — «(подагент)». В записи `Perm-Denied: <действие> (<ресурсы>)` или `… (подагент)`; на доске и в `spawn show|list` — «отказ в правах: …» / «отказ в правах (подагент): …». Во время хода строка ленты `permission` пишется сразу, без пометки «чей». Это эвристика: сопоставление — по вхождению пути, поэтому широкий ресурс (например, `/Users/x/*`) может приписать агенту отказ подагента под тем же путём; при нескольких отказах с похожими путями пометка может ошибиться.

**Контекст и токены.** `Context` — как его считает OpenCode: `input + output + reasoning + cache.read + cache.write` последнего `step_finish` основной сессии с ненулевыми токенами (шаг-ошибка с нулями его не обнуляет); подагенты не входят. `Tokens-Main-In|Out` и `Tokens-Sub-In|Out`: источник `export` — основная сессия и сумма дочерних раздельно; `stream` — только основная (подагенты неизвестны, не показываются). `Tokens-In|Out` — сумма (совместимость). **Стоимость** показывается, только если `Cost > 0` (у провайдера без цен — `0`, «$0.0000» не пишется). `Last-Text-Turn` — номер хода последнего текста: на доске «последний ответ (ход N[, идёт])».

#### Первый промпт, права, активность и токены

**Первый промпт** — короткий текст в `bin/brg` (имя с ключом, S, права и их смысл, подпись человека `--note`) + вывод join: «Окна у тебя нет: человек видит только `send --to human` и доску… `join` уже сделан… Когда свободен — заверши ход… Работает подагент — ход не завершай, жди в `wait --busy`… `brg wait` никогда не запускай в фоне».

**Права** — по тому, что реально делает OpenCode: `full` (по умолчанию) → `--auto`: «агент может всё, что можешь ты, в том числе вне каталога проекта и чтение `.env`»; `project` → без `--auto`: «правила OpenCode по умолчанию: в проекте можно всё — любые команды, правки, сеть, git push; вне проекта и `.env` — отказ». Настоящего ограничения внутри проекта этап A не даёт (§12). Вывод `spawn` и доска называют смысл дословно. **Отказ виден:** после хода надзор ищет в stderr хода `permission requested: … auto-rejecting` (ANSI снимается), запасной признак — `tool_use` со `"status":"error"` и «request was rejected»; найдено → строка `permission` в activity, `Last-Error`, на доске — «отказ в правах: <что>» и кнопка «дать полные права».

**Активность** — одна awk-программа по событиям хода (`events.log` с запомненного смещения): строки activity (`tool` — имя и `input.command|filePath|pattern|description`, до 200 байт; `text` — первые 200 байт; `error`), `sessionID`, сумма токенов и стоимости `step_finish`, последний текст, id дочерних сессий из вывода `task` (оба вида). JSON — регулярками по строке, без jq; неизвестные события пропускаются (сменится формат — теряется показ, не работа). **Маскировка ключа** — там же: `<харнесс>-<n>.` + шесть символов `[a-z2-9]`, за которыми не `[a-z0-9]`, → `<имя>.<3 символа>…` (шесть классов подряд, без интервалов `{6}` — их не понимает mawk); касается activity, последнего текста, `prompt.head`, вывода `spawn show|list`. Доска показывает «последний завершённый шаг» и «нет событий K мин», без обещания «сейчас делает»: идущий инструмент в потоке не виден.

**Токены.** После хода, в фоне: `"$bin" session export <spawn.opencode.args> <id>` своим ребёнком (`$!` — сам OpenCode, не конвейер), тайм-аут 20 с — SIGINT, затем TERM; из файла — только `head -c 2048 | tr -d '\n '` и регулярка `cost`/`tokens` (полный вывод большого экспорта через пайп может обрываться). **Только с `--standalone`** — иначе экспорт поднимет у человека фоновый сервис OpenCode. Основная сессия и все дочерние (`children`) считаются раздельно и складываются → `Tokens-*`, `Cost`, `Tokens-Source: export`, `Sub-Sessions`; дочернюю не экспортировать заново, если её итог не менялся 2 хода подряд и её id не встретился снова в выводе `task` этого хода. Экспорт не удался или выключен (`spawn.opencode.export: 0`) — сумма `step_finish` основной сессии, `Tokens-Source: stream`: доска честно подписывает «без подагентов».

**Настройки** (`config`): `spawn.opencode.bin` (`opencode`), `spawn.opencode.args` (`--standalone`), `spawn.opencode.export` (1), `spawn.wait_timeout` (3600), `spawn_stale` (30). Значения `spawn.*` — сырые (путь, несколько аргументов через пробел), остальные ключи — как раньше. Тестовые крючки: `BRG_SPAWN_STEP` (шаг сна надзора и обёртки, по умолчанию 1 с), `BRG_SPAWN_TEST_MAXLIFE` (надзор и обёртка выходят сами через N с или когда исчез каталог проекта), `BRG_SPAWN_EXPORT_TIMEOUT` (тайм-аут экспорта, по умолчанию 20 с), `BRG_SPAWN_TEST_DELAY_PARSE` / `BRG_SPAWN_TEST_DELAY_TOK` (пауза между дописками в `activity.log` и `turn.N.parse` / между `stream.tok` и итогом хода — тесты kill -9 в этих точках), `BRG_SPAWN_TEST_DELAY_END` (пауза между строкой «конец хода» и итогом в записи). Экспорт, как и харнесс хода, запускается под `set -m`: фоновая команда без управления заданиями получила бы SIGINT = SIG_IGN, и тайм-аут не мог бы прервать её штатно.

## 6. Задачи

**(решение человека)** В проекте одна активная задача; все подключённые агенты — её участники (неявное членство). Хранилище — по задачам, чтобы параллельные задачи с явным членством потом не требовали миграции.

- `task new --as X --title "…"` + постановка (дословно от человека → `brief.md`) → `T00N[-<slug>]`, Lead = X (автор), «новая задача» в `lobby`. Есть активная — отказ, либо `--cancel-current` (текущая отменяется); технически он доступен любому агенту, PROTOCOL рекомендует его, только если человек сам сказал бросить текущую. **(решение человека)** Агентский `task new` при общем стопе или общей паузе, а также при стопе или паузе автора отказывает (баннер первой строкой, как у команд, начинающих работу, §9; проверка — до всего, `--cancel-current` текущую задачу не отменяет): снимает эти флаги только человек. Подсказка lead'у: общие — «попроси человека: `brg resume`, `task new --as human` или доска»; свои — «`brg resume <имя>`» (для стопа — и `say --to <имя>`). Личные стоп и пауза других агентов не мешают и не снимаются.
- **`task new --as human`** — человек даёт задачу сам, без чата агента (из терминала; из браузера — тем же вызовом): §6.2.
- Переключение: wait всех агентов замечает смену `tasks/active` на ближайшем тике и слушает новую задачу. Из прошлых задач — только `common/` (рекомендация PROTOCOL).
- `task close --as <lead> [--force]`: всегда нужен непустой `summary.md` (первая строка — итог в `common/history.md`); отказ, пока есть подзадачи `claimed` или идущие прогоны (`--force` отменяет и останавливает их). Ревью не требуется (§1 п. 7; иначе тупик при одном агенте).
- **Непрочитанное перед закрытием — «отказ = доставка» (решение человека).** Сразу после проверки «ты lead» и **до** проверки `summary.md` (lead должен увидеть сообщения до того, как напишет итог) close ищет то, что разбудило бы wait lead'а: в его каналах (`lobby`, задача, недренированные завершённые — как у wait) после `Pending` есть будящее (`FMT_WAKE` > 0: сообщения ему или всем, в т.ч. личные системные — результат `run`, ревью, сданные подзадачи). Тихие системные (join/leave/claim) и собственные не мешают; сводки дедлайнов (§8) не учитываются — придут wait'у. Нашлось — close печатает на stdout всё для lead'а после `Pending` (тихое тоже), как wait, с капом `wait_output_max`; после вывода сдвигает `Pending` на последнее показанное (`Acked` не трогает) и отказывает: «учти их (при необходимости поправь summary.md) и повтори task close». Подсказка — повтор `close`, не `read`: `read` курсор не двигает, отказ «прочитай» зациклил бы. Повтор проходит, если нового нет; при капе — несколько отказов подряд, каждый двигает `Pending`. `--force` проверку не обходит (показанное уже доставлено — повтор проходит). Следующий wait подтверждает показанное (`Acked := Pending`) и не выдаёт его повторно; гонка с фоновым wait lead'а (он держит курсоры в памяти) даёт не потерю, а максимум дубль — at-least-once.
- `task cancel --as <lead|human>`: `claimed` → `cancelled`, резервирования и прогоны снимаются, всем — «прекрати правки»; незавершённые правки остаются в рабочем дереве — их судьбу решает lead новой задачи или человек. Человек отменяет только явным `--as human`: агент, забывший `--as`, не отменит задачу «от имени человека».
- `common/history.md` — строка при закрытии и при отмене. Статусы: `active`, `done`, `cancelled`; фазы работы — только в рекомендациях. События «новая / закрыта / отменена» — в `lobby`, смена lead — в канал задачи (уход lead'а — в `lobby`); в канал завершённой задачи писать нельзя.
- **Дренаж:** перестав слушать закрытую или отменённую задачу, wait сначала выдаёт её недоставленные адресованные сообщения (`── T001 (закрыта)`) — финальное слово лида не теряется.
- Курсоры канала задачи: бывшие на момент создания читают с начала, подключившиеся посреди — с конца (история — `read --channel T00N --since 0`); `join --as` после `leave` — с конца, без переписки задач, завершённых за время отсутствия. Нумерация сообщений своя в каждом канале, `--re` — к выбранному.

### 6.1 Роли

**(решение человека, 0.7.0)** Роль одна — **lead**: фасилитатор (§1 п. 8) **и** связь с человеком (вопросы, отчёты, итог). Роль host (кому человек дал задачу и кто пишет ему) убрана: она нужна была на случай «задачу дали A, вести лучше B», но тогда вопросы человеку шли из одного окна, а решения принимались в другом; с доской и браузером привязка к чату почти не нужна. Показать человеку что-то в чате (картинку, файл) — окно lead'а.

- **Lead** собирает предложения, фиксирует договорённости, решает спор, если бригада не договорилась. Он же — единственный, кто сам обращается к человеку: пишет в своём чате **и** тем же текстом `send --to human` (видно на доске — когда задачу дали с доски, это основной канал); вопрос — ещё и `--ask` (§9.2); остальные отвечают, если человек написал им сам. Запись задачи: `Host:` больше не пишется, у старых задач читается и игнорируется.
- **Lead есть всегда.** Выбор — §6.2. Уход (`leave`) lead'а: сразу, под блокировкой `task`, тот же детерминированный выбор среди оставшихся на связи (§6.2, шаги 2–3, ушедший исключён), сообщение в `lobby` («X отключился (был lead задачи T00N — lead теперь Y …)») будит всех, а строка «lead задачи T00N: X → Y (X отключился)» в канале задачи (`Wake: no`, без двойного пробуждения) нужна, чтобы смена была видна в переписке задачи на доске; на связи никого — `Lead:` пуст («lead — нет (назначится первому, кто выйдет на связь)» в `who`, `task show|list`, `status`, `history.md` и на доске), и дальше его берёт первый, кто выйдет на связь (самоназначение, §6.2).
- `lead give <имя>` — только текущий lead, не `gone`-агенту; `lead take` — только если текущий lead `asleep`/`gone` или его нет. **Человек** назначает lead'а в любой момент: `lead give <имя> --as human` — отдельная ветка без `need_agent`, `touch_seen`, `NEXT:`; правила «только текущий lead» на него не распространяются; цель — не `gone`; задача без lead'а — тоже можно; уже lead — «уже lead», сообщения нет; системное сообщение `From: human` в канал задачи будит всех (и на паузе). Агенты могут договориться о другом лиде — самоорганизация без тупика «лида нет».
- `host give|take` — отказ «роли host больше нет: связь с человеком — у lead'а» с подсказкой `lead give|take` и `NEXT:`.
- `send --to human` — не только копия для протокола: доска показывает такое сообщение, и когда задачу дали с доски, это основной канал lead'а к человеку (чат харнесса — по-прежнему, PROTOCOL, раздел 2 п. 3).

### 6.2 Задача от человека; выбор lead'а

**(решение человека, 0.7.0)** Человек даёт задачу сам: `brg task new --as human --title "…" [--cancel-current] [--file F] < постановка` — из терминала (бессерверная версия) и из браузера (кнопка «Новая задача» на доске с сервером, §9.1: тот же вызов). Отдельная ветка, как `task cancel --as human`: без `need_agent`, `touch_seen` и `NEXT:`; `Created-By: human`. Она снимает общий стоп и общую паузу (личные не трогает; стоп снят — «остановленные агенты завершили ход — напиши им «продолжай»»). Агенту — `task new` как раньше (lead = автор).

- **Выбор lead'а** (детерминированный, под блокировкой `task`):
  1. lead последней задачи (наибольший номер, любой статус), если он **на связи**;
  2. иначе — агент на связи: сначала свободные (без действительной пометки «работает», §5.4), затем занятые; при равенстве — раньше подключившийся (`Joined-Epoch`, затем имя);
  3. на связи никого — задача без lead'а (`Lead:` пуст), самоназначение ниже.
  
  **«На связи»** = `waiting`, **или** `working` без «не на связи» (между двумя `wait`: последнее присутствие в цикле `wait` не дальше таймаута `wait` + 60 с — без этого прошлый lead, отвечавший в эту минуту, был бы пропущен случайно). `asleep`/`gone` — не на связи. Агенты с личной паузой или личным стопом пропускаются (и прошлый lead тоже: задачу, которую он не может начать, ему не отдают). С `--cancel-current` занятость оценивается **до** отмены текущей задачи (после неё все пометки недействительны). **При общем стопе на связи никого нет** (стоп завершил ход всех, хотя их `wait` кончились секунды назад и по `agent_state` они `working`): lead остаётся пустым — и у `task new --as human` (стоп снимается после выбора), и при `leave` lead'а; первый оживший агент становится lead'ом сам.
- **Самоназначение при пустом `Lead:`** — в `wait` (на старте, после проверки STOP, до записи pid-файла; и при смене активной задачи в цикле — иначе агент, чей `wait` начался за миг до `task new --as human`, не стал бы lead'ом до конца `wait`), в `join` (после записи курсоров: сообщение окажется за ними и придёт его первому `wait`) и `lead take`. Двойная проверка: чтение без блокировки, блокировка `task` — только при пустом `Lead`, повторная проверка под ней: из двух одновременных `wait` побеждает один. Не для агента с личной паузой или личным стопом (после `resume` его следующий `wait` назначит), при общем стопе — тоже нет. Уведомление — обычное сообщение `From: brg`, `To: all`, в канал задачи: «X — lead задачи T00N (назначен brg: первый на связи). X: постановка — brief.md; начни с PROTOCOL.md, раздел 4…»; сам X получает его своей доставкой (`From: X` не годился бы: свои не доставляются). При общей паузе оно, как всякое сообщение не от человека, никого не будит — новый lead узнаёт о роли после снятия паузы.
- **Сообщения `task new --as human`:** в `lobby` — `From: human`, «новая задача T00N от человека: «…» · lead: X» (или «lead: нет — назначится первому, кто выйдет на связь») — будит всех; lead'у лично, в канал задачи (там все читают с начала) — «ты lead задачи T00N (назначил brg): прочитай постановку…; человек дал задачу не в твоём чате — он смотрит доску: вопросы ему — `send --to human --ask`, отчёты — `send --to human`».

## 7. Items and code

### 7.1 Items

- `item add` → `I00N` (`todo`); `--paths` — the proposed paths (`Paths-Hint`).
- `item claim I00N [--paths …|none]` — atomic. The paths must be named (`--paths` or the hint from `add`) or `none` must be said (research, review), so a reservation is not forgotten by accident. An overlap with someone else's reservation → a refusal with the list of conflicts. A repeated `claim` of one's own item changes its paths.
- An overlap with one's **own** reservation (another own item in progress) is not a refusal but a warning after the claim: «эти пути уже твои по I001 …; если I001 брал не ты — под твоим именем работает другая сессия: сообщи lead'у и человеку». This is how a double under one name surfaces (§3). No warning: `--paths none`, and an item overlapping itself on a repeated `claim`; `.` overlaps all one's own reservations — by design.
- `item done` — only the assignee (`--note`, `--result <path>`); it removes the reservation.
- `item release` (back to `todo`) — the assignee, or the lead if the assignee is `asleep`/`gone`. `item reassign --to <name>` — the lead, only if the assignee is `asleep`/`gone` and the new one is not `gone`; the reservation passes to the new one. The changes of a handed-in item are passed on the same way (the «правки» stage, §7.1.1).
- `item review --verdict ok|changes|skip` — for `claimed` or `done`; `ok`/`changes` are a review: the assignee cannot write one for their own item; a reviewer of the same model as the assignee, while an agent of another model is online, gets a warning, not a refusal. `skip` is the decision "no review is needed" (§7.1.1). Review records are immutable.
- All item changes are made under the task lock (a claim cannot slip into a task being closed).

### 7.1.1 Review and item stages

**(the human's decision)** How to work with an item — whether to review it, who reviews, in what order, changing one's mind along the way — is decided by the brigade: a review by another participant is a recommendation (PROTOCOL, section 3), not a rule. One thing is mandatory (PROTOCOL, section 2): **the item stage in brg matches what is happening** — the human follows the work on the board (§9.1). So brg gives flexible tools for every case, and the agents move the items through the stages themselves. brg imposes no order: `task close` does not refuse because of unreviewed items, it only lists them.

| Situation | Command | Stage (board) |
|---|---|---|
| claimed | `item claim` | «в работе» |
| dropped | `item release` | todo |
| handed in, review needed (the default) | `item done` | «на проверке» |
| started reviewing | `item review --start` | «на проверке · проверяет X» |
| reviewed | `item review --verdict ok` / `changes` | «готово» / «правки» |
| changes | `item claim` (the assignee) → `item done` | «в работе» → «на проверке» |
| no review needed — decided in advance | `item add --no-review` | after hand-in — «готово · без проверки» |
| … at hand-in | `item done --no-review` | «готово · без проверки» |
| … changed their mind after hand-in (under review, changes) | `item review --verdict skip [--comment "why"]` | «готово · без проверки» |
| changed their mind: review needed | `item review --start` (whoever will review) | «на проверке» |
| redo what was handed in (an accepted item too) | `item claim` (the assignee) | «в работе» |
| the item is not needed | `item cancel [--comment "why"]` | «отменено» |
| an own order (a separate review item, pair work, …) | mark the result with the commands above | — |

- `item add --no-review` → the header `Review: no`. `--paths none` does not exempt an item from review.
- `item done` writes `Done-Reviews: N` — how many review records there were at hand-in (this is how a review "after the hand-in" is told from one "before it", without comparing times). `item done --no-review` — the hand-in and at once a review record `skip` from the assignee (the comment is «при сдаче»), one system message.
- **Verdicts** of `item review --verdict`: `ok`, `changes` are a review; one's own item cannot be reviewed this way; with the same model as the assignee's — a warning (§7.1). `skip` is the decision "no review is needed": any participant may record it, the assignee too (a decision of the brigade, not a review); the comment is optional, stdin is not waited for without `--comment`/`--file`. All verdicts are immutable review records (history on the board). Any verdict on a `done` item clears `Reviewing:` entirely — the review round is over (whoever still reviews — `--start` again); the other reviewers (except the verdict's author) get a system message that wakes only them (`Wake: <names>`): «круг проверки I00N закрыт вердиктом X от Y — вас больше нет среди проверяющих; продолжаете проверку — повторите `item review I00N --start`; не нужна — дайте подагенту закончить, затем wait без --busy». Their marks «проверка I00N» are not removed (a subagent may still be working), and their `wait --busy "проверка I00N"` keeps the mark (§5.4). On a `claimed` item it removes only the author and sends nothing to the others.
- `item review I00N --start` — "started reviewing": the name goes into `Reviewing:` (comma-separated, no repeats), a quiet system message to everyone (like `claim`). The item is `claimed` or `done`, the reviewer is not the assignee; under a stop — a refusal (it starts work, §9); not together with `--verdict` and a text; stdin is not read; a repeated `--start` by the same agent — no duplicate and no message; the same-model warning is given already here.
- **Back to work** — `item claim I00N` by the assignee from `done` at any stage: changes after `changes`, redoing an accepted item or one handed in without review, withdrawing the item from review. The default paths are the previous ones (`Paths`), overlaps are checked as for an ordinary `claim`; `Claimed`/`Claimed-Epoch` — anew; `Done`, `Done-Reviews`, `Note`, `Result`, `Reviewing` are cleared (the previous hand-in stays in the conversation); the system message wakes the lead. Someone else's handed-in item cannot be taken this way (the refusal names the stage and the last verdict); if the assignee is `asleep`/`gone`, the lead passes the changes on with `item reassign` (the item becomes `claimed` by the new assignee with the previous paths). `item done` on an item at the «правки» stage refuses with the hint `item claim`.
- `item reassign` removes the new assignee from `Reviewing:`; `item release` clears `Reviewing:`.
- `item cancel I00N [--comment "why"]` → `cancelled` (+ `Cancelled`, `Cancelled-By`): `todo` — any participant; `claimed`/`done` — the assignee or the lead. It removes the reservation and `Reviewing:`; the system message wakes the lead, the assignee and the reviewers (except the author). Allowed under a stop (it does not start work). There is no way back from `cancelled`: needed again — a new item.
- **The stage** is one rule for `wait`, `item list|show`, `status`, `task close` and the board (bash `item_stage_v` and the page's JS — the same, abnormal values included). `todo`, `claimed` (in progress), `cancelled` — as they are. For `done`: n — the number of review records (files with a numeric name), the last one has the highest number, d — `Done-Reviews` (none — 0); the last verdict: `skip` — always «готово · без проверки» (a decision, not a review); `changes` and any other (`ok`, abnormal) — as below:
  - n > d (a verdict after the hand-in): `changes` → **«правки»** (on the board — in the «в работе» column, with a red mark), otherwise → **«готово»**;
  - 0 < n ≤ d (handed in after the last verdict): → **«на проверке»** — `changes`: handed in again after the changes; `ok`: handed in after a review — the work may have changed (a review of work in progress, redoing an accepted item), a new review is needed;
  - n = 0: `Review: no` (exactly) → **«готово · без проверки»**, otherwise → **«на проверке»**;
  - «готово» (without review included) with a non-empty `Reviewing:` → **«на проверке»** (someone is reviewing, so a review is going on: this is how "changed their mind: review needed" works).
  - A `claimed` item whose last verdict is `changes` is «в работе · правки по ревью».
- **Where it shows.** The `wait` summary (§5): `… · в работе I001 codex-1 · на проверке I003 (claude-2), I005 · правки I004 codex-1 · готово I002 · …` («(имена)» come from `Reviewing:`). `item list` — the stage in the line and in the final counter; `item show` — the stage, the reviewers, «без проверки» and who decided it. Every message and output of an item command names the stage the item went to (for example, ok after someone else's `changes` without a new hand-in: «правки не нужны — I00N готова»). `task close` lists the unaccepted items — «не приняты: I003 (на проверке), I005 (правки)» — as a warning, not a refusal.

### 7.2 Path reservations

- Paths are relative to the project root, comma-separated; they are normalised (`\` → `/`, no `./`, `//`, trailing `/`; `.` — the whole project). Not allowed: `..`, absolute paths, `~`, masks, control characters. No globs — deterministic and simple in bash.
- An overlap is a prefix on a component boundary (`src` and `src/a` — yes, `src/a` and `src/ab` — no), **case-insensitive** (the macOS and Windows file systems; on Linux false conflicts are possible — deliberately conservative). **(the human's decision)** Case is folded for ASCII `A–Z` and Russian Cyrillic (`А–Я`, `Ё` ↔ `а–я`, `ё`: 33 pairs of two-byte literals in awk under `LC_ALL=C`): `Данные` and `данные` conflict, `Данные` and `Дорога` do not. Other letters (`É`, other alphabets) and the NFC/NFD forms (`й` as two code points) are not folded (§12).
- A reservation holds while the item is `claimed` by this agent (a leftover after a crash is ignored); it is removed by `done`, `release`, by closing and by cancelling the task.
- It protects only those who use it: brg does not track file edits.
- Reservations guard only writing. brg neither restricts nor checks reading in the shared tree (§1: one FS, no protection from an agent): a brief condition like «не читать чужое до раскрытия» is only an agreement. PROTOCOL recommends that the lead at once tell the human such a condition cannot be checked and propose a frame that can (work outside the shared tree until the reveal, the reveal by agreement).

### 7.3 `brg run`

Tests, builds, linters run under a global lock: one command per project at a time, so runs never overlap. The queue does not serialise edits: a run may still see a neighbour's half-edited files. **In the background by default**: the agent at once gets `R00N` and its place in the queue, and the result (status, code, log tail, log path) comes to the initiator as a system message — long operations do not hit the harness's command limit and fit the "everything is a message" mechanics.

- Only with an active task; created under its lock (no race with `close`). `--item I00N`, `--timeout` (default `run_timeout`, 30 min). A single string argument runs through `bash -c`, several run as they are; the cwd is the project root. The command gets its run id in the environment: `BRG_RUN=R00N`.
- The queue `run/execq/` is in request order; the head starts after taking `run/locks/exec.lock`. The lock is held for the whole command and **is never broken by age** — only by the owner's death (confirmed by the heartbeat, see below) or a stale heartbeat.
- The runner is `nohup` under `set -m`, every fd redirected (the harness does not wait for it); the command runs in its own process group, and the group's leftovers are killed after it; a timeout or a cancel — TERM to the group, KILL after 5 s. Statuses: `queued`, `running`, `done`, `failed`, `timeout`, `killed`, `cancelled`. The result is a `From: brg` message to the initiator in the task channel (if the task is already finished — in `lobby`), exactly once.
- `--sync` is for short commands: it waits in place no longer than the agent's `wait_timeout` (a bigger `--timeout` — a refusal), the exit code is the command's; if it does not fit (the queue included), the result comes as a message. A runner that has finished gives a still-waiting synchronous caller up to 3 s to print the result itself; an unreachable caller pid (EPERM) counts as alive — then a separate message goes out with a delay of up to 3 s (acceptable).
- `run cancel R00N` — the initiator or the lead, through a flag file (no signals to foreign pids).
- **The runner heartbeat** — once a second. A live pid (an unreachable one too, EPERM) with a silent heartbeat is declared dead only by a waiting runner that has observed the silence continuously for longer than `runner_stale` (60 s, > `lock_stale`); a time jump at the observer (laptop sleep, SIGSTOP) resets the count. A runner that "comes back to life" after its lock was taken or its run closed kills its command and does not overwrite the verdict (an edge case: for up to ~1 s its command may run in parallel with the winner's).
- **A dead runner pid is not yet death:** in a sandbox's pid namespace a live process may answer ESRCH. A runner is dead only if (1) the pid is dead (`pid_alive`, §4.2), (2) its heartbeat (the exec lock or the queue record) is older than `runner_dead_grace` (5 s; 0 — trust the pid alone) and (3) the judging waiting runner has observed for at least `runner_dead_grace` without a jump (a jump longer than grace/2, but at least 2 s, resets the count: after sleep everyone's heartbeat is old). This count is separate from the `runner_stale` count (that one is reset by a jump longer than runner_stale/2, from 2 to 10 s): short jumps on a loaded machine do not delay the `runner_stale` verdict. Until the conditions hold, a runner with a dead pid is judged as alive — by `runner_stale`, so frequent jumps do not hang the queue either. A runner killed with `kill -9` is removed after about `runner_dead_grace`.
- Viewing (`run show/list`, `status`, `task close/cancel`, `run cancel`, `doctor` — one-off checks, the same verdict for all): the runner pid is dead and the heartbeat is older than `runner_dead_grace` → `killed` (one that has just died — from the next view after the grace; `run cancel` re-checks while it waits); alive but silent → «раннер не отвечает N с» (a one-off call cannot tell sleep from a hang), and `run cancel` closes such a run too. A runner killed with `kill -9` → the lock is removed; the orphan command is not killed (the message warns, the pgid is recorded). **What remains:** a one-off check does not observe continuously (there is no condition (3)) — in an ESRCH environment right after laptop sleep, when everyone's heartbeat is old, it may mark a live run `killed` (the runner itself, on waking up, sees the verdict and stops the command).
- `task cancel`, `--cancel-current`, `close --force` stop the task's runs; the task message lists them, there are no separate messages.

### 7.4 git

- Mandatory (§1 item 7; PROTOCOL, section 2, item 5): do not commit to `main`/`master` without the human's permission. The working tree is one for everyone: do not switch branches and do not touch other people's uncommitted changes without an agreement (no `stash`, `reset`, `checkout`, `restore`, `clean` over them).
- Recommended: one branch per task, created by the lead at the start; the lead commits. Codex may have `.git` read-only — then tell the lead.
- **(the human's decision)** Authorship (PROTOCOL's recommendation to the lead): the commit author comes from git config (the human: they are responsible for the merge), the participants are trailers at the end of the commit message, one per contributor, plus the task number:
  ```
  Co-Authored-By: claude-1 (claude, <model>) <claude-1@brigada.invalid>
  Brigada-Task: T001
  ```
  The name is the base name (without the key), the harness and the model are as in `who`. The email is required: without it GitHub does not recognise the trailer; the `.invalid` domain is reserved and leads nowhere. The ban on naming providers and models applies only to the brigada repository, not to users' projects.
- brg does not call git itself (it only finds the git directory for `info/exclude`).

## 8. Deadlines

`send … --reply-by 5m` (from 1 s to 24 h). At the deadline the sender's wait returns with the summary `── дедлайн по #N (T001) истёк: ответили: …; не ответили: …` — a deterministic basis for the rule "silence means consent".

- `Expect` — the addressees at send time (for `all` — everyone not `gone`, except the sender); if there are none, no deadline is set.
- A reply is a non-system message from an addressee in the same channel after the original: with `Re: <id>` **or** any message to the sender (personal or `all`) — models forget to set `Re:`.
- If everyone replied before the deadline, the summary comes at once, with the batch of the last reply (this saves a wake-up).
- The summary is given once: before printing, the marker `<channel>-<id>.done` is created atomically, and the index is deleted after the output. If the index is still there a minute after the deadline (the reporter died), the summary is given again: a duplicate is better than a loss.

## 9. Commands

For agents: `join`, `leave`, `send`, `wait` (`--busy`: the busy mark, §5.4), `busy` (the mark without waiting), `read`, `status` (a one-screen reorientation after compaction: who I am, role, task, my items and runs, unread messages, deadlines, whether my wait is alive, NEXT), `who`, `task …`, `lead give|take`, `item …`, `run …`. For the human: `init`, `board` (the board in a browser; with Python — with control, §9.1), `say` (from `human`; `--re N` — an answer to an agent's question, §9.2), `tail [-f]`, `who`, `stop`, `pause`, `resume`, `task new --as human` and `task cancel --as human` (§6.2), `lead give <name> --as human` (§6.1), `item list`, `run list`, `doctor`, `spawn` (§5.5, below). An agent passes in `--as` the full name from its `join` (with the key, §3); read commands accept the base name too, and `stop`/`pause`/`resume` and target names take the base name. `who` and `status` name the state with the words «ждёт» (free) and «работает[: подпись]» (§5.2). The syntax is in `brg help` and `brg <command> --help`.

**Stop.** `stop` sets the flag `run/stopped` (`stop <name>` — `run/stopped.<name>`, also for clearing ghosts). While the flag is set, any wait returns STOP **at once** (an agent that was working does not block again); live waits see the flag on the nearest tick — without signals, like the takeover. The flag is removed by `resume`, `say` (the general one and the named addressees' ones) and `task new --as human` (the general one); an agent's `task new` under a stop refuses (§6). The stopped agents have ended their turn — after the stop is lifted, the human writes «продолжай» to them in the chat.

**(the human's decision)** Even an agent that has not called wait for a long time sees the stop: any command with `--as` (under the general stop or this agent's stop, by the base name) prints `── STOP: …` as the first line of stdout. Except `wait` and `status` — they print STOP themselves (no duplicate). Commands that **start work** — `item add|claim|reassign`, `item review --start`, starting a `run` and an agent's `task new` (§6) — refuse under a stop, and `NEXT:` is «заверши ход» (not wait: otherwise the agent would return to the loop, and wait would return STOP at once). Handing in what is done and reporting are allowed: `send`, `item done|release|cancel`, `item review --verdict`, `task close|cancel`, `run cancel`, `lead give|take`, `busy` (the mark does not start work, §5.4), `leave`, read commands.

**Pause (the human's decision).** A stop ends the agent's turn — «продолжай» then has to be written in its window, and that cannot be done from a browser. A pause is softer: `pause` sets the flag `run/paused` (`pause <name>` — `run/paused.<name>`), the agent **does not end its turn**, stays in `wait` and wakes only on the human's messages and the lifting of the pause (§5 item 14); `resume` lifts both stops and pauses (without a name — all; with a name — only this agent's; the general pause holds until `resume` without a name is called, and `resume <name>` says so while it holds); from the browser — with the «Продолжить» button (the board with the server, §9.1). `say` does **not** lift a pause (it lifts a stop): the human can talk to the brigade during a pause. `task new --as human` lifts the general pause; an agent's `task new` under a pause (general or its own) refuses (§6).
- **Starting work is not allowed.** One function `work_refuse` at the same places as the stop: `item add|claim|reassign`, `item review --start` refuse under a pause (an agent's `task new` too, with its own function, §6); `NEXT:` is `wait` (the agent stays in the loop), and the text names who lifts the pause («`brg resume` или с доски; `say` её не снимает»). **`run` is allowed under a pause**: a subagent checks the work already started (`run --sync`), and a subagent working for a participant finishes its job — the pause does not stop it, and the busy mark (§5.4) stays as it is. Handing in what is done is allowed (`send`, `item done|release|cancel`, `item review --verdict`, `task close`).
- **The banner.** The first line of any command with `--as`: `── ПАУЗА: человек поставил на паузу <бригаду|тебя (имя)>. Новую работу не начинай; сдай сделанное и жди (wait).` For an agent launched by brg (§5.5) it depends on the busy mark, like `next_wait`: free — «сдай сделанное и заверши ход — brg разбудит тебя…», a valid mark (a subagent is working) — «доведи начатое и жди в wait --busy (как в NEXT), ход не завершай»; the same holds for the hint of the `work_refuse` refusal. Once per process, STOP takes priority; `wait` and `status` report the pause themselves (`status` — as a line in its output, `wait` — as lines of the batch, §5 item 14), `join` — as a warning.
- **Display.** `who` (the line «── ПАУЗА» under the general pause, «(пауза)» at an agent's state), `status`, `doctor` (the pause flags next to the stops), the board (general — a banner, personal — the chip «пауза»), the `wait` summary («свободны» — without the paused ones). A stopped agent on the board is "остановлен — напиши «продолжай» в его окне (имя · префикс ключа…)" (§9.1); one launched by brg is "остановлен — снимется кнопкой «Продолжить»" (the supervisor wakes it, §5.5).

**Launching agents (§5.5) is for the human only.** The refusal «запускает агентов только человек; попроси его: `send --to human --ask`» comes with `--as <agent>`, and also with `BRG_SPAWN` or `OPENCODE_SESSION_ID` in the environment (not with `CLAUDECODE`/`OPENCODE=1`: the human may work in a harness's terminal). The instructions for agents do not describe `spawn`, except «попроси человека».
- `brg spawn <harness> --model M [--rights full|project] [--count N] [--note "…"]` — checks: `.brigada` exists; macOS/Linux; the harness is supported (only `opencode`); the binary is found (`spawn.<h>.bin`); the platform is the same as that of the joined agents (§3); `--model` — `[A-Za-z0-9][A-Za-z0-9._:/@#+-]{0,119}` (not starting with `-`); `--count` 1–9; `--note` — one line ≤ 200 bytes. Under a stop — the warning «первый ход — после снятия стопа». A line per agent: `S003 → opencode-3 (provider/model) запущен · права: full — <смысл>`. It returns at once (the supervisor is detached, every fd redirected).
- `brg spawn list` — S, agent, harness/model, rights, state, turn, tokens, cost, token source, the last error (agents may read it too). `brg spawn show <S|name>` — the record, 20 lines of activity, the log paths; the key is masked.
- `brg spawn wake|rm|detach <S|name>`, `brg spawn rights <S|name> full|project`; internal ones — `__spawn S00N [--continue]`, `__turn S00N N`.
- `who`/`status` — «(запущен brg, S003)» and the record's state; `doctor` — a section on launches: live and dead supervisors (by the lock and `hb`), hanging wrappers, the harness binary.

### 9.1 The board

**(the human's decision)** `brg board [--interval S] [--port P] [--bind ADDR] [--static] [--once]` is a page for the human: the current task and its status, the brigade (state, lead, claimed items), the item kanban with reviews, runs, the conversation (the task and `lobby`), the brief, the plan, the summary, past tasks. Without Python it opens as `file://` — no server and no dependencies, view only. **(the human's decision)** With Python (≥ 3.8) `brg board` starts the human's server itself (below), and control appears on the same page: writing to the brigade, answering questions, giving a task, appointing the lead, pause and stop.

- **Structure.** `init` installs `template/board.html` as `.brigada/board.html`. Every `S` s (default 2, from 1 to 999999) `board` writes a snapshot into `run/board/` and runs in the foreground until Ctrl+C; on TERM/INT/HUP it deletes its own `.tmp` and exits with code 0 (like `tail -f`). `--once` — one snapshot (no server). The first output line is the address: `http://127.0.0.1:PORT/?t=TOKEN` with the server (with `--bind IP` — `http://IP:PORT/?t=TOKEN`, below), otherwise `file://…` (space, `#`, `?`, `%` are encoded); through `brg.cmd` the path is taken from `BRG_VIA_CMD` (`C:\…` → `file:///C:/…`), Git Bash without it — `/c/…` → `file:///C:/…`; other MSYS and WSL paths — the hint «открой `.brigada/board.html` в браузере».
- **The snapshot.** `run/board/data.js` = `window.BRG_BOARD = {…};` — `meta` (time, interval, version, project, stop, general pause), the agents (with the flags `stopped`, `paused`), all tasks (the `task` record + the first line of the summary), lobby and the **current task** whole (brief, plan, summary, items with reviews, runs, conversation). The current task is the active one, and if there is none — the last (by number) closed or cancelled one: right after `close` the human sees the summary. The other finished tasks are the cache `run/board/T00N.js` (`(window.BRG_TASKS = window.BRG_TASKS || {})["T00N"] = {…};`), written once, when the task has "settled" (all runs in a final status, or closed more than 60 s ago; until then it is rewritten every tick). If `run/board/VERSION` does not match brg's version, the cache is deleted. Writing is tmp + `mv`; a `mv` error (Windows: the browser holds the file) is not fatal and is printed at most once a minute.
- **The snapshot only reads.** The snapshot and the page only read; actions from the board with the server are brg calls on the human's behalf, and the server writes no state itself (below). `board` writes only into `run/board/`: no locks, cursors, Last-Seen, `metrics.log`, it wakes nobody; it has its own check "`.brigada` exists" without `mkdir` (not `need_root`), and errors go without `metric`. Runs are not judged to the end: a dead or silent runner is shown by a one-off check (`run_health`) as «раннер мёртв» / «не отвечает N с», and brg moves it to `killed` on the next view (§7.3). The page only shows the data.
- **Escaping.** The browser executes `data.js`: an escaping error means executing a message text as code. All data (record headers and bodies, texts, computed strings) is turned into JSON by one awk program; its input is a list of directives on stdin (data only through files and stdin, not `awk -v`: it expands `\n` and `\\`). `\` and `"` — `gsub(/[\\"]/, "\\\\&")` (portable between BWK awk, gawk and mawk: `"\\\\"` in gawk would give a single backslash); `\t`, `\r`, the other `\001`–`\037`, `\177`, U+2028/2029 → `\t`, `\r`, `\u00XX`, `\u2028`/`\u2029` — by a loop over the matches, only if they are in the string (the fast path). NUL: BWK awk loses it together with the rest of the line, gawk may pass it raw (JS survives that) — brg writes no such bodies. A newline in an element of the directive list (a file name from a glob, the `.brigada` path) is replaced with `?` — otherwise it would start a fake directive; such a path reads as missing. The page inserts data only through `textContent`/`createElement`, texts are `white-space: pre-wrap` (no markdown), links are only internal.
- **The tick costs O(1) processes:** `date`, one awk for all files (the conversation — the last 500 messages of the channel, picked by a glob in bash), `tail` of the log — only for a running run (for finished ones — once per process). The size of `data.js` is up to ~2 MB: beyond that the old messages are dropped and `meta` says «показаны последние N из M»; the brief, the plan, the summary and record bodies — up to 64 KB each.
- **The page** (`board.html`, one file, no CDN): the data comes by a classic `<script charset="utf-8">` with `?<time>` every 2 s (the old tag is removed); no file — «снимка ещё нет — запусти `brg board`»; a snapshot older than max(10 s, 3 × interval) — «доска не обновляется». A section is redrawn only if the `JSON.stringify` of its data changed (the scroll position and expanded parts are kept); the selected task is in `location.hash`, a past one is loaded from `T00N.js`. Deadlines («ждём / ответили»), the kanban, roles and durations are computed by the page.
- **The view (the human's decision).** The task — title, status, lead (empty — «нет — назначится первому, кто выйдет на связь») and progress (done / total). The kanban — `todo` · «в работе» · «на проверке» · «готово» (+ «отменено», only if there are such items); the stage follows the rule of §7.1.1; for a closed or cancelled task the «на проверке» column is called «не проверено». A card — the number and the title, who does it (under review — who reviews, from `Reviewing:`, or «ждёт проверяющего»), the time in the stage, the marks «правки по ревью от X», «без проверки» (and who decided — `Review: no` or the verdict `skip`), «исполнитель выпал»; the paths, the description, the summary, the reviews and the runs of the item are collapsed. Every agent has its own colour, stable (by name) and the same across the whole page — the brigade, the cards, the conversation: who does what is visible at first glance. The conversation — separate blocks with a stripe of the author's colour: a header (author → to whom, «лично», a reply to #N with the first line of the quoted message, time, deadline), a long body collapsed to ~12 lines; system messages — a compact line; the human's messages are highlighted. The brigade — a compact strip: an agent's chip shows **«ждёт»** (grey: free), **"остановлен — напиши «продолжай» в его окне (имя · префикс ключа…)"** (the human's stop ended the agent's turn — the flag is also removed by a button, but «продолжай» can be written to the agent only in its window), the chip **«пауза»** (a personal pause, §9) or **«работает · подпись · N мин»** (the agent's colour; the label and the time come from the snapshot's `mark`, §5.4; without a mark — «работает», when `working`); a label repeating an item from the list of its work («делает I015», «проверяет I014») is omitted, leaving «работает · 15 с · делает I015»; a label is needed only for work outside the list («финальная проверка»), and `working` without a wait also gets «не на связи N мин»; agents that left (`gone`) without a role, an item in progress or an open question are not shown — instead there is the chip «ушли N» (the names are in its tooltip); empty sections take no space.
- **Pause and stop on the page.** The general pause — the banner «ПАУЗА» (`brg resume`), a personal one — the chip «пауза» and the line «На паузе агенты: …»; the general stop — the STOP banner with a reminder that the stopped agents have ended their turn; the banner «бригада простаивает» is not shown during a pause (idling is the human's decision then). The «Пауза» / «Продолжить» buttons are in the server mode (below).
- **The human's server (the human's decision).** The optional `bin/brg-serve.py` (Python ≥ 3.8, stdlib; `init` installs it into `.brigada/bin/`). The Python rule is §1 item 4. No Python, no file, `--static`, `--once` or a server that did not start — the board is `file://` and view only, with one line of the reason («Python 3.8+ не найден — доска только для просмотра; отвечать — `brg say`»).
  - **Python is found by one function** (`py_find_v`; `doctor` calls it too): `BRG_PYTHON` (if set — only it; a bare name — through PATH) → `type -P python3` (a builtin; Homebrew, python.org, pyenv, conda fit) → on Windows (MSYS/Cygwin) `py -3`, `python3`, `python`. macOS: `/usr/bin/python3` is the Command Line Tools installer stub, so it is taken only if at least one of `$DEVELOPER_DIR/usr/bin/python3`, `/var/db/xcode_select_link/usr/bin/python3`, `/Library/Developer/CommandLineTools/usr/bin/python3`, `/Applications/Xcode.app/Contents/Developer/usr/bin/python3` exists; otherwise there is "no Python" — neither `xcode-select` nor the stub is called (no install dialog pops up). Windows: candidates from `…\Microsoft\WindowsApps\` (the Store stubs) are skipped. The check: `"$py" -I -c` — version ≥ 3.8 and `sys.executable`; the **executable file** is stored (not the command `py -3`), and the server is started with it, so `$!` is Python itself. Python not found — `brg board` writes «Python 3.8+ не найден — доска только для просмотра …» with the hint `BRG_PYTHON=/path/to/python3 brg board`; `BRG_PYTHON` is set but is not Python ≥ 3.8 — «BRG_PYTHON=… — не Python 3.8+».
  - **Start and parentage.** bash is the parent: the snapshot loop stays in `brg board`, and the server is its child (`"$py" -I -X utf8 …/bin/brg-serve.py --root <root> --port P [--bind ADDR] --interval S --alive alive.<own pid> --ready ready.<own pid>`, in the background, stdout/stderr — the same terminal; on Windows `--root` has the form `C:/…`). Signals go only to its own child (`$!`, not a pid from a file): TERM/INT/HUP at `brg board` → TERM to the server, a wait of up to 4 s, then KILL. **Heartbeat:** every tick the bash loop writes `run/board/alive.<own pid>` (tmp + `mv`; each `brg board` of the project has its own file — the server watches only its parent's file); the server exits if the file is older than max(15 s, 5 × interval) (on Windows `os.getppid()` does not change when the parent dies, and `kill` may have killed the launcher `py.exe` — so the main sign is the file, not the parentage); on Unix also when the parent changed. A `brg board` killed with `kill -9` leaves no server behind. **Test hooks** (the server's environment; not needed in normal work): `BRG_SERVE_ALIVE_MAX` (the limit of the `alive` age, s), `BRG_SERVE_NO_PPID` (do not watch the parent change), `BRG_SERVE_TEST_TOKEN` — comma-separated values: `nolink` (token creation without hard links), `stall` (the winner pauses between creating the file and writing it), `race` (a pause of 0.5 s after "no token" — both first starts surely go to create it), `BRG_SERVE_TEST_LISTEN=127.0.0.1` (the server really listens on loopback, while the Host/Origin rules and brg's lines follow `--bind` — so that tests do not listen on a network address; **only** the value `127.0.0.1` works, any other is ignored: the hook can only narrow what is listened on, never widen it). **Handshake:** each `brg board` has its own file `run/board/ready.<own pid>` (the name is passed to the server with `--ready`, like `--alive`: the Python pid in MSYS is not `$!`); bash deletes it and starts the server; after `bind` the server creates the token (if there is none) and atomically writes `port`, then its `ready.<pid>` (port, pid[, the busy previous port]); bash polls only its own file for ≤ 5 s, checking `kill -0 $!` (its own child). The address is printed only after `ready`. On exit the server deletes its `ready.<pid>`, and so does `brg board`; a `ready.<pid>` without `alive.<pid>` (the board was killed) is deleted by the server at start, and the legacy shared `run/board/ready` — if it is older than 60 s. The server died at once or did not answer within 5 s — the reason and `file://` (the server's exit code: 3 — the port is busy or unavailable, 5 — the `--bind` address is not on this machine, 2 — wrong parameters, 4 — `ready` not written); it died later — bash sees it within a tick (`kill -0 $!`): «сервер доски остановился — доска только для просмотра» and the `file://` address, and the snapshot loop goes on.
  - **Address and port.** `http://127.0.0.1:PORT/?t=TOKEN` is the first line (with `--bind`, below, — the address at which the board surely opens). The port: `--port P` (0 — any free one), otherwise the saved one (`run/board/port`), otherwise any free one. The saved one is busy — a new port and the line «порт P занят — новый адрес»; an explicit `--port` is busy or unavailable (`EACCES`: ports < 1024, the reserved Windows ranges) — «сервер доски не запустился: порт занят или недоступен» and `file://`. The token is `run/board/token` (`secrets.token_hex(16)`, created once, mode 600; two first starts at the same time get one token: the full value is written into a temp file and published with `os.link` — atomically and without overwriting, and the loser reads the ready file; without hard links (SMB, exFAT) — `O_EXCL`, and the loser waits up to 2 s for the winner to finish writing; a valid token never changes, a file without a valid token is replaced with a new one; it is permanent so that a bookmark of `/` and the address work across starts; if it leaked or you want a new one, delete the file and restart `brg board`, and old cookies stop matching); a second `brg board` in the same project gets another port (both loops write the same `data.js`; the files `token` and `port` are shared, `alive.*` and `ready.*` are their own).

  - **`--bind ADDR` (the human's decision: the board on a virtual machine, the browser on the host).** By default — only `127.0.0.1`. `--bind ADDR` — listen on this IPv4 address of the machine (decimal `a.b.c.d`, octets 0–255 without leading zeros: `010` is ambiguous) or on `0.0.0.0` (all addresses); names (`myvm.local`, `localhost`) and IPv6 are refused (code 1, «Использование»; checked in bash before the server starts: first the form — exactly three dots, only digits and dots, no empty octets, because `1.2.3.4.` and `1..2.3` read as four fields; then the octets; in Python — again, with its own regular expression, not `ipaddress`: in 3.8.0–3.8.11 and 3.9.0–3.9.4 it accepts leading zeros; code 2). **Only for this start** (the address is written neither to `config` nor to `run/board/`; the next `brg board` without the flag again listens only on `127.0.0.1` — safe by default; the port is saved as above). With `--static` and `--once` a wrong value is still an error, and a valid one silently has no effect (like `--port`). An explicit `--bind 127.0.0.1` is the same as no flag (the server gets no `--bind`, and the lines below are not printed); loopback is all of `127.0.0.0/8`. **Output**, the order of lines: address → [the line «доска слушает все адреса машины…»] → «ВНИМАНИЕ» (two lines) → [«порт P занят — новый адрес»] → «доска обновляется…». The first line: `--bind IP` — `http://IP:PORT/?t=TOKEN`; `--bind 0.0.0.0` — `http://127.0.0.1:PORT/?t=TOKEN` (it surely opens on this machine), and the next line says to replace `127.0.0.1` with this machine's IP (with a command hint: `ip -4 addr` / `ipconfig getifaddr en0`; brg does not guess the IP itself — virtual machines with NAT and host-only have several, `getfqdn` may hang, and the token is not printed a second time). For any address outside `127.0.0.0/8` — «ВНИМАНИЕ»: HTTP without encryption, the token and the conversation go in clear text, from the board one can control the brigade and **launch agents with full rights** (that is running commands on the machine), use a trusted network or an SSH tunnel (`ssh -N -L PORT:127.0.0.1:PORT <machine>` — the same port number on both sides: the cookie name and the `Host` check depend on it), after working over the network change the token (`rm .brigada/run/board/token` and a restart), the macOS/Windows firewall may ask permission for Python. **An address not on this machine** (`EADDRNOTAVAIL`; on Windows `WSAEADDRNOTAVAIL` 10049) — the server exits with code **5** and the reason in stderr, and brg says «сервер доски не запустился: адрес ADDR не на этой машине — доска только для просмотра (адреса машины: ifconfig / ip addr; все адреса: --bind 0.0.0.0)» and gives `file://`; the errno check comes **before** a retry on another port (the server's `--retry-any` would not help). Do not confuse the "port" reason with the address: `EACCES` at `bind` is about the port, and it stays code 3. The listening socket on `0.0.0.0` goes without `SO_REUSEADDR` on all platforms: on macOS with it `bind(0.0.0.0:P)` succeeds on top of a foreign `127.0.0.1:P`, "port busy" would not be detected, and the address on the first line would open a foreign application (the cost: a restart on the saved port within `TIME_WAIT` gives «порт P занят — новый адрес»). The server does not call `getfqdn` for the address (`server_bind` is overridden): a reverse DNS query would eat 5 s of the handshake.
  - **Protection** (the page has the whole conversation, and its buttons control agents): by default only `127.0.0.1` (on Windows `allow_reuse_address = False`: otherwise a second process takes the same port and "port busy" cannot be detected; `--bind` — above); `Host` is checked on **all** requests (DNS rebinding): the port is always its own (otherwise 403 «порт в адресе должен быть P — SSH-туннель с тем же номером порта с обеих сторон»), the name is `127.0.0.1` or `localhost` (always: also through a tunnel to a server listening on the network; an attacker's page has its domain name in `Host`), with `--bind IP` also `IP`, with `--bind 0.0.0.0` also **any IPv4 literal** (but not `0.0.0.0`: it is not a destination address). Names are refused under any `--bind` (403 «открой доску по IP-адресу, не по имени»): the protection from DNS rebinding rests on the rebound page having a name in `Host`; `[::1]` is refused; `GET /?t=TOKEN` sets the cookie `brg_<port>` (`HttpOnly; SameSite=Strict; Path=/`; the name carries the port, so the boards of two projects do not overwrite each other's cookie) and answers `303` to `/` — the token does not stay in the address bar and in the history; every GET needs a valid cookie (otherwise 403 «открой адрес из вывода brg board»); the token is put into the page (`<meta name="brg-token">` instead of the comment `<!--BRG_META-->`) only with a valid cookie; a POST needs the cookie **and** the header `X-Brg-Token`, `Content-Type: application/json`, and `Origin` (if present) equal to `http://` + **the `Host` of the same request** (already checked; same-origin; so with `Host: localhost:P` the `Origin: http://127.0.0.1:P` is refused, which a browser does not send anyway), `Content-Length` is required (chunked — 411), ≤ 1 MB (413), invalid JSON — 400; the token is compared with `hmac.compare_digest`; only GET and POST (any other method — `OPTIONS`, `TRACE`, `CONNECT`, … — 405 with `Allow: GET, POST`, no CORS); on every answer `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` (clickjacking of the «Стоп всех» buttons from a page of a neighbouring localhost port), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`; its own `log_message` without the URL (the standard one would print `?t=` to the terminal). Protection from a malicious local agent is not a goal (§1, non-goals): the token lies in `run/board/`, and `brg say` is available without a key anyway. With `--bind` the protection is extended, not weakened: the cookie does not get `Secure` (HTTP), `SameSite=Strict` and the cookie named by the port work the same way (a browser does not send the cookie to another `Host` — open the address with the token that you use); there is no protection from network sniffing (HTTP) — only a trusted network or a tunnel; from a malicious network neighbour — the token (128 bits) and the checks above.
  - **Paths.** `GET /` — `board.html`, `GET /run/board/data.js` and `/run/board/T00N.js` — a whitelist (with any `?…`); everything else — 404. The snapshot is served only if there is no `Sec-Fetch-Site` or it is `same-origin`: a page from a neighbouring port of the same host is the same "site" for `SameSite` and would include `data.js` with a `<script>` tag together with the cookie, while only the board itself may read the snapshot. **The token in the script address:** browsers send `Sec-Fetch-*` only to potentially trustworthy URLs (loopback, https), so on a network address (`http://192.168.64.5:P`) the header is absent and a check by it would silently pass — for example, the dev server of an application under development on `0.0.0.0:3000` would read the whole conversation. So the page that got `<meta name="brg-token">` adds `&k=TOKEN` to the addresses of `data.js` and `T00N.js` (without the meta — `file://` — it adds nothing), and the server: if `k` is present, it must match (`hmac.compare_digest`), otherwise 403; if `Host` is not loopback (`127.0.0.0/8`, `localhost`), `k` is required. On loopback `k` is not needed (`Sec-Fetch-Site` works there). `Referrer-Policy: no-referrer` and its own `log_message` keep the token from leaking from the address. The log of actions from the board on a non-loopback address appends the client's address: `── с доски: say → all (#42) (с 192.168.64.1)`.
  - **Actions** — `POST /api/<action>`, JSON → `{ok, code, out}` (an argument check error — 400 of the same form; a brg error — 200, `ok: false`, brg's words in `out`): `say` {to: "all" | [names], channel?, re?, text}, `task-new` {title, brief, cancel_current?}, `task-cancel`, `lead` {name}, `pause` / `resume` / `stop` {name?}. The server **writes nothing into the state itself** (except `run/board/token|port|ready.*` and temp text files): every action is a brg call on the human's behalf (`say`, `task new --as human`, `task cancel --as human`, `lead give <name> --as human`, `pause|resume|stop`), so all brg rules — choosing the lead, lifting a pause, closing a question with `--re`, refusals — work as from the terminal. The call: `bash <root>/bin/brg …` (`BRG_SERVE_BASH` from `brg board`), on Windows — `bin\brg.cmd` (decided by `sys.platform == 'win32'` in Python, not by brg's `PLATFORM`: an MSYS Python understands POSIX paths); the arguments go as a list, without a shell; `stdin=DEVNULL`, `cwd` — the project root (otherwise `brg.cmd` adds the `WIN_CD_HINT` line), the environment without `BRG_AS` and with `BRG_NO_CHCP=1` (parallel calls must not switch the code page of the shared console) and `MSYS=noglob` (otherwise Git Bash started from `python.exe` would expand a mask like `README*` in an unquoted argument — the task title), `timeout` 60 s, the output is UTF-8 with replacement. Names, channels, numbers are checked by regular expressions; **texts** (a message, a brief) go only through `--file`, into a temp file `run/board/.srv.tmp.*.txt` (UTF-8, deleted in `finally`; leftovers older than 60 s, like the `alive.*` of killed `brg board` processes, are deleted at server start); the task title (`--title`) is one line without control characters, ≤ 200 bytes, on Windows also without `" % ^ & | < > !` (cmd.exe expands them even inside quotes) — otherwise a clear refusal. Every action is a line in the `brg board` terminal (the server's stdout; `-X utf8`): `── с доски: say → all (#42)`.
  - **The page.** One page for `file://` and `http://`: control is switched on if the server put in `<meta name="brg-token">` (`file://` has none, and the page is view only). The header: «Новая задача» (title and brief; if there is an active task, the dialog honestly says it will be cancelled: `cancel_current`), «Пауза» / «Продолжить» (lift the general and personal pauses and stops), «Стоп всех» and «Отменить задачу» — **with confirmation**. The conversation: a message field (to whom — «всем» or agent chips, several; channel — the task or `lobby`; Ctrl/⌘+Enter), and «Ответить» at a question in the «Ждут вашего ответа» banner and at every agent message (the field gets the addressee, the channel and `Re: N`: the answer closes the question on the board, §9.2). The «⋯» menu at an agent chip: «сделать lead'ом», «пауза» / «снять паузу» (no such item under the general pause), «остановить» (with confirmation) / «снять стоп». After an action — an extra snapshot load after 0.3 and 1 s. brg's answer is a pop-up line at the bottom; an error is in red, in brg's words.
- **Launched by brg (§5.5).** The snapshot: an agent has the field `spawn` — `null` or `{id, harness, model, rights, state, turn, turn_start, turn_end, turn_result, last_event, last_error, perm_denied, rights_note, last_text, last_text_turn, context, tokens{in, out, reasoning, cache_read, cache_write, main_in, main_out, sub_in, sub_out}, cost, tokens_source, sub_sessions, supervisor_alive, note, prompt_head, activity}` (`activity` is `activity.tail` as a string, and the page parses its lines with TABs); the full key does not get into the snapshot (everything the supervisor wrote is already masked). `meta.spawn = {supported: ["opencode"], available: […]}` — the binaries are looked up (`type -P`) once, when `brg board` starts, not per tick; the tick still costs O(1) processes. The page: a launched agent's chip has «⚙ S003», the model, the rights, the tokens (main · subagents), the cost — only if > 0, the context («без подагентов» with `stream`); an expanding panel — the activity, «ход N идёт M мин · последнее событие K мин назад» / «ждёт N мин» / «упал: …» / «отказ в правах: …» / «надзор не отвечает» / «конфликт», the last answer («(ход N)» or «(ход N, идёт)»); in the task header — the sum of the launched agents' tokens. **The feed:** the line «ход N начат» is highlighted (a new turn is visible at once); the panel is redrawn only if its data changed; by the panel key (the launch id) the page remembers whether the human was at the bottom of the feed (or has not scrolled yet) — then after a redraw the feed is scrolled to the last line; if they scrolled up, their `scrollTop` is kept. With the server: «Добавить агента» (the harness from `meta.spawn.available`, the model — a text field with the last used one, the number 1–5, the rights — radio buttons `full`/`project` with the meaning verbatim, a note) and in the «⋯» menu of a launched agent — «Разбудить», «Дать полные права» (with `project`), «Забрать в окно» (shows the command), «Убрать» (with confirmation). The server: the actions `spawn` {harness, model, rights, count, note?} and `spawn-ctl` {id, op: wake|rm|detach|rights, rights?} — validated as in the CLI (`model` does not start with `-`; `id` — `S\d{3,}` or an agent name), the call `brg spawn …`, an answer in < 2 s (the supervisor does not hold the pipe). **Locale:** brg exports `LC_ALL=C`, so `brg board` passes the original `BRG_CMD_LC_SET`/`BRG_CMD_LC` to the server (as to the runner of `brg run`), and the server — into the environment of the `brg` call; `brg spawn` saves them in the record, preferring `BRG_CMD_LC*` from the environment to its own (that one is already `C`); the turn wrapper restores the locale. brg does not touch `LANG`/`LC_*`.
- **"Busy" honestly (the human's decision).** A participant «ждёт» ⇔ it is free (§5 item 13). The snapshot: an agent has the field `mark` — `{note, since, via, item}` or `null` (read by the same `busy_read`, read only). The page adds two places that show "it is unclear what is happening": (1) **the task state line** under the title — if the active (current) task has items and all of them are in final stages (done / cancelled): «подзадачи готовы · lead X работает: T» or «подзадачи готовы · lead X ждёт — итог ещё не подведён» (so a lead's final check while everyone waits is visible); (2) **the banner «бригада простаивает»** — the task is active, there is a live `wait` without a mark, **nobody is «работает»** (with a mark or `working`), there are no open questions to the human and no running runs, and the brigade is not stopped. The duration = max(how long the page has continuously observed this state, now − the time of the task's last message); the banner shows when it is > 2 min.

### 9.2 Questions to the human

**(the human's decision)** An agent's question to the human must not get lost: in the agent's chat it scrolls away under the output of `wait`, and the human may not see it. The harness chat stays the main channel (PROTOCOL, section 2 item 3); brg adds visibility to it: an open question is visible on the board, in `who` and in the `brg board` terminal until it is answered.

- **Asking** — `send --as <name> --to human --ask` (together with the same text in one's own chat). `--ask` only when `human` is among the addressees; the header `Ask: yes`. A question is one message: several questions go as a list in one body.
- **Open** while the same channel has no message with `Re: <question number>` **from the human or from the question's author**: the author got the answer in their chat and forwards its essence to the brigade with `send --re N` (this also closes the question — so the brigade learns the human's decision), or the human answers from the terminal with `say --re N …` (`say` has `--re` for this). A `--re N` answer by another agent (the question was addressed to it too: `--to human,codex-1`) does not close the question — the human has not answered yet. A question is refined with a new `--ask`, not with `--re`. Closing or cancelling the task removes its open questions (the messages stay). The answer hints (`who`, `status`, the output of `send --ask`, the board, the `board` terminal) name `--channel` if the question's channel is not the default one.
- **The index** — a marker per open question in `run/asks/` (written together with the `--ask` message, removed by writing a message with `Re` on it and by closing/cancelling the task): so `who`, `status` and the board tick see the open questions in O(1), without reading the conversation.
- **Where it shows:**
  - the board — the banner «Ждут вашего ответа» above the task: who asked (the agent chip), when (a live «N мин назад»), the start of the question (it expands in full), where to answer — "в чате <name> (в окне агента ищи «<name>.<3 символа ключа>») или `brg say --to <name> --re N …`"; with the server (§9.1) the «Ответить» button instead of the command (the message field gets the addressee, the channel and `Re: N`); the number of open questions — at the start of the tab title; at the asking agent in the brigade strip — «ждёт вашего ответа»; in the conversation the question is marked «вопрос человеку · открыт / отвечен #M / снят без ответа» (the last one — the task was closed or cancelled, and there was no answer with `Re`);
  - `brg board` in the terminal — a line per new open question (once): `── вопрос человеку от opencode-2 (#20, T004): <первая строка> — ответь в его чате`;
  - `who` — the line «ждут ответа человека: opencode-2 #20 (55 мин)»; `status --as <name>` — one's own open questions.
- **The key on the board.** So that the human finds the agent's window, the board shows **the first 3 characters of the key** next to the name (`opencode-2 · xqp…`): in the agent's window every command contains the full name `opencode-2.xqprxp`. The board does not show the full key (§3: the key cannot be taken from public output) — the snapshot holds only the prefix.
- For agents (README, section 3, the mechanics): a question to the human goes as text in the chat **and** as `send --to human --ask`; having got an answer, forward its essence to the brigade with `--re N`. A report to the human (not a question) goes without `--ask`.

## 10. Windows

- `bin/brg.cmd` (ASCII, CRLF) finds Git Bash itself: `BRG_BASH` → `%ProgramFiles%\Git\…` → `%ProgramFiles(x86)%\…` → `%LOCALAPPDATA%\Programs\Git\…` → scoop → through `where git`. It does not call `bash` from PATH and rejects a bash from System32/WindowsApps (WSL). It sets `BRG_VIA_CMD`, and brg prints `NEXT:` in the form `.\.brigada\bin\brg.cmd …` (it works in both PowerShell and cmd; a call not from the root comes with the hint `cd <root>`). For the time of the call it switches to `chcp 65001` (`BRG_NO_CHCP=1` disables that); brg's exit code is kept.
- `.gitattributes`: `bin/brg`, `bin/brg-global`, `bin/brg-serve.py`, `tests/fake_opencode`, `*.sh`, `template/*` — `eol=lf`, `*.cmd` — `eol=crlf`.
- **The board server (§9.1).** Python is looked up without shims (`py -3`, `python3`, `python`; the stubs `…\Microsoft\WindowsApps\` are skipped) and stored as `sys.executable`; the server's `--root` is `C:/…` (from `BRG_VIA_CMD` or `/c/…`); the server itself decides "`brg.cmd` or bash" (`sys.platform == 'win32'`); `BRG_NO_CHCP=1`, so that parallel calls do not touch the code page of the `brg board` console; `MSYS=noglob` — Git Bash does not expand masks (`*`, `?`, `[`) in the arguments a non-MSYS process passed to it; `allow_reuse_address = False`. Closing the window and Ctrl+C stop the server through a TERM from bash, and if that did not arrive — through the heartbeat `run/board/alive.*` (≤ 15 s). A brg with CRLF in itself gives a clear error (code 2).
- For agents in PowerShell/cmd: `.\.brigada\bin\brg.cmd …`, the body via `--file` (or `--desc`/`--comment`); a harness that runs commands in Git Bash (Claude Code on Windows) calls brg as usual.
- Timeouts per platform: `wait_timeout.<harness>.<platform>` (`darwin`, `linux`, `msys`, `wsl`). The user's `config` beats any defaults: `config` (`<h>.<plat>`, `<h>`) → `config.default` (the same) → the built-in ones (the same) → `wait_timeout.default` in the same order of files.
- `brg doctor [project]` — checks of the environment and the state (bash and the platform, the installation, CRLF, Python for the board server, `mkdir` atomicity, `mv` over an open file, process visibility, `.git/info/exclude`, the brigada block in `AGENTS.md`/`CLAUDE.md` (§3), locks, runners, hanging waits, launched agents, stop and pause, timeouts and numbers in `config`): ✓/⚠/✗ with hints, it changes nothing, code 1 only on ✗. Process visibility: `kill -0` of the parent gives EPERM — ⚠ «песочница: чужие процессы недоступны, brg считает их живыми, сироту wait не распознает»; an already finished own child gives EPERM — ⚠ «смерть процессов не видна, раннер снимается только по heartbeat (до `runner_stale`)». A sandbox where a pid namespace hides live processes (ESRCH) is not recognised by doctor (§12 item 3). Locks and runners are judged by doctor with the same verdict as by brg (§7.3, with `runner_dead_grace`). A broken installation (CRLF) is checked with a copy from the repository: `bash /path/to/brigada/bin/brg doctor <project>`.
- Nothing has been run on Windows: the check is `WINDOWS.md`, on the human's machine.

## 11. Implementation

- bash 3.2 (the bans are in `AGENTS.md`). Utilities: `mkdir mv rm cat sed awk date sleep kill ls head tail wc sort tr printf cp uname nohup`; no jq/node; Python — only `bin/brg-serve.py` and only in `board`/`doctor` (§1 item 4); `date` only formats. The harness CLI (`opencode run`, `opencode session export`) is called only by the supervisor and the turn wrapper of launched agents (§5.5); `spawn`, `doctor` and `board` only look the binary up (`type -P`). Inside, `LC_ALL=C` (byte semantics); UTF-8 passes through.
- One file `bin/brg` (+ the optional `bin/brg-serve.py`, §9.1). The tests are in pure bash (`tests/`; the client of `test_brg_serve.sh` is Python, and without it the server tests are skipped), including a concurrency stress test, takeover, stale locks and a scripted ping-pong of ≥ 200 exchanges with wait kills; `test_brg_docs.sh` checks the commands and flags in `README.md`, `DESIGN.md`, `AGENTS.md`, `bin/README.md`, `template/*.md` and `WINDOWS.md` against `--help`, the language of the English docs and of code comments, links, anchors and `§` references, and the markers of history and unfinished work.
- **Process liveness by a pid from a file** — only `pid_alive` (§4.2); it is the only place where the text of a `kill` error is parsed (under `LC_ALL=C` it is English). `kill -0` directly — only for own children and `$$`. The test hook `BRG_TEST_EPERM_PIDS` («pid pid …»; `*` — any): the listed pids answer as EPERM — this is how the tests reproduce a sandbox on any OS (pid 1 as "alive but unreachable" is not available everywhere).
- `run/metrics.log`: a line per command — `epoch agent command key=value…`. The main metric of the experiment is wake-ups per agent per hour and (by hand) tokens. The exception is `board`: it only reads (§9.1) and does not write into `metrics.log`.
- **Environment variables.** Set by the human: `BRG_AS` (the default of `--as`), `BRG_PYTHON` (the only Python tried for the board server, §9.1), `BRG_BASH` (the full path of Git Bash's `bash.exe`, §10), `BRG_NO_CHCP` (`brg.cmd` does not switch the console code page). Exported by brg to the programs it starts (not to be set by hand): `BRG_RUN` (the run id for the command of `brg run`, §7.3), `BRG_VIA_CMD` (brg was started through `brg.cmd`), `BRG_SPAWN` (the harness of an agent launched by brg and its subagents, §5.5), `BRG_CMD_LC` and `BRG_CMD_LC_SET` (the caller's locale for the commands brg starts), `BRG_SERVE_BASH` (the bash the board server calls brg with). Internal, between the supervisor and its `wait` (not an API): `BRG_SPAWN_WAIT`, `BRG_SPAWN_ID`, `BRG_SPAWN_HOLD`, `BRG_SPAWN_FORCE`, `BRG_SPAWN_ROLLBACK`, `BRG_SPAWN_EXECVER`. Test hooks and tuning knobs: `BRG_TICK` (the `wait`/`tail` tick, default 1 s, fractions allowed), `BRG_STDIN_WAIT` (reading a message body from stdin, 10 s), `BRG_KILL_GRACE` (`brg run`: TERM → KILL, 5 s), `BRG_PLATFORM` (overrides the detected platform), `BRG_BOARD_MAX` and `BRG_BOARD_BMAX` (the snapshot limits, 2000000 and 65536 bytes), `BRG_SOURCE_ONLY` (`=1`: load the functions only, for unit tests), `BRG_TEST_EPERM_PIDS` (above), `BRG_TEST_DELIVER_DELAY` (a delay inside the delivery of `wait`), `BRG_SPAWN_STEP` (the supervisor's sleep step, 1 s), `BRG_SPAWN_EXPORT_TIMEOUT` (the limit of `opencode session export`, 20 s), `BRG_SPAWN_TEST_MAXLIFE`, `BRG_SPAWN_TEST_DELAY_END`, `BRG_SPAWN_TEST_DELAY_PARSE`, `BRG_SPAWN_TEST_DELAY_TOK` (the supervisor's lifetime and delays in the turn wrapper), and the server's hooks `BRG_SERVE_ALIVE_MAX`, `BRG_SERVE_NO_PPID`, `BRG_SERVE_TEST_TOKEN`, `BRG_SERVE_TEST_LISTEN` (§9.1).

## 12. Known limitations

1. **The cost of waiting has not been measured** in Claude Code, OpenCode and Codex, so the `wait_timeout` values (§5.1) are conservative. With `wait_timeout.codex: 25` an idle Codex wakes up to ~144 times an hour.
2. Windows and bash ≥ 4 (Git Bash) have not been tested — `WINDOWS.md`.
3. **Process liveness has not been checked in a real Codex sandbox.** brg treats EPERM («Operation not permitted»; it is reproduced on macOS without a sandbox too: `kill -0 1`) as "alive" (`pid_alive`, §4.2), and a runner's death also needs a silent heartbeat (`runner_dead_grace`, §7.3); the tests imitate the sandbox with `BRG_TEST_EPERM_PIDS`. Not checked from a sandbox: `doctor` gives ⚠ about EPERM; `wait` does not go into `orphan`; two simultaneous `run`s go strictly in turn; `run list` does not mark a live run `killed`.
   **What remains.** If the sandbox's pid namespace hides a live process (ESRCH, not EPERM): ordinary locks are removed from a live owner at once, the `wait` orphan check falsely goes into `orphan`, one-off checks of runs right after laptop sleep may mark a live run `killed` (§7.3); the exec lock and the queue are protected by the heartbeat. `doctor` does not recognise this case. Under EPERM an orphan `wait` is not recognised (it exits by timeout). A `run` from a sandbox cannot reach local services (a database) — brg cannot fix that: the README for Codex says to run the state-changing brg commands, above all `wait` and `run`, outside the sandbox.

5. **`model=unknown`** (Codex): the check "a reviewer of the same model" (§7.1) does not work.
6. **The scope of a task changes inside the task** («изучить» → implementation), and the title in `history.md` misleads: there is no command to rename a task.
7. Small things: truncating `Note` eats the most meaningful part; that research items are claimed without paths (`--paths none`) is not obvious.
8. Not tested: changing the task in the middle of work, work in a branch (Codex: `.git` read-only), a slow provider.

10. The board has not been tested in Safari (`?<time>` of the script under `file://`; the server's `SameSite=Strict` cookie) and on Windows (`WINDOWS.md`, item 2.7). Safari before 16.4 has no `Sec-Fetch-Site`: the snapshot protection from a page of a neighbouring localhost port (§9.1) does not work there on loopback (over the network it is held by the token `k`); the rest (the cookie, `Host`, the token in the POST header) works.
11. **The human's server has not been run on Windows:** `brg.cmd` from Python (quotes and Cyrillic in arguments, a title like `README*` under `MSYS=noglob`), stopping `python.exe` from Git Bash by TERM (the fallback is the `alive` heartbeat), finding `py -3` (`WINDOWS.md`, item 2.8). On macOS it is covered by tests.
12. **Agents launched by brg (§5.5):** launching OpenCode is covered by tests with a fake harness; the current version has not been tried live. Only OpenCode is supported; on Windows (MSYS/WSL) `spawn` refuses. Not checked live: the own session id (`--session` «create if not exist»); whether `opencode run` exits while a background subagent is running; the separation of the main and child sessions' tokens in `session export`. The `project` rights add no restriction inside the project: they are OpenCode's default rules.
13. **The board over the network (`brg board --bind`).** IPv6 and host names are not supported in `--bind` and in `Host` (open the board by an IPv4 address), nor are HTTPS and a reverse proxy (`Host` is a name, `Origin` is `https://…`: both are refused): from outside, the board opens only through an SSH tunnel to the same port number. A known remainder: on macOS an ordinary `brg board` (`127.0.0.1:P`, with `SO_REUSEADDR`) may take a port on top of a foreign process listening on `0.0.0.0:P`; the reverse case is closed (`0.0.0.0` without `SO_REUSEADDR`), and it cannot be checked by a test — the hook listens on loopback. The token is permanent and goes over the network in clear text: after working over the network it has to be changed by hand. On Windows `--bind` has not been tested (the firewall, `WSAEADDRNOTAVAIL`).
14. **The one-command installation**: `curl -fsSL …/install.sh | bash` clones the repository (git is needed) and installs `brg`; tested only on macOS (bash 3.2); not tested on Windows (Git Bash) and with bash ≥ 4 (the mode test is `BASH_SOURCE` at the top level and `-f`; there, inside a function read from a pipe, it may be `main`); without git there is no one-command installation (only the manual one).
15. **Case in reservation paths (§7.2)** is folded only for ASCII and Russian Cyrillic. `É`/`é`, other alphabets and different Unicode normal forms (NFC/NFD) of one name count as different paths: on macOS and Windows such paths may be one directory, and the conflict is not detected.
