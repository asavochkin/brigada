# brigada — дизайн

Схема, по которой любое число агентов из разных харнессов (Claude Code, Codex, OpenCode, …) подключаются к проекту и дальше **сами** организуют работу над задачей человека: обсуждают, распределяют роли и подзадачи, проверяют друг друга.

Документ описывает, как устроено сейчас и почему. **(решение человека)** — решение, которое меняет только человек; остальное принято по ревью и подтверждено тестами. Изменение дизайна — сначала здесь, вместе с кодом.

---

## 1. Цели и ограничения

1. **(решение человека)** Наладка со стороны человека — разовый `brg init` в проекте и фраза агенту «подключись к .brigada, прочитай инструкцию в .brigada/README.md». Никакой настройки харнессов (хуков, конфигов, плагинов) и доп. установок (tmux и т.п.).
2. **(решение человека)** Базовое взаимодействие (сообщения, ожидание, роли, подзадачи) выполняет детерминированный скрипт, а не модель, разбирающая файлы.
3. **(решение человека)** Один механизм ожидания для всех харнессов: агент не завершает ход и ждёт в блокирующем `brg wait` (§5). Возможности отдельных харнессов (фоновые команды с пробуждением, шедулеры, `codex queue`) в протокол не входят; возможно, позже — как необязательная оптимизация.
4. **(решение человека)** Реализация на bash (3.2+). Windows — через Git Bash (§10).
5. **(решение человека)** Всё состояние — внутри `.brigada/`, по задачам; между задачами общее только `common/`. Смена задачи — без перезапуска сессий; новые агенты подключаются в любой момент.
6. **(решение человека)** Самоорганизация — суть эксперимента: агенты сами решают, кто ведёт и как решать задачу. brg ведёт состояние и правила переходов, решения принимают модели.
7. **(решение человека)** PROTOCOL задаёт только цель и минимальные рамки: безопасность; вопросы по бизнес-сути — человеку, технические решения — сами; человек видит вопросы и итог (по умолчанию — текстом в чате host'а); не коммитить в `main`/`master` без разрешения человека и не уничтожать чужую работу; связь — через brg; закрытие — `task close` с `summary.md`. Весь процесс (перекличка, лид, план, подзадачи, резервирования, ревью, ветка, `brg run`) — **рекомендации**: агенты вправе договориться о другом и строить свои инструменты. brg процесс не навязывает (например, не требует ревью для закрытия) — даёт инструменты и следит за целостностью состояния. Почему: регламент подменял бы самоорганизацию (п. 6).

Не цели MVP: параллельные задачи, worktree на агента, кросс-машинная работа (все агенты на одной машине, одна ФС), защита от злонамеренного агента.

## 2. Слои

| Слой | Чем реализован |
|---|---|
| Транспорт и состояние: каналы, курсоры, ростер, задачи, роли, дедлайны, подзадачи, резервирования, прогоны, блокировки | `bin/brg` (один bash-файл) |
| Ожидание | `brg wait` + правило «никогда не завершай ход» |
| Инструкции агентам | `README.md` — механика (обязательна), `PROTOCOL.md` — цель, рамки, рекомендации (из `template/`) |
| Инструменты человека (§9) | глобальная `brg` (`bin/brg-global`, `install.sh`); `bin/brg.cmd` на Windows |

Каждая команда печатает короткий результат и, где уместно, `NEXT:` — следующую команду дословно, с именем агента: так цикл переживает сжатие контекста.

## 3. Подключение

1. Человек в корне проекта: `brg init` (или `bash /путь/к/brigada/bin/brg init [проект]`) — создаёт `.brigada/` (§4). Повторный `init` обновляет `bin/`, `README.md`, `PROTOCOL.md`, `config.default`, `VERSION`, не трогая состояние и `config` (называет ключи шаблона, которых в `config` нет). **(решение человека)** `init` дописывает в `.git/info/exclude` (у worktree — общего git-каталога) `.brigada/` — весь каталог не коммитится: иначе `git add -A` любого агента закоммитит переписку, рантайм, копию `brg` и настройки бригады. Строки brg ≤ 0.2.0 (`.brigada/{tasks,lobby,run,agents}/` и их комментарий) повторный `init` заменяет на `.brigada/` и подсказывает убрать из индекса уже закоммиченное (`git rm -r --cached .brigada`; сам brg git не вызывает, §7.4). `doctor` — ✗, если `.brigada/` в exclude нет.
2. Человек агенту: «подключись к .brigada, прочитай инструкцию в .brigada/README.md».
3. Агент по README определяет харнесс (`claude`, `codex`, `opencode`, иначе короткое имя; синонимы нормализуются) и модель; `join --harness <h> --model <m>` выдаёт полное имя `<harness>-<n>.<ключ>` (`claude-1.k7f3q9`, ключ сессии — ниже) и сводку: кто онлайн, активная задача, таймаут `wait`, «Таймаут инструмента» (как вызывать `wait` в этом харнессе), `NEXT:`. Агент разрешает вызовы brg «навсегда», читает PROTOCOL и входит в цикл (§5).

- **Идентичность** — явный `--as <имя>` в каждом вызове (`BRG_AS` — альтернатива). Опознание по `$PPID` отклонено: в Codex команды идут через обёртку песочницы, на Windows/MSYS свои PID. Отклонено и опознание по дереву процессов (сравнить предка вызывающего с родителем живого `wait`): причины те же, и вдобавок нужен `ps`, которого нет в списке утилит (§11).
- **Ключ сессии в имени** — **(решение человека)** защита от ошибки модели, а не от злоумышленника (профили читаемы, §1). Случай из демо: сессия, получившая задачу в промпте, пропустила `join`, увидела в `who` агента своего харнесса (`opencode-1`) и решила, что это она; `status` ответил «Мой wait: работает» — это сошло за подтверждение личности. Итог — два процесса под одним именем: оба вели задачу как lead, дублировали подзадачи и правили одни и те же файлы (резервирования своих путей не ловят), а двойник без `wait` не получал STOP.
  - `join` выдаёт полное имя `<базовое>.<ключ>`. Ключ — 6 символов `[a-z2-9]` из `$RANDOM` (без `l` и `o`), хранится как `Key:` в `agents/<имя>`. Имена харнессов — только `[a-z0-9]`, поэтому имя и ключ однозначно делятся по первой точке.
  - **Состояние — только на базовом имени**: файлы агентов, курсоры, `From:`, `Assignee`, Host/Lead, резервирования, флаги стопа, `metrics.log`. Ключ пишется только в профиль. Другим имя показывается без ключа (`who`, `tail`, сообщения), поэтому из `who` ключ не взять. Полное имя brg печатает только самому агенту — в подсказках `--as` и в `NEXT:`; сжатие контекста ключ переживает так же, как имя: через последний `NEXT:`.
  - **Изменяющие команды требуют ключ:** `send`, `wait`, `leave`, `task new|close|cancel`, `lead|host give|take`, `item add|claim|done|release|reassign|review`, `run` (запуск и `cancel`). Голое имя → отказ: «имя занято другой сессией; твоё имя — только из вывода твоего join в этом чате; не видишь его — сделай join». `join --as` здесь не подсказывается.
  - **Команды чтения** (`status`, `read`, `who`, `task show|list`, `item show|list`, `run show|list`) принимают и голое имя — их вызывают подагенты (§5.4). Без ключа они не освежают Last-Seen (иначе двойник «оживлял» бы настоящего агента), подсказки с `--as` в их выводе — с заглушкой `<твоё имя из join>`, а `status` не подтверждает личность: «wait агента X работает (pid N). Если ты не делал join в этом чате — ты не X: сделай join», `NEXT:` — `join`.
  - Ключ не `[a-z2-9]{6}` или не совпадает с профилем → отказ в любой команде: «ключ устарел или с ошибкой: под этим именем переподключилась другая сессия».
  - При отказе по ключу `NEXT:` — `join`, а не «исправь и повтори … --as X»: повтор с тем же именем зациклил бы агента. У `wait` — по-прежнему код 0 и последняя строка `NEXT:` (§5).
  - Имена-цели (`send --to`, `item reassign --to`, `lead|host give`) принимаются и с ключом — ключ отбрасывается: агенты копируют своё полное имя.
  - Совместимость: профиль без `Key:` (агент подключился до 0.2.0) принимает голое имя везде; ключ он получит при `join --as`.
- **Возврат** после потери контекста — `join --as <имя> --harness <тот же>` (имя голое или полное): только тот же харнесс; снимает `Left`; курсоры сохраняются; выдаёт **новый ключ**, прежний перестаёт работать (старая сессия, если жива, получит «ключ устарел»). В `lobby` — «X переподключён новой сессией; прежний ключ недействителен» (будит host'а). Отказ:
  - у имени живой `wait`: «если это твой wait и ключ потерян — дождись его конца и повтори join --as»;
  - **(решение человека)** агент не «выпал»: возврат разрешён только после тишины — ни `wait`, ни вызовов brg — дольше max(`wait_timeout` + 60 с, `dropout_after`), как у пометки «возможно выпал» (§5.2), либо в состоянии `asleep`/`gone` (в т.ч. после `leave` — сразу). Иначе двойник, знающий базовое имя из `who`, забрал бы имя вместе с ролями у работающего агента: «мёртвый wait» — обычное состояние агента между вызовами (в демо он подолгу работал без `wait`). Отказ: «X активен (последний вызов N с назад). Если это ты и ключ потерян — он в последней строке NEXT; иначе подожди M с или подключись под новым именем». Флаг стопа на условие не влияет. Цена: агент, потерявший ключ, ждёт до ~5 минут или подключается под новым именем.
- **Одна платформа на `.brigada`**: `join` отказывает, если платформа (Darwin, Linux, MSYS, WSL, …) не совпадает с подключёнными не-`gone` агентами — pid, блокировки и пути у WSL и Git Bash разные.
- **Глобальная команда человека:** `bash install.sh` ставит `bin/brg-global` как `~/.local/bin/brg`. Из любого подкаталога проекта она запускает ближайший `.brigada/bin/brg`, `brg init` — версией репозитория, вне проекта — `brg` репозитория; если копия в проекте устарела — подсказывает `brg init`. Агенты по-прежнему вызывают `bash .brigada/bin/brg …` — от их окружения ничего не требуется (§1 п. 1).

## 4. Хранилище

```
.brigada/
  README.md, PROTOCOL.md # для агентов (копии template/; init перезаписывает)
  VERSION
  config.default         # значения по умолчанию (копия template/config; init перезаписывает)
  config                 # настройки проекта: init создаёт один раз и не трогает
  bin/brg, bin/brg.cmd
  agents/<name>          # профиль: Name, Key (ключ сессии, §3), Harness, Model, Platform, Joined… [, Left, Rejoined]
  lobby/                 # канал проекта: seq, messages/000001.msg, cursors/<name>
  common/project.md      # устойчивые факты о проекте (стек, тесты, конвенции) — пишут агенты
  common/history.md      # реестр закрытых и отменённых задач — пишет brg
  tasks/active           # имя каталога активной задачи (нет файла — нет активной)
  tasks/T001-<slug>/     # slug — из латиницы заголовка (может отсутствовать)
    task                 # Id, Title, Status, Host, Lead, Created…, Closed…
    brief.md             # постановка человека дословно
    seq, messages/, cursors/<name>
    items/I001           # Id, Title, Status, Creator, Assignee, Paths, Paths-Hint, … + описание
    items/I001.reviews/<n>   # неизменяемые записи ревью
    reservations/I001    # Item, Agent, Time + пути построчно
    shared/              # plan.md, решения, артефакты — свободно для агентов
    shared/runs/R001     # прогон: заголовки; рядом .log, .sync, .cancel, .notified
    summary.md           # итог (обязателен для закрытия)
  run/                   # рантайм, не история
    locks/<name>.lock/owner   # roster, task, runs, chan.<канал>; exec.lock (+ run, hb)
    seen/<name>          # Last-Seen (отдельно от профиля — без гонок read-modify-write)
    wait/<name>.pid|.hb|.last # владелец wait (takeover); "pid epoch" живого wait; его последнее завершение
    deadlines/<отправитель>/<epoch>-<канал>-<id>, deadlines/<канал>-<id>.done
    execq/<n>, runs.seq  # очередь brg run; сквозной по проекту счётчик прогонов
    stopped, stopped.<name>   # флаги стопа (§9)
    runner.log, metrics.log
```

### 4.1 Формат записей

Все записи — «заголовки `Key: value` + пустая строка + тело» (как email). Без JSON: разбирается `sed`/`awk`, читается людьми и моделями. Сообщение `messages/000014.msg`:
```
Id: 14
Channel: T001
From: codex-1            # агент | human (say) | brg (результат run)
To: all                  # all | имя[,имя] | human (можно с именами)
Kind: msg                # msg | system
Re: 12
Reply-By: 1759838400     # необязательно, epoch
Expect: claude-1,opencode-1   # при Reply-By: чьего ответа ждём
Wake: no                 # только у системных: no — не будит; <имя>[,<имя>] — будит только их
Time: 2026-10-07T12:03:11Z
Epoch: 1759838191

тело
```

Время: ISO для людей, epoch для вычислений (разбор дат в BSD/GNU `date` различается — только форматируем).

### 4.2 Запись и блокировки

- Блокировка — `mkdir run/locks/<имя>.lock` + `owner` («pid epoch»). Протухшая (владелец мёртв, лок старше `lock_stale` или без `owner` дольше `lock_stale`; `lock_stale` ≫ любой критической секции) снимается **атомарно**: `mv` лока в уникальное имя (побеждает ровно один; лок, сменивший владельца, не трогается), затем `rm`. Снимает лок только владелец. Вложенность: task → runs → chan; exec → runs → chan.
- **«Мёртв»** — у pid, прочитанного из файла, всегда по одной функции `pid_alive` (§11): `kill -0` успешен или отвечает EPERM («Operation not permitted» — процесс есть, но недоступен: песочница Codex, чужой пользователь) — жив; ESRCH и любой другой ответ — мёртв. Лок недоступного владельца снимается только по возрасту (`lock_stale`), exec-лок — по heartbeat (§7.3).
- Сообщение — под блокировкой канала: `seq+1` → тело во временный файл в том же каталоге → `mv` в `messages/NNNNNN.msg` → обновить `seq`. Нумерация без дыр, курсор не «перепрыгнет» сообщение. Упали между `mv` и `seq` — `seq` пересчитывается по максимальному номеру файла.
- Остальные файлы — тоже tmp + `mv`; `mv` — с повторами (Windows: файл может держать антивирус или читатель).
- **Тексты** (сообщение, постановка, описание подзадачи, комментарий ревью) — из stdin (heredoc `<<'BRG_EOF'`) или `--file`; `say` — ещё и аргументами; `item add --desc`/`item review --comment` — однострочная альтернатива (в т.ч. для PowerShell, где нет heredoc, а пайп в Windows PowerShell 5.1 портит кодировку). CRLF → LF, BOM снимается, UTF-16 отвергается. Лимиты: сообщение — `msg_max_bytes` (8 КБ; больше — отказ с подсказкой положить текст в `shared/`), постановка — 64 КБ. stdin-пайп, не закрывшийся за 10 с, — отказ, ничего не отправлено.
- **Короткие поля из опций по длине не отвергаются** (отказы стоят агентам шагов): `--title` (200 байт), `--note` (500), `--desc`/`--comment` (`msg_max_bytes`) обрезаются по границе UTF-8 с пометкой «…(обрезано)» и предупреждением.

## 5. Ожидание и рабочий цикл

**(решение человека)** Единственный механизм — блокирующий `brg wait --as <имя> [--timeout S]`. Последнее действие каждого шага агента — `wait`; ход не завершается (кроме STOP).

1. **Один wait на агента, takeover без сигналов.** Новый wait пишет свой pid в `run/wait/<имя>.pid`; старый каждый тик (1 с) проверяет владение и, увидев чужой pid, выходит. Сигналы не посылаются: pid из файла мог быть переиспользован. Дубликаты (wait, уведённый харнессом в фон) не съедают почту.
2. **Вытесненный wait не провоцирует новый:** печатает `── SUPERSEDED: … НЕ вызывай wait повторно.` — это рвёт цепочку «уведомление о завершении старого wait → модель зовёт ещё один». TERM/INT/HUP — только от харнесса или человека (лимит команды, Esc), поэтому `── прерван сигналом … · NEXT: …` — цикл продолжается (pid-файл уже чужой — SUPERSEDED).
3. **Доставка хотя бы один раз.** Wait сначала подтверждает пачку предыдущего (`Acked := Pending`), затем ищет новое. `Pending` пишется только после вывода: убитый до вывода wait не теряет сообщения.
4. **Каналы:** `lobby` и активная задача (плюс дренаж только что завершённой, §6). Доставляется адресованное агенту или `all`, кроме собственного. Чужие личные не доставляются (видны в `tail` и `read --all`): шум и контекст дороже прозрачности.
5. **Heartbeat:** каждый тик — `run/wait/<имя>.hb`, раз в `heartbeat` с — Last-Seen (его обновляет и любой вызов brg). Живой wait = pid жив (`pid_alive`, §4.2: EPERM — жив) **и** hb свежий (защита от переиспользования pid).
6. **Сироты:** умер родитель — wait выходит молча, не держа призрака в `waiting` (родитель `1` — обёртка, MSYS — не проверяется). Недоступный родитель (EPERM, песочница) считается живым: сирота там не распознаётся и выходит по таймауту — это лучше ложного `orphan` у живого агента.
7. **Сам завершается раньше лимита харнесса:** таймаут из `config` по харнессу и платформе (§5.1); `--timeout` переопределяет и повторяется в `NEXT:`.
8. **Будят:** новая почта, сводка дедлайна (§8), стоп (§9), `leave` (`── LEFT`). **Тихие системные события** (`Wake: no`: подключился, отключился, взял подзадачу) не будят и приходят со следующей будящей пачкой — иначе каждый join стоил бы вызова модели каждому ждущему. Адресные (`Wake: <имена>`) будят только названных. Новая/закрытая/отменённая задача, смена lead/host, уход агента с ролью — будят всех; «подключился/вернулся» при активной задаче — host'а (иначе он не знает, что участники пришли); `item add`, `done`, `release` — lead'а; `reassign` — нового исполнителя; `review` — исполнителя и lead'а; `claim` — никого; результат `brg run` — инициатора. Автор события не будится.
9. **Дайджест на таймауте:** при активной задаче перед `── нет новых` — строка `T001: todo 1 · в работе I002 codex-1 · готово I003 · ревью ждут I003 · прогонов идёт 1` (иначе лид опрашивает `who`/`item list`).
10. **Кап вывода** `wait_output_max` (~20 КБ, лимит inline-вывода харнессов): `Pending` = последнее показанное, остаток — следующим wait сразу (строка `── ещё N в <канал> не вошло …` с командой `read`).
11. **Всегда код 0**, статус — в тексте. Последняя строка — `NEXT:` (кроме STOP, SUPERSEDED, LEFT и выхода сироты), в том числе при ошибке аргументов и отказе по ключу (§3) — иначе агент выпадет из цикла.
12. `read` курсор не двигает и по умолчанию показывает всё после `Acked`, включая последнюю выданную пачку — безопасный повтор, если агент не уверен, что видел вывод. Новый агент стартует с конца `lobby` и активной задачи.

Курсор `cursors/<name>`: `Acked: 14` (всё ≤ 14 обработано), `Pending: 15` (выдано последним wait, подтвердит следующий). Вывод:
```
── T001 · 2 новых ─────────────────────────────
#14 codex-1 → all · re #12 · 12:03
  Предлагаю лидом claude-1: …
#15 [система] claude-1 → all · 12:04
  …
── NEXT: обработай, затем: bash .brigada/bin/brg wait --as claude-1.k7f3q9
```
Таймаут: `── нет новых (100 с) · NEXT: …`. Стоп: `── STOP: человек остановил бригаду. Заверши ход.`

### 5.1 Таймауты по харнессам

Значения **консервативные — до замеров** в каждом харнессе. Все ниже 120 с — дефолтного лимита команды: модель может не передать увеличенный таймаут инструмента (особенно после сжатия контекста). Повышать — только если замер покажет, что модель делает это стабильно.

| Харнесс | Лимит команды | `wait_timeout` сейчас | Цель после замера |
|---|---|---|---|
| Claude Code | по умолч. 2 мин, макс. 10 мин (параметр `timeout`); на лимите уводит в фон | 100 | 540, если модель стабильно передаёт `timeout: 600000` |
| OpenCode | по умолч. 2 мин, верхний предел снят | 100 | 540 при том же условии |
| Codex (macOS/Linux) | unified_exec: команда «паркуется» через 10–30 с, дальше опрос моделью (`write_stdin`) | 25 (вернуться до парковки) | по замеру |
| Codex (Windows) | unified_exec по умолчанию выключен — ближе к обычной блокирующей команде | 100 (`wait_timeout.codex.msys`) | по замеру |
| неизвестный | — | 100 (`wait_timeout.default`) | — |

Таймаут инструмента = `wait_timeout` + 60 с (≤ 600 с) — печатают `join` и `status`. `doctor`: `wait_timeout` > 540 с — ✗, > 110 с (Codex вне Windows — > 25 с) — ⚠.

«Выпадение из цикла» — латентность модели (выход `wait` → следующий вызов инструмента) > 60 с без учёта повторов запроса провайдером, или самостоятельное завершение сессии. Опросы запаркованной команды Codex в логе `wait` не видны — их стоимость оценивается по транскрипту. Токены на пробуждение = токены сессии / вызовы `wait`, на модели, что реально будет в бригаде.

**Правило жизнеспособности:** **≤ 15 вызовов модели на час простоя.** Не достигающий его харнесс (ожидаемо — Codex с парковкой) участвует с повышенной стоимостью простоя либо только «по тычку» человека — решение по итогам замера.

### 5.2 Живость агента

Состояние в `who`/`status`: `waiting` (жив wait), `working` (недавний вызов brg), `asleep` (нет wait и вызовов дольше `asleep_after`, 15 мин), `gone` (`leave` или тишина дольше `gone_after`, 1 ч). Пороги щедрые: агент, 10 минут гоняющий тесты, не пропал. Пометки: «без wait N мин» — wait не идёт дольше `wait_timeout` + 60 с; «возможно выпал» — ни wait, ни вызовов brg дольше max(`wait_timeout` + 60 с, `dropout_after` = 300 с), кроме остановленных: подсказка человеку написать агенту в чат «продолжай».

### 5.3 Известные минусы (приняты сознательно)

- Сообщение человека в чате харнесса дойдёт, когда wait вернётся (до `wait_timeout`), либо после Esc.
- Простой не бесплатен: один вызов модели на таймаут на агента.
- Гарантии нет: агент может завершить ход. Это видно (`без wait`, «возможно выпал», `asleep`); lead переназначает его подзадачи, человек говорит «продолжай».

### 5.4 Подагенты

PROTOCOL рекомендует отдавать объёмную работу (чтение кода, реализацию, прогоны, ревью diff) подагентам харнесса: контекст участника живёт всю задачу и растёт с каждым пробуждением — чем он меньше, тем дешевле пробуждение и позже сжатие. Механика (README, обязательна): подагент не вызывает `join`, `wait`, `leave`, `stop` — его `wait` под именем участника вытеснит wait участника (SUPERSEDED), и тот выпадет из цикла; можно команды для чтения и короткий `run --sync` под именем участника. `run` — изменяющая команда (§3), поэтому подагенту передаётся полное имя участника, с ключом; командам чтения хватает и базового. brg подагента от участника не отличает — правило только в документах.

## 6. Задачи

**(решение человека)** В проекте одна активная задача; все подключённые агенты — её участники (неявное членство). Хранилище — по задачам, чтобы параллельные задачи с явным членством потом не требовали миграции.

- `task new --as X --title "…"` + постановка (дословно от человека → `brief.md`) → `T00N[-<slug>]`, Host = Lead = X, «новая задача» в `lobby`. Есть активная — отказ, либо `--cancel-current` (текущая отменяется); технически он доступен любому агенту, PROTOCOL рекомендует его, только если человек сам сказал бросить текущую. `task new` снимает общий стоп и стоп автора: человек только что дал работу.
- Переключение: wait всех агентов замечает смену `tasks/active` на ближайшем тике и слушает новую задачу. Из прошлых задач — только `common/` (рекомендация PROTOCOL).
- `task close --as <lead> [--force]`: всегда нужен непустой `summary.md` (первая строка — итог в `common/history.md`); отказ, пока есть подзадачи `claimed` или идущие прогоны (`--force` отменяет и останавливает их). Ревью не требуется (§1 п. 7; иначе тупик при одном агенте).
- **Непрочитанное перед закрытием — «отказ = доставка» (решение человека).** Сразу после проверки «ты lead» и **до** проверки `summary.md` (lead должен увидеть сообщения до того, как напишет итог) close ищет то, что разбудило бы wait lead'а: в его каналах (`lobby`, задача, недренированные завершённые — как у wait) после `Pending` есть будящее (`FMT_WAKE` > 0: сообщения ему или всем, в т.ч. личные системные — результат `run`, ревью, сданные подзадачи). Тихие системные (join/leave/claim) и собственные не мешают; сводки дедлайнов (§8) не учитываются — придут wait'у. Нашлось — close печатает на stdout всё для lead'а после `Pending` (тихое тоже), как wait, с капом `wait_output_max`; после вывода сдвигает `Pending` на последнее показанное (`Acked` не трогает) и отказывает: «учти их (при необходимости поправь summary.md) и повтори task close». Подсказка — повтор `close`, не `read`: `read` курсор не двигает, отказ «прочитай» зациклил бы. Повтор проходит, если нового нет; при капе — несколько отказов подряд, каждый двигает `Pending`. `--force` проверку не обходит (показанное уже доставлено — повтор проходит). Следующий wait подтверждает показанное (`Acked := Pending`) и не выдаёт его повторно; гонка с фоновым wait lead'а (он держит курсоры в памяти) даёт не потерю, а максимум дубль — at-least-once.
- `task cancel --as <host|lead|human>`: `claimed` → `cancelled`, резервирования и прогоны снимаются, всем — «прекрати правки»; незавершённые правки остаются в рабочем дереве — их судьбу решает lead новой задачи или человек. Человек отменяет только явным `--as human`: агент, забывший `--as`, не отменит задачу «от имени человека».
- `common/history.md` — строка при закрытии и при отмене. Статусы: `active`, `done`, `cancelled`; фазы работы — только в рекомендациях. События «новая / закрыта / отменена» — в `lobby`, смена lead/host — в канал задачи; в канал завершённой задачи писать нельзя.
- **Дренаж:** перестав слушать закрытую или отменённую задачу, wait сначала выдаёт её недоставленные адресованные сообщения (`── T001 (закрыта)`) — финальное слово лида не теряется.
- Курсоры канала задачи: бывшие на момент создания читают с начала, подключившиеся посреди — с конца (история — `read --channel T00N --since 0`); `join --as` после `leave` — с конца, без переписки задач, завершённых за время отсутствия. Нумерация сообщений своя в каждом канале, `--re` — к выбранному.

### 6.1 Роли

- **Host** — кому человек дал задачу (её создатель). Только host сам начинает разговор с человеком; остальные отвечают, если человек написал им напрямую. **Канал к человеку — чат харнесса:** отчёт и вопрос агент пишет обычным текстом в своём чате перед очередным wait (его человек видит); `send --to human` — копия для протокола (видна только в `tail`).
- **Lead** — оркестратор, по умолчанию Lead = Host. `lead give <имя>` — только текущий lead и не `gone`-агенту; `lead take` — только если текущий lead `asleep`/`gone`. То же `host give|take`. Агенты могут договориться о другом лиде — самоорганизация без тупика «лида нет».
- Уход (`leave`) агента с ролью lead или host будит всех с подсказкой `take`.

## 7. Подзадачи и код

### 7.1 Подзадачи

- `item add` → `I00N` (`todo`); `--paths` — предлагаемые пути (`Paths-Hint`).
- `item claim I00N [--paths …|none]` — атомарно. Пути надо назвать (`--paths` или подсказка из `add`) либо сказать `none` (исследование, ревью) — резервирование не забудется случайно. Пересечение с чужим резервированием → отказ со списком конфликтов. Повторный `claim` своей меняет пути.
- Пересечение со **своим** резервированием (другая своя подзадача в работе) — не отказ, а предупреждение после взятия: «эти пути уже твои по I001 …; если I001 брал не ты — под твоим именем работает другая сессия: сообщи lead'у и человеку». Так всплывает двойник под одним именем (§3). Без предупреждения: `--paths none` и пересечение подзадачи с самой собой при повторном `claim`; `.` пересекается со всеми своими — так и задумано.
- `item done` — только исполнитель (`--note`, `--result <путь>`); снимает резервирование.
- `item release` (в `todo`) — исполнитель, или lead, если исполнитель `asleep`/`gone`. `item reassign --to <имя>` — lead, только если исполнитель `asleep`/`gone` и новый не `gone`; резервирование переходит новому.
- `item review --verdict ok|changes` — для `claimed` или `done`; своё ревью исполнитель писать не может; ревьюер той же модели, что исполнитель, при онлайн-агенте другой модели — предупреждение, не отказ. Записи ревью неизменяемы.
- Все изменения подзадач — под локом задачи (claim не проскочит в закрывающуюся задачу).

### 7.2 Резервирования путей

- Пути от корня проекта, через запятую; нормализуются (`\` → `/`, без `./`, `//`, хвостового `/`; `.` — весь проект). Запрещены `..`, абсолютные пути, `~`, маски, управляющие символы. Без глобов — детерминированно и просто в bash.
- Пересечение — префикс по границе компонента (`src` и `src/a` — да, `src/a` и `src/ab` — нет), **без учёта регистра** (ФС macOS и Windows; на Linux возможны ложные конфликты — сознательно консервативно).
- Резервирование действует, пока подзадача `claimed` этим агентом (остаток после падения игнорируется); снимается `done`, `release`, закрытием и отменой задачи.
- Защищает только тех, кто им пользуется: brg правки файлов не отслеживает.
- Резервирования охраняют только запись. Чтение в общем дереве brg не ограничивает и не проверяет (§1: одна ФС, без защиты от агента): условие постановки вида «не читать чужое до раскрытия» — лишь договорённость. PROTOCOL рекомендует host'у сразу назвать такое условие человеку непроверяемым и предложить проверяемую рамку (работа вне общего дерева до раскрытия, раскрытие по договорённости).

### 7.3 `brg run`

Тесты, сборка, линтеры — под глобальной блокировкой: не гонять тесты на полуотредактированных файлах соседа. **По умолчанию в фоне**: агент сразу получает `R00N` и место в очереди, результат (статус, код, хвост лога, путь к логу) приходит инициатору системным сообщением — долгие операции не упираются в лимит команды харнесса и встраиваются в механику «всё — сообщения».

- Только при активной задаче; создаётся под её локом (нет гонки с `close`). `--item I00N`, `--timeout` (по умолчанию `run_timeout`, 30 мин). Одна строка-аргумент — через `bash -c`, несколько — как есть; cwd — корень проекта.
- Очередь `run/execq/` в порядке запросов; голова запускается, захватив `run/locks/exec.lock`. Он держится всю команду и **не ломается по возрасту** — только по смерти владельца (подтверждённой heartbeat, см. ниже) или устаревшему heartbeat.
- Раннер — `nohup` под `set -m`, все fd перенаправлены (харнесс его не ждёт); команда — в своей группе процессов, после неё остатки группы добиваются; таймаут или отмена — TERM группе, через 5 с KILL. Статусы: `queued`, `running`, `done`, `failed`, `timeout`, `killed`, `cancelled`. Результат — сообщение `From: brg` инициатору в канал задачи (задача уже завершена — в `lobby`), ровно один раз.
- `--sync` — для коротких команд: ждёт на месте не дольше `wait_timeout` агента (`--timeout` больше — отказ), код выхода — код команды; не уложилась (в т.ч. из-за очереди) — результат придёт сообщением. Раннер, закончив, даёт ещё ждущему синхронному вызывающему до 3 с напечатать результат самому; недоступный pid вызывающего (EPERM) считается живым — тогда отдельное сообщение уходит с задержкой до 3 с (допустимо).
- `run cancel R00N` — инициатор или lead, через файл-флаг (без сигналов чужим pid).
- **Heartbeat раннера** — раз в секунду. Живой pid (в т.ч. недоступный, EPERM) с молчащим heartbeat объявляет мёртвым только ждущий раннер, непрерывно наблюдавший молчание дольше `runner_stale` (60 с, > `lock_stale`); провал времени у наблюдателя (сон ноутбука, SIGSTOP) сбрасывает отсчёт. «Оживший» раннер, у которого забрали лок или закрыли прогон, убивает свою команду и не перезаписывает вердикт (край: до ~1 с его команда может идти параллельно с командой победителя).
- **Мёртвый pid раннера — ещё не смерть:** в pid-namespace песочницы живой процесс может отвечать ESRCH. Раннер мёртв, только если (1) pid мёртв (`pid_alive`, §4.2), (2) его heartbeat (exec-лок или запись очереди) старше `runner_dead_grace` (5 с; 0 — верить одному pid) и (3) судящий ждущий раннер наблюдал без провала не меньше `runner_dead_grace` (провал дольше grace/2, но не меньше 2 с, сбрасывает отсчёт: после сна heartbeat у всех старый). Этот отсчёт отдельный от отсчёта `runner_stale` (тот сбрасывает провал дольше runner_stale/2, от 2 до 10 с): короткие провалы на загруженной машине не откладывают вердикт `runner_stale`. Пока условия не выполнены, раннер с мёртвым pid судится как живой — по `runner_stale`, поэтому и частые провалы не повесят очередь. Раннер, убитый `kill -9`, снимается примерно через `runner_dead_grace`.
- Просмотр (`run show/list`, `status`, `task close/cancel`, `run cancel`, `doctor` — разовые проверки, вердикт у всех один): pid раннера мёртв и heartbeat старше `runner_dead_grace` → `killed` (умерший только что — со следующего просмотра после grace; `run cancel` перепроверяет, пока ждёт); живой, но молчащий → «раннер не отвечает N с» (разовый вызов не отличит сон от зависания), `run cancel` закрывает и такой. Раннер убит `kill -9` → лок снимается; команда-сирота не убивается (сообщение предупреждает, pgid записан). **Остаток:** разовая проверка не наблюдает непрерывно (условия (3) нет) — в среде с ESRCH сразу после сна ноутбука, когда heartbeat у всех старый, она может отметить живой прогон `killed` (сам раннер, проснувшись, увидит вердикт и остановит команду).
- `task cancel`, `--cancel-current`, `close --force` останавливают прогоны задачи; их перечисляет сообщение о задаче, отдельных сообщений нет.

### 7.4 git

- Обязательно (PROTOCOL, §1 п. 7): не коммитить в `main`/`master` без разрешения человека. Рабочее дерево одно на всех: не переключать ветки и не трогать чужие незакоммиченные правки без договорённости (никаких `stash`, `reset`, `checkout`, `restore`, `clean` поверх них).
- Рекомендовано: одна ветка на задачу, её создаёт lead в начале, коммитит lead. У Codex `.git` может быть только для чтения — тогда сказать lead'у.
- **(решение человека)** Авторство (рекомендация PROTOCOL lead'у): автор коммита — из git config (человек: он отвечает за слияние), участники — трейлерами в конце сообщения коммита, по одному на каждого, кто внёс вклад, плюс номер задачи:
  ```
  Co-Authored-By: claude-1 (claude, <модель>) <claude-1@brigada.invalid>
  Brigada-Task: T001
  ```
  Имя — базовое (без ключа), харнесс и модель — как в `who`. Email обязателен: без него GitHub трейлер не распознаёт; домен `.invalid` зарезервирован и никуда не ведёт. Запрет называть провайдеров и модели относится только к репозиторию brigada, не к проектам пользователей.
- brg сам git не вызывает (только находит git-каталог для `info/exclude`). Worktree на агента — отложено.

## 8. Дедлайны

`send … --reply-by 5m` (от 1 с до 24 ч). По сроку wait отправителя возвращается со сводкой `── дедлайн по #N (T001) истёк: ответили: …; не ответили: …` — детерминированная основа правила «молчание = согласие».

- `Expect` — адресаты на момент отправки (для `all` — все не-`gone`, кроме отправителя); их нет — дедлайн не ставится.
- Ответ — не системное сообщение адресата в том же канале после исходного: с `Re: <id>` **или** любое сообщение отправителю (лично или `all`) — модели забывают ставить `Re:`.
- Ответили все до срока — сводка приходит сразу, с пачкой последнего ответа (экономит пробуждение).
- Сводка выдаётся один раз: перед печатью атомарно создаётся маркер `<канал>-<id>.done`, индекс удаляется после вывода. Индекс остался через минуту после срока (репортёр умер) — сводка выдаётся повторно: дубль лучше потери.

## 9. Команды

Агентам: `join`, `leave`, `send`, `wait`, `read`, `status` (одноэкранная реориентация после сжатия: кто я, роль, задача, мои подзадачи и прогоны, непрочитанное, дедлайны, жив ли мой wait, NEXT), `who`, `task …`, `lead|host give|take`, `item …`, `run …`. Человеку: `init`, `say` (от `human`), `tail [-f]`, `who`, `stop`, `resume`, `task cancel --as human`, `item list`, `run list`, `doctor`. Агент передаёт в `--as` полное имя из своего `join` (с ключом, §3); команды чтения принимают и базовое, `stop`/`resume` и имена-цели — базовое. Синтаксис — `brg help` и `brg <команда> --help`.

**Стоп.** `stop` ставит флаг `run/stopped` (`stop <имя>` — `run/stopped.<имя>`, в т.ч. для зачистки призраков). Пока флаг стоит, любой wait возвращает STOP **сразу** (агент, бывший в работе, не заблокируется снова); живые wait видят флаг на ближайшем тике — без сигналов, как и takeover. Флаг снимают `resume`, `say` (общий и названных адресатов) и `task new` (общий и автора). Остановленные агенты завершили ход — после снятия стопа человек пишет им в чат «продолжай».

**(решение человека)** Стоп видит и агент, давно не звавший wait: любая команда с `--as` (общий стоп или стоп этого агента, по базовому имени) первой строкой stdout печатает `── STOP: …`. Кроме `wait` и `status` — они печатают STOP сами (без дубля), и `task new` — он стоп снимает и говорит об этом. Команды, **начинающие работу**, — `item add|claim|reassign` и запуск `run` — при стопе отказывают, `NEXT:` — «заверши ход» (не wait: иначе агент вернётся в цикл, а wait тут же вернёт STOP). Сдать сделанное и сообщить — можно: `send`, `item done|release|review`, `task close|cancel`, `run cancel`, `lead|host give|take`, `leave`, команды чтения.

## 10. Windows

- `bin/brg.cmd` (ASCII, CRLF) сам находит Git Bash: `BRG_BASH` → `%ProgramFiles%\Git\…` → `%ProgramFiles(x86)%\…` → `%LOCALAPPDATA%\Programs\Git\…` → scoop → через `where git`. `bash` из PATH не вызывает, bash из System32/WindowsApps (WSL) отвергает. Ставит `BRG_VIA_CMD` — brg печатает `NEXT:` в форме `.\.brigada\bin\brg.cmd …` (работает и в PowerShell, и в cmd; вызов не из корня — с подсказкой `cd <корень>`). На время вызова `chcp 65001` (`BRG_NO_CHCP=1` отключает); код выхода brg сохраняется.
- `.gitattributes`: `bin/brg`, `bin/brg-global`, `*.sh`, `template/*` — `eol=lf`, `*.cmd` — `eol=crlf`. brg с CRLF в самом себе выдаёт понятную ошибку (код 2).
- Агентам в PowerShell/cmd: `.\.brigada\bin\brg.cmd …`, тело — `--file` (или `--desc`/`--comment`); харнесс, выполняющий команды в Git Bash (Claude Code на Windows), вызывает как обычно.
- Таймауты по платформе: `wait_timeout.<харнесс>.<платформа>` (`darwin`, `linux`, `msys`, `wsl`). Пользовательский `config` побеждает любые значения по умолчанию: `config` (`<h>.<plat>`, `<h>`) → `config.default` (то же) → встроенные (то же) → `wait_timeout.default` в том же порядке файлов.
- `brg doctor [проект]` — проверки среды и состояния (bash и платформа, CRLF, атомарность `mkdir`, `mv` поверх открытого файла, видимость процессов, `.git/info/exclude`, блокировки, раннеры, зависшие wait, таймауты): ✓/⚠/✗ с подсказками, ничего не меняет, код 1 только при ✗. Видимость процессов: `kill -0` родителя даёт EPERM — ⚠ «песочница: чужие процессы недоступны, brg считает их живыми, сироту wait не распознает»; EPERM даёт уже завершённый собственный ребёнок — ⚠ «смерть процессов не видна, раннер снимается только по heartbeat (до `runner_stale`)». Песочницу, где pid-namespace прячет живые процессы (ESRCH), doctor не распознаёт (§12 п. 3). Блокировки и раннеры doctor оценивает тем же вердиктом, что и brg (§7.3, с `runner_dead_grace`). Сломанную установку (CRLF) проверяют копией из репозитория: `bash /путь/к/brigada/bin/brg doctor <проект>`.
- На Windows ничего ещё не запускалось — проверка по `WINDOWS.md` на машине человека.

## 11. Реализация

- bash 3.2 (запреты — в `AGENTS.md`). Утилиты: `mkdir mv rm cat sed awk date sleep kill ls head tail wc sort tr printf cp uname nohup`; без jq/python/node; `date` — только форматирование. Внутри `LC_ALL=C` (байтовая семантика), UTF-8 проходит насквозь.
- Один файл `bin/brg`. Тесты — на чистом bash (`tests/`), включая конкурентный стресс, takeover, протухшие блокировки и скриптовый пинг-понг ≥ 200 обменов с убийствами wait; `test_brg_docs.sh` сверяет команды и флаги в `template/*.md` и `WINDOWS.md` с `--help`.
- **Живость процесса по pid из файла** — только `pid_alive` (§4.2); единственное место, где разбирается текст ошибки `kill` (под `LC_ALL=C` он английский). `kill -0` напрямую — только для своих детей и `$$`. Тестовый крючок `BRG_TEST_EPERM_PIDS` («pid pid …»; `*` — любой): перечисленные pid отвечают как EPERM — так тесты воспроизводят песочницу на любой ОС (pid 1 как «живой, но недоступный» есть не везде).
- `run/metrics.log`: строка на команду — `epoch агент команда ключ=значение…`. Главная метрика эксперимента — пробуждения на агента в час и (вручную) токены.

## 12. Открытые вопросы

1. **Стоимость ожидания:** можно ли в Claude Code и OpenCode поднять `wait_timeout` до 540 с и во что обходится ожидание в Codex — нужен замер, правило §5.1. При `wait_timeout.codex: 25` простой Codex — до ~144 пробуждений в час, далеко за правилом.
2. Windows и bash ≥ 4 (Git Bash) не проверялись — `WINDOWS.md`.
3. **Живость процессов в песочнице Codex — исправлено (этап 6.1), подтвердить на машине с Codex.** EPERM («Operation not permitted»; воспроизводится и на macOS без песочницы: `kill -0 1`) brg теперь считает «жив» (`pid_alive`, §4.2), а смерть раннера требует ещё и молчания heartbeat (`runner_dead_grace`, §7.3). Проверить из песочницы: `doctor` даёт ⚠ про EPERM; `wait` не уходит в `orphan`; два одновременных `run` идут строго по очереди; `run list` не помечает живой прогон `killed`.
   **Остаток.** Если pid-namespace песочницы прячет живой процесс (ESRCH, а не EPERM): обычные блокировки снимаются у живого владельца сразу, сирота `wait` ложно уходит в `orphan`, разовые проверки прогонов сразу после сна ноутбука могут отметить живой прогон `killed` (§7.3); exec-лок и очередь защищены heartbeat. `doctor` этот случай не распознаёт. Сирота `wait` при EPERM не распознаётся (выходит по таймауту). `run` из песочницы не достучится до локальных сервисов (БД) — это brg не исправит: README для Codex велит запускать меняющие состояние команды brg, прежде всего `wait` и `run`, вне песочницы.
4. **Повторная сдача после `item review --verdict changes`:** подзадача остаётся `done`, исполнитель не может пересдать. Варианты: `changes` возвращает её в `claimed` или исполнитель может пересдать `done` поверх своего `done`.
5. **`model=unknown` у Codex** — проверка «ревьюер той же модели» (§7.1) не работает. Подсказка в README (`--model` из `~/.codex/config.toml`) или считать разные харнессы разными моделями.
6. **Объём задачи меняется внутри задачи** («изучить» → реализация), и заголовок в `history.md` вводит в заблуждение: команда переименования задачи или рекомендация «реализация — новой задачей».
7. Мелочи: обрезка `Note` съедает самое содержательное; что исследовательские подзадачи берутся без путей (`--paths none`), неочевидно; `wait --help` не упоминает LEFT; `install.sh` ломается на `#`/`&` в пути к репозиторию.
8. Не проверялись: смена задачи посреди работы, работа с веткой (Codex: `.git` только для чтения), медленный провайдер.
9. Позже: параллельные задачи, worktree на агента, необязательные оптимизации ожидания под конкретные харнессы.
